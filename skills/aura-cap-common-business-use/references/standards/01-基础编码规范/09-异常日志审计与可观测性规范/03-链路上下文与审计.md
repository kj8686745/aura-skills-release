# AURA（天玑）基础编码规范：链路上下文与审计

<!-- 规范类型：基础编码规范 -->
<!-- 规范编号：BASE-09 -->
<!-- 规范版本：0.1.0-draft -->
<!-- 模板版本：基础编码规范模板 v3 -->

**适用对象**：使用 AURA 开展业务应用、服务、工具和平台工程开发的团队和开发人员

**规范目标**：让一次业务调用可被关联，让高风险动作形成可信审计事实，并避免上下文串线。

**边界说明**：本文件负责链路标识、请求上下文、异步关联和审计事实；日志字段遵循日志与敏感信息，指标与告警遵循对应分类，身份与敏感信息遵循 `BASE-07`，异步任务细节遵循 `BASE-10`。

## 一、链路与上下文

### AURA-BASE-OBS-009：链路上下文必须贯穿一次调用

**必要性**：必须

**为什么需要**：统一的链路标识可以把入口、内部调用、异步处理和外部依赖串成一次可追踪的业务过程。

入口、应用用例和外部调用应按接口与调用约定传递请求或链路标识。由请求或事件触发的异步任务和消息可开启新的追踪片段，但必须保留可回溯到原操作的关联标识；系统定时任务则建立自身的任务标识。不能要求所有异步步骤共用一个未声明生命周期的 `traceId`。

**正确写法**：入口生成或接收 `requestId`，服务调用传播链路上下文；异步任务保存 `taskId` 与原请求的关联，在日志和任务结果中均可定位。

**错误写法**：消息消费和异步线程丢弃原请求上下文，无法关联原始操作。

**判断要点 / 验证方式**：执行一次跨服务及异步流程，从入口请求标识定位外部调用、任务接收、重试和最终结果，确认关联不会跨用户或租户串线。

### AURA-BASE-OBS-010：上下文不得通过全局可变状态传递

**必要性**：禁止

**为什么需要**：全局可变状态会在并发请求之间串数据，造成身份、租户和链路信息污染，且难以稳定复现。

用户、租户、请求和链路上下文不得存入共享的全局可变变量。线程切换、异步执行和服务间调用必须明确传递字段、建立作用域并在执行结束后清理；使用框架管理的线程局部上下文时仍须确认复制和清理行为。

**正确写法**：任务提交时显式携带授权范围和关联标识，执行结束清理任务上下文；服务间调用使用约定的请求上下文封装。

**错误写法**：用静态变量保存当前用户和 traceId。

**判断要点 / 验证方式**：并发请求和异步执行下检查上下文是否串线。

## 二、审计规则

### AURA-BASE-OBS-011：高风险业务动作必须产生审计事实

**必要性**：必须

**为什么需要**：高风险操作需要能够还原谁在什么时间对什么对象执行了什么动作，才能支持追责、复核和异常调查。

业务项目负责的登录、授权变更、敏感数据访问、关键配置变更、批量导出、删除等高风险动作应由可信服务端记录操作者或系统执行主体、租户/数据范围、对象、动作、结果、时间及请求标识。已有框架审计能力时沿用其入口，不重复制造一套审计事实；权限或关键配置变更还应保留足以解释变更前后差异的信息。失败尝试按场景记录，不得仅靠前端点击日志充当审计。

**正确写法**：授权变更审计记录执行主体、被授权对象、变更前后权限、结果、时间和请求标识；批量导出记录操作者、范围及最终结果，不保存导出文件全文。

**错误写法**：只在前端记录“用户点击了按钮”，服务端没有可信审计事实。

**判断要点 / 验证方式**：绕过前端执行成功和失败的高风险动作，核对审计主体、租户/范围、对象、结果与实际业务状态一致，且不包含敏感原文。

### AURA-BASE-OBS-012：审计记录不得替代业务数据

**必要性**：禁止

**为什么需要**：审计记录用于说明行为事实，业务数据用于表达当前状态，分开维护才能避免审计缺失或业务状态被日志替代。

审计事件用于说明谁在什么时间对什么对象做了什么，不替代业务状态、操作结果和数据事实。对于要求留痕的动作，应明确审计写入失败时是阻断操作还是进入可靠的待补录状态；不得在审计事实丢失、业务状态不确定时仍声称完整成功。

**正确写法**：业务表记录当前状态，审计记录操作事实；审计暂不可用时，按该动作的约定拒绝提交或持久化待补录记录，不返回与实际状态不符的成功结果。

**错误写法**：用一条日志代替业务状态，或把审计字段当作业务结果来源。

**判断要点 / 验证方式**：模拟业务失败、审计写入失败和补录重试，核对审计事实与最终业务状态可解释且不会重复记成多次成功。

## 三、典型使用示例：批量导出链路与高风险审计

**场景目标**：批量导出从用户请求到异步任务、重试、文件下载和最终结果都可关联；高风险导出由服务端形成可信审计事实，上下文不在并发任务之间串线。

**输入条件**：用户发起跨模块导出；入口生成 `requestId` 和 `taskId`；任务按租户范围执行；文件下载需要再次复核权限；导出成功或失败都必须可追踪。

**正确调用链**：

```text
入口生成 requestId/taskId
  → 应用用例保存任务和租户范围
  → 异步任务建立新的执行片段并保留原请求关联
  → 服务间调用显式传递最小权限和关联标识
  → 任务重试记录同一 taskId 下的尝试次数
  → 文件下载重新校验任务归属和权限
  → 服务端写入提交、下载和失败审计事实
```

异步线程显式携带任务、租户和关联标识，执行结束清理上下文；不把当前用户或 `traceId` 放在静态变量中。审计记录主体、租户/数据范围、对象、动作、结果、时间和请求标识，不保存导出文件全文。审计不可用时按动作约定阻断提交或进入可靠待补录状态，不能返回与事实不符的成功。

**错误调用链**：异步线程直接读取全局当前用户；消息消费丢弃原请求关联；下载接口只凭文件名放行；前端点击日志代替服务端审计；审计写入失败仍返回“导出成功”。

**验证步骤与预期结果**：

1. 并发提交不同租户的导出任务，预期日志、任务和审计不发生上下文串线。
2. 模拟任务重试、下载权限变化和文件已过期，预期每次结果都能回溯到原请求并按当前权限处理。
3. 绕过前端直接调用下载和取消入口，预期服务端仍校验任务归属、租户范围和操作权限。
4. 模拟审计写入失败，预期按约定阻断或进入待补录状态，不把不可解释的操作标记为成功。

## 四、开发者自检

- 请求、服务间调用和异步任务是否保留可回溯的关联标识；
- 上下文是否显式传递并在执行结束清理，没有使用全局可变状态；
- 高风险动作是否由服务端形成可信审计事实；
- 审计失败时，业务结果和补录策略是否仍然可解释。
