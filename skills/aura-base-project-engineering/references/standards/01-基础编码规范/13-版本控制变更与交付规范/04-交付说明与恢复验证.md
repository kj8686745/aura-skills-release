# AURA（天玑）基础编码规范：交付说明与恢复验证

**规范对象**：使用 AURA 开展业务应用、服务、工具和平台工程开发的团队和开发人员

**规范目标**：让接收方了解交付行为、版本、验证范围和高风险恢复结果。

**跨规范边界**：研发自测结论遵循 `BASE-12`；本规范不替代测试部门的测试和验收结论。

## 一、文档与交付说明

### AURA-BASE-VC-010：变更说明必须覆盖使用者需要的行为

**必要性**：必须

交付说明必须让接收方看清变更目的、受影响模块、实际发生的配置、数据、接口或消息变化，以及适用的升级步骤、兼容窗口、已验证范围和已知限制。没有触及的领域不要求填空，也不要求另建与项目已有变更记录重复的说明文件。

**为什么需要**：使用者需要知道如何正确升级和判断变更后的行为，而不是只看到代码差异。

**正确写法**：列出新增配置、默认值、旧配置是否继续生效、数据库脚本顺序和接口消费者迁移方式。

**错误写法**：只写“修复若干问题、优化性能”，不说明配置、数据和调用方式变化。

**判断要点 / 验证方式**：由未参与实现的开发者按说明核对实际受影响的升级与恢复步骤，确认没有依赖口头补充的关键条件。

### AURA-BASE-VC-011：版本标识必须能够区分交付内容

**必要性**：必须

可交付版本、数据库脚本、接口契约和配置样例必须使用稳定且可追踪的版本标识，禁止多个不同内容共用同一无法区分的标识。

**为什么需要**：准确的版本标识是定位问题、关联证据和恢复历史交付物的基础。

**正确写法**：使用项目约定的版本号或源码提交标识区分每次交付，并在脚本和说明中保持一致。

**错误写法**：所有构建包都命名为 `latest.zip`，发布说明不记录源码版本。

**判断要点 / 验证方式**：检查包名、镜像标签、脚本版本和变更说明是否能唯一指向同一交付内容。

### AURA-BASE-VC-012：文档、示例和实现必须同步表达当前行为

**必要性**：必须

接口文档、配置样例、代码注释和示例工程中受本次行为变化影响的内容必须同步更新；过期示例不得继续作为可复制用法保留。未受影响的材料无需机械改写。

**为什么需要**：使用者通常从文档和示例开始开发，过期内容会把错误用法扩散到新项目。

**正确写法**：新增分页参数后同步更新接口文档、前端调用示例、后端校验和对应测试。

**错误写法**：代码已改为异步任务，文档仍指导调用方等待同步结果。

**判断要点 / 验证方式**：核对受影响文档与实现的请求、响应和配置；可运行的关键用法变化应按示例执行，未实际执行时不得声称示例已验证。

## 二、交付说明与恢复验证

### AURA-BASE-VC-013：交付说明必须区分研发自测与测试结论

**必要性**：必须

交付说明必须区分研发已完成的自测及其范围、未完成或受环境阻断的自测，以及待测试部门验证的内容；测试部门尚未形成结论时，不得把研发自测通过写成系统测试或验收测试通过。没有未完成项时无需虚构栏目。

**为什么需要**：研发自测和测试部门结论责任不同，混写会造成风险和责任边界不清。

**正确写法**：说明“研发已完成接口、权限和异常自测；性能容量和完整回归待测试部门验证”，并标出因环境缺失未能自测的设备断线场景。

**错误写法**：只写“测试通过”，但实际只运行了本地单元测试。

**判断要点 / 验证方式**：检查已有交付说明是否区分验证主体、范围、实际未验证项和阻断原因；由未参与开发的人员判断哪些内容仍待测试部门执行。

### AURA-BASE-VC-014：高风险恢复路径必须经过可重复演练

**必要性**：必须

涉及历史数据迁移、版本并存、不可逆消息或外部副作用等高风险变更时，必须在与恢复条件相符的可控环境中演练适用的恢复、补偿或前向修复路径，并在已有交付材料中记录执行条件与结果。纯代码或可直接恢复的配置变更应验证恢复路径，但不强制另做数据迁移演练；仅保留未经验证的回滚脚本不能证明高风险恢复可行。

**为什么需要**：未演练的恢复步骤可能因顺序、权限、数据状态或外部副作用而无法执行。

**正确写法**：模拟历史数据迁移中途失败，按预案暂停写入并切换兼容版本；对无法安全逆转的数据执行已验证的前向修复或受控恢复，再核对关键接口、任务和数据数量，并记录演练结果。

**错误写法**：发布说明只写“必要时回滚上一版本”，没有数据、消息和验证步骤。

**判断要点 / 验证方式**：先按实际变更判定是否属于上述高风险情形；对命中的路径检查恢复前提、执行顺序、数据校验、外部副作用处理和可控环境演练记录，确认结果与恢复说明一致。未演练的路径不得标为已验证。

## 三、模块级正例与反例

### 正例：兼容迁移与可恢复交付

```text
1. 增加新字段并保留旧字段读取；
2. 发布兼容版本，回填并校验历史数据；
3. 切换新版本写入并执行消费者回归；
4. 旧读写路径和恢复窗口结束后清理旧字段；
5. 对不能安全逆转的数据采用已演练的前向修复或受控恢复。
```

该变更能够说明影响范围、兼容窗口和实际可执行的恢复路径，交付物也可关联到已验证的源码版本。

### 反例：不可追踪的直接替换

```text
直接删除旧字段，修改所有代码后打包为 latest.zip；
发布说明只写“完成字段升级”，失败时重新部署上一版本。
```

该做法既无法确认交付物来源，也无法处理已发生的数据迁移和兼容问题。

## 四、开发者自检

- 变更是否能关联明确来源且范围单一可解释；
- 共享边界的消费者和兼容策略是否已列出；
- 数据、配置和依赖升级是否支持分阶段验证；
- 交付物是否与已验证的源码、配置和依赖一致；
- 是否具备代码、配置、数据和外部副作用对应的恢复路径；
- 未完成实现、本地依赖和调试数据是否已隔离；
- 版本标识、变更说明、文档和示例是否与当前行为一致；
- 交付说明是否区分研发自测和测试部门结论，高风险恢复路径是否已有可控环境演练结果。
