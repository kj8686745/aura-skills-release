# AURA（天玑）基础编码规范：配置管理

<!-- 规范编号：BASE-06 -->
<!-- 规范版本：0.1.0-draft -->
<!-- 模板版本：基础编码规范模板 v3 -->

**适用对象**：使用 AURA 开展业务应用、服务、工具和平台工程开发的团队和开发人员

**规范目标**：让配置来源、默认值、环境差异和动态生效行为可理解、可复现、可验证。

**边界说明**：本文件负责业务项目如何管理配置；依赖、环境启动和构建分别见本目录其他分类文件，能力包专属配置按对应能力包的公开文档执行。

## 一、配置规则

### AURA-BASE-CONF-001：敏感配置不得进入代码和交付物

**必要性**：禁止

**为什么需要**：避免凭据随代码、镜像、日志或文档扩散，降低泄露后被直接利用的风险。

密码、Token、私钥、真实连接串和其他可用凭据不得写入源码、配置样例、镜像、构建日志、测试资源或文档。仓库只能保存安全默认值、占位符和配置来源说明。

**正确写法**：配置文件只保存 `${DEVICE_SERVICE_TOKEN}` 占位符，运行环境通过受控密钥注入。

**错误写法**：把真实 Token 写入 `application-prod.yml`、Docker 镜像层或启动日志。

**判断要点 / 验证方式**：扫描源码、历史提交、镜像配置、测试资源和日志，确认没有可用凭据。

### AURA-BASE-CONF-002：配置键必须表达稳定能力语义

**必要性**：必须

**为什么需要**：稳定、可理解的配置键便于跨环境维护、兼容旧版本并准确判断配置影响范围。

配置键按项目统一前缀和领域能力组织。同一配置不得长期保留多套别名；历史别名必须有兼容期限、优先级和删除计划。

**正确写法**：项目使用唯一的 `app.device-service.read-timeout`，旧键在兼容期提示迁移并登记删除版本。

**错误写法**：同一超时同时使用 `timeout`、`deviceTimeout` 和 `prodTimeout` 三套别名。

**判断要点 / 验证方式**：列出所有配置键和引用，检查重复别名、前缀和兼容期限。

### AURA-BASE-CONF-003：成组配置必须使用类型化配置对象

**必要性**：必须

**为什么需要**：类型化配置可以集中校验相关字段和默认值，避免字符串散落、单位混乱和启动后才暴露错误。

多个字段共同描述一项能力时，必须聚合为类型化配置对象，明确类型、单位、默认值、说明和校验；单个独立配置不要求为凑结构额外创建配置类。时长、容量、比例等值不得用无法判断单位的裸数字表达。

**正确写法**：使用类型化配置对象读取 `Duration`、`DataSize`，并校验最小值和最大值。

**错误写法**：使用 `@Value("${timeout}") long timeout`，调用方无法判断单位。

**判断要点 / 验证方式**：提供缺失值、非法值、边界值和配置元数据测试。

### AURA-BASE-CONF-004：环境差异必须由配置层表达

**必要性**：必须

**为什么需要**：把环境差异放在配置层可以保持同一份代码可复用，避免通过分支或硬编码地址改变业务行为。

开发、测试和生产差异通过环境配置、配置中心或受控注入表达，业务代码不得散落环境判断。每个配置键必须能说明来源、覆盖优先级和适用环境。

**正确写法**：代码只消费类型化配置，开发、测试和生产通过环境配置覆盖地址和开关值。

**错误写法**：在业务代码中散落 `if (prod)`，根据环境字符串改变业务流程。

**判断要点 / 验证方式**：检查环境配置、覆盖优先级和代码中的环境分支。

### AURA-BASE-CONF-005：配置变更必须说明兼容与恢复方式

**必要性**：必须

**为什么需要**：配置经常独立于代码生效，明确实际受影响的兼容与恢复路径才能避免调整后服务不可用。

新增、重命名或删除配置时，必须说明默认值、校验方式，以及对实际存在的旧实例和消费者的兼容与恢复方式；全新且无旧消费者的配置无需虚构兼容窗口。实际支持动态刷新的配置，还须说明刷新失败时如何保留上一份有效配置并定位故障。非法配置不得静默生效。

**正确写法**：重命名配置时在兼容期双读旧键和新键，明确新键优先，发现旧键使用时提示迁移；验证后再删除旧键，并保留回退方式。

**错误写法**：直接删除线上仍在使用的配置键，非法刷新后让部分字段生效。

**判断要点 / 验证方式**：按实际变更验证旧配置与新配置的适用性、非法配置处理和恢复结果；动态刷新或灰度仅在项目实际使用时验证，不机械要求所有配置变更具备灰度流程。

### AURA-BASE-CONF-006：功能开关必须有边界

**必要性**：必须

**为什么需要**：明确开关的作用域、默认值和清理时间，才能避免临时试验逻辑长期存在或绕过权限和数据保护。

定时任务、消息消费、外部同步、实验能力和高风险操作使用功能开关时，必须明确默认值、作用域、关闭语义、监控和清理条件；临时开关还需标明预计移除时间。功能开关不得替代权限或租户控制。

**正确写法**：消息消费开关登记默认值、作用域、关闭语义、监控和清理版本，关闭后不再接收新任务。

**错误写法**：用功能开关绕过权限校验，或让临时实验开关在没有清理条件时长期保留。

**判断要点 / 验证方式**：测试开启、关闭、动态刷新、执行中任务和清理到期行为。

### AURA-BASE-CONF-007：配置优先级必须固定且可解释

**必要性**：必须

**为什么需要**：固定优先级可以让开发、联调和运行环境对最终生效值形成一致判断，避免配置来源互相覆盖。

项目必须按所用框架和配置组件的实际行为，说明默认配置、文件配置、环境变量、配置中心和启动参数等已使用来源的覆盖顺序；同一配置被多个来源设置时，最终值必须能够被定位，不能依赖个人环境中的隐式覆盖。

**正确写法**：若项目实际验证启动参数覆盖环境变量、环境变量覆盖配置文件，就在项目文档按此顺序记录，并只输出生效来源和非敏感摘要；未使用配置中心时不虚构其优先级。

**错误写法**：同一键在多个文件和本机变量中重复设置，最终值依赖 IDE 或启动顺序，开发者无法判断实际生效值。

**判断要点 / 验证方式**：分别设置各层配置并启动，检查最终值、来源和冲突提示。

### AURA-BASE-CONF-008：配置默认值必须适合安全和业务语义

**必要性**：必须

**为什么需要**：安全且可解释的默认值可以避免缺少配置时误连生产、扩大权限或执行不可逆操作。

默认值只能用于安全、可解释且不会误触发高风险行为的场景；权限、外部写入、消息消费和生产数据操作不得通过隐式默认值开启。

**正确写法**：对新接入、可能产生外部副作用的消息消费，未完成必要配置时保持关闭或启动失败；超时默认值明确单位和上限，缺少必需的生产目标地址时启动失败。已有稳定消费业务按其已登记的默认行为运行，不以“默认关闭”覆盖实际契约。

**错误写法**：缺少配置时默认连接生产服务、默认开启批量删除或默认授予全部权限。

**判断要点 / 验证方式**：删除配置后启动并执行关键操作，确认默认行为不会扩大权限或产生不可逆副作用。

### AURA-BASE-CONF-009：动态配置必须定义生效范围和一致性

**必要性**：必须

**为什么需要**：动态刷新可能影响并发请求和正在执行的任务，明确生效范围和失败回退才能避免同一操作使用矛盾配置。

支持运行时刷新的配置必须说明生效对象、刷新时机、并发可见性、失败回退和是否影响正在执行的请求；不能让同一请求在处理中途使用互相矛盾的配置版本。

**正确写法**：限流配置按新请求生效，正在执行任务继续使用开始时的版本，刷新失败保留上一份有效配置。

**错误写法**：请求执行过程中读取多次动态配置，导致同一任务前后使用不同超时和权限策略。

**判断要点 / 验证方式**：并发刷新配置并执行长请求，检查请求内版本一致性和刷新失败后的回退。

## 二、典型使用示例

为外部设备服务增加连接与读取超时，使用带单位的配置并绑定到同一对象：

```yaml
app:
  device-service:
    connect-timeout: 2s
    read-timeout: 5s
```

```java
import java.time.Duration;
import org.springframework.boot.context.properties.ConfigurationProperties;
import org.springframework.boot.context.properties.EnableConfigurationProperties;
import org.springframework.context.annotation.Configuration;

@ConfigurationProperties(prefix = "app.device-service")
public record DeviceServiceProperties(Duration connectTimeout, Duration readTimeout) {
    public DeviceServiceProperties {
        if (connectTimeout == null || readTimeout == null
                || connectTimeout.isNegative() || connectTimeout.isZero()
                || readTimeout.compareTo(connectTimeout) < 0) {
            throw new IllegalArgumentException("设备服务超时配置无效");
        }
    }
}

@Configuration
@EnableConfigurationProperties(DeviceServiceProperties.class)
class DeviceServiceConfiguration {
}
```

开发和联调环境如需覆盖超时值，通过项目实际使用的配置来源覆盖，并在项目文档说明来源优先级。缺少值或填写 `0s` 时应在启动阶段报出配置错误；测试应覆盖有效值、缺失值、非法值和覆盖顺序。实际构建仍使用项目统一的编译、测试和打包入口。

错误做法：

```java
if ("prod".equals(environment)) {
    timeout = 5000L;
}
```

这种写法隐藏单位和配置来源，业务代码还必须知道环境名称，开发者无法仅通过配置与启动检查判断实际生效值。

## 三、开发者自检

- 敏感值是否只通过受控环境注入；
- 配置键、类型、单位、默认值和来源是否明确；
- 环境差异是否没有散落在业务代码；
- 动态配置是否说明生效范围、版本一致性和失败回退。
