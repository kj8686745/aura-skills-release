**规范对象**：使用 AURA 开展业务应用、服务、工具和平台工程开发的团队和开发人员

**本文件内容**：数据访问边界、事务一致性、缓存、生命周期、数据库约束与迁移。

## 一、数据访问、事务与数据生命周期

### 1. 数据访问与模型

### AURA-BASE-DATA-001：数据访问必须经过明确边界

**必要性**：必须

业务用例通过 Repository、Mapper 或公开数据客户端访问数据，禁止在 Controller、页面、公共工具或跨模块代码中直接操作数据库连接和内部表。

**为什么需要**：统一数据访问入口，避免协议层和跨模块代码绑定数据库实现。

**正确写法**：

```java
Device device = deviceRepository.findById(deviceId).orElseThrow();
```

**错误写法**：

```java
Connection connection = dataSource.getConnection();
return connection.prepareStatement("select * from device where id=?");
```

**判断要点 / 验证方式**：检查 Controller、页面和公共工具是否直接获取连接或访问内部表，确认调用经过 Repository、Mapper 或公开客户端。

### AURA-BASE-DATA-002：数据模型必须表达所有权和用途

**必要性**：必须

实体、查询模型、命令模型、响应模型和报表模型应按用途定义。跨模块不得无条件复用对方 Entity 或内部字段。

**为什么需要**：隔离持久化结构与公开契约，避免一个模块的字段变化扩散到调用方。

**正确写法**：`DeviceQuery`、`DeviceEntity` 和 `DeviceResponse` 分别用于查询、持久化和响应。

**错误写法**：跨模块直接把 `DeviceEntity` 作为接口响应返回。

**判断要点 / 验证方式**：检查模型命名、引用方向和跨模块字段依赖，确认每个模型都有明确用途。

### AURA-BASE-DATA-003：查询必须有规模和排序边界

**必要性**：必须

列表、导出和批量查询必须限制页大小或批次，排序字段使用白名单，结果顺序需要稳定。不得默认把全表读入内存。

**为什么需要**：控制查询资源和结果稳定性，避免数据量增长导致超时、内存溢出或排序注入。

**正确写法**：分页查询设置业务允许的最大页大小，排序字段通过白名单映射；按创建时间分页时再追加唯一标识作为同时间记录的稳定次序。导出按固定批次或游标读取，不一次载入全表。

**错误写法**：调用 `selectAll()` 后在内存排序，直接拼接请求中的 `sort` 字段。

**判断要点 / 验证方式**：使用超大页、非法排序和大数据夹具验证是否拒绝或受控。

**边界说明**：本规则约束数据访问层必须保证查询规模、排序和结果稳定；接口参数和公开响应边界遵循 `BASE-05`，后端查询方法的职责落点遵循 `BASE-03`。

**分页与关联补充**：先定义分页单位是主记录、明细还是聚合结果。一对多关联不得先按展开行分页、再由 Java 去重冒充主记录分页；只为过滤子表时优先考虑 `EXISTS`，需要展示子表时可先分页主记录，再按本页主键批量查询子表。count 与列表必须使用一致的过滤、租户、组织和删除语义；空授权集合不得被解释为不加过滤。排序相同时追加唯一键；稳定排序只解决次序不确定，不承诺并发修改期间的快照一致。大偏移查询按实际成本选择游标或其他方案，不强制所有普通列表改为游标。

### AURA-BASE-DATA-004：写入必须表达业务结果

**必要性**：必须

新增、更新、删除和状态变更必须根据实际影响行数、版本条件和业务状态返回真实结果，不得无条件返回成功。

**为什么需要**：让调用方能够区分成功、对象不存在、并发冲突和重复提交。

**正确写法**：条件更新影响行数为 0 时返回版本冲突或对象不存在。

**错误写法**：无论影响行数是否为 0 都返回“操作成功”。

**判断要点 / 验证方式**：模拟对象不存在、版本冲突和重复提交，检查响应及业务状态。

### 2. 事务与一致性

### AURA-BASE-DATA-005：事务边界应覆盖本地一致性用例

**必要性**：应当

事务应由应用用例控制，覆盖必须一起成功或失败的本地数据变更。事务内不得长时间等待外部网络、文件处理或人工操作。

**为什么需要**：确保本地数据原子性，同时避免事务长时间占用连接和锁。


**正确写法**：审核状态和审核记录在同一应用用例事务内提交。

**错误写法**：在 Controller 事务中等待远程服务和文件处理完成。

**判断要点 / 验证方式**：注入中途失败，确认本地变更整体回滚且事务内无外部长等待。

**边界说明**：本规则约束本地数据变更的原子性和外部副作用边界；事务代码应放在业务用例的具体位置由 `BASE-03` 的 `BE-010` 规定。

### AURA-BASE-DATA-006：外部副作用不得伪装成本地事务

**必要性**：禁止

数据库事务不能自动回滚已经发送的消息、调用的外部服务或写出的文件。需要通过事件、状态记录、补偿或幂等策略衔接。

**为什么需要**：明确本地事务与外部副作用的边界，避免出现“本地回滚但外部已成功”。

**正确写法**：需要保证外部操作最终执行时，在同一本地事务内保存业务状态和待执行记录；事务提交后由任务或消息投递程序读取记录、重试并使用幂等键防重。若外部操作失败，保留可查询的失败状态和补偿路径。

**错误写法**：数据库事务内调用远程服务并假定回滚能够撤销远程副作用。

**判断要点 / 验证方式**：分别模拟本地提交失败、提交成功但投递失败、外部成功但回执丢失，检查待执行记录、幂等重试、补偿和最终状态；单纯“提交后调用一次”不能证明消息不会丢失。

### AURA-BASE-DATA-007：并发写入必须有一致性策略

**必要性**：必须

并发修改根据业务选择版本号、唯一约束、条件更新、锁或串行化策略，并明确冲突时的结果。不能只依赖前端按钮禁用。

**为什么需要**：防止并发覆盖和重复操作造成数据错误。

**正确写法**：更新使用 `version` 条件，冲突时返回明确的并发修改结果。

**错误写法**：先查询再无条件更新，仅依靠前端禁用按钮防重复。

**边界说明**：本规则约束数据库写入的一致性机制；接口层如何公开冲突响应遵循 `BASE-05`，后端用例如何组织冲突处理遵循 `BASE-03`。

**判断要点 / 验证方式**：并发提交同一版本的两个请求，确认只有一个成功且冲突可见。

### AURA-BASE-DATA-008：删除必须说明语义

**必要性**：必须

删除、作废、停用和归档必须区分。涉及审计、恢复或关联数据时，应按业务保留要求选择状态、软删除或物理删除，并说明默认查询和恢复行为。

**为什么需要**：避免误删、无法恢复和关联数据失去解释。

**正确写法**：需要恢复的设备使用 `archived` 状态区分归档，默认查询排除归档并提供受控恢复入口；明确无需保留的临时数据按期限物理清理。

**错误写法**：直接物理删除且未说明关联数据和审计影响。

**判断要点 / 验证方式**：验证默认查询、恢复、关联记录和审计结果。

### 3. 缓存与数据同步

### AURA-BASE-DATA-009：缓存只能作为明确的加速边界

**必要性**：必须

用于加速持久数据读取的缓存必须说明键、事实来源、有效期、失效、回源和不可用时的处理方式；不得把这类缓存当作唯一事实来源。独立的短期状态存储应按其实际数据责任设计，不套用“可丢失的查询缓存”语义。

**为什么需要**：保证缓存只是可控的加速边界，不把临时数据误当作业务事实。

**正确写法**：在缓存适配器中集中定义键、来源、TTL 和失效规则；读取缓存失败时按业务允许的方式回源或明确失败。

**错误写法**：多个业务方法自行拼接缓存键并把缓存当作唯一数据来源。

**判断要点 / 验证方式**：清空缓存、缓存服务不可用和过期后检查回源与降级。

### AURA-BASE-DATA-010：缓存更新必须考虑一致性窗口

**必要性**：必须

写入、删除和状态变更后必须说明缓存刷新、失效或延迟同步策略。不能只更新数据库却假定所有缓存立即一致。

**为什么需要**：控制数据库与缓存之间的可见性差异和一致性窗口。

**正确写法**：数据库提交后删除旧缓存，读取 miss 时回源并重建；失效失败时记录并重试，或由受控的过期时间限制旧值可见窗口。

**错误写法**：只更新数据库却假定所有缓存立即一致。

**判断要点 / 验证方式**：在写入、提交失败、失效失败和并发读取场景检查可见性窗口，确认回源和失败处置符合约定。

### 4. 生命周期与数据责任

### AURA-BASE-DATA-011：数据必须有生命周期

**必要性**：必须

数据应说明创建、使用、更新、归档、恢复和删除阶段。临时数据、任务数据和导入文件不得无限期保留。


**为什么需要**：防止临时数据无限增长，并让恢复和清理行为可预期。

**正确写法**：导入文件和失败任务分别约定保留期限、查询方式与到期清理动作；需要恢复的数据同时约定恢复期限。

**错误写法**：临时文件和任务记录永久保留，没有清理任务或期限。

**判断要点 / 验证方式**：检查生命周期字段、清理任务、恢复入口和到期行为。

### AURA-BASE-DATA-012：敏感和审计数据必须按用途保留

**必要性**：必须

敏感数据、审计数据和业务主数据的保留期限、访问范围和删除方式必须分别定义，不得用一个默认清理策略覆盖所有数据。

**为什么需要**：让数据保留与业务用途、审计责任和敏感等级相匹配。

**正确写法**：审计记录按审计期限保留，敏感字段按用途最小化并到期删除。

**错误写法**：所有数据使用同一永久保留策略，敏感字段和审计数据不区分。

**判断要点 / 验证方式**：核对保留配置、访问权限、脱敏和到期删除结果。

### AURA-BASE-DATA-013：跨模块数据必须有事实来源

**必要性**：必须

每个共享字段、状态和统计结果必须明确事实来源、同步方式和冲突处理。下游不得通过读取上游内部表来替代公开契约。

**为什么需要**：避免多个模块各自解释同一状态，形成不可收敛的数据事实。

**正确写法**：设备状态以设备服务为事实源，下游通过公开查询或事件同步。

**错误写法**：报表模块直接读取设备模块内部表并自行解释状态值。

**判断要点 / 验证方式**：检查契约、同步路径、冲突策略和事实源唯一性。

### AURA-BASE-DATA-014：数据迁移必须可验证并具备恢复路径

**必要性**：必须

字段、表、索引或数据格式变更必须说明适用的兼容读写、迁移步骤、校验口径和失败处置。恢复路径应依据历史数据和版本并存情况选择旧结构保留、前向修复、补偿或受控数据恢复等可行方式；不能安全反向迁移时，不得把反向脚本或重部署旧代码当作恢复保证。不可逆变更应先完成适用的备份和恢复验证。未完成验证不得删除仍被使用的旧数据结构。

**为什么需要**：保证数据结构变更可验证、可恢复，并支持按实际消费者分阶段切换。

**正确写法**：先增加新字段并兼容读取旧值，按批迁移并核对数量与关键值；切换写入前验证适用的恢复路径，确认旧实例、消费者和恢复窗口均已结束后再清理旧字段。

**错误写法**：直接删除旧字段并在未验证数据完整性前发布。

**判断要点 / 验证方式**：执行样例迁移，核对数量、关键值和消费者读取结果；验证所选恢复路径，并按 `AURA-BASE-VC-014` 判断是否需要可控环境演练。

**增量演进补充**：沿用项目已使用的迁移目录、工具和版本规则，不修改已经应用的版本脚本。新增字段、历史数据回填、读写切换、非空/唯一等约束收紧和旧结构清理分别安排可核对的步骤；小变更不机械拆成多个发布。回填使用有界批次、稳定游标和可重复条件，记录进度与失败处理；业务不变量不能仅用总行数核对。涉及旧实例并存时核对双方写入行为，旧代码仍可能写入空值时不能提前收紧约束。旧代码回退不等于数据能够回退，破坏性 DDL 必须核对具体数据库版本、锁等待、表重写及适用恢复路径。

### AURA-BASE-DATA-015：表结构与数据库约束必须承载关键数据不变量

**必要性**：必须

新增或变更表结构时，字段类型、精度、可空性、唯一性、外键或等效关联约束应与业务数据含义一致。对必须由数据库保证的唯一键和非空字段，不得仅依赖页面或先查后写校验；索引应依据实际过滤、关联和排序查询设计，避免为每个字段盲目建索引。

**为什么需要**：应用层校验无法阻止并发写入或其他入口写入错误数据，不合理的索引又会增加写入和维护成本。

**正确写法**：业务编号由唯一约束兜底，必填字段设置非空约束；根据高频查询的过滤条件和排序设计索引，并确认写入成本可接受。

**错误写法**：创建业务编号时只先查询“是否存在”，表中没有唯一约束；为所有字段各建一个索引而不检查查询路径。

**判断要点 / 验证方式**：核对表结构与模型约束；并发插入相同业务编号，确认数据库约束生效；用实际查询条件核对执行计划、索引使用与查询成本。

**索引补充**：按真实过滤、关联、排序、选择性和返回规模核对候选索引，比较已有索引的覆盖、冗余及写入成本。不得根据字段名自动生成“最优索引”，也不得把线上建索引等同于无锁、无等待或无资源影响。唯一索引建立前先检查重复和空值语义；索引语法、在线能力和事务限制以目标数据库及版本为准。

### AURA-BASE-DATA-016：SQL 查询必须参数化并验证数据规模

**必要性**：必须

SQL 值参数使用绑定参数；无法参数化的表名、列名和排序方向只能从受控映射中选择，不得直接拼接外部输入。复杂查询、分页、聚合和批量写入应按实际数据量检查执行计划、扫描范围、锁范围及超时边界。

**为什么需要**：外部输入拼接会造成注入风险；只在少量测试数据上运行正常，不能说明真实数据规模下的查询成本可控。

**正确写法**：按业务查询字段构造参数化条件，排序键由白名单映射到受控列；对高频慢查询使用代表性数据检查执行计划后调整索引或查询方式。

**错误写法**：把请求中的 `name` 或 `sort` 直接拼进 SQL；在大表上无过滤地查询全部记录，再由应用内存分页。

**判断要点 / 验证方式**：检查 SQL 构造与参数绑定；输入引号、非法排序字段和大数据量查询，核对拒绝结果、执行计划及资源占用。

**执行计划补充**：记录目标数据库、版本、代表性参数与数据规模，区分估计计划和实际执行统计。`EXPLAIN ANALYZE` 会执行被分析语句，不能把它当作无副作用的只读格式检查。读写语句的实际执行、数据库连接及运行环境须在任务授权范围内；只保存 SQL 文本或看到索引存在不能宣称性能验证通过。

### AURA-BASE-DATA-017：数据库重复结构应使用受控模板生成

**必要性**：应当

新增普通数据库表时，应先依据当前项目已经核实的 ORM、基础实体、主键策略和迁移工具，使用数据库层字段模板生成 Entity、Mapper/Repository 和迁移文件的重复结构；脚本只处理确定性结构，不推断业务字段、索引、租户范围、逻辑删除、事务或权限。

**为什么需要**：将字段到代码骨架的重复工作交给可复用脚本，减少大模型重复生成造成的命名、主键映射、迁移文件名和字段类型错误，同时把业务判断保留给开发者。

**正确写法**：先用 `Plan` 预览字段、输出路径和主键策略；确认项目真实依赖后再用 `Apply` 生成。数据库下划线字段生成 Java 小驼峰并保留明确列映射；已有文件内容不一致时返回阻断并人工合并。项目已核实使用公共基础实体时，显式选择对应模式并校验继承字段，不重复声明基础字段。

**错误写法**：让脚本猜测项目基础实体或逻辑删除字段；把 Service、Controller 和复杂 SQL 一并批量生成；直接覆盖已有 Entity 或迁移文件；只因为脚本生成成功就宣称事务、租户边界、索引和数据库行为已经完成。

**模板最小输入**：字段名、Java 类型、SQL 类型、可空性、主键和自增属性；必要时显式提供 Java 字段名。字段清单必须有且只有一个主键，SQL 类型和输出路径使用受控白名单。模板默认只生成持久化骨架，不生成空 Service、Controller、DTO 或 XML。

**判断要点 / 验证方式**：检查脚本是否先输出计划、是否拒绝越界路径和非法字段、是否保护已有文件；检查生成的 Entity、Mapper 和迁移脚本是否与项目实际基础实体、主键、命名、表约束和迁移工具一致。生成后仍须按本规范验证事务、数据范围、索引、约束、正常读写和失败回滚，未执行的数据库行为只能标为未证实。

### AURA-BASE-DATA-018：缓存接入必须先证明业务收益

**必要性**：必须

后端默认不为所有查询接入缓存。新增缓存前必须说明被缓存对象、原始成本、预期收益、事实来源、允许陈旧范围、缓存不可用时的行为和验证指标。没有明确的重复访问、昂贵查询/计算、外部调用、状态读取或并发协调收益时，不得仅因项目已有 Redis、Caffeine 或缓存 SDK 就新增缓存。

**为什么需要**：缓存会增加失效、容量、序列化、监控和一致性成本。没有收益基线的缓存可能增加系统复杂度、占用资源，并掩盖真实的查询或架构问题。

**正确写法**：记录“设备详情多表查询平均耗时较高且被多个接口重复读取，允许 60 秒陈旧；目标是降低数据库 QPS 和接口 P95；缓存故障时回源数据库”，再选择查询缓存或状态投影方案。

**错误写法**：看到数据库查询就加 `@Cacheable`；只填写缓存名称和 TTL；以缓存命中率代替数据库压力、外部调用量或接口延迟收益；为低频、强一致或每次都变化的数据强行缓存。

**判断要点 / 验证方式**：对比接入前后的查询次数、数据库 QPS、外部调用量、CPU/聚合耗时、P95/P99、回源率和缓存错误率；没有基线或收益指标时标记为未完成，不以代码存在判定缓存设计有效。

### AURA-BASE-DATA-019：不同业务缓存必须按事实责任分类

**必要性**：必须

缓存必须至少区分：查询结果缓存、关系/物模型预计算、外部状态投影、本地或多级状态缓存、鉴权/会话状态、临时任务状态、限流/幂等/分布式锁和消息发布订阅。不同类别必须分别定义事实来源、丢失影响、过期语义、失效方式、故障行为和验证边界，不得用一个普通查询缓存模板覆盖全部 Redis 或本地缓存使用。

**为什么需要**：商品展示缓存可以回源，库存和支付不能只信缓存；设备在线状态过期应返回 `UNKNOWN`，不能当作离线；分布式锁关注 owner 和释放，不能按命中率评价；会话丢失可能造成业务中断，不能视为普通可丢失副本。

**正确写法**：为监控统计定义查询结果缓存，为设备在线状态定义带更新时间和 `UNKNOWN` 的状态投影，为 Token 定义认证状态，为限流定义原子计数窗口；每类使用独立键前缀和验证场景。

**错误写法**：所有 Redis key 都放入一个 `CacheService`；用查询缓存模板生成库存扣减、支付状态、分布式锁或 Pub/Sub；缓存过期后把未知状态补成确定成功或离线。

**判断要点 / 验证方式**：核对缓存分类、事实来源、数据丢失影响、键范围、TTL/空闲过期、刷新和失效链路；模拟缓存缺失、过期、不可用、事件延迟和多实例访问，确认每类场景的结果语义不同且可解释。

### AURA-BASE-DATA-020：缓存必须具备键、版本、生命周期和故障边界

**必要性**：必须

缓存契约必须明确业务范围、键前缀、租户/组织/用户隔离、值类型或序列化版本、TTL/空闲过期、容量上限、刷新/预热方式、失效方式、回源策略和缓存故障处理。关键业务事实必须保存在持久化来源；查询缓存默认采用按需回源和失效策略，只有满足读后立即读取和写入协调要求时才选择写穿透或其他模式。

**为什么需要**：没有版本和范围的缓存会产生跨租户污染和旧结构反序列化；没有容量和生命周期会造成内存持续增长；没有故障边界会让 Redis 故障放大为数据库雪崩或业务不可用。

**正确写法**：键包含应用、环境、版本和租户范围；更新主数据成功后删除相关查询缓存，读取 miss 时回源重建；本地缓存声明最大容量和空闲过期；缓存不可用时按业务选择回源、降级、返回 `UNKNOWN` 或明确失败；对热点过期使用单飞、互斥或提前刷新。

**错误写法**：使用用户输入拼接完整 key；结构变更仍复用旧缓存；没有最大容量；只设置长期 TTL；缓存异常被静默吞掉；缓存成为唯一权限、库存、支付或审计来源；多个实例各自更新本地缓存却没有事件失效。

**判断要点 / 验证方式**：检查键和版本是否能隔离环境、租户和数据结构；检查 TTL、容量、失效、刷新、回源、降级和监控配置；验证正常命中、miss、过期、失效失败、缓存不可用、热点并发、权限变更和服务重启恢复。未运行的缓存行为只能标为未证实。

## 二、典型使用示例：设备审核与异步通知

**场景目标**：用户审核设备时，在服务端完成租户范围查询、版本条件更新、审核记录写入和待通知记录写入；事务提交后再投递通知，缓存只作为可失效的加速边界。

**输入条件**：请求只携带 `deviceId`、审核结果和业务说明；当前用户与租户来自受信任上下文；设备记录包含 `version` 和状态字段；通知服务可能暂时不可用；设备详情存在查询缓存。

**正确调用链**：

```text
Controller 解析审核命令
  → 应用用例按可信租户查询设备
  → Repository 按 deviceId、tenantId、version 条件更新
  → 同一事务写入审核记录和待通知记录
  → 提交成功后由投递任务按幂等键发送通知
  → 失效设备缓存并按需回源
  → 返回实际更新结果和可查询的通知状态
```

事务只覆盖设备状态、审核记录和待通知记录等本地变更，不在事务中等待通知服务或执行文件处理。条件更新影响行数为 0 时返回对象不存在或并发冲突；通知发送失败保留待处理状态并按幂等键重试，不能把本地回滚当成远程撤销。缓存失效失败时记录并重试，不能把缓存当作设备状态的唯一事实源。

**错误调用链**：先查询设备再无条件更新；只依据前端按钮禁用防止重复审核；事务内同步调用通知服务；通知失败后仍返回“已通知”；只更新数据库却假定缓存立即一致。

**验证步骤与预期结果**：

1. 两个请求使用同一 `version` 并发审核，预期只有一个成功，另一个得到明确的并发冲突结果。
2. 模拟本地提交失败、提交成功但通知投递失败、通知成功但回执丢失，预期本地状态、待通知记录、幂等重试和最终状态均可查询。
3. 使用其他租户设备、无权限设备和不存在的设备 ID，预期查询、更新和审计路径都执行同一数据范围约束。
4. 清空缓存、使缓存不可用或让失效操作失败，预期按约定回源或进入可观察的失败处置，不改变数据库事实。

## 三、典型使用示例：历史字段迁移与生命周期清理

**场景目标**：为设备表增加归档时间和导入文件关联字段，在仍有旧实例和历史数据时完成兼容迁移，并对临时导入文件和失败任务执行有期限的清理。

**正确迁移链**：

```text
增加可空新字段和必要索引
  → 旧代码仍可读写旧字段
  → 新代码兼容读取旧值并双写或按批补齐
  → 校验记录数量、关键值、索引和消费者读取结果
  → 切换默认读取新字段
  → 观察旧消费者和恢复窗口
  → 完成备份/恢复验证后再清理旧字段
  → 按保留期限清理临时文件和失败任务
```

首次定义且没有旧数据或旧消费者的字段，不虚构兼容对象；已经存在历史数据时必须记录迁移批次、校验口径和失败处置。临时文件、成功任务和失败任务分别定义保留期限、查询方式和清理动作；清理任务按批处理并可重复执行，不能用一次无限事务删除全部数据。

**错误迁移链**：直接删除旧字段并发布新代码；未校验历史数据就声明迁移完成；把所有任务和文件永久保留；清理任务一次读入全部记录并在单个长事务中删除。

**验证步骤与预期结果**：

1. 使用代表性旧数据执行迁移，核对总数、关键字段、空值和关联文件数量。
2. 在新旧代码并存期间分别读取和写入，预期双方都能按兼容契约处理。
3. 中途停止迁移，预期可从已记录批次继续或按已选恢复路径恢复，不产生无法解释的半迁移状态。
4. 到达保留期限后执行清理，预期只清理到期且未被保护的数据，保留审计数据和仍可恢复的数据。

## 四、查询与结构演进开发示例

### 1. 主记录分页与标签过滤

**适用规则**：`AURA-BASE-DATA-001～003`、`AURA-BASE-DATA-013`、`AURA-BASE-DATA-015～016`。以下为同一模块的 `device` 与 `device_tag` 示例，不允许据此跨模块读取其他业务的内部表。字段、权限入口和删除值按实际工程替换。

需求是“每页显示设备，允许按标签筛选”，分页单位是设备，不是设备与标签展开后的行。应用服务先从可信身份解析租户和组织范围，校验页码、页大小和排序键；授权组织为空时直接返回空页。前端不得提供可信租户或任意列名；排序键只在后端映射到固定分支。

**正确示例：MyBatis XML 查询核心**。`query.tenantId`、`query.orgIds` 由服务端解析；调用前保证授权集合非空。count 与列表共用同一个谓词片段。

```xml
<sql id="VisibleDeviceFilter">
  d.tenant_id = #{query.tenantId} AND d.del_flag = '0'
  AND d.org_id IN
  <foreach collection="query.orgIds" item="orgId" open="(" close=")" separator=",">
    #{orgId}
  </foreach>
  <if test="query.tag != null">
    AND EXISTS (
      SELECT 1 FROM device_tag t
      WHERE t.device_id = d.id AND t.tenant_id = #{query.tenantId}
        AND t.del_flag = '0' AND t.tag_name = #{query.tag}
    )
  </if>
</sql>

<select id="countVisible" resultType="long">
  SELECT COUNT(*) FROM device d WHERE <include refid="VisibleDeviceFilter"/>
</select>

<select id="selectVisiblePage" resultType="example.DeviceRow">
  SELECT d.id, d.name, d.updated_at FROM device d
  WHERE <include refid="VisibleDeviceFilter"/>
  <choose>
    <when test="query.sort == 'name'">ORDER BY d.name ASC, d.id ASC</when>
    <otherwise>ORDER BY d.updated_at DESC, d.id DESC</otherwise>
  </choose>
  LIMIT #{query.pageSize} OFFSET #{query.offset}
</select>
```

本例显式使用 LIMIT/OFFSET，不再叠加一次 ORM 分页插件。项目使用分页插件时遵循其实际契约，不把两套分页重复应用。`offset` 由已校验页码与大小在后端安全计算，并按业务限制深页；count 与数据查询可能观察到不同提交，严格一致结果需要另定隔离或快照，不以相同过滤条件代替该保证。

页面需要展示标签时，收集本页设备 ID，一次批量查询相关标签，并保留同样的可信租户和适用删除过滤；再按 ID 组装结果。没有主记录时不执行空 `IN`；不能每个设备再查一次标签造成 N+1。关联表的其他组织/权限条件按真实授权关系核实，不把示例中的租户条件当作所有数据权限均已覆盖。

**反例**：`device LEFT JOIN device_tag` 后直接 LIMIT，再在 Java 中按设备去重；count 用 `COUNT(*)` 统计标签行；排序用请求中的 `${sort}`；列表有租户条件而 count 或子表查询遗漏。这样会产生页内主记录不足、总数不符或数据范围泄漏，不能用“加 DISTINCT”替代对分页单位和授权关系的核对。

**验证步骤与预期**：构造同一设备多标签、同名同更新时间、其他租户同名标签、空授权集合、已删除记录和最后一页；核对主记录不因标签重复，count 与列表口径一致，空授权不执行无范围查询，标签批量读取有界。并发更新、深页成本和执行计划分别取证，静态 XML 检查只提供候选。

### 2. 新字段、回填与约束收紧

**适用规则**：`AURA-BASE-DATA-014～017`。示例场景是新增设备位置编码 `location_code`，旧数据来自 `legacy_location`，仍可能存在旧实例；不假定这两个字段已经存在于任何真实项目。

**正确示例：演进顺序**：

1. 使用项目既有的新迁移版本增加可空字段；更新 Entity/结果映射，核对旧实例可继续运行。
2. 按已确认语义规范化旧值；不能映射的数据进入明确异常清单，不随意填 `UNKNOWN` 掩盖缺失。
3. 使用稳定主键范围和有界批次回填，限制每批事务、耗时与并发；仅填尚未转换的数据，已完成批次可重复执行而不覆盖新值。
4. 校验适用记录数、剩余空值、关键值、重复/关联约束与新旧读写结果；并存期间按已选兼容策略处理旧实例写入。
5. 旧写入已退出且数据满足要求后，再用后续迁移收紧业务确需的约束；保留恢复窗口，最后才考虑清理旧字段。

下面假设业务已确认“新编码就是旧值去除首尾空白”，参数需通过项目数据访问层绑定，并非可直接在生产执行的脚本；有编码映射、大小写或非法值处理规则的项目必须替换该转换：

```sql
UPDATE device
SET location_code = TRIM(legacy_location)
WHERE tenant_id = :trustedTenantId
  AND id > :batchStart AND id <= :batchEnd
  AND location_code IS NULL
  AND legacy_location IS NOT NULL AND TRIM(legacy_location) <> '';
```

该示例逐行转换旧值，不把整批记录覆盖成同一个位置编码。无法转换的空值仍保留并计入校验，不据此直接收紧非空约束。检查点必须在相应批次提交后推进；部署回退时核对新字段写入是否丢失，不能直接附一份 DROP 脚本当作安全回滚。

**反例**：发布时直接将新增列设为 NOT NULL，历史数据未回填；一个长事务更新全表；旧实例仍会写空值时宣布迁移完成；修改已经应用的旧迁移脚本；未确认消费者退出就 DROP 旧列。

**验证步骤与预期**：在代表性数据中断、重跑回填，核对不覆盖新值、进度与提交一致、错误记录可定位；验证旧实例并存和约束收紧前后的写入。记录 DDL 锁等待及恢复路径，未运行迁移时不得写成迁移已成功。

## 五、开发者自检

- 数据访问是否经过明确边界；
- 查询、导出和批处理是否有规模、排序和进度边界；
- 事务是否只覆盖本地一致性；
- 外部副作用是否有事件、补偿或幂等策略；
- 并发写入、删除和归档语义是否明确；
- 缓存是否有失效、回源和一致性策略；
- 数据生命周期、保留期限和迁移回退是否可验证。
- 表结构、数据库约束和索引是否与数据含义及实际查询相符；SQL 值是否参数化，动态标识符是否受控。
