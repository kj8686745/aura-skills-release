**规范对象**：开发、维护周期任务、补偿扫描、批处理和调度入口的业务研发人员。

**规范目标**：让任务在约定时间处理获准的数据，遇到重复触发、实例重启、失败和停用时仍有明确结果。调度组件负责触发，业务用例负责授权、数据和副作用的正确性。

**阅读边界**：本文规定定时任务怎样设计和开发；XXL-JOB 的真实依赖、启用及 Handler API 见任务与调度能力说明。消息和普通后台受理继续按[异步任务与消息处理](./01-异步任务与消息处理.md)执行。任务状态、重试和资源保护复用既有规则，不另造统一任务数据库或强制每个任务安装分布式锁。

## 一、先定义任务

### AURA-BASE-ASYNC-027：周期任务必须明确触发方式与业务时间

**必要性**：必须

先明确任务处理的业务对象、执行周期和允许延迟，再按以下边界选型：需要统一启停、人工补跑、失败重试或多实例治理的业务任务优先使用现有 XXL-JOB；仅维护本进程状态、且允许每个实例执行的清理、保活等任务可使用 Spring `@Scheduled`。有明确项目替代方案时说明其等效处理与依据；存量任务按本次影响核对，不要求无差别迁移。框架提供执行器不能代替业务方案，使用本地触发也不能默认多实例只执行一次。

Cron 任务明确实际生效时区及调度端配置；本地声明 `zone` 或证明已配置的调度时区。固定延迟表示前次完成后间隔，固定频率表示按时间节奏触发，具体重叠行为还受调度器、线程池和异步使用影响。处理窗口按业务时间明确起止、边界和迟到数据策略；周期重试和人工补跑沿用原窗口，不能随每次 `now()` 漂移成新批次。

**为什么需要**：机器时区、实例数和业务日口径变化，可能导致漏跑、重复处理或跨天数据错误。

**正确写法**：设计确定按 `Asia/Shanghai` 每日生成上一业务日的 `[start,end)` 汇总，任务传入业务日期；补跑同一日期复用同一窗口。进程内缓存过期清理说明每个实例独立执行。

**错误写法**：只写“每天凌晨执行”，不确定由谁触发和时区；重试时重新按当前日期生成范围；认为 `@Scheduled` 自动具备集群单次执行保证。

**判断要点 / 验证方式**：核对实际调度配置、时区、首次启用和日期边界；用固定时钟或明确业务日期验证窗口和补跑，不能只检查 Cron 字符串能解析。

### AURA-BASE-ASYNC-028：任务参数与执行权限必须在业务入口确认

**必要性**：必须

任务参数属于输入，不能直接作为受信身份或数据授权。Handler 只解析和校验必要字段，并调用可复用业务用例；系统任务按模块权限方案建立服务执行主体及允许租户、机构或资源范围。跨租户任务先从可信来源得到获准租户集合，逐租户隔离处理；不因空参数、租户为空或用户上下文缺失就退化为全局范围。

需要线程上下文时按公开能力建立并在成功、异常、提前结束后恢复；任务不依赖请求线程残留身份。后台处理的创建者是审计、数据范围还是不适用，以模块已确认策略为准。危险参数、非法窗口或无权范围在写入前拒绝。

**为什么需要**：定时触发没有自然的登录用户，照搬 HTTP 身份或直接信任租户参数会扩大授权。

**正确写法**：Handler 接收业务日期，Service 从已授权任务配置加载租户范围，进入每个租户上下文后查询并写入，最后恢复；未授权租户被拒绝且零写入。

**错误写法**：从调度参数取 `tenantId` 后直接设置上下文；`SecurityUtils.getUser()` 为空就设管理员；任务入口同时查询多个 Mapper 完成全部业务逻辑。

**判断要点 / 验证方式**：重放缺参数、无权租户、异常退出和连续两个租户执行，核对数据与上下文；静态看见 `TenantBroker` 或权限注解不能证明范围正确。

## 二、重复、并发与执行预算

### AURA-BASE-ASYNC-029：重复触发与多实例执行必须有业务处理约定

**必要性**：必须

按任务实际副作用决定“允许重复但效果幂等”“同窗口互斥”“按资源分片”等策略。业务去重键应表达同一操作，例如任务类型、租户、业务日期/窗口和必要资源维度；调度日志 ID、触发时间或每次新生成的 UUID 不能替代稳定业务键。人工补跑、重试与正常触发必须共用同一业务约束。

单机串行、线程内锁和调度路由不自动保证跨实例业务唯一。只有业务确需共享互斥时才引入已验证的锁、租约或原子认领，明确作用键、持有者、期限、释放和过期后的旧执行者处理。锁超时不等于旧操作停止，必要时用版本、持有者条件或其他机制防止旧执行者继续提交。

**为什么需要**：调度重复、重试和实例变动不应导致重复扣费、重复通知或覆盖新结果。

**正确写法**：日报以“租户＋业务日”为唯一键，重跑返回或更新同一结果；有不可重复副作用时，将原子认领或幂等依据落实到副作用边界。纯本地缓存清理可按实例独立执行，不加全局锁。

**错误写法**：每次触发生成新批次键后新增同一日报；把 `synchronized`、XXL 单机阻塞策略或一个 Redis 锁调用写成业务恰好一次的证明。

**判断要点 / 验证方式**：重复和并发触发相同业务键，检查实际结果及副作用数量；使用共享机制时再验证失效、租约过期和旧执行者写回，不能只看锁方法返回值。

### AURA-BASE-ASYNC-030：漏跑、超时和积压必须有有界处理方式

**必要性**：必须

设计停机、长时间运行和错过周期后的处理方式：忽略、合并处理、补指定窗口或受控追赶。调度中心的过期补偿只表示再触发，不表示每个漏掉的业务窗口已经恢复。补跑数量、批大小、并发和单次总耗时必须有界；数据多时按稳定顺序或游标分批，避免全表载入和无止境循环。

任务超时明确可安全终止的位置、对外调用超时和已提交批次如何保留。线程中断只是停止信号，代码要配合响应，不能据执行器超时或 Future.cancel 推断已经停止写入。分片策略说明资源划分和实例数变化的影响，跨分片重复仍按业务键处理。

**为什么需要**：一次漏跑不应演化为无限追赶、资源耗尽或同一批次持续并发。

**正确写法**：每轮只追赶限定数量的业务日，每批处理固定上限，并检查耗时；剩余窗口留存待后续处理。达到预算时记录实际进度及未完成状态。

**错误写法**：启动后用 while 一直追赶所有历史数据；无上限查询全租户；认为任务超时标失败后后台线程不可能继续产生副作用。

**判断要点 / 验证方式**：模拟积压、慢调用、超时和停止，检查批次上限、剩余工作和线程/连接释放；仅小数据成功不能证明有界。

## 三、失败、结果与恢复

### AURA-BASE-ASYNC-031：调度结果必须与业务完成判据对应

**必要性**：必须

分别定义“触发成功”“Handler 执行结果”“业务批次结果”。Handler 正常返回前检查业务结果，不吞掉异常或部分失败。业务返回结果对象时按已选成功判据向调度组件报告失败或终止；没有数据是正常空跑、数据缺失还是失败，应由业务明确。并发未取得处理权时的跳过结果也应可解释。

业务状态按需求记录：简单无副作用本地清理可以用日志/指标表达，不强制建任务表；需要人工补跑、结果追踪或跨进程恢复的任务保留可查询的业务窗口、处理进度和失败依据。多租户部分失败不能仅记录“本次任务成功”。

**为什么需要**：注册、触发和调度绿色状态都可能与业务数据完成情况不一致。

**正确写法**：Service 返回 100 条成功、2 条失败，Handler 按“本批必须全部成功”的方案报告失败，记录可重试失败项；允许部分成功的任务明确终态和后续处理。

**错误写法**：catch Exception 后只打印一行并正常返回；Handler 把任务放进线程池就报告完成；只记录扫描条数，把它当作成功处理条数。

**判断要点 / 验证方式**：分别验证空跑、全成功、部分失败和系统异常，核对业务数据、结果及调度判定；脱离调度器的 Service 测试不能称已验证真实调度回调。

### AURA-BASE-ASYNC-032：重试和补跑必须复用业务依据并控制副作用

**必要性**：必须

重试沿用同一业务键和窗口，只重做获准且未完成的部分。临时连接失败等可按总预算有限重试；参数、权限、确定性数据错误先修正原因，不能自动无限重试。外部结果未知时先查询或复用受对方保证的幂等键，不重新发送不可确认的副作用。避免调度层、客户端和业务层重试倍增。

人工补跑明确操作授权、窗口、已完成项处理、与定时执行冲突及结果查看方式。补跑的参数形式和业务用例与定时触发共用；不能增加绕过校验、扩大租户范围的“强制成功”入口。

**为什么需要**：失败恢复应修复未完成工作，而不是重放所有已完成的外部动作。

**正确写法**：原租户原日期的批次失败项再次处理；已经完成的项保持结果。失败的外部创建先按原业务键查询确认，再决定重试。

**错误写法**：失败后换新批次ID重新扣费；开启三个位置各重试三次却未计算总尝试；提供允许任意租户和日期的匿名补跑接口。

**判断要点 / 验证方式**：在部分提交、结果未知和重复补跑后检查唯一结果、实际尝试次数及拒绝边界；按已确认业务契约判断，不一律要求自动续跑。

### AURA-BASE-ASYNC-033：任务启停与重启恢复必须保持状态真实

**必要性**：必须

关闭新的调度、禁止新认领、终止在途执行和清理结果是不同动作。说明停用配置在哪里生效、已执行任务如何收尾以及如何重新启用；不承诺删除调度配置能够撤回已产生的副作用。

进程中断后明确选择失败收口、幂等重跑或凭持久化进度恢复；只有具备真实恢复依据时才承诺断点续跑。依赖本机内存的回调和游标不能当作跨重启依据。清理业务结果或历史记录不能破坏仍有效的幂等判断与补偿证据。

**为什么需要**：发布重启或停用任务时，不能留下永远运行中、重复写入或已丢失的恢复依据。

**正确写法**：任务停用后不再获取新窗口，在途批次按方案完成或保留未完成点；无可靠续跑定义时标记失败，由受控补跑恢复，不伪造自动续跑。

**错误写法**：重启后把全部 RUNNING 直接改成功；持有内存闭包却承诺自动重建；为省存储删除仍承担去重作用的近期记录。

**判断要点 / 验证方式**：在执行前、批次提交后、外部结果未知时分别停用或中断，核对新触发、在途处理和恢复结果；未测试重启就保留未验证。

### AURA-BASE-ASYNC-034：任务交付必须能定位配置、业务结果和验证边界

**必要性**：必须

在模块现有设计或 docs 中关联任务名称/Handler、所属模块、触发配置来源、时区/窗口、执行主体与范围、重叠/重复处理、失败和恢复方式。日志和指标按业务需要记录业务键、租户、窗口、尝试、成功/失败/跳过数、耗时和稳定失败原因；不输出 Token、完整敏感参数或海量逐行报文。

研发自测至少覆盖适用的正常、参数/权限拒绝、重复触发、业务失败和状态结果；涉及并发、多租户、停用或外部副作用时追加对应场景。分开记录组件依赖解析、Bean 创建、执行器注册、真实触发和业务结果，已有设计与验证文件可直接引用，不逐任务新造过程文档。

**为什么需要**：研发接手者能从任务入口追踪到配置、真实执行和待处理问题，避免只凭一个注解或成功日志判断已交付。

**正确写法**：设计与实现记录说明 `tenantDailySummary` 对应哪个业务日、哪个用例和结果表；隔离测试已验证重复写入保护，但调度中心注册和回调未验，分别列出。

**错误写法**：只交付 Handler 类，无配置、业务键或结果入口；执行一次 Java 方法后宣称生产调度已可用。

**判断要点 / 验证方式**：沿文档→配置→Handler/触发器→Service→数据与外部副作用→结果核对，证据缺失标未验证，不扩大到未使用的能力内部实现。

## 四、简明实施示例

**场景**：租户日报，技术设计确认使用统一调度；输入为业务日期，按租户分批。创建者只记录审计，服务身份的租户范围由受信任务配置提供。业务去重键为“日报类型＋租户＋业务日”，日报使用唯一约束或已确认的条件更新实现幂等。

```java
@Component
@RequiredArgsConstructor
public class TenantDailySummaryHandler {
    private final TenantDailySummaryService service;

    @XxlJob("tenantDailySummary")
    public void execute() {
        // 同一次业务窗口补跑必须传相同日期，不在重试时改用 LocalDate.now()。
        LocalDate day = LocalDate.parse(XxlJobHelper.getJobParam());
        // 下列 Service/Result 是业务示例类型；由 Service 验证获准租户、窗口和幂等。
        DailySummaryResult result = service.summarize(day);
        if (result.failedCount() > 0) {
            // 本示例要求全批成功；业务失败不能正常返回并被当成调度成功。
            XxlJobHelper.handleFail("业务日=" + day + ",失败数=" + result.failedCount());
        }
    }
}
```

示例需要真实公开 XXL-JOB 依赖及相应 Java/Spring 注解导入；`TenantDailySummaryService`、`DailySummaryResult` 为拟建业务类型，不是框架公共 API。调度参数格式错误会终止本次执行；数据库事务、上下文恢复、唯一键和部分提交状态在 Service/Repository 中实现。该片段不等于完整可运行项目，也不证明执行器已注册。

**反例**：Handler 里遍历全部租户，逐行执行 Mapper 与远端扣费，每次新生成键，捕获异常后返回成功；即使 Cron 正确，也未满足授权、幂等或结果规范。

**验证顺序**：先在隔离环境验证业务日期、无权范围零写入、重复/并发与部分失败，再在获授权环境验证执行器注册及真实触发，最后核对停用与恢复。无需为仅清理本进程过期项的任务引入全套业务批次表。
