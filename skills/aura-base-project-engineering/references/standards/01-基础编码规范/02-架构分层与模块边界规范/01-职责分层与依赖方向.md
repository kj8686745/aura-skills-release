# AURA（天玑）基础编码规范：职责分层与依赖方向

<!-- 规范编号：BASE-02 -->
<!-- 规范版本：0.1.0-draft -->
<!-- 模板版本：基础编码规范模板 v3 -->

**规范对象**：使用 AURA 开展业务应用开发的团队和开发人员

**规范定位**：定义前端、后端、工具和平台项目共同适用的职责分层、业务调用方向与技术实现依赖边界。



## 一、规范范围

本规范解决所有 AURA 业务项目都会遇到的共同问题：

- 一个代码单元、模块或服务应该承担什么职责；
- 业务调用方向和代码依赖方向如何保持一致；
- 公开契约与内部实现如何隔离；
- 模块、公共模块和服务如何划分；
- 如何避免循环依赖、反向依赖和无意义拆分；
- 项目规模变化时如何调整架构边界。

本规范不要求所有项目采用相同的目录名称、框架写法或文件数量。项目可以按规模合并层级，但不能因此混淆职责或让内部实现穿透公开边界。

## 二、与前端、后端及其他规范域的边界

本规范只保留跨前后端共同适用的架构要求，具体实现分别由对应规范域定义：

| 内容 | 归属规范域 |
| --- | --- |
| Controller、Resource、应用服务、领域对象、Repository、Mapper、Client、Adapter 的具体职责和写法 | `BASE-03 后端基础编码` |
| 页面、组件、请求封装、路由、状态管理、前端类型和交互的具体职责和写法 | `BASE-04 前端基础编码` |
| 请求、响应、错误、分页、文件、事件和异步结果的公开表达 | `BASE-05 接口规范体系` |
| 配置项、依赖版本、环境差异和构建入口 | `BASE-06 配置、依赖、环境与构建` |
| 身份、权限、租户、敏感信息和审计要求 | `BASE-07 安全、身份、权限与敏感信息` |
| 数据库、事务、缓存、数据生命周期和数据所有权的具体要求 | `BASE-08 数据访问、事务与数据生命周期` |
| 物联、消息、视频、模型、地图、文件等专项能力的专属调用方式 | 对应能力包使用规范 |

例如，“接口入口不能直接访问数据层”属于后端规范的具体规则；本规范只规定更上位的共同原则：协议适配、业务编排、业务规则和技术实现不能互相混淆。

## 三、职责分层与依赖方向

### AURA-BASE-ARCH-001：每个代码单元必须有明确职责

**必要性**：必须

**为什么需要**：职责混杂会让协议、业务和存储变化牵动同一个单元，难以定位修改和测试范围。

每个页面、组件、入口、业务单元、技术适配、公共模块和服务都必须能够说明其唯一主要职责。

一个代码单元不得同时承担互相冲突的职责，例如同时负责协议接收、业务编排、数据持久化、外部调用和用户界面展示。


**正确写法**：Controller 只接收请求并调用 ApplicationService，Repository 只负责数据访问。

**错误写法**：Controller 同时解析协议、拼接 SQL、调用远程服务并组装页面响应。

**判断要点 / 验证方式**：按类的入口、依赖和变更原因检查是否只有一个主要职责。
### AURA-BASE-ARCH-002：依赖方向必须能够解释

**必要性**：必须

**为什么需要**：业务调用与代码实现依赖是两种关系；混用箭头会掩盖反向依赖和不必要的技术耦合。

项目必须分别说明：

```text
业务调用方向：
业务入口 → 业务用例 → 业务规则

技术实现关系：
技术适配实现 → 上层边界定义的接口
```

两种关系不能用同一条含义不清的箭头表达。具体前端和后端层次名称由各自规范定义，但不能改变上述职责关系。


**正确写法**：业务入口调用用例，技术适配实现用例定义的接口，依赖箭头方向可从架构图还原。

**错误写法**：业务代码直接依赖数据库驱动和具体 HTTP 客户端，调用方向无法解释。

**判断要点 / 验证方式**：检查依赖图，分别确认业务调用方向和技术实现关系。
### AURA-BASE-ARCH-003：业务代码不得依赖技术实现细节

**必要性**：禁止

**为什么需要**：把驱动或客户端当作业务依赖，会让技术替换和外部协议变化扩散到业务规则。

业务规则和业务用例不得把数据库驱动、具体网络客户端、缓存客户端、消息客户端、文件系统或第三方 SDK 实现对象当作业务依赖。

业务需要使用技术能力时，应通过能够表达业务意图的接口、公开契约或能力公开入口接入。


**正确写法**：业务用例依赖 `DeviceRepository` 接口，数据库实现放在 infrastructure 层。

**错误写法**：业务规则直接创建 `JdbcTemplate`、Redis 客户端或第三方 SDK。

**判断要点 / 验证方式**：扫描业务包依赖，确认没有数据库、缓存和 SDK 实现类引用。
### AURA-BASE-ARCH-004：技术实现不得反向依赖上层协议

**必要性**：禁止

**为什么需要**：技术适配一旦依赖页面或接口细节，入口变化就会迫使底层实现一起变化。

数据库、缓存、文件、外部服务和其他技术适配不得依赖页面协议、路由、用户界面状态、具体入口响应结构或其他上层展示细节。

技术实现变化不应迫使业务代码了解其内部连接、客户端和存储细节。

**正确写法**：数据库适配器只实现领域接口，不引用 Controller、路由参数或页面状态。

**错误写法**：Mapper 根据页面路由和按钮名称决定数据库写入逻辑。

**判断要点 / 验证方式**：检查技术适配包的反向引用，确认不依赖上层协议和展示对象。

## 四、共同依赖允许矩阵

下表只表达跨前后端共同适用的职责关系，具体对象名称由 `BASE-03` 和 `BASE-04` 规定：


| 代码边界 | 可以依赖 | 禁止直接依赖 |
| 业务入口边界 | 业务用例、公开类型、公开错误模型 | 数据库、技术客户端、其他模块内部状态 |
| 业务用例边界 | 业务规则、上层定义的接口、公开能力入口 | 技术驱动、页面展示细节、原始外部响应 |
| 业务规则边界 | 业务模型、业务约束、业务接口 | 上层协议、数据库驱动、具体第三方客户端 |
| 技术适配边界 | 上层边界定义的接口、技术客户端、转换器 | 页面、业务入口、其他模块内部业务流程 |

## 五、业务与技术关系示例

### 1. 正确的业务与技术关系

```text
业务入口
  → 业务用例
    → 业务规则
      → 业务意图接口
        ↑
      技术适配实现
```

上层使用业务意图，底层负责技术实现；项目不要求固定类名，但必须保持这种关系。

## 六、开发者自检

新增或调整职责分层和依赖方向时，至少确认：

- 每个代码单元和模块是否有清晰的主要职责；
- 业务调用方向和技术实现关系是否分别可解释；
- 业务代码是否依赖具体技术实现；
- 技术实现是否反向依赖上层协议或展示细节；
- 前端和后端的具体实现是否已经转到对应规范域，而不是在本规范重复定义。

## 七、与其他基础规范域的关系

- 工程结构、命名和项目文档，遵守 `BASE-01`；
- 后端具体分层、接口入口和数据访问写法，遵守 `BASE-03`；
- 前端具体页面、组件、请求和状态写法，遵守 `BASE-04`；
- API、事件、错误和跨模块公开契约，遵守 `BASE-05`；
- 配置、依赖、环境和构建，遵守 `BASE-06`；
- 数据访问、事务和数据生命周期，遵守 `BASE-08`。

本规范只规定共同架构边界，不重复定义前端或后端实现规则。
