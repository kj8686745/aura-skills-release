## 一、规范定位

本规范规定前后端和模块间如何共同维护可执行的接口契约。接口文档是调用方和提供方共同使用的公开技术契约，不是后端实现说明、前端页面说明或详细设计的替代品。

详细设计负责说明一次功能如何实现；本规范负责说明接口本身如何被调用、返回、失败、兼容和验证。

## 二、接口文档的事实来源

接口文档必须与实际可运行的接口契约保持一致。项目应明确唯一事实来源：

- 手工维护的 Markdown 接口文档；或
- OpenAPI/JSON Schema/事件 Schema 等机器可读契约生成的参考文档。

同一接口不得同时维护多份互相独立的字段规则。自动生成的参考文档不能反过来替代真实契约定义。

## 三、核心规则

### AURA-BASE-API-DOC-001：每个公开接口必须有唯一身份

**必要性**：必须

**为什么需要**：唯一身份可以让提供方、调用方、版本和生命周期被准确关联，避免同名接口或历史版本混淆。

接口文档按业务模块维护一份；模块内每个接口必须包含唯一编号或稳定标识、名称、方法与路径、提供模块、调用方、版本和状态。共同约定可在模块级只写一次，接口差异必须在对应明细中写清。

**正确写法**：`API-DEVICE-REVIEW-001`，提供方为设备服务，调用方为设备审核页面，版本为 `v1`。

**错误写法**：只写“审核接口”，无法区分路径、版本和责任方。

**判断要点 / 验证方式**：检查接口文档是否能唯一定位提供方、调用方、版本、路径和当前状态。

### AURA-BASE-API-DOC-002：接口必须完整描述请求契约

**必要性**：必须

**为什么需要**：完整请求说明可以让前后端依据同一字段、类型和校验规则开发，减少联调阶段反复猜测。

必须说明请求方法、路径、请求头、路径参数、查询参数、请求体、字段类型、必填性、默认值、枚举和校验规则。

不能只给出 URL 或一段未经说明的 JSON 示例。

**正确写法**：按字段表说明请求头、参数位置、类型、必填性、默认值、枚举和校验规则，并提供完整请求示例。

**错误写法**：只粘贴一段 JSON 或只写路径，不说明字段含义、类型和必填性。

**判断要点 / 验证方式**：逐项核对请求方法、路径、请求头、参数、请求体、字段规则和示例是否一致。

### AURA-BASE-API-DOC-003：接口必须完整描述响应契约

**必要性**：必须

**为什么需要**：明确响应结构和空值语义可以让调用方覆盖成功、空数据和分页场景，避免只按单个成功样例实现。

必须说明成功响应结构、字段语义、空值规则、分页结构、业务状态和响应示例。内部实体、数据库字段或第三方原始响应不得直接作为公开契约。

**正确写法**：分别说明成功、空结果、分页和业务状态，并给出与字段表一致的响应示例。

**错误写法**：只提供一份成功 JSON，或直接把数据库实体字段表作为响应说明。

**判断要点 / 验证方式**：核对响应外壳、字段类型、空值语义、分页结构和示例是否可由调用方直接使用。

### AURA-BASE-API-DOC-004：接口文档必须列明错误类别与处理方式

**必要性**：必须

**为什么需要**：文档明确错误类别和处理方式后，调用方才能区分提示、重试、重新认证和人工处理，而不是统一显示失败。

必须分别说明 HTTP 状态、业务错误码、错误信息、是否可重试、前端处理方式和用户可见结果。不能用 HTTP 200 包装所有失败，也不能只写“请求失败”。

**正确写法**：按参数、认证、权限、冲突、限流和系统故障列出状态码、错误码和处理方式。

**错误写法**：所有失败都写成“请求失败”，或只说明 HTTP 200 与一段错误文本。

**判断要点 / 验证方式**：逐项检查错误类别、错误码、重试语义、前端处理和用户可见结果是否完整。

### AURA-BASE-API-DOC-005：权限和调用上下文必须进入接口文档

**必要性**：必须

**为什么需要**：记录身份、租户、权限和链路上下文的来源，可以避免接口实现完成后才发现调用方缺少必要安全信息。

接口必须说明身份、租户、组织、数据范围、操作权限、必要请求头和 Trace/请求标识的来源及传递方式。

前端按钮或路由控制不能替代接口文档中的后端授权约定。

**正确写法**：记录认证来源、租户头、权限标识、数据范围和 TraceId 传递方式。

**错误写法**：只写“需要登录”或只依赖页面按钮隐藏说明权限。

**判断要点 / 验证方式**：对照接口实现和联调请求，确认必要上下文均已记录且名称一致。

### AURA-BASE-API-DOC-006：分页、排序、过滤和批量边界必须明确

**必要性**：必须

**为什么需要**：明确数据规模和默认行为可以保证前后端对查询结果、性能边界和超限处理理解一致。

列表、搜索、导出和批量接口必须说明参数语义、默认值、最大值、排序规则、数据范围和超限处理。不能让前后端各自猜测分页字段和最大数量。

**正确写法**：明确 `pageSize` 默认值、最大值、排序白名单、批次上限和超限错误码。

**错误写法**：只写“支持分页和筛选”，不说明默认值、上限和超限行为。

**判断要点 / 验证方式**：使用边界值和超限请求验证文档字段、实现行为和响应结果一致。

### AURA-BASE-API-DOC-007：接口文档必须说明写操作的幂等与并发结果

**必要性**：必须

**为什么需要**：调用方需要依据文档决定是否可以重试、如何处理重复提交和版本冲突，避免产生重复副作用。

创建、提交、审核、删除、批量操作和异步触发接口必须说明幂等键、重复请求结果、版本校验、并发冲突和重试边界。

**正确写法**：明确幂等键来源、重复请求返回结果、版本冲突错误和可重试范围。

**错误写法**：只写“接口支持重试”，不说明重复请求和并发冲突如何处理。

**判断要点 / 验证方式**：重复发送和并发提交请求，核对文档描述与实际结果是否一致。

### AURA-BASE-API-DOC-008：接口文档必须说明接口变更的兼容与迁移方式

**必要性**：必须

**为什么需要**：接口文档是迁移和联调依据，按实际影响记录兼容范围、切换条件和恢复方式，可以避免调用方继续依据过期契约开发。

接口字段、枚举、路径、错误码和响应结构发生变化时，必须说明实际受影响的调用方、兼容范围及适用的版本或同步切换方式；需要迁移或废弃时再写明顺序与时间，涉及既有状态或外部副作用时说明可执行的恢复方式。全新且无旧调用方的契约不虚构兼容窗口。删除或改变既有语义不得只修改文档而不记录变更。

**正确写法**：已发布响应新增可选字段时，记录旧调用方是否能忽略该字段及验证结果；准备删除旧字段时，再记录旧调用方迁移顺序、停止使用时间和实际可执行的恢复路径。

**错误写法**：直接删除字段或改变枚举含义，只更新当前文档内容。

**判断要点 / 验证方式**：按实际存在的旧调用方检查变更记录、兼容验证和适用的迁移步骤；涉及恢复时核对执行前提和结果，不把未验证的回滚声明当作证据。

### AURA-BASE-API-DOC-009：接口文档必须区分提供方与调用方责任

**必要性**：必须

**为什么需要**：清晰的责任划分有助于定位问题归属，也能防止调用方把内部实现误当成公开接口的一部分。

接口文档必须明确：提供方负责契约实现、授权、业务校验和错误语义；调用方负责参数组装、展示状态、调用重试边界和用户反馈。调用方不得依赖提供方内部类、数据库字段或内部地址。

**正确写法**：在文档中分别列出提供方责任、调用方责任和不属于公开契约的内部实现。

**错误写法**：只列接口字段，不说明授权、错误处理和调用方重试责任，或要求调用方引用内部实体。

**判断要点 / 验证方式**：由前后端分别复述责任边界，确认不存在依赖内部实现的隐含约定。

### AURA-BASE-API-DOC-010：接口文档必须提供可重复的联调验证方式

**必要性**：必须

**为什么需要**：覆盖正常、失败、权限、冲突和兼容场景，才能证明文档不仅可阅读，而且足以指导真实联调和问题复现。

必须说明正常、参数校验、权限、空数据、业务冲突、超时、重复请求和兼容场景的验证方式。Mock 只能用于开发辅助，不能替代真实接口的契约约定。

**正确写法**：提供可重复的请求样例、前置数据、预期响应、失败场景和验证顺序。

**错误写法**：只验证一次成功请求，或只提供 Mock 结果而没有真实接口联调方式。

**判断要点 / 验证方式**：按文档执行正常、失败、重复、权限和兼容场景，确认结果可复现。

## 四、接口文档最小结构

一份模块接口文档至少包含模块信息和接口总览，并对模块内每个接口分别记录：

1. 接口身份和版本；
2. 提供方、调用方和职责边界；
3. 请求契约；
4. 成功响应契约；
5. 错误和异常契约；
6. 权限、租户和上下文；
7. 幂等、并发、超时和重试；
8. 兼容和变更记录；
9. 前后端联调验证；
10. 请求和响应示例。

认证、租户、通用响应外壳、联调环境等共同约定可归并在模块级；若某个接口不同，应在该接口明细中覆盖，不能让调用方猜测。相关接口不应机械拆成一接口一文件。

推荐的阅读顺序如下；实时事件、服务间调用和公开 OpenAPI 可以增加专项章节，但必须能够定位到同一组章节锚点：

1. **模块/接口基本信息**：模块编号、接口编号、提供方、调用方、版本、状态和事实来源；
2. **接口总览**：模块内全部接口的方法、路径、调用方和状态；单接口文档至少列出当前接口；
3. **职责与调用边界**：提供方、调用方和禁止依赖的内部实现；
4. **统一认证、租户与请求上下文**：认证、租户、权限、数据范围和请求标识的共同约定；
5. **接口逐项契约**：每个接口的请求、成功响应、错误、幂等、超时、兼容和运行约定；
6. **专项协议**：事件字段、心跳恢复、服务认证、分页字段或公开签名等只在适用时增加；
7. **联调、发布与完成自检**：可重复场景、版本、运行关注项、废弃替代和最终自检。

示例中的章节编号可以因专项内容展开而不同，但“接口逐项契约”必须作为稳定标题；不应继续使用“二点一”“四点一”一类临时编号，也不能把每个接口拆成独立文件。

## 五、适用场景

### 新增接口

必须先完成接口文档，再由前后端分别实现提供方和调用方；字段和错误语义不能在联调时临时决定。

### 修改既有接口

必须标出变更前后差异，并确认旧调用方是否仍可运行；涉及删除字段、改变枚举语义、改变错误码或权限边界时，必须进入兼容评估。

### 跨模块或能力调用

只能引用公开入口和公开契约，不得把 SDK 内部类、内部 Topic、数据库表或内部地址当作接口文档内容。

## 六、开发者自检

- [ ] 接口身份、版本、提供方和调用方明确；
- [ ] 请求、响应、错误和示例完整；
- [ ] 权限、租户、数据范围和上下文明确；
- [ ] 分页、过滤、批量和边界明确；
- [ ] 幂等、并发、超时和重试明确；
- [ ] 受本次变更影响的兼容、废弃、迁移和恢复条件已明确；不适用的事项不虚构；
- [ ] 提供方与调用方职责没有混淆；
- [ ] 联调场景和双方处理约定已列出。

## 七、前后端联调约定

接口文档应说明前后端如何依据同一份契约完成联调，包括联调顺序、双方责任、测试场景和问题处理方式。

### 7.1 联调前置条件

进入联调前，提供方和调用方必须共同确认：

1. 接口编号、版本、三层路径和改写责任方；
2. 请求头、认证方式、租户/组织、权限和请求标识；
3. 请求字段、响应字段、错误码、分页、空值和枚举；
4. 幂等、并发、超时、重试、异步和文件边界；
5. 测试环境、服务地址、依赖服务、测试账号和测试数据；
6. Mock 使用范围、真实接口切换时间和问题反馈渠道。

以上内容应在联调前完成约定，避免在联调过程中临时决定接口语义。

### 7.2 联调阶段与责任

| 阶段 | 提供方责任 | 调用方责任 | 共同记录 |
| --- | --- | --- | --- |
| 契约确认 | 固化接口和错误语义 | 确认页面状态和数据展示需求 | 接口文档 |
| 提供方自测 | 验证认证、权限、参数、业务和异常 | 提供调用场景和边界数据 | 自测结果 |
| 调用方接入 | 提供环境、账号和依赖说明 | 完成领域 API、类型和页面状态 | 接入结果 |
| 联合验证 | 修复服务端问题 | 验证正常、失败、空数据和重复请求 | 问题与处理记录 |
| 联调结束 | 确认服务端版本和部署配置 | 确认页面和调用方版本 | 双方确认结果 |

### 7.3 最小联调场景

同步接口至少验证：正常、必填缺失、格式错误、无认证、无权限、跨租户、空数据、业务冲突、重复提交、超时/依赖失败和兼容调用。分页接口还要验证第一页、最后一页、超大页和无数据；文件接口还要验证无权限、未完成、过期、非法 Range 和大文件；异步接口还要验证受理、处理中、成功、失败、重复消费和补偿。

### 7.4 联调完成约定

联调完成后，提供方和调用方共同确认接口契约、主要场景、版本和问题处理结果；接口文档同步记录最终采用的约定。
