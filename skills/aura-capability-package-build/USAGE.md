# 能力包构建使用说明

版本见 VERSION，供内部能力负责人使用。发布工具保留内部标签；技能产出能力包候选，候选仍需复核，不因此将本技能标为建设中。本地升级不等于已上传新版。

可以直接说：“使用 $aura-capability-package-build，把当前项目的文件存储能力整理成能力包。”技能先识别已有项目和能力目录，说明建议范围；缺少规范仓库位置等关键信息时再引导补充，不要求先填写完整模板。确认后连续建设和检查，普通步骤不逐项确认。续接会复用已确认范围和现有内部记录。

工作区和输出位置见[建设与归档指南](references/governance/研发人员能力包建设与归档指南.md)第2～4节，按问题选读，不要求全文预读。需要能定位规范仓库和源码；前者接收文档，后者默认只读。只有技能而没有规范仓库时，不会在业务项目下代建能力包。

> 使用 $aura-capability-package-build，将指定版本的平台功能整理为能力包。先核实真实功能，再写任务操作与结果；对外最多形成能力说明、接入与使用手册、版本与兼容记录三份；操作规则、示例、接口和数据模型同在第二份手册。保留内部证据，不把建设过程写进使用说明。

支持三类任务：平台操作说明、API/SDK 接入、同一能力包的组合交付。交付内容按任务选择章节，不要求每次输出全部三份文件。完成标准包括读者能走通一个任务及查到准确参数，而不只是填满章节。

续接已有内容时可以说：“按模板复核当前能力包，统一排版，逐接口列出字段与示例缺口，并更新使用模块候选。”技能会区分排版完成、契约内容完整和实际运行验证，检查结论归入已有内部记录。

无需另装业务使用技能才能建设；交付本技能完整目录及准确来源位置即可。后端默认设计随研发入口使用的模块候选，不为每个能力新增安装项。不存在或未证实的能力不写成可用。

只建设当前任务指定的能力包，不重写基础规范、不替换前端负责人基线、不自行发布。包的构建与版本验收、纳入研发技能和对外发布是不同状态。

## 随包检查工具

Python 3.9+，仅标准库，在本技能目录执行。文档路径相对明确指定的规范仓库；含空格时加引号：

```text
python -B -X utf8 scripts/check-capability-delivery.py --standards-root <规范库根> --package-path <具体能力目录/候选对外内容> --phase preflight --mode candidate --json
python -B -X utf8 scripts/check-capability-delivery.py --standards-root <规范库根> --package-path <具体能力目录/候选对外内容> --phase content --mode candidate --internal-record <治理区内部记录.md> --json
```

`preflight` 只核对仓库和计划输出归属，输出目录可以尚不存在；通过不代表已有文档。`content` 核对实际文件、最多三份 Markdown、顺序编号、已识别“规则 ID”块的必要性与相邻正反例标记、本地链接和明显过程文字线索。内部记录只核对位置和存在性，不在输出中复制证据正文。修订已准入包用 `--mode update` 指向公司级规范05-能力包内的现有包，授权仍由当前任务决定，参数不授予修改或发布权限。

工具不写文件、不切分支、不运行源码、不读取远端或凭据。约定远端为指南中的公司 SSH 规范库地址，其他传输形式需人工核实或明确扩展工具，不能用业务仓库绕过；非1.0.0个人分支返回待核实，不自动切换。退出0仅说明支持的机械项无已识别问题，1为确定错误，2为缺项、候选线索或检查不完整。

规则文字不同、正文缺少可识别规则块或嵌套复杂 Markdown 时，脚本不能证明规则覆盖与正反例充分。总—分—总阅读效果、真实入口、全字段、权限/失败行为、来源映射和可运行性仍按规范与模板人工复核；不能用过检补造能力或兼容结论。结果归并既有内部记录，不为每次检查新增一份报告。
