# AURA（天玑）能力包统一定义模板

**性质**：能力包建设的内部统一模板  
**适用对象**：受托建设能力包的能力负责人、物联与 AI 团队规范维护者和内部审查人员  
**使用边界**：本模板用于建设和审查能力包，不是业务开发者使用规范，也不是正式能力包发布内容。

填写前先读[能力包通用构建规范](./能力包通用构建规范.md)。本模板记录事实与移交，不强制为每一栏单独建文件；同一能力包的内部记录优先归并成一份，较长的原始证据用链接指向源码或附件。

## 一、能力包基本信息

| 项目 | 内容 |
| --- | --- |
| 能力包名称 | 例如：基础功能工具能力包 |
| 能力包编号 | 统一、稳定、不可与其他能力包重复 |
| 候选版本 | 例如：`0.1.0-draft` |
| 建设状态 | 建设中、待审查、受控试用、正式可用、限制使用、停止新增使用或废弃；不得自行宣称正式可用 |
| 能力负责人 | 承接此能力包建设与后续维护的团队/人员 |
| 规范维护者 | 物联与 AI 团队的规则与发布责任人 |
| 适用 AURA 版本 | 已核定版本；未核定时写“待核定”，不得据此宣称兼容或发布 |
| 实现来源 | 仓库、分支及提交，SDK 制品及精确版本、现有公开契约 |
| 目标使用者 | 业务应用开发者、框架扩展开发者或其他明确角色 |
| 本次变更来源 | 需求、源码事实、试点反馈或审查结论 |

## 二、能力定位与边界

必须先回答能力包“解决什么问题”，再定义入口和实现：

1. 能力解决的业务或研发问题；
2. 适用的项目类型和使用场景；
3. 不适用的项目类型和场景；
4. 与其他能力包的职责边界；
5. 与 AURA 基础编码规范的关系；
6. 不纳入公开使用内容的内部实现。

能力包不得仅以现有仓库、模块或内部类名作为边界。源码结构只能作为事实依据，不能自动转化为公开能力边界。

## 三、能力事实盘点

对每项候选能力记录以下信息：

| 字段 | 内容 |
| --- | --- |
| 能力名称 | 业务可理解的名称 |
| 当前实现位置 | 内部事实，不能直接作为公开入口 |
| 能力类型 | API、组件、事件、配置、命令或其他 |
| 公开状态 | 已公开可用、受限可用、仅内部实现、未验证、已废弃 |
| 依赖关系 | 必要依赖和兼容约束 |
| 可公开性判断 | 可公开、需收敛后公开、仅内部、不纳入 |
| 判断依据 | 具体文件/符号与版本、SDK 导出、接口契约、配置、运行结果或试点反馈；区分直接事实与推断 |
| 待确认事项 | 需要人工决策的问题 |

能力事实必须区分“已确认事实”“推断”和“待人工确认”，不能把 AI 分析结果直接写成正式契约。逐项写明对外表述去向：进入能力地图、保留为限制、仅内部记录或暂不纳入。

## 四、对外公开契约

只有已经核实公开入口与对应版本的能力，才能进入候选公开契约。每项至少包含：

- 公开名称和稳定标识；
- 能力作用；
- 适用场景；
- 公开入口；
- 输入、输出或配置契约；
- 默认行为；
- 错误和失败行为；
- 权限、租户、数据范围或上下文要求；
- 生命周期、重试、幂等、顺序或并发约束；
- 不支持的用法；
- 兼容范围和升级方式。

填写时以一项能力为一个小节，附上对应事实记录的证据定位；无证据的字段标注“待核实”，不得用通用经验补写。公开视图不携带内部证据路径。

内部包名、实现类、缓存键、过滤器、拦截器、自动配置和历史迁移细节，不得替代公开契约。

## 五、业务使用内容结构

能力包正式发布后，对外使用视图统一按以下顺序组织：

1. 这个能力包提供什么，我是否应该使用；
2. 接入前需要满足什么条件；
3. 最小接入步骤；
4. 正确调用或配置方式；
5. 错误用法和边界情况；
6. 如何验证已经正确接入；
7. 版本和兼容说明；
8. 遇到问题如何反馈。

业务使用内容不展示内部审查评分、源码分析过程、治理任务和发布决策过程。

## 六、示例工程要求

每个进入受控试用或正式发布的能力包，至少关联：

- 一个最小能力示例；
- 一个正确用法；
- 一个错误用法或边界用法；
- 一个可构建、可运行的验证路径；
- 与基础编码规范的关联说明。

记录示例工程位置、对应提交、依赖版本、构建/运行命令、执行结果和未覆盖的真实环境条件。没有运行过的代码只称“文档示例”，不能作为可运行证明。

示例用于证明公开契约能够被使用，不等于要求业务项目复制示例中的业务名称、目录或页面。

## 七、Skills 绑定要求

能力包建设与使用存在两类不同的 Skills：

- **能力包构建 Skill**：内部使用，统一指导各能力负责人分析源码、整理契约与形成候选；它不随能力包交给业务使用者；
- **使用规范 Skills**：面向业务使用者，绑定已确认的公开能力和 AURA 版本。

后端能力默认交付为后端开发技能内的使用模块，不单独创建 `SKILL.md`。内部记录须登记承载技能、模块路径、命中场景、能力包版本与来源；只有存在独立使用任务时才单独建设使用技能。模块准入前仍为候选，不随已就绪的承载技能交付。

能力包尚未完成公开边界审查时，可编写候选使用技能用于内部试用，但不发布给业务使用者。

使用模块或独立使用技能所绑定的能力包版本必须与公开能力包版本一致；不一致时应提示升级或拒绝准入。聚合技能另有自身版本，不要求其版本号同时等于多个能力包版本；逐模块记录的绑定关系才是版本核对依据。

## 八、版本与生命周期

每个能力包只维护一份统一版本记录；可在本模板的内部记录中作为一节，不以大量过程文件替代。版本记录至少包含：

- 当前版本和状态；
- 本版本公开能力；
- 本版本不包含的能力；
- 兼容范围；
- 已知限制；
- 关联示例；
- 关联 Skills；
- 变更和迁移说明；
- 待处理问题。

生命周期统一为：

```text
事实盘点
  → 公开边界候选
  → 示例验证
  → 内部审查
  → 受控试用
  → 正式发布
  → 版本维护或废弃
```

## 九、内部审查最小项

内部审查至少确认：

- 能力包边界是否与其他能力冲突；
- 是否泄漏内部实现；
- 公开入口和行为是否有源码或运行证据；
- 配置、依赖和版本是否能够说明；
- 错误、失败、重试、幂等和权限语义是否清楚；
- 示例能否构建、运行和复现；
- 使用规范、示例和 Skills 是否引用同一版本；
- 是否仍存在只能依赖口头解释的内容。

内部审查材料只进入治理维护体系，不进入业务使用者的公开规范包。

## 十、能力包目录与移交

能力包候选按对外模板准备内容；进入对外交付集合时采用以下结构。内容少时可合并能力说明和使用规范；不能因文件合并而省略内容：

```text
05-能力包/
└─ <能力域>/
   └─ <能力包名称>/
      ├─ 总入口.md
      ├─ 能力说明.md
      ├─ 使用规范.md
      └─ 使用示例.md
```

内部建设材料采用独立目录：

```text
03-能力包治理/
└─ <能力域>/<能力包名称>/
   ├─ 内部定义与版本记录.md
   └─ 候选对外内容/           # 按上方四类内容准备；不是发布目录
```

一个能力域下有多个能力包时使用上述两级结构；能力域本身就是唯一能力包时，内部和对外目录都直接使用 `<能力域>/`，不创建 `<能力域>/<同名能力包>/`。候选对外内容按“总入口、能力说明、使用规范、使用示例”组织，内容少时可合并说明与规范。候选状态写在内部定义与版本记录中，不由父级目录名表达。

证据较多时可在治理区另设 `证据/`，不为了模板的每个章节拆文件。移交时提供内部记录、候选对外内容、示例工程定位与验证结果、候选使用技能位置及尚未解决的问题；规范维护团队决定是否进入试用或发布。受托建设者不修改对外索引；现有索引中的文档入口也不能代替整体版本的发布判断。
