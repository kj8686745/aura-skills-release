# AURA 能力包通用构建规范

**适用范围**：全部 AURA 能力域及其具体能力包  
**维护位置**：内部治理维护体系  
**当前状态**：建设中

本文件是能力包建设者的统一依据，由 AURA 规范维护团队维护。各能力负责人可以建设自己负责的能力包候选与使用技能，但不能修改基础编码规范、改变本文件的统一要求，或自行将候选标为正式发布。具体能力事实以指定版本的源码、SDK 制品、公开契约和可复现结果为准；现有文档与技能只是线索。

## 建设分工与最小输入

研发人员具体操作见建设与归档指南。

**AURA-CAP-BLD-012：输出必须归入指定维护仓库。** 必要性：必须。开始生成前核对 aura-code-nexus 的实际根目录、remote、工作分支、已有包目录及输出绝对路径；源码仓库与输出仓库分别识别。业务源码默认只读，不能因当前会话在业务仓库就向其写入能力包。规范根缺失或无法确认时停止文件生成，可继续只读分析并请求补充规范位置，不回退其他目录。技能源码只在 aura-skills 中维护。

正例：从业务仓库读取指定提交，文档写入已确认的规范仓库能力目录，内部记录独立归档。反例：把能力包写进业务项目 docs，或写进已安装技能的 references。检查：最终文件路径均在确认的维护仓库内，来源与输出可分别定位。

首次建设按内部候选路径提交复核；已准入包的授权修订沿用现有目录，不无条件复制全包。维护团队归档时归并对外内容、修复索引和引用、清理被替代候选，内部记录保留；同版只有一份现行文档。提交、推送、归档与发布分别记录。

规范维护团队提供本规范、内部定义模板、对外内容模板和内部构建技能；能力负责人提供能力域、拟建设范围、源码或 SDK 的可访问位置与版本、已有公开契约和示例工程位置。缺少资料时，建设者先完成可核验的部分并列出缺口，不用猜测补齐 API。

能力负责人交付的是一个**候选能力包**：内部事实与取舍记录、按对外模板写成的候选内容、可复现的示例或尚缺的验证证据、候选使用技能及版本对应关系。规范维护团队负责统一规则裁决、跨包边界和最终发布；候选文档不得通过移动到公开目录来代替发布判断。

## 1. 能力包是什么

能力包首先是框架能力的公开说明，使业务开发者能够回答四个问题：AURA 提供什么、什么时候使用、从哪里接入、使用后会得到什么结果。使用规范规定正确接入和使用方式；示例展示完整业务场景。三个部分必须围绕同一组已核验的能力，不得各自扩展口径。

能力域是分类，能力包是可独立选择和使用的具体能力集合。公共工程的模块划分是盘点线索，不能直接决定能力包数量或对外名称。

## 2. 建设顺序

1. **确定能力域与能力包边界**：用业务语言说明解决的问题、适用场景、相邻能力包及依赖关系。
2. **盘点真实能力**：从源码、SDK 制品、配置、公开接口和现有项目调用中核验能力是否存在，区分已公开可用、受限可用、仅内部实现、未验证和已废弃。源码存在不等于对外开放。
3. **确定公开能力地图**：列出每项能力的作用、入口、输入输出、默认行为和适用条件。不能公开的实现类只保留在治理资料。
4. **编制使用规范**：针对每项已确认能力，规定接入、调用、权限与租户边界、失败行为、正例、反例和验证方式；按本能力包的对外内容模板编写专项使用规则，不复制基础编码规范正文。
5. **编制场景示例**：从开发者任务出发，展示能力选择、最小接入、实际调用及可观察结果。示例必须与公开契约和使用规范一致。
6. **核对版本和兼容**：记录已核验的源码提交、SDK 制品版本、公开能力变化、依赖和限制；AURA 整体版本尚未核定时标为“待核定”，不猜测兼容结论。一个候选版本集中维护一份记录。
7. **移交候选并复核**：能力负责人提交候选和证据缺口；规范维护团队核对公开边界、示例、索引与使用技能，再按能力包治理流程决定试用或发布。

## 2.1 建设规则与检查点

下列编号约束的是**建设过程及候选质量**，不复制进业务开发者的能力包正文。每项均应在内部候选中留下可定位证据。

| 编号 | 必须做到 | 正确做法 | 错误做法 | 复核点 |
| --- | --- | --- | --- | --- |
| AURA-CAP-BLD-001 | 以用户可复用的能力划包，先交代能力价值与边界 | “设备状态订阅”按使用任务归入对应能力包，并说明依赖 | 按仓库或 Java 包名机械地一模块一包 | 能力包定位、相邻包关系 |
| AURA-CAP-BLD-002 | 逐项核对公开入口和版本，标记证据级别 | 从指定 SDK 制品导出与公开文档核对方法签名 | 看见内部类就宣布可供业务调用 | 内部事实记录中的版本、路径、证据和结论 |
| AURA-CAP-BLD-003 | 只有已核验的公开能力可写成“可使用” | 未验证的重试行为留在内部缺口 | 将推断的默认值写进对外说明 | 公开能力地图与事实记录逐项对应 |
| AURA-CAP-BLD-004 | 对每项能力写清接入、输入、输出、失败与边界 | 同时给依赖、配置、调用参数、返回与失败结果 | 只写“支持设备查询”而无接入条件 | 阅读者能据此完成一次调用或接入 |
| AURA-CAP-BLD-005 | 每条使用规则附相邻正反例，示例标明验证程度 | 可复制代码使用已核验 API，说明可观察结果 | 伪代码不标注，或只有成功片段 | 规则、示例与对应版本相符 |
| AURA-CAP-BLD-006 | 候选规范、示例工程和使用技能绑定同一已核验来源版本 | 候选技能按任务只读同版能力说明及示例；整体版本未定时标“待核定” | 技能引用旧 API，却把能力包标为新版或已兼容 | 来源版本映射、技能链接和示例运行证据 |
| AURA-CAP-BLD-007 | 治理证据与对外内容分开 | 源码差异、待确认项留在治理区 | 把审查意见、建设计划写入能力说明 | 对外目录仅保留使用者需要的内容 |
| AURA-CAP-BLD-008 | 移交候选时说明已证实、未证实及阻断项 | 给出证据位置、验证结果和缺口 | 未验证就移动到现行发布并宣称可用 | 移交记录与发布状态一致 |

## 3. 每个能力包的对外内容

每个具体能力包对外最多保留三份 Markdown 文件。能力少时可以减少文件数，但不能把使用规则、接口模型或版本边界省略。目录索引属于整个规范体系，不作为每个能力包额外的“总入口”文件。

| 内容 | 必须回答的问题 | 允许的典型文件名 |
| --- | --- | --- |
| 能力说明 | 能解决什么问题、适用场景、能力地图、价值与任务导航 | `01-能力说明.md` |
| 接入与使用手册 | 接入前提、操作和调用规则、正反例、完整业务示例、API/SDK 接口及数据模型、失败与验证 | `02-接入与使用手册.md` |
| 版本与兼容记录 | 当前交付版本、API/SDK/服务对应关系、兼容限制和按时间倒序归并的变更 | `03-版本与兼容记录.md` |

分类目录只作路由，不能代替具体能力包内容；具体能力包也不重复维护通用构建规则。纯平台或组件能力仍使用“接入与使用手册”承载操作规则和示例，不生成空的 API 章节。第三份记录只写使用者需要的版本与兼容事实；源码提交、审查过程和候选状态保留在内部记录。同一版本的公开变化归并到这一份记录，不按版本增文件。

## 4. 能力说明的统一骨架

每个能力包的能力说明按以下次序编排：

1. 能力包定位、目标使用者和典型场景；
2. 能力地图：每项能力的业务名称、作用、公开入口和使用条件；
3. 能力选择：用户遇到什么问题时选择哪一项；
4. 能力间关系：与基础能力及其他能力包如何组合；
5. 使用后可观察的业务结果和不支持的场景；
6. 指向接入手册与版本记录的准确章节。

未核验的模块可以出现在内部事实盘点，不能仅凭类名进入“可用能力”地图。

## 5. 使用规范和示例的统一要求

### 使用者阅读与交付原则

能力包是可复用能力的组织单位，SDK 是入口之一。控制台、配置、组件和 API/SDK 可以属于同一能力，不为不同入口重复划包。

能力说明参考平台能力使用说明模板中的能力与任务表达，具体接入步骤、字段、失败处理和完整示例归入第二份手册。第 4 节骨架是信息覆盖要求，不要求元数据和大表格前置。

提供 API/SDK 时在第二份手册中参考接入手册模板，按“选择方式 → 首次调用 → 使用规则 → 模块接口和数据模型 → 完整示例 → 排错”组织。纯界面、组件或配置能力不生成空 SDK 章节。接口和共享数据模型按模块分节，不一接口一文件；版本与兼容信息集中在第三份记录，手册只保留链接。

| 编号 | 必须做到 | 正确做法 | 错误做法 | 复核点 |
| --- | --- | --- | --- | --- |
| AURA-CAP-BLD-009 | 用具体任务与结果说明能力 | 查看设备状态写操作入口、刷新条件、结果和业务方责任 | 只有“设备管理、提升效率”和方法列表 | 不读源码即可判断选什么及得到什么 |
| AURA-CAP-BLD-010 | 首次使用形成可执行闭环 | 准备资源、操作、结果和失败处理连续可查 | 只写“配置后调用接口” | 配置值来源、动作和结果完整 |
| AURA-CAP-BLD-011 | 说明与参考同源分工 | 场景在能力说明，规则、完整字段和示例在手册并相互链接 | 多处各写一套字段或虚构 SDK | 能力、接口与示例一致，无重复契约 |
| AURA-CAP-BLD-013 | 每份对外文件形成总—分—总阅读闭环 | 开头说明目标和结果，中间按任务展开，结尾回收结果、边界和下一步入口 | 以清单、代码片段或最后一个接口表结束 | 抽查每份文件的开头、中段、结尾是否分别具备三类内容 |
| AURA-CAP-BLD-014 | 对外文件最多三份并按职责归并 | 能力说明、接入与使用手册、版本与兼容记录各自承担稳定职责 | 单独拆总入口、规则集、示例集、接口模型集，或一接口一文件 | 对外文件数、职责、重复段落和交叉链接检查 |
| AURA-CAP-BLD-015 | 每项能力和规则具备可追踪编号与必要性 | 能力 ID 关联入口、规则、示例和检查；标明必须、条件必须或可选 | 只有能力包总编号，正文靠自然语言引用 | 编号唯一性、反向引用和必要性标注检查 |
| AURA-CAP-BLD-016 | 候选重建建立源码到公开内容的映射 | 保留“源码入口 → 能力规则 → 示例结果”的逐项映射，并标记验证程度 | 直接复制正式文档后只改目录，无法说明本次版本变化 | 映射表、版本记录、构建和联调证据 |

章节分工不等于拆文件。短能力包可少于三份；已有同版接口参考可引用准确章节，不再复制。能力说明必须让人判断是否采用该能力，手册必须教会使用。可读性复核选一个真实任务，检查能否逐步定位前提、动作、结果及失败处理，再查一个参数或方法，确认能够直接定位其含义。缺失证据留在内部记录，不以空泛占位或伪造结果填充正式文档。

每项已确认能力至少给出：适用场景、最小接入、正确用法、错误用法、失败和边界行为、开发者可执行的验证方式。规则有稳定编号；每条规则的正例和反例贴在该规则附近，不另建“正例合集”。

示例至少展示一个可以串起能力选择、接口或组件调用、权限/数据边界以及结果验证的业务场景。代码中的类、注解、方法和配置键必须在指定版本真实存在；示意性伪代码只能明确标为“概念示意”，不能冒充可复制代码。达到试用或发布阶段时，还需要关联可构建、可运行的示例工程。

对外文件只呈现开发者需要的能力和用法。源码盘点表、待确认项、审查记录、生成脚本与发布过程保留在治理区。新建候选按对外模板写在 `03-能力包治理/<能力域>/<能力包名>/候选对外内容/`；如果能力域本身就是唯一能力包，则直接归入 `03-能力包治理/<能力域>/`，不再创建同名嵌套层。状态只在内部记录中表达；受托建设者不自行修改对外索引。工作区已有文档入口只用于定位内容，不构成可接入或已发布的承诺；实际对外交付索引以整体版本选定的能力集合为准。

## 6. 分类和索引

能力包先归入一个主能力域。内部台账记录建设状态、来源和审查结论；对外能力包索引只提供业务场景与文档入口，不放建设状态、审查结论或维护动作。跨域复用使用引用，不在多个能力包复制同一套规则。已有能力域不合适时，再评估新增分类，而不是为了一个模块建立新能力域。

内部台账的状态必须与实际产物一致：“建设中”不等于“可试用”，“有源码模块”不等于“已发布”。对外索引列出文档入口不构成能力发布；整体版本发布时，还须按发布集合核对该版本允许公开的入口。

### 索引与使用技能路由

- **AURA-CAP-IDX-001**：使用技能处理能力相关任务时，先读取能力包索引，再根据任务命中能力说明、手册中的对应规则与必要示例，不以“AURA”关键词加载全部能力包。
- **AURA-CAP-IDX-002**：对外索引只承载场景与入口，不承载完整 API、配置、源码实现、历史迁移或内部治理资料；详细内容回到对应能力包。
- **AURA-CAP-IDX-003**：命中具体任务后按需加载正文和示例；只需判断能力是否适用时，不加载长示例和源码证据。
- **AURA-CAP-IDX-004**：未命中入口或公开契约不足时，使用技能说明缺口并停止推断，不自行选择未公开 SDK、组件或接口。

## 7. 内部产物与对外产物的对应关系

| 内部治理产物 | 对外产物 |
| --- | --- |
| 能力事实盘点、源码证据 | 能力地图和来源确认后的公开入口 |
| 公开契约候选、边界审查 | 能力说明和接入与使用手册 |
| 示例验证记录 | 手册中的完整示例及可运行示例工程 |
| 版本记录、兼容核验 | 版本与兼容记录 |
| 使用技能建设记录 | 与版本匹配的使用技能 |

使用技能由维护者直接编写任务选路和开发步骤，按需引用本能力包的规范与示例；不得把技能当成第二份能力说明。规范变化时人工复核对应技能的路由、入口和版本。Python 自动生成不是后续能力包技能建设步骤。

后端能力包的默认交付形式为纳入后端开发技能的使用模块：提供触发场景、能力入口、前置条件、具体接入路由、验证办法和来源版本，保留能力包自己的规范目录。本文其他章节中的“候选使用技能”包含这种使用模块形式，不再要求每个后端能力包都有独立 `SKILL.md` 和安装入口。模块验证和准入要求不降低；未准入模块不随已就绪研发技能交付。只有确有独立使用场景且边界清楚时才另建使用技能。

具体字段和内部审查要求见能力包统一定义模板；对外文件的统一写法见能力包对外内容模板。建设者使用 `aura-skills/skills/aura-capability-package-build/` 中的能力包构建技能时，仍以本规范与模板为准。
