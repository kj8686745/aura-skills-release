# 研发人员能力包建设与归档指南

适用对象：负责把已有平台、组件、API 或 SDK 整理成可复用能力包的研发人员。普通业务项目接入已有能力不属于本流程。

## 技能如何引导研发人员

可以只说“把当前项目的文件存储能力整理成能力包”，不必先填完整表单或读完本指南。技能先核对当前任务、仓库与已有目录，再给出简短的已识别结果和需要补充的内容。

1. 先区分新建、更新已有包和业务接入。只要求在业务中使用能力时，不进入能力包建设。
2. 先从已提供路径、当前仓库及明确相关的相邻工作区定位规范库与源码；不扫描全盘，不输出可能含凭据的完整配置。已知分支、提交和 SDK 版本由文件读取，不重复询问。
3. 汇总建议的能力边界、已有包复用位置、产物类型及输出路径。用户已经明确的事项直接沿用；存在多个合理包边界、多个规范工作副本或契约冲突时，给证据与推荐选项再询问。
4. 缺少信息时一次归并相关问题，先问能决定下一步的问题，不让研发填写长清单。普通说明性缺口记入内部记录；只有影响目标、公开契约或输出位置的缺口才暂停相关动作。
5. 确认目标后连续完成事实核验、文档、示例和检查，不逐节问“是否继续”。新发现冲突只暂停受影响能力，其他已明确部分继续。
6. 续接时先读已有内部记录和 Git 差异，复用已确认选择，仅在输入或契约变化时重新确认。状态归入现有记录，不另外创建问答日志。
7. 收尾列出文件链接、已完成检查、证据缺口和归档状态。尚未授权提交或推送时给出具体目标与变更范围，不将“同意文档内容”推断为发布授权。

例如：识别到业务仓库中已有文件上传接口及规范库中的文件能力包后，优先更新已有包；找不到规范库时只问“规范仓库的本地路径在哪里？”，不在业务 docs 下生成替代文档。只拿到使用手册而无实现或制品证据时，可以整理结构，但不能宣称已核实可用。


## 1. 先区分两个项目

| 位置 | 用途 | 允许产生的内容 |
| --- | --- | --- |
| 能力实现或业务源码仓库 | 作为能力事实输入，分析入口、配置、模型和调用链 | 本任务默认只读；不在这里生成能力包文档 |
| aura-code-nexus 规范仓库 | 能力包文档的统一维护与归档 | 能力说明、接入手册、使用规则、示例文档及内部版本记录 |
| aura-skills 技能仓库 | 技能源码的统一维护 | 构建技能、已准入的使用模块或独立使用技能 |

安装构建技能不等于已经有规范仓库。不能因会话打开在业务项目中，就将当前目录当作能力包输出位置。业务项目自己的开发文档仍按项目文档规范管理，不因此迁入规范仓库。

## 2. 准备工作区

取得团队规范仓库，已有工作副本可直接使用：

```powershell
git clone --branch 1.0.0 ssh://gogs@git.fxft.net:2222/other/aura-code-nexus.git
```

建议在规范仓库中打开研发会话；源码仓库可在其他目录，通过明确路径作为只读输入。使用完整的 aura-capability-package-build 技能目录，不只复制 SKILL.md。

开始时让 AI 核对规范仓库根、remote、分支、工作树和已有能力目录。维护基线为 1.0.0；有个人分支时明确其目标为 1.0.0，不自动切换或覆盖未提交工作。先复用既有能力目录，不重复创建同名包。

规范仓库不可访问或输出目录无法确认时，可以继续只读分析，但应停止能力包文件生成并说明缺少的路径。不得退回业务目录、桌面或技能安装目录输出。

## 3. 给 AI 的任务示例

复制下列内容并替换括号；不需要另填一份审批表：

```text
使用 $aura-capability-package-build 建设能力包。

规范仓库根：<aura-code-nexus 本地绝对路径>
源码仓库：<实际路径>；源码版本：<分支及提交>
SDK / 现有手册：<位置及精确版本，没有则说明>
能力域与包名：<已有分类和能力包>
本次范围：<平台操作说明 / API-SDK 接入 / 两者>
负责人：<团队或人员>

先核对输出目录位于该规范仓库中，复用已有包目录。
业务源码只作分析输入，不在业务项目中创建能力包文档。
先核实实际能力，再按模板形成文档、示例及一份内部定义与版本记录。
完成后给出变更文件、来源版本、检查结果和待处理问题。
本次只准备本地变更，不推送、不发布、不修改正式索引。
```

从业务项目会话发起也可以，但仍须明确规范仓库位置；切换输出目标不意味着修改业务源码。

## 4. 文件写在哪里

相对于 aura-code-nexus 根目录：

```text
AURA天玑规范体系/
├─ AURA天玑规范建设管理/治理维护体系/03-能力包治理/
│  └─ <能力域>/<能力包>/
│     ├─ 内部定义与版本记录.md
│     └─ 候选对外内容/
│        ├─ 01-能力说明.md
│        ├─ 02-API与SDK接入手册.md      # 有相应入口才产生
│        └─ 03-使用规则与示例.md       # 短内容可并入前两份
└─ AURA天玑公司级框架规范/05-能力包/
   └─ <能力域>/<能力包>/              # 经维护团队纳入的对外文档
```

这是新包首次建设的路径，不要求每个包固定三个文件。单包能力域可省略同名包层级；已有编号和文件应复用，不因本示例重新编号。候选状态写在内部记录，不再额外创建“建设中”父目录。

已纳入对外集合的能力包：内部记录仍在治理目录；已授权的文档修订直接修改规范仓库中的现有文件并保留 Git 差异，不无条件复制全包。涉及未核验新能力的内容先保留在内部候选，不混入现行可用能力说明。

示例工程已有独立仓库时只登记准确仓库、提交、运行方式和结果，不复制整个业务工程。新增工程须在明确指定的位置实施。使用模块候选以路由、资料和版本设计记录在内部文档；实际技能源码仅在 aura-skills 中维护，不在规范仓库新增 SKILL.md，也不直接写入技能安装目录。

## 5. 研发人员检查与提交

完成后先检查：

1. 每项公开能力有对应版本和入口依据，无臆造方法、默认值或能力。
2. 读者能够找到任务、准备条件、操作、结果及失败处理；API/SDK 字段和示例契约一致。
3. 文件均在指定归档位置；内部证据没有进入使用说明。
4. 示例区分文档走查与实际运行结果；未验证内容如实记录。
5. 本次变更仅包含目标包，不夹带其他人员的修改或配置密钥。

向维护团队交付：规范仓库分支与提交（未提交则注明）、相对文件路径、源码/SDK 版本、检查结果和缺口。经授权提交时，仅暂存本包及必要索引文件；推送到约定分支交由维护团队合并，不用聊天附件代替仓库归档。

## 6. 维护团队如何归档

研发人员完成候选后，维护团队核对跨包边界、能力事实、模板完整性和版本关系；确认纳入时，将通过复核的对外内容归并到正式能力目录，修复索引及相对链接。内部定义与版本记录继续留在治理目录。

同一文档只保留一个现行维护位置；迁入正式目录后清理已被替代的候选副本，独有证据仍保留在内部记录或 Git 历史中。迁移先检查引用和差异，不覆盖其他人的未提交内容。

随后在 aura-skills 更新使用模块或技能引用、版本和规范来源提交。规范提交、远端推送、技能发布是不同状态，应分别记录。本地生成不等于已归档到团队远端；合并归档也不自动表示能力或 SDK 已发布。

## 7. 下一次修改

沿用同一能力包目录和内部版本记录，按已选源码/SDK 新版本核对变化。更新受影响的能力说明、接口参考、示例和使用技能；不要再生成“新版”“最终版2”等平行文档。新的版本记录归并到既有文件，历史内容由 Git 追溯。
