# 能力包对外内容模板

**用途**：为每个能力包编写面向业务开发者的能力说明、使用规范和示例。使用时替换占位内容，不能把本模板或维护说明复制到对外能力包目录。公开契约、接入配置和版本限制应写在下列对应章节，不另拆成多个空泛文件；能力少时可合并说明与规范。若能力对外提供 OpenAPI 或 SDK，平台能力说明仍按本模板编写，接口字段、SDK 方法、依赖和迁移内容另按[对外 API/SDK 交付手册模板](./对外API-SDK交付手册模板.md)维护，二者通过能力编号和接口编号关联，不重复定义。

## 使用模板的统一编排要求

每份对外文件都必须独立完成一次“总—分—总”阅读：

1. **开头总述**：说明本文件解决的业务问题、适用对象、使用后得到的结果，以及不负责的内容；
2. **中间分述**：按能力、任务或模块展开，每个单元都写清前置条件、操作或调用、输入输出、失败边界和验证方式；
3. **结尾总结**：回收本文件覆盖的能力、可观察结果、限制和下一步入口，不能以最后一个代码片段或一张表结束。

文件拆分以阅读职责为依据，不以一条接口或一个类拆分。拆分后每份文件仍必须满足总—分—总；内容不足以独立说明一项任务时，应合并到相邻文件。所有能力组使用稳定编号（如 `AURA-CAP-IOT-BUS-DEV-001`），规则编号、示例编号和接口编号通过该编号关联。

对外文件不得出现源码盘点、候选重建、审查评分、内部发布过程、未完成验证说明或建设任务记录。这些信息进入治理区内部记录；对外文档只保留会影响开发者选择、接入、调用和排错的边界。

### 阅读版式

表格用于能力选择、字段和结果对照，每个单元格只放同一类信息；操作顺序、长解释和代码放在表格外。导航链接使用短名称并直达章节，稳定能力编号在能力地图统一列出，任务导航可用编号后缀关联，避免每行重复长前缀。编号后缀必须说明共同前缀，不能成为第二套编号。

接口卡片依次区分请求、参数、SDK 示例、响应和调用注意。多行或需要复制的代码使用带语言的代码块，并注释输入来源、关键操作和结果含义；行内代码只放方法名、字段或简短表达式。共享对象字段只定义一次，卡片链接具体章节。

标题以任务或对象命名，末尾不加句号；标题、段落、表格和代码块之间保留空行。内容过长时按模块设小节，不为排版再拆出只有几行的文件。排版完整与契约完整分别复核：有标题、表格或接口编号，不代表字段、约束和成败示例已齐全。

## 三、使用规范

```markdown
# <能力包名称>使用规范

## <能力名>

### <稳定规则 ID>：<规则标题>

适用场景：<何时命中>  
使用要求：<开发者应如何接入与调用，关联本包公开契约>  
正确写法：<已核验 API 的最小正例，并说明可观察结果>  
错误写法：<同一规则的对应反例及失败原因>  
失败与边界：<权限、租户、超时、异常等>  
检查方式：<开发者如何验证结果>
```

规则数量由实际能力决定，不按固定数量凑文件。每条规则的正例和反例就在本规则下。

每条规则必须同时提供：

- 稳定规则 ID、必要性（必须 / 条件必须 / 可选）；
- 适用任务和前置条件；
- 正确写法及其可观察结果；
- 对应反例及违反后的具体后果；
- 失败、超时、权限和版本边界；
- 开发者可以执行的检查方式。
