# AURA 能力包构建

本技能供内部能力负责人和受托建设者使用。产物是可复核的**候选能力包**，不是发布决定，也不是业务使用者的能力使用技能。基础编码规范的定义由规范维护团队负责；本技能不得借能力包建设改写基础规范。

## 开始前

先引导，不要求用户读完指南或填满输入表。用当前请求区分新建、更新和业务接入；普通接入不触发建设。仅在已提供路径、当前仓库及明确相关的相邻工作区做轻量识别，不全盘搜索；已有提交、依赖版本和目录能读取就不询问。

首次反馈用“已识别事实 → 建议范围、产物与输出目录 → 真正缺失的问题”。已有明确选择直接沿用；只有包边界歧义、多个目标仓库、公开契约冲突或输出根缺失才询问，并说明证据与推荐项。相关问题合并询问，不逐字段盘问；普通缺口记入内部记录，不阻塞独立部分。

目标明确后连续执行到可复核产物，不逐节等待“继续”。续接先读已有内部记录和 Git 差异，复用已确认信息；只有事实变化才重新确认。不另建问答日志。详细引导场景见[建设与归档指南](references/governance/研发人员能力包建设与归档指南.md)的“技能如何引导研发人员”。

先按[建设与归档指南](references/governance/研发人员能力包建设与归档指南.md)第 2～4 节核对来源仓库与输出仓库。必须确认 aura-code-nexus 根目录、remote、工作分支、已有能力目录及目标绝对路径；写文件前检查目标解析后仍在规范仓库内。源码仓库默认只读，不以当前 cwd 作为输出根。规范仓库缺失或目标不明确时停止生成文件并请求路径，可以继续只读分析；不得回退业务项目 docs、桌面或技能安装目录。

首次建设写入规范仓库治理区的内部记录与候选对外内容；已准入包的授权修订复用现行文件，不复制全包。实际技能源码仅维护在 aura-skills。交付时分别报告本地生成、提交、推送、合并归档和发布状态；没有 Git 写操作授权时只交本地差异，不自动推送。

先读[能力包通用构建规范](references/governance/能力包通用构建规范.md)中与当前任务相关的章节，再选择资料，不预加载全部模板：

| 当前任务 | 读取资料 |
| --- | --- |
| 盘点事实、记录边界和版本 | [内部定义模板](references/governance/能力包统一定义模板.md) |
| 组织总入口、使用规则和示例 | [对外内容模板](references/governance/能力包对外内容模板.md) |
| 编写平台操作、组件或能力说明 | [平台能力使用说明模板](references/governance/平台能力使用说明模板.md) |
| 能力实际提供 API/SDK | [对外交付规范](references/governance/10-对外能力交付规范.md)与[接入手册模板](references/governance/对外API-SDK交付手册模板.md) |

这些是规范仓库的同版交付视图，不是第二份规则源。只修改一项能力时读取命中章节，不加载其他能力的接口、示例或内部证据。纯平台操作不生成 SDK 手册，也不加载 API/SDK 模板。

确定拟建能力域与候选包边界、能力负责人、源码仓库提交、SDK 制品精确版本、已有公开契约和示例工程。AURA 整体版本尚未核定时，在内部记录中写“待核定”并继续可核验的事实盘点；某项能力缺少必要证据时保持“未验证”，不能对外写为可用。

交给另一位建设者时，可直接指定本技能并说明：“在 `<能力域>` 建设 `<候选能力包>`；源码/SDK/契约位于 `<位置与版本>`；按本技能内构建规范形成内部记录和候选对外内容，提交到规范仓库对应能力域，不修改公开索引。”一个能力域有多个能力包时再分包目录；域本身就是唯一能力包时不建同名嵌套层。候选状态写入内部记录，不通过额外的“建设中”目录表达。建设者缺少的输入应列为待提供资料，而不是转成对业务使用者填写的表单。

## 建设路径

1. **定义可复用能力**：从使用者要完成的任务划定能力包，说明解决什么问题、适用与不适用场景、与相邻包的关系。不要照抄模块清单成能力包。
2. **反向核实事实**：从公开导出、接口/组件/SDK 类型、配置、调用链及现有消费者交叉核对。逐项标记“已公开可用、受限可用、仅内部实现、未验证、已废弃”，记录具体版本和证据位置。现有能力包、手册和技能只是线索，不能替代源码或制品证据。
3. **形成内部记录**：按内部定义模板写一份归并的内部定义与版本记录，保留证据、判断和待确认项。真实冲突先列出两边证据，请规范维护团队裁决，不选一个顺眼的结果写进公开契约。
4. **编写候选对外内容**：只将已核验的公开能力按模板写成总入口、能力说明、使用规范和使用示例。先解释能力与使用收益，再写依赖/配置、公开入口、入参与返回、失败与边界；每条使用规则配相邻正反例。示例区分已运行工程与未运行的文档片段。
5. **核对示例与使用模块**：需要试用或发布时，关联可构建运行的最小示例，记录精确版本、运行命令和可观察结果。后端能力默认交付可纳入后端开发技能的**使用模块候选**，提供触发场景、能力入口、接入路由、验证方式和来源版本，不另建 `SKILL.md`。只有确有独立使用任务时才建设独立使用技能。按需引用同版公开说明和示例，不把内部构建规范或证据带入使用模块；未验证模块不并入已就绪技能。
6. **移交复核**：对照构建规范 `AURA-CAP-BLD-001` 至 `016`，按归档指南第 5～7 节交付相对路径、来源版本、变更、验证和缺口；由维护团队完成归档及技能同步。公开索引及发布集合由维护团队处理，受托建设者不自行更新。

对外内容必须形成“选中任务 → 准备条件 → 实际操作或首次调用 → 观察结果 → 失败处理”的阅读闭环，再提供按模块查阅的详细参考。能力说明不是宣传摘要，SDK 也不是能力包本身；共享字段只定义一次。核对至少一个完整任务路径和一个字段查阅路径，区分文档走查与实际运行，不伪造耗时或成功证据。

按所选模板逐文件核对总述、任务分述和结果总结；接口手册再逐卡片核对权限、字段类型/必填/约束、请求代码、响应及成败示例。标题和接口数量齐全只能说明目录覆盖，缺字段或示例仍记为内容缺口。排版按[对外内容模板的阅读版式](references/governance/能力包对外内容模板.md#阅读版式)处理，长参考按命中模块或接口读取，不要求一次载入全包。

## 交付与停止边界

优先把内部事实和版本记录合成一份文档；对外内容按阅读需要分块，不按一条能力或一条规则建立一个文件。不要在公开文件里写源码盘点过程、审查评分、建设计划或“本轮任务”说明。

如无公开入口、版本冲突未裁决、权限/失败语义无法证实、示例引用不存在的 API，明确列出缺口并停在候选状态；不得用通用经验猜测。可以完成已经确认的其他能力项。不得自行移动候选到正式目录、修改公开索引或宣布能力包可用。

独立交付本技能给其他建设者时，须连同上述同版治理规范和模板一起提供，并保持相对目录关系；单独一个 `SKILL.md` 不构成完整建设依据。

版本与随包依据见[来源记录](references/source.json)，使用方式见 [USAGE.md](USAGE.md)。本技能只建设候选；跨技能同步、目录归并和发布准备由规范维护任务处理，不在能力建设中扩大修改。
