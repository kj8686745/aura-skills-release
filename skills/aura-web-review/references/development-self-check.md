# 开发自检模式

`mode=development-self-check` 是本技能的语义执行模式，供 `aura-web-develop` 自动调用，也可明确指定。它没有对应 PowerShell 参数。默认正式审查不进入此流程。

## 边界与输入

只读被检查业务源码、配置和依赖；审查不实施修复。记录执行者为开发自检；同一 Agent 开发后检查不构成独立人工或独立代理审查。接收用户任务类型（新开发/功能修改或纯注释/说明整理）、项目绝对路径、业务块与必要调用链、需求/原型、代码基线、业务说明、适用必需检查计划和检查记录位置。缺项先从任务和项目读取可确认事实；关键缺口记阻断，继续可独立检查。

沿用入口的 Aura 身份识别、敏感信息排除、范围及最新规范基线。aura-ui 的 AuraDictTag / AuraDictText / AuraDictSelect 纳入 FE-025 并关联 FE-019，其余 aura-ui 范围排除；ui-plus 正常纳入，公共能力摘要分列。筛选/表单的 Select 与展示 Tag/Text 均按共用路线取证检查，不因开发自检模式跳过。

不运行 `Review-Frontend.ps1 -Action Collect/Check` 作为自检入口，不创建六文件报告或审查结果包。直接用现有只读工具记录范围、版本/摘要和证据；确需其它扫描时先核对副作用及授权，输出到任务证据目录。不得调用 Collect 后删除报告来伪装无报告模式。

纯注释/说明整理只允许修改注释和说明文档，不修改可执行代码、DOM 属性、组件、import、状态、接口、控制流、依赖或配置。既有 FE 功能偏差继续如实记录规则结论、证据与建议，标原有问题/本次未修改，不自动要求开发侧加重试、useForm、竞态或字典替换；不因这些旧偏差停止已授权整理。

## 规则适用与语义取证

读取同版 [rules.json](rules.json) 及[审查路由](审查路由.md)，逐条判断 27 条规则与本业务块的关系，按需读取对应 standard 正文。沿用[取证与报告](取证与报告.md#项目识别)中的身份识别及逐规则取证方法；其中脚本接口、六文件字段/编号/统计、包内证据目录和原报告复核只适用于正式审查，不向自检套用。

用一张轻量规则表保留原 ID、来源、范围关系、纳入/已检查/未检查对象、结论和证据。范围外写“范围外未检查”，不当作规范不适用；没有运行材料、没有检查或候选零命中均不等于通过。适用规则沿用“通过、偏差、未证实、不适用”判定；规则含多个对象/条件时保留分项。未证实说明所缺条件与补证办法，不适用要有事实。证据支持真实要求和实际行为，不凭方法名、注释存在、目录标题或机械词匹配判通过。

跟踪页面 → 组件/Composable/Store → 领域 API → 统一请求入口及实际数据消费，核对需求、状态、权限、异常、取消、竞态和清理等适用条件。静态事实与运行事实分别记录。扫描候选需上下文确认；零发现不证明全部对象符合。

分页仅核对前端传参与显示对应：沿页面 → API 参数 → 统一请求序列化，确认公共 Hook 使用 `current/size`，响应消费 `records/total` 并正确映射 `useTable/AuraPagination`；有排序再核对 `orders` 的 `column/asc`，无排序不强求。按已有[查询表格规范](../knowledge/PIGX前端开发规范/页面模式/查询表格页.md)判断，`pages` 可选，前端使用真实 TypeScript 数字类型，不照搬 Java `long`。真实接口协议不同的，只在项目已有 API 适配边界明确转换请求与响应，公共 Hook 和页面保持统一契约；返回专用字段不作为请求参数，不在页面维护多套分页状态。前端参数/消费代码证据即可支持本项，必要测试可用 Mock 验证传参与显示；不审计 API 实现或后端分页算法，不要求真实后端联调来证明这项，也不把脚本扫描称为分页语义已通过。

## 可读性补充检查

先从实际源码提取本次业务对象清单，不按既有注释反推范围：变量/常量/ref/reactive/computed/解构服务及业务局部，模板返回/标题/说明/操作/业务内容/表单等区块与业务语义元素，自定义/公司/第三方业务组件实例，以及事件/生命周期/复杂逻辑。直接阅读源码即可，不要求新扫描器。逐对象记录“对象—用途/状态—注释位置—结论”，核对内容、位置与真实实现；漏项必须整改，不以零散有注释、行数或覆盖百分比判通过。 模板必须沿真实 AST/源码树根到子级递归核验，清单标明层级/分支、独立子节点及注释归属：父区块不能替动态文案、业务条件分支、循环集合/项及其内部标题操作、关键模型/事件、loading/空态说明；仅class布局可省。复选组核对选值来源/多选作用、循环项编码/名称含义，空态说明加载结束与无候选的真实条件。表单项上方规则保留，子节点注释贴自身所有者，不藏标签文本。原条件缺陷只记录，不借注释修功能。

## 轻量检查记录与返回

优先写任务指定证据目录；无约定可用 `docs/development-checks/<任务>/<业务块>.md`，这是一份内部过程记录，不是供人工审阅的最终报告。输出内容按实际事实填写：

- 模式、执行者、时间、技能实际路径/版本、需求和业务说明路径、业务范围/上下文、提交及未提交状态或文件摘要。
- 原规则表与补充检查表：原 ID/补充 ID、来源、纳入对象、实际结论/证据及未检查或排除理由。aura-ui 三个字典组件结果、其余排除与 ui-plus 结果分列。
- 可读性取证保留实际检查的变量声明用途覆盖、方法步骤、国际化字段/列及主要操作的注释位置和结论，按业务语义核对覆盖与准确性；文件头、大区块或注释数量不代替逐项证据。
- 问题稳定标识、要求与实际差异、具体位置/影响、修复建议及关闭条件；复查时保留问题、修复位置、代码版本、新证据和当前结果，不覆盖失败历史。明确记录当前有效、受后续变更影响待复查或历史状态；旧记录保留原范围与证据并链接后续记录，不将旧快照视为当前通过。
- 测试与验证：准确命令、工作目录、工具版本、退出码、结果及日志位置；已有由开发侧执行的证据可复用，但必须核对版本、覆盖和有效性，不能把未运行写成通过。
- 按任务类型总结：纯整理返回“注释/说明整理范围通过 / 需整改 / 阻断或检查未完成”，分列可读性/行为保持与既有 FE 功能偏差；功能任务返回“通过 / 需整改 / 阻断或检查未完成”，剩余必需项及下一步。不以六文件命名、E/C/F 卡片或完整报告统计作为本模式门槛。

READ-01/03/04 的适用注释或业务说明缺项、不可读或与真实实现不符记偏差并返回需整改，不只作 warning；由开发侧修改，再逐项复核对应方法步骤、模板字段与主要操作的新证据。

纯整理仅在本次可读性缺陷关闭、行为保持检查通过时返回限定范围通过，可生成“注释/说明整理审阅报告”，明确既有功能偏差、范围和未修改事项，不宣称整体 FE 合规。若用户明确要求全规范通过，旧功能偏差阻断该目标，列具体需授权修改，继续独立整理；不一律反复询问授权。

新开发/功能修改仅全部适用必需检查与测试通过、授权内偏差关闭且没有必需项未证实或未执行时返回“通过”；不适用有事实依据，范围外事项不虚构结论。可静态取证未完成时继续检查，不将尚未检查批量记为最终未证实。

将问题和记录位置按任务授权交回开发技能整改；纯整理只改注释/文档、既有功能偏差只记录，修改后重查受影响对象并更新证据；不改业务代码，不降低检查门槛。环境、材料、授权或业务决定缺失时返回阻断及待补条件，继续独立检查。功能任务只有授权内全部必需项通过后才生成开发报告，并标“自检通过，待人工审查”；纯整理按上述限定门槛交整理审阅报告。后续改动影响旧证据时重新取证，整体完成再核对跨块衔接。
