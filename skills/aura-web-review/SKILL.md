# AURA 前端代码审查

当前版本：`0.4.3`（2026-10-27）。

只读目标前端项目的源码、配置、依赖声明与已有产物，审查页面、组件及前端运行链路。先确认 Vue 3 + Vite 和 Aura 多文件证据，识别规则见[取证与报告](references/取证与报告.md#项目识别)。已有 Aura 专有线索的 IncompleteCandidate 在明确规范审查任务中使用 `-ReviewCandidate` 盘点并按最新规范报告缺项；普通 Vue/Vite 或只有单一联邦插件的项目不接管。接口仅核对前端调用与消费公开契约，不扩展到其他领域实现。随包示例仅供判断，不授权安装、修改配置或开发。

## 入口与依据

先按用户范围选择模式；模式是技能语义约定，不是 `Review-Frontend.ps1` 参数：

| 请求 | 模式与交付 | 按需读取 |
| --- | --- | --- |
| 明确限定 files、diff、一次变更或局部模块的日常审查 | 默认 `change-review`，一份报告 | [变更审查](references/change-review.md) |
| 全项目、完整规范审查，或明确要求正式审查/六文件 | `formal-review`，六文件结果包；限定范围也可明确选择正式模式 | 下文正式流程及[六文件模板](references/审查结果包模板.md) |
| 开发技能闭环调用，或明确 `mode=development-self-check` | 开发自检，轻量检查记录 | [开发自检](references/development-self-check.md) |

未给范围时按项目全部适用对象执行正式审查；已有明确范围时不反复确认。变更审查和开发自检均不调用 `Collect/Check`，不创建六文件或结果包。明确的开发自检调用保持该模式，检查范围按调用要求。

纯补注释/说明整理不会自动触发本技能；只有明确要求审查、自检或真实项目门禁时才按请求范围调用。仅检查注释时按已选模式读取命中的 READ 资料及必要上下文，不自动切换模式，也不扩展为全项目 27 条 FE 检查；完整规范审查仍保留正式范围。

首次调用说明审查范围，已有项目位置和任务时直接推进。项目全部适用对象为默认范围；用户限定模块或变更时遵从限定，必要调用方和配置仅作判定上下文。用法问答才读 [USAGE.md](USAGE.md)。

先读[审查路由](references/审查路由.md)，按任务读取 `knowledge/PIGX前端开发规范/` 中命中的文件。沿用现有前端技能的知识库组织；规则以随包同版正文为准，证据以目标源码、依赖、声明、配置与运行结果为准。二者冲突时明确版本与适用条件，不能让项目已有写法代替规范。

凡审查范围涉及业务表单，正式审查、变更审查和功能开发自检均必须按[表单共用取证](references/审查路由.md#表单生命周期取证)核对 web-kit `useForm` 的实际接入。未使用、只导入或绕过公共 Hook 调实例不能判通过；按事实记录偏差或缺证，不能因用户未提 Hook 而漏检。扩展 API、来源与未发布边界见[表单维护记录](references/form-hook-source.json)。仅注释检查沿既有范围执行。

27 条 FE 规则及必要性见[逐规则路由](references/rules.json)，来源与变更状态见[来源记录](references/source.json)。运行只读随包知识；Git 来源字段仅供维护追溯，不要求联网拉仓库。

维护技能版本时，同步在 [CHANGELOG.md](CHANGELOG.md) 记录版本日期、用户可见变化及必要兼容影响；同一未发布版本的补充归并原条目。提交、安装和发布状态留来源记录，不由日志版本推断。业务审查无需读取历史日志。

FE-001～004、019、024 命中 Vue/TS/样式组织时，按[文件组织与职责拆分](knowledge/PIGX前端开发规范/文件组织与职责拆分.md)核对职责、所有权、消费者与依赖；只凭长度、无 Hook 或 CSS 未外置不判偏差。纯注释不触发结构整改；本轮规范工作树与局部视图的[来源记录](references/file-organization-source.json)待提交绑定，保留原框架及历史来源基线。

请求针对整个页面/模块的结构优化验收时，还须按[完整结构范围复核](references/development-self-check.md#完整结构范围复核)覆盖原任务的职责与入口剩余部分；不能只审新增 Hook 或 diff 就宣布整个模块完成。限定局部审查仍按其明确范围，不自动扩展。

正式审查按全规则集合读取适用正文；变更审查和功能开发自检聚焦限定范围及必要上下文，复用已读且有效的资料，不机械枚举 27 条 FE 或重复全链取证。明确限定注释检查时只读命中的可读性资料及必要上下文；可读性补充项另标来源。本次模式变更见[本地变更记录](references/readability-source.json)，保留既有规范来源与未提交状态。

`aura-ui` 仅纳入 `AuraDictTag` / `AuraDictText` / `AuraDictSelect` 的公开接入与筛选/表单/字典展示消费，其余 aura-ui 范围排除；`ui-plus` 正常纳入。FE-025 保留原编号，注明三个字典组件及 ui-plus 子项，FE-019 关联筛选/表单 Select 与展示 Tag/Text 消费；命中三组件时读取随包 [aura-ui 组件库入口](knowledge/PIGX前端开发规范/aura-ui组件库/README.md)，按已安装版本核对；入口后仅加载实际使用组件的 DictTag.md / DictText.md / DictSelect.md。正式审查与功能开发自检均按适用范围核对依赖、实际 exports/types、import 或自动导入/Resolver 注册及真实展示使用，不扩展为 SDK 底层专项。公共能力摘要分别列 aura-ui（三个组件结果及其余排除）与 ui-plus；排除部分不计未证实，纳入项缺证仍如实记录。未使用须有依赖/调用盘点依据才判不适用。能力包建设暂缓。

## 正式审查连续工作流

1. **冻结与盘点**：核对 Git 提交、未提交差异、审查范围和规范来源。运行 `scripts/Review-Frontend.ps1 -Action Collect -ProjectRoot <项目>`；Aura 候选明确审查时加 `-ReviewCandidate`，限定范围使用 `-Scope`。读取返回的 `reportDirectory` 写六报告。脚本仅提供摘要和候选，Agent 补充未涵盖的入口、配置和资产。
2. **确认框架与适用性**：核对 package.json、锁文件、实际安装声明、Vite 和 config/aura。统一按最新基线 MF Vite 1.23.5、enhanced 2.9.2、web-kit 精确1.9.0（声明、锁文件与安装一致）、TS 5.9.3、ESLint 8.57.1 / typescript-eslint 8.46.1 检查，不增加旧版适配。实际版本或配置缺项据规范和源码确认偏差；仅真正无法取得证据的部分保留未证实。
3. **逐规则取证**：按路由读取页面、组件、请求、Store、权限、配置和相邻调用方。每条规则分别填写纳入对象、已检查对象、未检查对象、排除依据及证据。候选无命中不能判通过；直接请求可能位于允许的适配层，原生表单方法可能处于公共封装内部，需要追踪调用链。
4. **归并与判定**：由 Agent 根据实际取证编写报告，为证据、候选和发现分配稳定 E/C/F 编号。候选判为确认偏差、排除或待补证，规则判为通过、偏差、未证实或不适用。确认偏差必须有原规范要求、实际行为、位置、影响、证据、整改建议及关闭条件；纯建议不计入偏差。不要求填写机器判定 JSON。
5. **必要补证**：只执行项目已有且符合授权范围的检查命令。先检查 scripts 副作用；不运行带 --fix/--write 的格式化或 lint，不安装依赖、不修改锁文件。构建产物使用约定目录或隔离副本。无浏览器、依赖、业务材料或命令失败时记缺口，继续其余审查，不修改项目以掩盖失败。
6. **交付与复核**：Agent 按原模板直接编写六份 Markdown，逐规则核对状态、范围、证据和统计；可运行 `scripts/Review-Frontend.ps1 -Action Check -ReportDirectory <结果包>` 辅助检查结构。交付前复核被审版本及资产增删改，必要时在新目录再次盘点并对比；变化影响的证据重新获取，旧证据保留原版本。执行状态与项目质量分别说明。

进度消息不作为逐阶段确认节点。项目不可定位或关键边界确需用户决定时集中询问；普通环境缺口不暂停其余工作。

正常审查应连续完成全部可静态核对项，不能以大量“尚未检查”作为最终交付。未证实只留真实的运行条件或必要材料缺口，明确补证办法；尚未完成的过程包只能标部分完成。用户限定抽查时如实说明范围。

## 正式审查报告结构

必须遵循[原审查结果包模板](references/审查结果包模板.md)，保留六个文件名、报告卡片字段、状态及统计口径：

默认目录为 `<ProjectRoot>/审查结果包-项目名-提交短号-日期/`，已有目录追加序号不覆盖；无 Git 用可取得指纹/时间代替短号。脚本可省略 `-OutputDirectory` 自动创建该包的 `证据/`，返回 `reportDirectory`；用户显式指定输出优先。项目内仅允许专用结果包目录，全部结果包及其 JSON 自动排除出盘点。不得因此改源码、lock、env 或 gitignore。

`01` 第 5 节必须用中文对照表解释“规则中文名称 + ID、规范要求、实际检查情况、结论/缺证分类、证据位置及补法”；`02` 首列包含中文名称，编号不能代替解释。确认偏差卡片继续保留要求、实际、影响和证据。

```text
审查结果包-项目简称-提交短号-日期/
├─ 00-结果包说明.md
├─ 01-审查报告.md
├─ 02-规则核查矩阵.md
├─ 03-证据与执行记录.md
├─ 04-整改与复核清单.md
├─ 05-扫描候选与判定.md
└─ 证据/
```

脚本接口、逐规则取证、报告核对及复核方式见[取证与报告](references/取证与报告.md)。脚本沿用 `.ps1` 形式，支持 PowerShell 5.1/7；运行环境缺失时 Agent 直接完成可执行审查并记录辅助脚本未运行，不自动安装运行时。盘点试跑包只标部分完成。`Check` 通过只说明已检查的结构成立，不证明统计、证据链、脱敏或项目合规。

## 完成边界

开发自检输入须识别功能任务与明确要求验证的纯注释/业务说明整理。整理仅检查所请求注释、说明及行为保持范围，既有 FE 功能偏差不转为功能整改授权，不要求改 DOM、组件、import、状态、接口、控制流、依赖或配置。用户要求完整规范时执行其范围；旧偏差阻断该合规目标时如实记录，继续独立整理。普通补注释默认不调用本模式、不创建检查记录或报告。

不修改被审业务源码、配置、依赖、登录态或部署；整改由用户另行授权。原始日志与截图在落盘前脱敏，包内只保留必要证据，不保存密码、Token、私钥或敏感业务数据。

取证前排除 `.npmrc`、`.yarnrc*`、`.env*`、私钥与凭据文件；不批量打印全目录配置、认证值或环境变量。需要核对依赖源时使用已脱敏材料；缺少材料记录未证实。源码也可能含敏感值，工具查询限定文件、符号与必要上下文，保存前再脱敏。

正式审查交付前按[完整性清单](checklists/审查交付.md)实际核对。全部纳入规则均有状态、范围与依据且完成候选判定和六文件复核，才可称静态审查完成；范围受限用抽查完成，尚未执行取证用部分完成，关键目标不可访问用阻断。发布准入审查完成必须满足项目既定验收条件。运行缺口可以保留未证实，但不能把尚未读取的规则填写占位依据后称完成。变更审查按单报告要求核对，不给全项目通过结论；开发自检按其记录与通过条件核对，必需项缺证或未执行不能返回通过，由开发技能负责整改及通过后的记录/报告。

已请求的 API/类型注释检查按[声明字段门槛](references/development-self-check.md#read-0102-声明字段门槛)覆盖完整授权文件，逐字段确认自己的相邻中文。只读检查器为可选诊断，仅用户要求结构检查或真实项目门禁时运行；普通补注释不因此触发。用户仅维护技能时只读业务资料，不修业务源码。
