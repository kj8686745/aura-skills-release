**规范对象**：使用 AURA 开展业务应用、服务、工具和平台工程开发的团队和开发人员

**跨规范边界**：本文件约束运行时资源耗尽、后台故障和诊断入口；环境探针遵循 `BASE-06`，异步任务与消息结果遵循 `BASE-10`，身份和敏感信息遵循 `BASE-07`。具体框架组件的接入方式以对应能力包为准。

## 一、异常运行与资源保护

### AURA-BASE-RUNTIME-010：运行时资源耗尽必须有保护行为

**必要性**：必须

线程池、连接池、队列、内存、文件和磁盘接近或达到容量边界时，应用必须采取限流、有界等待、拒绝或降级等实际保护行为，并提供可定位的状态或告警；仅记录告警或继续无界排队不算保护。

**为什么需要**：资源耗尽如果没有保护，会从局部拥塞演变为整体不可用。

**正确写法**：队列达到上限时拒绝新任务并说明是否可重试，线程池满载时限制并发、记录积压及恢复状态。

**错误写法**：无界队列接收所有请求，直到进程内存耗尽后被系统强制终止。

**判断要点 / 验证方式**：逐步增加并发、队列和数据量，确认资源上限、拒绝结果和恢复行为符合预期。

### AURA-BASE-RUNTIME-011：运行时错误不得导致静默失效

**必要性**：禁止

后台任务、消费者、定时器和关键资源初始化失败时，必须记录可关联的错误并改变相应状态；不得捕获异常后继续运行而不留下任何可观察结果。

**为什么需要**：静默失败会让服务表面存活但实际已经停止处理业务。

**正确写法**：关键消费者异常退出后撤销相应服务就绪并记录任务与恢复状态；非关键消费者故障时保留核心服务就绪，但标记受影响功能降级并按明确策略恢复。

**错误写法**：`catch (Exception ignored) {}`，任务停止后健康状态和日志仍显示正常。

**判断要点 / 验证方式**：分别注入关键与非关键后台任务故障，检查就绪或降级状态、日志、指标和恢复动作是否与实际承载能力一致。

### AURA-BASE-RUNTIME-012：运行时诊断入口必须受控且不改变业务状态

**必要性**：必须

调试、线程、配置和依赖诊断信息必须经过访问控制和敏感信息过滤；只读诊断不得隐式修改业务数据。需要远程探测时必须有超时、频率和资源边界，不得由一次诊断请求触发无界扫描或批量副作用。

**为什么需要**：诊断入口既要帮助定位问题，也不能成为未授权访问和新的故障源。

**正确写法**：提供受保护的只读线程和依赖状态摘要，敏感配置只显示是否存在，不显示原文。

**错误写法**：公开返回完整配置、凭据和线程堆栈，或访问诊断接口就触发全量缓存刷新。

**判断要点 / 验证方式**：检查权限、返回字段、调用副作用和大规模请求行为，确认诊断功能可控。

## 二、典型使用示例：消费者故障与资源保护

**场景目标**：消息消费者、线程池和连接池达到容量或发生故障时，系统通过有界拒绝、状态变化、诊断摘要和恢复动作表达真实承载能力，不出现静默失效。

**输入条件**：消费者处理设备分析任务；执行器、连接池和队列均有上限；诊断入口只允许受控运维角色访问；部分依赖故障不应拖垮核心查询。

**正确处理链**：

```text
队列接近上限 → 限制受理或拒绝新任务并说明可重试条件
消费者异常退出 → 记录 taskId/原因，标记受影响能力并撤销对应就绪
非关键依赖故障 → 核心查询保持就绪，受影响功能进入明确降级
诊断请求 → 受控返回线程、队列和依赖摘要，不显示密钥原文
资源恢复 → 按边界重新接管任务，恢复状态并解除告警
```

诊断调用设置超时、频率和返回规模，不触发全量缓存刷新或业务写入；错误日志与任务状态保留可关联标识，不能仅记录“异常”后继续显示正常。

**错误处理链**：无界队列继续接收直至 OOM；`catch` 后忽略消费者异常；诊断接口公开环境变量和 Token；一次诊断触发全表扫描；恢复后无记录地重放所有任务。

**验证步骤与预期结果**：

1. 逐步增加队列、线程、连接和磁盘压力，预期触发有界等待、拒绝或降级，并能定位恢复条件。
2. 注入关键与非关键消费者故障，预期就绪、降级、日志、指标和恢复动作与实际影响一致。
3. 使用未授权诊断、超频诊断和大规模诊断请求，预期被拒绝、限流或截断，不改变业务状态。

## 三、开发者自检

- 资源接近上限时是否会限流、有界等待、拒绝或降级；
- 后台任务和关键资源故障是否有可关联错误与状态变化；
- 诊断入口是否受访问控制、敏感信息过滤和调用边界约束；
- 诊断请求是否保持只读，不会触发无界扫描或批量副作用。
