### 工程结构、命名与项目文档分类

本类规范适用于使用 AURA 开展业务应用、服务、工具和平台工程开发的团队和开发人员，统一项目工程结构、代码命名和项目文档组织。后端、前端、接口及能力包的专项要求由对应规范补充。每条规则只在一份分类文件中定义：

| 分类 | 适用任务 |
| --- | --- |
| [工程结构与代码组织](./01-工程结构命名与项目文档规范/01-工程结构与代码组织.md) | 新建工程或模块、确定职责目录、拆分文件、抽取公共能力 |
| [命名与代码表达](./01-工程结构命名与项目文档规范/02-命名与代码表达.md) | 命名文件和代码对象、统一格式、类型、常量、注释与导入导出 |
| [项目文档与资料组织](./01-工程结构命名与项目文档规范/03-项目文档与资料组织.md) | 建立项目和模块文档入口、确定资料归属、编号、模板、链接与过程资料隔离 |

开发者应自行核对工程目录、模块边界和文件归属是否清晰；名称和代码表达是否统一；项目与模块文档入口是否唯一；正式资料、示例和过程文件是否分离；是否出现重复文件、无意义拆分或无法判断来源的临时文件。具体正反例和验证方式以命中的分类正文为准。

## 二、推荐阅读和使用顺序

```text
总则
→ 工程结构、命名与项目文档
→ 架构分层与模块边界
→ 后端或前端基础编码
→ 接口规范体系
→ 配置与构建
→ 安全权限
→ 数据处理
→ 异常与可观测性
→ 异步与外部集成
→ 运行时与资源

→ 版本变更与交付
```

业务开发任务按实际涉及的模块组合使用，不要求一次性加载全部规范正文。专项设备、消息、视频、模型和地图能力由对应能力包补充。

规范要求以本目录正文为准；按当前研发任务选读，不需通读全部模块。

### 前端开发自检与交付

完成前端新增页面、领域模块或请求能力后，按命中的规则正文和正反例核对：

- 页面是否直接拼接内部服务地址、直接使用内部 DTO 或响应结构；API 是否集中封装；
- 重复提交、错误、空数据和无权限状态是否正确区分；
- 组件、类型和工具是否存在无理由的过度拆分；新增文件归属按 `AURA-BASE-STRUCT-002/003`，页面和组件命名按 `AURA-BASE-NAME-FE-001` 判断。

最小执行证据应能说明页面、请求封装、类型和状态的发现路径，真实接口与 Mock 的区分方式，加载、成功、失败、空数据、无权限和提交中等适用状态，路由、菜单和按钮权限的来源，以及本次构建、自测或真实联调的验证结果。页面截图或 Mock 成功不能单独证明接口契约、后端授权和生产可用性。

页面暂时只有一个接口、后端字段与页面字段恰好相同，均不构成绕过请求和模型边界的理由；不能为了方便在组件内拼接服务地址，也不能为了减少文件而把多个领域的状态放入同一个全局 Store。代码生成页面、框架约定目录和能力包专属组件可以保留特殊结构，但须说明其入口、依赖和适用范围。
