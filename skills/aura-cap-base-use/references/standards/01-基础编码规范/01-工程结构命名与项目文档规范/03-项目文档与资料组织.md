## 项目文档管理

项目文档必须与代码一起纳入版本管理，并按影响范围就近存放：

```text
项目根目录
├─ README.md
├─ docs/
│  ├─ README.md
│  ├─ 架构说明.md
│  ├─ 开发指南.md
│  ├─ 部署运行.md
│  └─ 决策记录/
├─ 模块A/
│  ├─ src/
│  └─ docs/
│     ├─ README.md
│     ├─ 接口说明.md
│     └─ 配置说明.md
└─ 模块B/
   └─ docs/
      └─ README.md
```

### AURA-BASE-DOC-001：项目必须有根 README

**必要性**：必须

根目录必须提供唯一的 `README.md`，说明项目用途、启动方式、主要模块和文档入口。

**为什么需要**：根 README 是所有开发者和 AI 进入项目后的第一事实入口，避免项目说明散落在多个文件中。

**正确写法**：根 README 明确项目用途、启动命令、模块清单、配置入口、测试方式和文档入口。

**错误写法**：根目录存在多个项目说明文件，或 README 只写项目名称而没有启动和文档信息。

**判断要点 / 验证方式**：是否只有一个根 README；内容是否能完成首次定位；链接是否指向当前目录；检查文件存在性、入口链接和启动说明；按 README 完成一次项目定位。

**例外**：无。多模块项目仍只能有一个项目根 README。

### AURA-BASE-DOC-002：项目级文档放在根 docs

**必要性**：必须

所有项目必须创建根目录 `docs/`，并提供 `docs/README.md`。影响整个项目或多个模块的文档必须放在根目录 `docs/` 下并由其导航；没有项目级文档时也不得删除该入口目录。

**为什么需要**：项目级文档需要统一入口，否则架构、开发、部署和决策说明会散落在代码目录或聊天记录中。

**正确写法**：根 `docs/README.md` 导航架构说明、开发指南、部署运行和决策记录。

**错误写法**：把架构说明放在某个业务模块下，或在根目录并列放置多份部署说明而没有主入口。

**判断要点 / 验证方式**：根 docs 是否存在、是否有 README、项目级文档是否都从该入口可达；扫描根目录和 docs 链接，检查项目级文档是否越过根 docs。

**例外**：无。即使当前文档很少，也必须保留根 docs 及其入口。

### AURA-BASE-DOC-003：模块文档就近存放

**必要性**：必须

业务、技术或公共模块存在独立的设计、接口、配置、运行或排障资料时，必须在该模块的 `docs/` 下提供文档入口。只服务于单个模块并随模块变化的文档放在该模块的 `docs/` 下，不得上收到项目根目录代替模块文档入口；没有独立模块文档时不为满足形式创建空目录或空入口。

**为什么需要**：模块文档与模块代码就近维护，才能在模块变更时同步更新，避免开发者跨项目目录寻找局部约束。

**正确写法**：有独立接口、配置和运行资料的模块建立 `docs/README.md` 并维护相应说明；没有独立文档的模块从项目入口即可定位职责，不建空 `docs/`。

**错误写法**：所有模块文档都集中放在根 docs，模块目录没有自己的文档入口。

**判断要点 / 验证方式**：先判断模块是否存在独立文档；存在时检查 `docs/README.md`、内容归属及入口链接；不存在时检查项目入口能否定位模块职责，且未创建空壳目录。

**例外**：模块文档入口随实际文档建立；公共模块、工具模块和技术模块适用同一判断条件。

### AURA-BASE-DOC-004：文档按影响范围归属

**必要性**：必须

| 文档影响范围 | 存放位置 |
| --- | --- |
| 整个项目或多个模块 | 项目根目录 `docs/` |
| 单个模块 | 对应模块 `docs/` |
| 单个能力、组件或公共库 | 对应代码目录或能力包文档目录 |
| 自动生成的接口、类型或配置参考 | 以代码或契约为事实源，按项目方式管理 |

一份文档同时影响多个模块时，应上收到项目级 `docs/`，不在多个模块复制。

**为什么需要**：按影响范围归属可以避免同一规则在多个模块分别维护后产生冲突。

**正确写法**：跨模块架构、接口约束和部署要求放在根 docs；单模块使用说明放在模块 docs。

**错误写法**：把同一份接口或部署说明复制到多个模块目录，修改时只更新其中一份。

**判断要点 / 验证方式**：文档影响范围是否与存放位置一致；是否存在重复主文档；人工确认影响范围，检查重复标题和相互复制的文档内容。

**例外**：模块 docs 可以提供摘要和链接，但不得复制完整主文档。

### AURA-BASE-DOC-005：同一内容只能有一个主文档

**必要性**：必须

同一接口、配置、架构决策、运行约束或使用方法只能有一份主文档。其他位置使用相对链接引用，不得维护互相可能过期的副本。

**为什么需要**：唯一主文档是避免内容漂移和 AI 读取冲突的前提。

**正确写法**：确定一份主文档，其他 README 或模块文档只保留摘要和相对链接。

**错误写法**：根 docs、模块 docs 和代码注释分别维护同一份完整配置说明。

**判断要点 / 验证方式**：同一主题是否有多个完整版本；引用是否指向唯一事实源；搜索重复标题和关键段落，检查引用链是否可达。

**例外**：自动生成参考文档可以存在，但必须声明代码或契约是事实源，不能人工维护第二份规则。

### AURA-BASE-DOC-006：文档必须和代码同步

**必要性**：必须

代码变更影响模块职责、接口、配置、部署、运行行为或使用方式时，必须在同一次变更中更新受影响的主文档。

**为什么需要**：文档落后于代码会让开发者和 AI 按过期约束实施，形成比缺少文档更严重的误导。

**正确写法**：接口、配置、目录或运行方式变更时，在同一变更中更新对应的接口说明、配置说明或运行说明主文档。

**错误写法**：先合并接口或配置变更，之后再依赖个人记忆补写对应的主文档。

**判断要点 / 验证方式**：变更是否影响主文档中的事实；对应主文档是否在同一变更中更新。示例及导航入口另按 `AURA-BASE-DOC-019` 检查。

**例外**：纯内部重命名且不影响职责、使用方式或入口的变更，可以不新增文档，但应确认无影响。

### AURA-BASE-DOC-007：文档按使用目的组织

**必要性**：必须

项目文档至少区分：

- 快速开始；
- 操作指南；
- 参考说明；
- 设计解释。

快速开始用于首次运行，操作指南用于完成明确任务，参考说明用于准确查询，设计解释用于说明架构和决策。不能用过程讨论代替正式使用说明。

**为什么需要**：不同阅读目的需要不同信息密度，混在一份长文档中会降低查找效率并扩大 AI 加载范围。

**正确写法**：按快速开始、操作指南、参考说明和设计解释组织文档，并从 docs README 导航。

**错误写法**：把会议纪要、设计过程、启动命令和接口参考全部堆在一个“项目说明”文件中。

**判断要点 / 验证方式**：文档是否能让读者快速判断用途；过程记录是否误充正式使用说明；从 docs README 分别定位首次运行、具体操作和准确参考内容。

**例外**：短小项目可以合并内容，但必须在同一主文档中使用明确章节，不得取消分类语义。

### AURA-BASE-DOC-008：文档名称和链接必须稳定

**必要性**：必须

文档名称必须表达主题，不使用“临时”“新建”“最终版”“最新版”或日期堆叠作为主名称。项目内使用相对链接，文档移动、合并或废弃时同步更新引用。

**为什么需要**：稳定名称和相对链接是目录治理、版本管理和 AI 索引持续有效的基础。

**正确写法**：使用 `部署运行.md`、`接口说明.md`、`决策记录/xxx.md` 等稳定主题名称。

**错误写法**：使用 `最终版.md`、`最新版-2.md`、`临时部署说明-2026.md`，或在文档中写死本机绝对路径。

**判断要点 / 验证方式**：名称是否表达稳定主题；移动或合并后是否同步修复链接；是否存在失效路径；扫描不稳定命名、绝对路径和失效相对链接。

**例外**：历史归档文件可以保留日期，但不得作为当前主文档入口。

## 文档边界与目录

### AURA-BASE-DOC-011：项目必须有唯一总入口文档

**必要性**：必须

每个项目必须在约定的项目文档根目录提供一个总入口，说明项目定位、模块清单、文档目录、运行入口和关键约束。其他文档不得替代总入口承担项目全貌说明。

**为什么需要**：新成员和维护人员需要先了解项目全貌，再进入具体模块，避免从散落文件中猜测结构。

**正确写法**：在 `docs/README.md` 列出 `用户中心`、`设备管理`、`消息处理` 模块及各自文档入口。

**错误写法**：项目只有多个模块说明文件，没有总目录；或把临时会议记录当作项目入口。

**判断要点 / 验证方式**：从项目根目录进入文档，确认能够在总入口找到模块、启动说明和主要规范文件。

### AURA-BASE-DOC-012：模块文档必须归属对应模块目录

**必要性**：必须

只描述某个模块的设计、接口、配置、运行或排障资料，必须存放在该模块的 `docs` 目录或其明确的文档子目录；跨模块内容放在项目总文档目录。

**为什么需要**：按模块归属文档可以减少根目录文件堆积，并让代码与说明保持邻近。

**正确写法**：`modules/device/docs/` 存放设备模块设计和接口说明，`docs/` 存放项目架构和全局运行说明。

**错误写法**：把所有模块的几十份说明文件都放在项目根目录 `docs/`，或把设备文档放进用户模块目录。

**判断要点 / 验证方式**：根据文档内容判断唯一归属，检查目录位置是否与模块边界一致。

## 命名、编号与模板

### AURA-BASE-DOC-014：按编号管理的正式文档必须以编号和主题命名

**必要性**：必须

按编号管理的正式设计、接口、配置和运行文档，文件名必须包含稳定编号和明确主题，编号在所属项目或模块范围内唯一。`README.md`、`AGENTS.md` 等约定的入口文件沿用固定名称，不为了编号改名；临时记录不得使用会与正式文档混淆的名称。

**为什么需要**：编号可以支持排序、引用和自动识别，主题可以帮助人工快速判断内容。

**正确写法**：`01-设备审核详细设计.md`、`02-设备审核接口文档.md`。

**错误写法**：`新建文档.md`、`最终版2.md`、`说明_updated.md`。

**判断要点 / 验证方式**：检查文件名是否能表达归属和主题，并确认同一目录没有重复编号或含义不明的版本后缀。

### AURA-BASE-DOC-015：正式文档必须使用对应模板

**必要性**：必须

详细设计、接口文档、配置说明、运行说明和能力示例等不同类型文档，必须使用与其目的匹配的模板；不得用一份泛化模板掩盖不同文档的必要内容。

**为什么需要**：不同文档的读者和决策内容不同，模板不匹配会导致关键内容缺失或结构混乱。

**正确写法**：技术详细设计使用技术路线、模块设计和异常处理模板，接口文档使用模块接口清单和联调约定模板。

**错误写法**：把接口字段表、数据库设计和部署步骤全部塞进同一份“项目说明”模板。

**判断要点 / 验证方式**：检查文档类型、模板标识和必填章节，确认内容与读者任务匹配。

### AURA-BASE-DOC-016：文档引用必须使用稳定标识

**必要性**：必须

跨文档引用应使用文档编号、规则编号、接口编号或稳定路径；不得只引用易变的页码、标题片段或本地绝对路径。

**为什么需要**：标题和页面位置会变化，稳定标识才能在文档调整后继续定位内容。

**正确写法**：引用 `BASE-03`、`接口-DEVICE-001` 或 `01-设备审核详细设计.md`。

**错误写法**：写“见上面的第三段”或引用 `C:\Users\...\桌面\说明.docx`。

**判断要点 / 验证方式**：点击或搜索引用标识，确认能够在当前项目中唯一定位目标内容。

## 内容完整性与维护

### AURA-BASE-DOC-017：技术文档必须说明适用范围与必要边界

**必要性**：必须

技术设计和使用说明必须让读者判断其适用模块、场景及必要前置条件；只有遗漏边界会导致误用时，才说明不负责的内容或指向其他文档。不要求每份短文档机械列出“不包含”清单。

**为什么需要**：读者需要判断文档何时适用，避免把其他模块或专项能力的做法误套到当前场景，同时减少无意义的固定栏目。

**正确写法**：接口文档说明适用于设备审核模块，并注明认证、通用错误码和异步消息分别引用基础规范。

**错误写法**：只列出实现步骤，不说明适用模块、版本或必要依赖；或者在简单说明里堆砌与使用无关的排除项。

**判断要点 / 验证方式**：由未参与编写的开发者判断该文档是否适用于当前任务，确认不会产生歧义。

### AURA-BASE-DOC-018：文档示例必须能够对应当前实现

**必要性**：必须

示例中的目录、类名、接口、配置键、请求响应和命令必须与当前代码和规范一致；不能用无法运行或已废弃的示例充当规范说明。

**为什么需要**：开发者通常直接复制示例，过期示例会把错误用法扩散到新代码。

**正确写法**：接口示例使用当前路径、字段和状态码，并通过最小联调场景验证请求和响应。

**错误写法**：文档仍使用旧路径和旧字段，只在正文中口头说明“实际以代码为准”。

**判断要点 / 验证方式**：按示例从零执行或编译，核对关键输入、输出、配置和实际结果。

### AURA-BASE-DOC-019：变更必须同步更新受影响的示例与文档入口

**必要性**：必须

代码、接口、配置、数据结构、目录或运行方式发生变化时，必须同步更新直接受影响的示例、文档导航和入口链接；主文档内容的同步由 `AURA-BASE-DOC-006` 约束。无法同步时，不得把旧示例或失效入口继续标记为当前用法。

**为什么需要**：文档滞后会让项目使用方式与实际行为分离，增加联调和维护成本。

**正确写法**：新增异步审核状态后，按 `AURA-BASE-DOC-006` 更新主文档，并同步更新前端调用示例和项目总入口链接。

**错误写法**：只更新主文档，仍保留旧的同步调用示例和指向失效文档的导航链接。

**判断要点 / 验证方式**：从变更清单反查示例和导航入口，确认链接仍可达，示例仍符合当前行为。

### AURA-BASE-DOC-020：临时资料必须与正式资料隔离

**必要性**：必须

调研记录、草稿、会议纪要、迁移记录和试验输出必须放入明确的临时或过程目录，不得与正式规范、正式设计和当前使用说明混放。

**为什么需要**：过程资料和正式资料的有效性不同，混放会让使用者误把未确认内容当成当前规则。

**正确写法**：使用 `docs/过程记录/` 保存调研和草稿，正式文档目录只保留当前生效内容。

**错误写法**：把多个“最终版”“待确认”“试验结果”文件直接放在正式文档根目录。

**判断要点 / 验证方式**：检查正式目录是否存在草稿、截图、临时导出和重复版本文件。

## 模块级正反例

### 正例：总入口与模块文档分层

```text
docs/
├─ README.md                 # 项目总入口
├─ 架构总览.md                # 项目级架构
├─ 接口规范/                  # 项目级接口约定
├─ 过程记录/                  # 草稿、调研和临时记录
└─ modules/
   ├─ device/docs/            # 设备模块详细设计、接口和排障
   └─ user/docs/              # 用户模块详细设计、接口和排障
```

总入口说明模块关系，模块文档维护模块事实，重复内容通过稳定链接关联。

### 反例：正式内容与过程文件混放

```text
docs/
├─ 最终版设计.md
├─ 最终版设计2.md
├─ 设备接口旧版.md
├─ 会议纪要-待确认.md
├─ 截图.png
└─ 用户模块说明.md
```

该结构无法判断当前有效版本、模块归属和正式程度，也不利于自动识别和维护。

## 项目文档自检

- 是否存在唯一项目总入口并能找到模块文档；
- 模块文档是否归属对应模块目录；
- 同一事实是否只有一个维护源；
- 文件名、编号和引用是否稳定且可检索；
- 是否使用了与文档类型匹配的模板；
- 适用范围、必要边界、示例和前置条件是否足以支持使用；
- 代码、接口、配置变化是否同步更新文档和示例；
- 草稿、调研和临时输出是否与正式资料隔离。

## 典型开发场景示例

### 项目级与模块级文档管理

**适用任务**：工程结构、文档管理、交付维护  
**关联规则**：AURA-BASE-DOC-001、AURA-BASE-DOC-002、AURA-BASE-DOC-003、AURA-BASE-DOC-004、AURA-BASE-DOC-005、AURA-BASE-DOC-006、AURA-BASE-DOC-007、AURA-BASE-DOC-008  
**示例级别**：完整示例

#### 场景目标

将项目级、模块级和历史资料分开管理，保证每类文档只有稳定入口和唯一主文档。

#### 输入条件

- 项目包含多个业务或技术模块；
- 文档涉及架构、接口、配置、部署和模块使用说明；
- 文档需要随代码进入版本管理。

#### 推荐目录

```text
project/
├─ README.md
├─ docs/
│  ├─ README.md
│  ├─ 架构说明.md
│  ├─ 快速开始.md
│  └─ 决策记录/
└─ device/
   ├─ src/
   └─ docs/
      ├─ README.md
      └─ 接口说明.md
```

#### 完整正确示例

跨模块架构和部署约束只在根 docs 维护；设备模块接口和配置说明只在设备模块 docs 维护；其他位置通过相对链接引用，不复制全文。

#### 错误示例与问题说明

```text
README.md
接口说明.md
device接口说明.md
docs-old/
临时部署说明.md
```

问题：没有稳定文档分类和唯一主文档，无法判断哪些内容有效，也无法保证代码变更时文档同步。

#### 验证步骤与预期结果

1. 从根 README 定位根 docs；
2. 从根 docs 定位项目级文档和模块；
3. 从模块 docs 定位模块文档；
4. 扫描不稳定名称、重复主题、绝对路径和失效链接；
5. 预期每个主题只有一份主文档。

#### 人工确认点

- 文档影响范围是否判断正确；
- 是否存在复制全文的副本；
- 代码变更是否同步更新对应文档；
- 历史和过程资料是否没有进入当前使用入口。

## 项目文档正反例

### 正确示例

```text
项目根 README.md
  → docs/README.md
  → docs/架构说明.md
  → device-service/docs/README.md
  → device-service/docs/接口说明.md
```

### 错误示例

```text
项目根目录/
├─ 项目说明-最终版.md
├─ 接口说明.md
├─ device接口说明.md
├─ src/device/README.md
├─ 临时部署说明.md
└─ docs-old/
```

错误示例的问题是总入口不唯一、模块文档没有稳定归属、正式文档与临时材料混在一起，无法判断哪份内容有效。
