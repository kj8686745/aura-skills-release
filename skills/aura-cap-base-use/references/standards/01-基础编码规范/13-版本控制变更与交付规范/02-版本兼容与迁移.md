**规范对象**：使用 AURA 开展业务应用、服务、工具和平台工程开发的团队和开发人员

**规范目标**：明确公开行为、数据、配置和依赖变更的兼容及迁移方式。

**跨规范边界**：接口契约细节遵循 `BASE-05`，数据迁移细节遵循 `BASE-08`；专项能力的版本与接入条件以对应能力包为准。

## 一、版本、兼容与迁移

### AURA-BASE-VC-004：公开行为变更必须明确兼容策略

**必要性**：必须

接口、事件、公共组件、配置和文件格式的行为变更必须结合现有消费者明确兼容、增加版本、分阶段迁移或有序废弃的策略；不得在未识别消费者和协商切换条件时直接改变既有含义。

**为什么需要**：调用方可能与提供方不同步发布，隐式改变行为会造成难以定位的运行故障。

**正确写法**：为已发布响应增加可选字段，先验证旧调用方能忽略该字段；确需改变既有字段语义时提供新版本或明确同步切换条件与过渡范围。

**错误写法**：把原来的 `status=1` 直接改成另一种含义，要求所有调用方“自行适配”。

**判断要点 / 验证方式**：按实际存在的旧调用方、配置和历史数据验证变更；全新且无旧消费者的契约不虚构兼容场景。

### AURA-BASE-VC-005：数据和配置迁移必须支持分阶段执行

**必要性**：必须

数据库字段、索引、配置键和文件格式变更必须依据历史数据、版本并存时间和消费者切换顺序设计可执行的迁移路径。存在旧版并行或历史数据时，优先按新增、兼容读写、数据迁移、切换和清理分阶段执行；局部且已证明不影响旧消费者的变更可一次完成。清理旧结构前必须确认旧读写路径和恢复需求已结束。

**为什么需要**：分阶段迁移可以降低版本不同步和回退时的数据损失风险。

**正确写法**：新增 `reviewed_at` 字段后让新代码兼容旧记录，分批回填并校验；旧版实例退出、读取切换完成且恢复窗口结束后再清理旧字段。

**错误写法**：发布时直接重命名生产字段并删除旧配置，未验证历史数据和旧版本代码。

**判断要点 / 验证方式**：对适用的历史数据、重复执行和中途停止场景核对记录数量、关键值与兼容读取；不能安全反向迁移时说明前向修复或数据恢复方式。

### AURA-BASE-VC-006：依赖升级必须说明版本和行为影响

**必要性**：必须

第三方库、运行时、基础组件和能力包版本变更必须在现有变更材料中记录旧版与新版、受影响的行为、适用的兼容验证及失败时的恢复或缓解方式，不得只修改版本号；无需为单次升级另建固定表单。

**为什么需要**：依赖升级可能改变序列化、线程、默认配置或安全行为，即使业务代码没有变化也会产生风险。

**正确写法**：升级 JSON 库时记录解析差异、受影响 DTO、回归范围，以及失败时可恢复的已验证版本或前向修复措施。

**错误写法**：批量刷新依赖到最新版本，只验证项目能够编译。

**判断要点 / 验证方式**：核对锁定文件、变更日志、关键行为测试和运行时依赖树，确认不存在未解释的间接升级。

## 二、典型使用示例：新增字段与依赖升级的分阶段迁移

**场景目标**：为审核记录增加 `reviewedAt` 字段并升级 JSON 依赖时，旧版本实例、历史数据和旧调用方在过渡窗口内仍可工作，升级行为和恢复方式可解释。

**正确迁移链**：

```text
记录旧/新依赖版本与行为差异
  → 增加可空字段并兼容读取旧记录
  → 新旧代码并存期间双读/双写或按批回填
  → 验证历史数据、旧调用方和序列化行为
  → 切换新写入并观察消费者
  → 恢复窗口结束后再清理旧字段或旧配置
```

如果数据不能安全反向迁移，交付说明必须采用前向修复、补偿或受控数据恢复，不把重新部署旧代码当成恢复保证。依赖升级须记录锁定文件、运行时依赖树、受影响 DTO 和失败缓解方式，不以“能够编译”代替行为验证。

**错误迁移链**：直接重命名字段并删除旧配置；批量刷新到未锁定的最新依赖；只运行编译，不验证历史数据、旧消费者和序列化差异；发布失败只说回滚版本。

**验证步骤与预期结果**：

1. 在新旧实例并存、历史数据和重复执行条件下执行读写，预期数据数量、关键值和消费者结果一致。
2. 验证依赖升级前后的空值、日期、枚举和错误解析行为，预期差异已被记录和处理。
3. 中途停止迁移，预期能按记录的批次继续或按适用恢复路径处理，不产生未说明的半迁移状态。
