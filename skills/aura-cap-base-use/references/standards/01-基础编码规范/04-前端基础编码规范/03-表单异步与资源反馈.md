## 一、异步提交

### AURA-BASE-FE-009：异步提交必须区分受理与完成

**必要性**：必须

异步提交必须区分请求中、已受理、执行中和最终完成等适用状态，并处理取消、失败、部分成功及恢复入口。不得将提交接口返回的任务编号或受理响应直接解释为业务成功；同一写操作的前端重复触发控制另按 `AURA-BASE-FE-013` 执行。

**为什么需要**：异步任务的受理和执行结果可能相隔较久，混为一谈会让用户误以为操作已经完成。

**正确写法**：

```ts
// 状态值以当前模块接口契约为准；页面状态是前端展示状态，不直接复用接口枚举。
type ImportTaskStatus = 'ACCEPTED' | 'RUNNING' | 'SUCCEEDED' | 'PARTIAL' | 'FAILED' | 'CANCELED' | 'PENDING_CONFIRMATION'
type ImportUiState = 'idle' | 'submitting' | 'submit-rejected' | 'submit-unknown' | 'accepted' | 'running' | 'partial' | 'completed' | 'task-failed' | 'cancelled' | 'needs-confirmation'
// 这是业务请求封装的示例结果类型，不是 AURA 框架提供的类型。
type ImportSubmitResult = { kind: 'accepted'; taskId: string } | { kind: 'rejected' }

const taskStateByStatus: Record<ImportTaskStatus, ImportUiState> = {
  ACCEPTED: 'accepted',
  RUNNING: 'running',
  SUCCEEDED: 'completed',
  PARTIAL: 'partial',
  FAILED: 'task-failed',
  CANCELED: 'cancelled',
  PENDING_CONFIRMATION: 'needs-confirmation',
}

const taskId = ref<string | null>(null)
const submitState = ref<ImportUiState>('idle')
const statusError = ref('')

async function submitImport(fileId: string) {
  if (['submitting', 'submit-unknown', 'accepted', 'running', 'needs-confirmation'].includes(submitState.value)) return
  taskId.value = null
  statusError.value = ''
  submitState.value = 'submitting'
  try {
    // 请求封装仅把服务端明确拒绝的响应转成 rejected；超时、断连等结果未知的情况抛错。
    const result: ImportSubmitResult = await importApi.submit({ fileId })
    if (result.kind === 'rejected') {
      submitState.value = 'submit-rejected'
      statusError.value = '提交请求被拒绝，请检查输入或权限'
      return
    }
    taskId.value = result.taskId
    submitState.value = 'accepted'
  } catch {
    submitState.value = 'submit-unknown' // 未拿到受理结果，先按模块契约回查，不直接再次提交
    statusError.value = '提交结果尚未确认，请先核对任务记录再决定是否重试'
  }
}

async function refreshTaskStatus() {
  if (!taskId.value) return
  try {
    const task = await importApi.queryTask(taskId.value)
    const nextState = taskStateByStatus[task.status as ImportTaskStatus]
    if (!nextState) {
      statusError.value = '任务状态暂无法识别，请核对接口契约'
      return // 未知状态不覆盖上次已确认状态，也不显示为成功
    }
    submitState.value = nextState
    statusError.value = ''
  } catch {
    statusError.value = '任务状态暂不可用，请稍后重试'
    // 查询失败不等于任务失败，保留 taskId 和上次已确认状态
  }
}
```

提交成功只展示已受理；通过查询或订阅真实任务结果后，才展示完成、失败、取消或部分成功。示例中的 `ImportSubmitResult` 由业务请求封装按该模块接口契约产生：服务端明确拒绝才返回 `rejected`，未能确认是否受理的超时、断连等结果进入 `submit-unknown`；不得仅凭请求库抛出异常就判定为明确拒绝。模块未支持取消、部分成功或待确认状态时，从示例的类型和映射中删除相应分支；新增状态时同步扩展映射，未知值保留上次已确认状态并提示核对契约。请求超时或连接中断可能发生在服务端受理之后，未收到响应时应先按模块契约通过业务幂等键、任务列表或其他已登记入口核对；无法确认时保留“提交结果未知”并提示人工处理，不能自动再次提交。部分成功应提供失败项处理入口；需要跨页面恢复时，按项目约定保存任务标识，不能只依赖组件内存状态。

**错误写法**：接口一返回任务编号就提示“导入成功”，或任务失败后把表单状态重置成成功。

**判断要点 / 验证方式**：检查接口状态到页面状态的映射、已受理与最终完成的分别表达，以及取消、失败和恢复入口；用受理后失败、提交响应丢失、部分成功、页面刷新后恢复等结果验证状态转换。

**例外**：同步返回最终业务结果的操作不需要额外的任务受理状态，但仍须按结果显示成功或失败。

## 二、常用交互与资源边界

### AURA-BASE-FE-013：提交操作必须防止重复触发

**必要性**：必须

创建、更新、删除、导入和发送等会产生副作用的操作，必须阻止同一动作在请求未完成时被前端重复触发；异步任务已受理后，应按任务状态决定何时允许再次提交。前端防重不得替代后端对重复请求的处理，受理与最终完成的区分按 `AURA-BASE-FE-009` 执行。

**为什么需要**：用户连续点击、网络延迟和重复提交会产生重复数据或重复外部副作用。

**正确写法**：同一动作先检查 `submitting`，提交中阻止再次触发；明确拒绝、结果未知和已受理或已完成分别更新交互状态。结果未知时沿用原请求标识，按 `AURA-BASE-API-007` 已约定的查询或同键幂等方式确认，不生成新标识盲目重试；异步任务已受理时保留任务标识，按业务契约决定能否再次提交；后端按公开契约处理重复请求。

**错误写法**：点击事件直接调用 API，不保存请求状态，用户可以连续触发多个相同请求。

**判断要点 / 验证方式**：检查请求中、明确拒绝、结果未知、任务已受理和组件卸载时能否重复触发及恢复交互；用快速连续点击、慢网络、响应丢失和超时场景验证前端不会并发发起同一动作，也不会在未知结果下换标识重建。业务副作用是否只发生一次仍须通过后端契约验证；没有查询或同键幂等保证时，须给出人工确认入口，不能通过开放重试按钮解除未知状态。

### AURA-BASE-FE-014：并发请求必须处理竞态和过期响应

**必要性**：必须

同一页面或查询条件存在多个并发请求时，必须通过取消、请求序号或条件校验，避免较早请求的响应覆盖较新请求的状态。

**为什么需要**：搜索、筛选和快速切换页面时，响应返回顺序可能与发起顺序不同。

**正确写法**：为每次查询保存请求序号，只提交当前查询序号的结果；切换条件时取消不再需要的请求。

**错误写法**：每次输入都直接请求，任何响应回来都覆盖列表和分页状态。

**判断要点 / 验证方式**：检查请求取消、结果归属和加载状态是否绑定当前条件；人为延迟旧请求并快速发起新请求，确认页面最终显示最新条件的结果。

### AURA-BASE-FE-015：列表和大数据展示必须有分页或虚拟化边界

**必要性**：必须

列表、树、日志和搜索结果必须根据数据规模使用分页、分段加载、虚拟滚动或异步导出，不得默认把不可预测的全部数据加载到浏览器内存。

**为什么需要**：大数据量会导致浏览器卡顿、渲染超时和请求响应过大。

**正确写法**：列表使用服务端分页，导出转为异步任务，长列表使用虚拟滚动。

**错误写法**：页面初始化时请求全表并一次性渲染所有行。

**判断要点 / 验证方式**：检查页大小上限、加载方式、空结果和导出入口；使用大数据量、慢网络和连续翻页，确认内存、渲染时间和请求大小受控。

### AURA-BASE-FE-016：页面必须提供结果反馈与恢复入口

**必要性**：必须

涉及请求或异步任务的页面必须为成功无数据、业务失败、网络失败、无权限和登录失效等适用结果提供可理解的展示与恢复入口，不得用空白区域或统一“加载失败”替代所有结果。状态是否对应真实请求和任务生命周期按 `AURA-BASE-FE-005` 判断。

**为什么需要**：同样没有内容，可能是正常空结果、请求失败或权限不足；区分原因才能给出正确的下一步操作。

**正确写法**：空数据提供创建或调整筛选入口；只读查询的网络失败提供重试入口，写操作结果未知则先按接口契约提供查询、同键重试或人工确认入口，不换标识直接重建；无权限显示权限提示，登录失效进入统一会话处理。

**错误写法**：请求失败时直接把列表清空，让用户误以为系统没有数据。

**判断要点 / 验证方式**：检查空数据、业务失败、网络失败、403 和会话失效的展示与恢复入口是否各有对应处理；用空数组、业务错误、网络超时、403 和会话失效响应逐一验证页面行为。

### AURA-BASE-FE-017：文件上传下载必须受控并反馈进度

**必要性**：必须

文件操作必须限制类型、大小、数量和并发，使用统一请求或文件服务封装；上传、下载、取消、失败和完成状态必须可见，文件名和地址不得直接信任用户输入。

**为什么需要**：文件操作同时涉及资源消耗、权限和用户体验，直接使用浏览器默认行为难以控制。

**正确写法**：上传前校验大小和类型，上传中显示进度，下载地址由后端授权生成并在完成后释放临时资源。

**错误写法**：页面直接拼接文件 URL，把用户输入作为下载路径，失败后没有重试或取消入口。

**判断要点 / 验证方式**：检查文件校验、权限、进度、取消、错误和临时地址处理；使用超大、非法类型、重复、断网和过期地址，确认前端阻止或正确反馈。

### AURA-BASE-FE-018：时间、金额和枚举展示必须使用公共转换

**必要性**：必须

时间、金额、单位、状态和枚举文本必须通过统一格式化工具或组件展示，页面不得自行加减时区、拼接金额或根据显示文本判断业务。

**为什么需要**：局部格式化会造成同一字段在不同页面显示和判断不一致。

**正确写法**：使用公共时间组件显示 `2026-09-22 10:30:00`，使用状态代码映射展示文本。

**错误写法**：页面手工给时间加 8 小时，或通过“处理中”文本决定是否显示操作按钮。

**判断要点 / 验证方式**：检查格式化入口、状态代码使用和空值展示；切换语言、空值、未知状态和不同浏览器环境，确认展示和业务判断稳定。

## 三、典型开发场景示例

### 同步创建表单与防重复提交

**适用任务**：前端页面、前端组件、前端状态、前端请求  
**关联规则**：FE-003、FE-004、FE-005、FE-010、FE-012、FE-013  
**跨分类规则**：FE-003、FE-004、FE-005 见[工程组织与页面状态](./01-工程组织与页面状态.md)；FE-010、FE-012 见[请求路由权限与数据适配](./02-请求路由权限与数据适配.md)。  
**示例级别**：完整示例

#### 场景目标

完成“创建设备分组”的表单提交。页面必须清晰表达填写、校验、提交中、明确拒绝、结果未知和创建成功；请求未完成时不能重复触发，结果未知时不能用新请求标识盲目再建。

#### 输入条件

- 页面需要收集分组名称与说明；
- 本示例的业务接口以 `requestId` 作为幂等键：相同标识与相同请求内容重复提交返回同一创建结果，标识相同而内容不同时明确拒绝；这是示例业务契约，不是 AURA 框架固定字段；
- 后端接口同步完成创建并返回新分组标识；项目请求封装只把已收到、可确认未创建资源的拒绝结果标记为 `confirmed-rejection`，超时、断连和无法确认副作用的错误不使用该标记；
- 本地校验失败不发起请求；服务端业务校验失败需要保留已填写内容；
- 用户可以连续点击提交按钮，或在网络缓慢时重复操作。

#### 完整正确示例

示例沿用项目已有的 `@/services/request`，其 `post<T>` 在业务成功后返回解包数据、失败时抛出错误；项目请求封装须按上面的契约区分明确拒绝与结果未知。`requestId` 与错误标记均为本示例业务项目约定，实际落地时以模块接口文档和项目请求封装为准，不可照搬为 AURA 公共 API。

```ts
// views/device-group/api/device-group-api.ts
import { request } from '@/services/request'
import type { DeviceGroupForm, DeviceGroupCreated } from '../model/device-group-model'

type CreateDeviceGroupResponse = { id: string; created_at: string }

// 仅识别项目请求封装已明确归类的拒绝；其余异常均不能证明服务端未创建资源。
export function isConfirmedCreateRejection(error: unknown): boolean {
  return typeof error === 'object' && error !== null
    && 'kind' in error && error.kind === 'confirmed-rejection'
}

export async function createDeviceGroup(form: DeviceGroupForm, requestId: string): Promise<DeviceGroupCreated> {
  const response = await request.post<CreateDeviceGroupResponse>('/device-groups', {
    name: form.name.trim(),
    description: form.description.trim() || undefined,
    requestId,
  })
  return { id: response.id, createdAt: response.created_at }
}
```

```ts
// views/device-group/composables/use-device-group-submit.ts
import { ref } from 'vue'
import { createDeviceGroup, isConfirmedCreateRejection } from '../api/device-group-api'
import type { DeviceGroupForm } from '../model/device-group-model'

export function useDeviceGroupSubmit() {
  const submitting = ref(false)
  const submitError = ref('')
  const resultUnknown = ref(false)
  let pendingRequestId: string | null = null
  let pendingForm: DeviceGroupForm | null = null

  async function submit(form: DeviceGroupForm) {
    if (submitting.value) return
    if (!pendingRequestId || !pendingForm) {
      pendingRequestId = crypto.randomUUID()
      pendingForm = { ...form }
    }
    const requestId = pendingRequestId
    const requestForm = pendingForm

    submitting.value = true
    submitError.value = ''
    try {
      // 结果未知后的再次提交仍使用原标识和原请求内容，不生成第二次创建动作。
      const created = await createDeviceGroup(requestForm, requestId)
      pendingRequestId = null
      pendingForm = null
      resultUnknown.value = false
      return created
    } catch (error) {
      if (isConfirmedCreateRejection(error)) {
        pendingRequestId = null
        pendingForm = null
        resultUnknown.value = false
        submitError.value = '创建请求被拒绝，请检查填写内容或权限。'
        return undefined
      }
      resultUnknown.value = true
      submitError.value = '创建结果尚未确认；仅可使用原请求标识和原内容重试，不要发起新的创建请求。'
      return undefined
    } finally {
      submitting.value = false
    }
  }

  return { submitting, submitError, resultUnknown, submit }
}
```

```vue
<!-- views/device-group/components/DeviceGroupForm.vue -->
<script setup lang="ts">
import { computed, ref } from 'vue'
import type { DeviceGroupForm } from '../model/device-group-model'

const props = defineProps<{ modelValue: DeviceGroupForm; submitting: boolean; resultUnknown: boolean }>()
const emit = defineEmits<{
  'update:modelValue': [value: DeviceGroupForm]
  submit: []
}>()
const validationError = ref('')
const name = computed({
  get: () => props.modelValue.name,
  set: (value: string) => emit('update:modelValue', { ...props.modelValue, name: value }),
})
const description = computed({
  get: () => props.modelValue.description,
  set: (value: string) => emit('update:modelValue', { ...props.modelValue, description: value }),
})

function submitForm() {
  if (props.submitting) return
  if (props.resultUnknown) {
    emit('submit') // 沿用同一请求标识和原内容，由服务端幂等契约返回同一结果
    return
  }
  if (!name.value.trim()) {
    validationError.value = '请填写分组名称'
    return
  }
  validationError.value = ''
  emit('submit')
}
</script>

<template>
  <form @submit.prevent="submitForm">
    <label for="group-name">分组名称</label>
    <input id="group-name" v-model="name" :disabled="submitting || resultUnknown" />
    <label for="group-description">说明</label>
    <textarea id="group-description" v-model="description" :disabled="submitting || resultUnknown" />
    <p v-if="validationError" role="alert">{{ validationError }}</p>
    <button type="submit" :disabled="submitting">{{ submitting ? '提交中' : resultUnknown ? '按原标识重试' : '创建' }}</button>
  </form>
</template>

import { ref } from 'vue'

领域 API 负责请求模型和响应模型转换；提交组合逻辑只有一个入口；提交中状态阻断并发请求。明确拒绝后保留输入并允许修正；结果未知时保留原请求标识与内容，只在服务端已保证同键幂等时允许按原请求核对；获得稳定创建结果后才进入下一步。示例只覆盖当前页面生命周期；刷新或跨页面恢复必须按该模块接口文档提供的请求标识查询或其他确认入口处理，不能刷新后用新标识盲目重建。

}
```

问题：没有提交中状态，重复点击会形成重复请求；直接把页面对象发给接口；请求失败时异常冒泡且用户输入处理不明确；仅凭 HTTP 请求返回就清空表单，未核对业务结果。

#### 验证步骤与预期结果

1. 表单必填项为空，预期组件显示校验提示且不发送请求。
2. 连续点击提交按钮，预期仅发起一次请求，直到当前请求结束。
3. 服务端返回业务校验失败，预期展示可理解错误并保留填写内容。
4. 网络失败或超时，预期展示“结果未知”，保留原请求标识与内容；在本示例已约定的同键幂等前提下，再次操作只核对原请求结果，不产生第二个资源。若实际接口没有该保证，应禁用重试并转入已约定的查询或人工确认入口。
5. 创建成功，预期仅在获得稳定创建结果后跳转；不以 Toast 出现作为成功依据。

#### 人工确认点

- 哪些校验属于页面即时校验，哪些必须由后端作为最终业务裁决；
- 创建幂等键的传递位置、同键重复结果、不同内容冲突结果，以及刷新或跨页面后如何按原标识查询或确认；
- 成功后的跳转、刷新或返回列表是否符合业务流程；
- 服务端错误码与用户提示之间的转换是否完整且不暴露内部信息。
