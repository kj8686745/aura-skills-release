# 基础通用支撑能力包使用示例

## 1. 场景

以“设备配置查询与修改”为例，展示一个业务模块如何组合基础公共能力：

- 查询接口返回统一 `R<DeviceView>`；
- 修改接口声明业务权限；
- 当前操作人从安全上下文获取；
- 实体复用 `BaseEntity`；
- 修改记录操作日志和数据审计；
- 重复提交需由项目中已验证的服务端幂等实现保护；
- 设备摘要缓存使用带业务域和租户边界的 key。

这个示例采用统一的 `R<T>` 契约；公开 OpenAPI 仅通过 DTO、认证和数据范围控制内容。示例先确定接口契约，再处理权限、租户、数据和缓存边界。代码不依赖未经项目验证的幂等注解。

## 1.1 从需求到交付

| 开发阶段 | 本示例的产物 | 使用的基础能力 |
| --- | --- | --- |
| 需求识别 | 查询、修改设备配置 | 统一响应、权限、审计、缓存；重复提交另选已验证的服务端实现 |
| 详细设计 | 接口、数据、权限和缓存边界 | 接口契约、租户上下文 |
| 编码实现 | Controller、Service、Entity、Mapper | `R<T>`、安全上下文、Redis、公共实体 |
| 联调准备 | 请求、响应、权限编码和错误场景 | OpenAPI、统一响应 |
| 研发自测 | 未登录、无权限、重复提交、跨租户和缓存失效 | 安全、已验证的幂等实现、租户、缓存 |
| 交付审查 | 能力入口、边界处理和正反例 | 基础编码规范 + 本能力包 |

## 2. Controller

```java
@RestController
@RequestMapping("/device/config")
@RequiredArgsConstructor
public class DeviceConfigController {

    private final DeviceConfigService service;

    @GetMapping("/{id}")
    public R<DeviceView> detail(@PathVariable Long id) {
        return R.ok(service.detail(id));
    }

    @PutMapping("/{id}")
    @HasPermission("device:config:update")
    @SysLog("修改设备配置")
    @Audit(name = "设备配置更新", spel = "@deviceConfigService.auditSnapshot(#id)")
    public R<Void> update(@PathVariable Long id, @Valid @RequestBody DeviceUpdateCommand command) {
        service.update(id, command);
        return R.ok();
    }
}
```

## 3. Service

```java
@Service
@RequiredArgsConstructor
public class DeviceConfigService {

    private final DeviceConfigMapper mapper;

    @Transactional(readOnly = true)
    public DeviceView detail(Long id) {
        Long tenantId = requireTenantId();
        String key = "aura:device:tenant:" + tenantId + ":detail:" + id;
        DeviceView cached = RedisUtils.get(key);
        if (cached != null) {
            return cached;
        }
        DeviceView value = mapper.selectView(id, tenantId);
        if (value != null) {
            RedisUtils.set(key, value, 300);
        }
        return value;
    }

    @Transactional
    public void update(Long id, DeviceUpdateCommand command) {
        Long tenantId = requireTenantId();
        var currentUser = SecurityUtils.getUser();
        String operator = currentUser.getUsername();
        int affected = mapper.updateConfig(id, tenantId, command, operator);
        if (affected != 1) {
            throw new CustomException("设备配置不存在或无权修改");
        }
        String key = "aura:device:tenant:" + tenantId + ":detail:" + id;
        TransactionSynchronizationManager.registerSynchronization(new TransactionSynchronization() {
            @Override
            public void afterCommit() {
                RedisUtils.delete(key);
            }
        });
    }

    public DeviceView auditSnapshot(Long id) {
        return mapper.selectView(id, requireTenantId());
    }

    private Long requireTenantId() {
        var currentUser = SecurityUtils.getUser();
        Long tenantId = TenantContextHolder.getTenantId();
        if (currentUser == null || tenantId == null || !tenantId.equals(currentUser.getTenantId())) {
            throw new CustomException("身份与租户上下文不匹配");
        }
        return tenantId;
    }
}
```

## 4. Entity 与 Mapper

```java
public class DeviceConfig extends BaseEntity {
    private Long tenantId;
    private String deviceCode;
    private String configValue;
}

public interface DeviceConfigMapper {
    DeviceView selectView(Long id, Long tenantId);
    int updateConfig(Long id, Long tenantId, DeviceUpdateCommand command, String operator);
}
```

Mapper 的查询和更新 SQL 必须同时约束 `id`、`tenant_id`、逻辑删除状态及该业务需要的数据范围；自定义更新 SQL 还须显式写入修改人和修改时间。这里的 Mapper 方法是业务模块契约，需在项目中提供 SQL 实现。缓存只在事务提交后失效，避免回滚或提交前的并发查询写回旧值。幂等保护须由项目中实际验证过的实现补齐，不能仅给方法加注解。

## 5. 适用边界

本例只覆盖 HTTP 业务接口的基础支撑能力。文件、消息、实时推送和动态数据源按各自能力包接入；公开 OpenAPI 使用专用认证，但沿用统一响应与错误契约。

## 6. 场景二：只读列表查询

### 6.1 能力选择

只读列表通常选择：统一响应、查询参数校验、租户数据边界、接口描述；如果数据量较大，再增加分页和缓存策略。

### 6.2 推荐实现

```java
@GetMapping
@HasPermission("device:config:list")
public R<PageResult<DeviceView>> page(DeviceQuery query) {
    return R.ok(deviceConfigService.page(query));
}
```

Service 层负责查询条件组合和租户边界，Controller 不直接操作 Mapper、Redis 或远程服务。

### 6.3 反例

```java
@GetMapping
public List<DeviceConfig> page(DeviceQuery query) {
    return deviceConfigMapper.selectList(query.toWrapper());
}
```

该写法缺少统一响应、权限声明，并可能直接暴露持久化实体。

### 6.4 自测重点

- 无权限用户不能查询；
- 查询条件不会绕过租户边界；
- 分页参数和空结果符合接口契约；
- 返回模型不泄露内部字段。

## 7. 场景三：带租户的数据维护

### 7.1 能力选择

数据维护通常组合：统一响应、权限、当前用户、租户上下文、审计和操作日志；需要防重复提交时再使用已验证的服务端幂等实现。

### 7.2 开发顺序

1. 先定义新增、修改、删除的权限编码；
2. 再定义数据所属租户和唯一业务键；
3. 使用安全上下文获取当前操作人；
4. 对修改和删除增加审计，对可重复提交的操作使用已验证的服务端幂等实现；
5. 成功后清理相关缓存，失败时保持原数据和上下文完整。

### 7.3 反例

```java
@PutMapping("/{id}")
public void update(@PathVariable Long id, @RequestBody Map<String, Object> body) {
    mapper.updateById(body);
}
```

该写法没有权限、租户、当前用户、审计和响应契约，且使用无约束的 Map 作为业务输入。

### 7.4 自测重点

- 跨租户 ID 不能修改；
- 重复提交不会产生重复数据；
- 审计能记录修改前后的关键字段；
- 异常时租户上下文和幂等键不会污染后续请求。

## 8. 场景四：跨服务调用

### 8.1 能力选择

跨服务调用组合：API 契约、Feign、统一响应、认证上下文、超时和降级、OpenAPI 描述。

### 8.2 API 模块

```java
@FeignClient(contextId = "deviceOwnerService", value = ServiceNameConstants.OWNER_SERVICE)
public interface DeviceOwnerService {

    @GetMapping("/owner/{id}")
    R<OwnerView> getOwner(@PathVariable("id") Long id);
}
```

调用方只依赖 API 模块，不在业务代码中拼接 URL，也不复制远程服务的 DTO。

### 8.3 业务服务调用

```java
OwnerView owner = RetOps.of(deviceOwnerService.getOwner(ownerId))
        .assertSuccess(result -> new RemoteCallException(result.getMsg()))
        .getData()
        .orElseThrow(() -> new RemoteCallException("负责人不存在"));
```

### 8.4 反例

```java
String url = ownerUrl + "/owner/" + ownerId;
String body = restTemplate.getForObject(url, String.class);
```

该写法绕过统一契约、认证上下文、超时和降级约定，调用关系也无法由 API 模块统一维护。

### 8.5 自测重点

- 成功响应和业务失败响应都能正确处理；
- 目标服务超时或不可用时有明确降级结果；
- 认证和租户上下文按约定传递；
- API 文档与真实请求、响应保持一致。
