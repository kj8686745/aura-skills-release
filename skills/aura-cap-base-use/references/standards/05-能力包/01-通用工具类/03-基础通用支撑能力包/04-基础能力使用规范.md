## 0. 能力使用总览

基础通用支撑能力包的核心不是记忆公共包名称，而是根据业务问题选择框架已经提供的能力，沿着统一开发路径完成实现。

| 业务问题 | 应使用的框架能力 | 业务开发结果 |
| --- | --- | --- |
| HTTP 接口需要统一成功、失败和数据结构 | 统一响应能力 | 所有 Controller 返回 `R<T>`；公开 OpenAPI 通过 DTO、认证和数据范围控制内容 |
| 需要把请求内容转换为 JSON 或读取 JSON | 统一 JSON 能力 | 使用公共 JSON 工具和统一序列化配置 |
| 需要知道当前是谁在操作 | 身份上下文能力 | 从安全上下文读取当前用户 |
| 需要限制谁可以执行操作 | 权限声明能力 | 在接口或方法声明权限编码 |
| 需要区分不同租户的数据 | 租户上下文能力 | 请求、任务和远程调用携带正确租户边界 |
| 需要缓存热点数据或控制重复访问 | 缓存能力 | 使用带业务域、租户边界和有效期的缓存键 |
| 需要记录谁做了什么 | 操作日志能力 | 使用统一操作日志注解或工具 |
| 需要记录数据修改前后的差异 | 数据审计能力 | 使用统一审计注解和审计对象 |
| 需要处理重复提交 | `@Idempotent` 候选入口或项目已验证的服务端方案 | 先核实拦截是否生效，再按接口契约处理重复请求 |
| 需要调用其他业务服务 | 服务调用能力 | API 模块定义契约，Feign 负责调用 |
| 需要让前后端理解接口 | 接口描述能力 | 使用统一 OpenAPI 描述和响应模型 |

业务开发者应先从这张表定位能力，再阅读对应接入要点和示例，不应从公共包源码反向猜测用法。

## 0.1 能力应用路线

一个使用基础通用支撑能力包的业务功能，按以下顺序推进：

```text
识别业务问题
→ 选择框架能力
→ 确认所需依赖和配置
→ 在 API/Controller/Service 中按能力入口编码
→ 补充权限、租户、日志、审计、幂等等横向能力
→ 依据统一响应和接口规范联调
→ 按基础编码规范完成自测和交付
```

能力不是为了增加注解数量。只有业务问题真实存在时才启用对应能力；启用后必须完成该能力要求的边界处理。

## 0.2 能力卡片

### 统一响应能力

框架提供 `R<T>` 和 `RetOps<T>`。所有 HTTP 接口使用 `R<T>`；使用相同契约的服务间调用可用 `RetOps<T>` 判断结果。公开 OpenAPI 只通过 DTO、认证和数据范围控制内容，不得自定义第二套响应包装类。分页统一使用 `PageResult<T>` 语义，不直接暴露 ORM `Page/IPage`。

常见开发方式：

```java
R<DeviceView> response = deviceClient.getDevice(id);
DeviceView device = RetOps.of(response)
        .assertSuccess(result -> new RemoteCallException(result.getMsg()))
        .getData()
        .orElseThrow(() -> new BusinessException("设备不存在"));
```

### JSON 能力

框架提供统一 JSON 序列化和反序列化工具。只在需要把对象转换为字符串、字节或树模型时使用 `JsonUtils`；Controller 的正常请求和响应交给统一 Web/Jackson 配置处理。

```java
String payload = JsonUtils.toJson(command);
DeviceCommand restored = JsonUtils.parse(payload, DeviceCommand.class);
```

不得为了一个局部转换重新创建 `ObjectMapper`，也不得在同一服务混用多套日期、枚举和空值序列化规则。

### 身份与权限能力

框架提供安全上下文读取、权限声明和内部调用边界。开发顺序是：先判断接口是否需要认证，再为业务操作定义权限编码，最后在服务中从上下文读取当前用户。前端按钮隐藏不能替代后端权限。

### 租户与数据边界能力

框架提供租户上下文和基础实体。开发实体时复用公共审计字段；开发查询、缓存、异步任务和远程调用时，确保租户边界不会丢失或串用。

### 缓存能力

框架提供统一 Redis 工具。开发者需要先确定缓存对象、业务域、租户边界、有效期和失效时机，再编写读写代码；缓存不能成为未定义的数据源。

### 日志、审计与幂等能力

框架提供操作日志、数据审计入口；`@Idempotent` 目前只作为需在目标项目验证拦截效果的候选入口。操作日志回答“谁做了什么”，审计回答“数据改了什么”；重复请求如何处理，须由已生效的服务端方案和接口契约确定。三者解决的问题不同，不能互相替代。

### 服务调用与接口描述能力

框架提供 Feign 和 OpenAPI 的统一基础。服务调用先在 API 模块定义请求、响应和服务契约，再由业务服务实现；接口文档描述真实的业务契约，不暴露内部实现对象。

## 0.3 所选能力的接入结果

本包不要求使用者为接入公共工具另建一套业务模块或交付文件。选用了哪项能力，就核对该项入口在目标项目中的依赖、配置、调用与实际结果；身份、租户、日志、缓存、服务调用等只核对本次涉及的组合。Controller、Service/Mapper、接口文档与研发自测的共同要求按[基础编码规范矩阵](../../../01-基础编码规范/规范矩阵.md)定位，不在此另设最小交付清单。

## 0.4 按能力开展开发

### 0.4.1 统一响应能力的开发路径

1. 先确定接口返回的业务数据类型和公开字段范围；
2. 所有 HTTP Controller 使用 `R<T>`；公开 OpenAPI 通过 DTO、认证和数据范围控制内容；
3. 服务间调用方使用 `RetOps<T>` 处理远程结果；
4. 在接口文档中按统一契约描述 `code`/`msg`/`data`，并按边界补充认证、数据范围和公开字段；
5. 自测成功、业务失败、参数错误和未授权四类结果。

**完成判据**：接口没有自定义第二套响应包装类，前后端能够依据统一 `R<T>` 契约处理成功和失败结果。

### 0.4.2 身份与权限能力的开发路径

1. 判断接口是登录后使用、公开使用还是可信内部调用；
2. 为新增、修改、删除、导入、导出和授权操作定义权限编码；
3. 在方法入口声明权限，在业务逻辑中从安全上下文读取当前用户；
4. 对内部调用配置最小可信边界，不能把内部标识交给客户端决定；
5. 自测无令牌、无权限、有效权限和内部调用四类请求。

**完成判据**：接口权限可以被独立识别和审查，当前操作人不依赖请求参数，内部入口不会被普通外部请求直接调用。

### 0.4.3 租户与数据能力的开发路径

1. 明确业务数据是否属于租户；
2. 实体优先复用 `BaseEntity`；
3. 普通用户请求核对已认证用户的租户归属与上下文租户；查询、写入、缓存和远程调用均保留租户边界；
4. 异步任务或线程池任务执行前建立上下文，结束后清理上下文；
5. 自测跨租户查询、无租户上下文和异步执行三类场景。

**完成判据**：不同租户不能互相读写数据；上下文非空不单独构成授权；异步和远程边界不会丢失或污染租户上下文。

### 0.4.4 缓存能力的开发路径

1. 先判断数据是否适合缓存，以及缓存失效能否接受；
2. 设计包含业务域和必要租户标识的 key；
3. 为缓存设置明确有效期，并定义新增、修改、删除时的失效策略；
4. 使用统一 Redis 工具，不在业务中直接创建新的 RedisTemplate；
5. 自测缓存命中、未命中、过期、更新失效和异常降级。

**完成判据**：缓存不会跨业务或跨租户污染，缓存失效后仍能从真实数据源恢复。

### 0.4.5 日志、审计和幂等能力的开发路径

1. 识别操作日志、数据审计和幂等分别要解决的问题；
2. 对有业务影响的操作补充操作描述；
3. 对需要记录前后差异的数据修改补充审计信息；
4. 对可能重复提交的写操作定义稳定幂等键和有效期，并先确认项目中的幂等切面确实拦截该注解；
5. 自测正常请求、重复请求、异常回滚和敏感字段脱敏。

**完成判据**：能够回答“谁做了什么、数据改了什么、重复请求如何处理”，且日志和审计不泄露凭据。

### 0.4.6 服务调用与接口描述能力的开发路径

1. 先定义服务边界和 API 契约；
2. 在 API 模块放置 DTO、Feign 接口和服务名常量；
3. 使用统一响应体、超时、降级和认证上下文；
4. 为公开接口补充 OpenAPI 描述；
5. 自测成功、超时、服务不可用、无权限和响应结构变化。

**完成判据**：调用方不拼接内部 URL，接口契约可独立复用，服务异常能按约定降级或返回明确错误。

## 0.5 业务需求到能力选择的判断表

| 需求描述 | 可选能力组合（按实际场景） |
| --- | --- |
| 新增一个只读查询接口 | 统一响应 + 接口描述 + 必要权限 |
| 新增一个带租户的数据维护接口 | 统一响应 + 权限 + 当前用户 + 租户 + 审计 |
| 新增一个可能重复提交的创建接口 | 统一响应 + 权限 + 当前用户 + 已验证的服务端重复请求方案 + 按需日志 |
| 增加热点详情查询 | 统一响应 + 租户 + 缓存 + 接口描述 |
| 调用其他业务服务 | API 契约 + Feign + 统一响应 + 超时/降级 |
| 修改敏感业务数据 | 权限 + 当前用户 + 日志 + 审计 + 敏感字段保护 |

上表用于发现可能复用的能力，不是要求每个同类需求都启用全部组件。选择前仍须核对实际业务场景、项目依赖和对应能力的开放状态。

## 1. 依赖接入

### AURA-CAP-BASE-001：选择公共 BOM 或已有聚合依赖

依赖版本的共同要求见 `AURA-BASE-DEP-001`。接入前先查看项目父 POM/BOM 和依赖树：已有服务聚合依赖且包含目标模块时沿用现状；没有时按能力清单选择需要的 `aura-common-*` 模块。聚合 starter 的存在不表示所有业务服务都必须引入。

**正例**：

```xml
<dependency>
    <groupId>net.fxft</groupId>
    <artifactId>aura-common-core</artifactId>
</dependency>
<dependency>
    <groupId>net.fxft</groupId>
    <artifactId>aura-common-security</artifactId>
</dependency>
```

**反例**：

```xml
<dependency>
    <groupId>net.fxft</groupId>
    <artifactId>aura-common-core</artifactId>
    <version>业务模块自行填写的版本</version>
</dependency>
```

**接入核对**：项目实际解析出的公共包版本一致，且目标模块已进入依赖树；版本约束仍按 `AURA-BASE-DEP-001` 判断。

### AURA-CAP-BASE-002：为所选能力确定最小公共模块

**正例**：只需要统一返回体时引入 `aura-common-core`。  
**反例**：只使用 `R<T>` 却引入包含数据库、缓存和 Web 全量启动能力的聚合 starter。  
**接入核对**：确认引入的是目标能力所在模块，并核对传递依赖；共同依赖边界见 `AURA-BASE-DEP-002/007`。

## 2. 统一响应与 JSON

### AURA-CAP-BASE-003：HTTP Controller 使用统一响应体 `R<T>`

本接入要点适用于浏览器、服务间和公开 OpenAPI 的 HTTP 接口；公开接口仍按[接口规范](../../../01-基础编码规范/05-接口规范体系/01-接口规范.md)使用 DTO、公开认证和数据范围，但响应外壳仍为统一 `R<T>`。

**正例**：

```java
@GetMapping("/{id}")
public R<DeviceVO> get(@PathVariable Long id) {
    return R.ok(deviceService.getView(id));
}
```

**反例**：

```java
@GetMapping("/{id}")
public Map<String, Object> get(@PathVariable Long id) {
    return Map.of("success", true, "data", deviceService.getView(id));
}
```

**检查要点**：先识别接口边界，再核对响应外壳；新增接口不得自行定义第三种 `Result`、`Response` 或重复的 code/data/msg 结构。

### AURA-CAP-BASE-004：选择公共 JSON 入口

**正例**：使用 `JsonUtils` 或注入项目统一配置的 `ObjectMapper`。  
**反例**：在业务类中 `new ObjectMapper()`，或混用多个 JSON 库改变日期、枚举和空值规则。  
**接入核对**：确认项目实际使用的 `JsonUtils` 或统一配置的 `ObjectMapper` 与接口序列化行为一致；共同的输出契约见 `AURA-BASE-API-014`。

## 3. 身份、权限与内部调用

### AURA-CAP-BASE-005：通过 `SecurityUtils` 获取当前用户

**正例**：

```java
String username = Optional.ofNullable(SecurityUtils.getUser())
        .map(UserView::getUsername)
        .orElseThrow(UnauthenticatedException::new);
```

**反例**：直接信任请求体中的 `userId` 作为创建人或当前操作人。  
**检查要点**：当前人、角色和会话信息不得由前端参数决定。

### AURA-CAP-BASE-006：使用 `@HasPermission` 声明业务权限

**正例**：

```java
@HasPermission("device:config:update")
@PutMapping("/{id}")
public R<Void> update(@PathVariable Long id, @RequestBody DeviceUpdateCommand command) {
    deviceService.update(id, command);
    return R.ok();
}
```

**反例**：只在前端隐藏按钮，后端接口不声明权限。  
**检查要点**：新增、修改、删除、导入、导出和授权等写操作均有可追踪权限编码。

### AURA-CAP-BASE-007：内部调用标识只用于明确的可信边界

**正例**：内部接口在服务端完成调用方校验后，再使用 `@Inner` 标记明确的内部入口。  
**反例**：把登录、用户修改等外部业务接口整体标成内部接口，或允许客户端自行提交内部标识。  
**检查要点**：开放范围最小化，内部调用不能替代认证和授权设计。

### AURA-CAP-BASE-008：使用公共日志能力时处理认证字段

**正例**：记录请求编号、业务标识和结果，不记录 `Authorization`、token、client secret。  
**反例**：`log.info("request headers: {}", request.getHeader("Authorization"));`  
**接入核对**：使用公共日志注解或工具后，检查异常、调试和远程调用日志的实际输出；禁止泄露凭据的规则以 `AURA-BASE-SEC-008`、`AURA-BASE-OBS-007` 为准。

## 4. 数据、租户与缓存

### AURA-CAP-BASE-009：使用租户上下文与 `TenantBroker`

**正例**：普通请求使用已验证的租户边界；临时切换租户使用 `TenantBroker`，自行设置上下文的任务须在 `finally` 清理。  
**反例**：在线程池任务中设置租户后不清理，导致后续任务复用旧租户。  
**检查要点**：同步、异步和远程调用三类边界均需核对正常、异常和提前结束路径的上下文生命周期。请求可从请求头或参数取得租户，缺省还可能设置默认租户；租户存在且有效，不等于当前登录用户获准访问该租户。普通用户业务必须核对两者归属，再落实到实际读写条件。

### AURA-CAP-BASE-010：设计公共缓存 key 的业务与租户部分

**正例**：`aura:device:tenant:{tenantId}:detail:{deviceId}`。  
**反例**：`detail:{deviceId}` 或直接使用用户输入拼接全局 key。  
**接入核对**：在项目使用的缓存入口核对 key、过期时间与失效方式；共同的缓存和租户规则见 `AURA-BASE-BE-037`、`AURA-BASE-DATA-009`、`AURA-BASE-SEC-006`。

### AURA-CAP-BASE-011：选择 Redis 扫描入口

**正例**：按明确前缀使用 `RedisUtils.scan(pattern)`，并限制返回量。  
**反例**：业务请求中对大实例调用 `RedisUtils.keys("*")`。  
**接入核对**：需要按模式查找时确认 `RedisUtils.scan` 的范围、返回量和运行代价；通用查询规模边界见 `AURA-BASE-DATA-003`。

### AURA-CAP-BASE-012：在适用实体中复用 `BaseEntity`

**正例**：业务实体继承 `BaseEntity`，仅增加领域字段。  
**反例**：每个实体重新声明 id、createBy、updateBy、createTime、updateTime、delFlag，并产生不一致注解。  
**接入核对**：先确认表结构和业务实体确实需要公共审计字段，再检查继承与字段映射；数据模型职责见 `AURA-BASE-DATA-002`，不要把 `BaseEntity` 强加给不适用的对象。

## 5. 记录与可靠性

### AURA-CAP-BASE-013：按场景选择 `@SysLog` 与 `@Audit`

**正例**：写操作按需要组合 `@SysLog` 和 `@Audit`，审计表达式指向修改前数据。  
**反例**：在 Controller 中手工拼接审计文本，或把密码、令牌写入审计内容。  
**检查要点**：日志描述可读，审计对象和敏感字段处理明确。

### AURA-CAP-BASE-014：确认 `@Idempotent` 的实际接入效果

**正例**：订单创建、批量导入等可重复提交操作定义稳定业务键；只有确认项目实际拦截 `@Idempotent` 后，才使用该注解，并用重复请求验证效果。  
**反例**：只依赖按钮置灰，或只添加 `@Idempotent` 而未核对实际拦截与重复请求结果。  
**接入核对**：在目标项目验证注解是否被实际拦截、键的来源与有效期、重复请求结果及失败释放；写操作是否需要幂等由 `AURA-BASE-BE-052`、`AURA-BASE-API-018` 判断。不能仅凭注解类存在宣称能力已生效。

## 6. 服务调用与文档

### AURA-CAP-BASE-015：通过公共 Feign 能力调用服务间 API

**正例**：Feign 接口、DTO 和服务名常量位于 API 模块，业务实现位于服务模块；返回值使用 `R<T>`。  
**反例**：在业务实现模块复制远程接口，或让调用方直接拼接内部 URL。  
**检查要点**：调用契约、超时、降级和认证边界与接口规范一致。

### AURA-CAP-BASE-016：使用公共 OpenAPI 描述入口

**正例**：为需要联调的 Controller 和字段补充 `@Operation`、`@Schema` 说明；公开 OpenAPI 同样使用统一 `R<T>`，并通过 DTO 标出公开字段。  
**反例**：把内部实现类、令牌字段和数据库对象原样暴露到接口文档。  
**接入核对**：核对 `@Operation`、`@Schema` 与实际公开请求、响应；通用接口文档和敏感字段边界以接口与安全规范为准。

## 7. 启动与配置

业务服务按实际需要在启动类启用资源服务安全、公共 Feign 客户端扫描和 OpenAPI 能力。启用注解使用当前项目依赖实际导出的入口，不复制公共包内部配置类。例如只展示 OpenAPI 入口：

```java
@EnableOpenApi("device")
@SpringBootApplication
public class DeviceApplication {
}
```

### AURA-CAP-BASE-017：核对业务所需的公共启用入口

**正例**：业务服务启动类集中声明安全、Feign 和 OpenAPI 入口，业务配置类只补充本服务差异。  
**反例**：在多个业务配置类中重复导入安全过滤器、Feign 注册器或 OpenAPI 自动配置。  
**接入核对**：以当前依赖导出的注解和实际启动行为为准，确认需要的安全、Feign 或 OpenAPI 能力已启用；不因本示例而要求每个服务都声明全部入口。

### AURA-CAP-BASE-018：配置公共能力与业务差异项

推荐的最小配置结构：

```yaml
spring:
  application:
    name: aura-device-biz
  data:
    redis:
      host: ${REDIS_HOST}
      port: ${REDIS_PORT:6379}

security:
  oauth2:
    client:
      ignore-urls:
        - /v3/api-docs/**
        - /swagger-ui/**
```

**正例**：公共认证、Redis 和 OpenAPI 配置由环境配置注入，业务服务只维护自己的路由和业务参数。  
**反例**：在代码中硬编码 Redis 地址、密码、令牌地址或客户端密钥。  
**检查要点**：配置可按环境替换，凭据不进入源码，公共配置不在多个文件重复定义。

### AURA-CAP-BASE-019：配置公共认证放行路径

**正例**：只开放健康检查、接口文档资源和明确的登录入口，业务写接口仍需要认证。  
**反例**：使用 `/**`、`/api/**` 等大范围规则绕过认证。  
**接入核对**：逐项核对项目实际使用的认证配置、公开路径和业务写接口；服务端权限的共同规则见 `AURA-BASE-SEC-004`。

### AURA-CAP-BASE-020：核对公共自动配置与业务扩展点

**正例**：业务服务通过标准属性调整本服务端口、上下文路径和环境地址。  
**反例**：重新声明 `ObjectMapper`、`RedisTemplate`、安全过滤器或 Feign 注册器，改变公共能力默认行为。  
**接入核对**：业务配置若替换了公共 Bean，先查公共模块是否提供该扩展点，并验证启动后的实际行为；配置优先级和启动行为见 `AURA-BASE-CONF-007`、`AURA-BASE-ENV-002`。
