# 09-能力包任务入参规范

**状态**：候选规范  
**适用对象**：使用 AI 判断、接入或审查 AURA 能力包的业务研发人员  
**定位**：规定能力包任务如何从当前需求和项目事实取得必要信息，再进入公开能力入口。本文件不定义具体能力的依赖、配置或调用契约。

能力包任务不要求使用者填写固定表单。使用者说明要解决的问题；项目路径、已有实现、依赖版本和可用示例等能从工作区或公开能力资料取得的信息，由 AI 先定位。普通基础编码任务未涉及具体能力时，无需加载能力包资料。

## 一、围绕当前任务取得信息

### AURA-AI-CAP-IN-001：能力包入参必须服务当前任务

**必要性**：必须

判断或使用能力包时，先明确当前业务目标、期望效果和已知限制，再选择与该目标直接相关的项目事实。能力包说明用于回答“框架提供什么、当前场景如何使用”，不替代业务需求，也不把所有能力资料作为默认上下文。

**正例**：用户要在设备详情页展示在线状态，AI 先确认页面目标和已有设备接口，再查命中的物联能力说明。

**反例**：用户只修改设备名称展示，却预读视频、地图、消息等全部能力包；或只凭能力示例反推项目业务需求。

**检查方式**：所读取的项目资料和能力说明与当前目标有直接关系；未命中的能力没有进入任务上下文。

### AURA-AI-CAP-IN-002：能力包任务应从现有资料取得基本事实

**必要性**：应当

AI 应先从当前请求、已加载的项目入口、目标代码和项目文档取得业务场景、目标位置、已有接入方式及限制。不能查到、且会改变实现结果的事实，才向使用者提出具体问题。项目路径、文件名、能力名称、版本和验证命令不是用户每次必须填写的字段。

**正例**：用户说“在现有设备页显示在线状态”，AI 从当前工作区找到页面、接口及已用的设备能力，再询问唯一缺失的状态刷新要求。

**反例**：在检查工作区前要求用户填写项目路径、目标文件、SDK 版本、输入输出和测试命令全套表单；或缺少关键事实仍直接猜测。

**检查方式**：能从项目或公开资料取得的信息没有被重复索要；提问能说明该缺口如何影响结果。

### AURA-AI-CAP-IN-003：不同能力任务应选取不同的必要信息

**必要性**：应当

信息随任务变化，不使用统一的必填清单：

| 当前任务 | 优先核对的信息 |
| --- | --- |
| 判断是否复用能力 | 业务目标、已有实现、期望结果、公开能力范围与限制 |
| 接入已选定能力 | 当前项目依赖、适用版本、公开入口、必要配置、调用输入输出和最小验证场景 |
| 审查能力使用 | 当前变更或目标文件、实际调用入口、适用的公开契约及验证证据 |
| 定位能力问题 | 错误现象、当前调用与配置、相关日志或响应、版本及可复现线索 |

这些信息可以由 AI 从项目和能力文档取得，不要求开发者逐项抄入提示词。缺少可核实依据时区分已知事实与待确认假设，避免编造调用方式。

**正例**：排查 SDK 调用失败时先核对现有依赖、请求和报错；不要求用户补页面字段清单。

**反例**：审查一个能力调用也强制提供完整业务方案，或把只有场景说明的选型任务当成已有 SDK 可直接编码。

**检查方式**：信息选择与任务类型相符；关键缺口未被猜测填补，也没有无关字段阻碍开展工作。

## 二、公开能力入口与使用依据

### AURA-AI-CAP-IN-004：接入能力前必须核对公开能力入口

**必要性**：必须

准备接入 AURA 能力时，先通过 `05-能力包/能力包索引.md` 定位能力入口，再从命中的能力包核对具体能力、适用版本、公开接口、限制和示例。索引只是导航，不能代替能力包正文或项目当前依赖事实；目录分类名称也不能证明某个 SDK 或方法已对外开放。

索引未命中时，不臆造 AURA 的公开接入方式，也不因此中止与该能力无关的已授权开发。若项目已有其他可核实的公开契约，应核对其来源和适用版本；仍缺少接入依据时说明缺口，不把推测写成正式能力。

**正例**：从能力包索引进入物联中枢云入口，确认当前项目可用版本与公开 SDK 方法后再接入。

**反例**：只看到“视频中台”分类名称就编造依赖和播放方法；或索引暂未列出某能力便停止同任务中的普通页面布局工作。

**检查方式**：实际接入能指向公开入口和适用版本；未命中的能力没有被宣称为已提供的正式调用契约。

### AURA-AI-CAP-IN-005：能力接入应核对场景与公开契约是否匹配

**必要性**：应当

已指定能力时，不重复询问“是否使用”，而应核对当前业务输入、期望输出与能力公开场景是否匹配，项目版本和必要条件是否满足。尚未选定能力、且选型会明显改变业务方案时，应先给出依据和差异，再请求有决定权的人选择。能力包示例只能展示使用方法，不能替代项目业务模型。

**正例**：项目已指定使用文件导出能力，AI 核对现有数据来源、导出格式和公开调用方式后完成接入。

**反例**：每次调用既定 SDK 都重新要求选型确认；或把示例中的设备实体字段直接复制成项目业务字段。

**检查方式**：能力选择与当前授权一致；接入输入输出对应实际业务，未把示例数据模型或未经确认的能力假定为项目契约。

## 三、保持上下文聚焦

### AURA-AI-CAP-IN-006：不得用无关材料替代能力任务事实

**必要性**：禁止

完整历史聊天、未筛选截图、全项目文件列表、过期设计和无关仓库，不能代替当前业务目标、项目实现和公开能力依据。历史材料确有必要时，只取与当前问题有关的片段，并核对版本及状态。不要把未确认的旧结论当成当前能力契约。

**正例**：定位设备指令失败时，使用当前调用代码、相关响应及对应版本的公开说明；必要时补一段已脱敏的历史日志。

**反例**：把多年聊天记录和全量项目目录交给 AI，却没有当前报错与实际调用；或依据旧草稿声称某方法已开放。

**检查方式**：关键判断有当前项目事实和公开能力依据；历史资料的来源、版本及关联已核对。

### AURA-AI-CAP-IN-007：能力任务出现上下文失真时必须收束

**必要性**：必须

AI 把旧能力版本当现行版本、混淆不同能力、反复询问已确认事项，或持续生成偏离目标的结果时，应暂停扩大读取，回到当前目标、项目依赖和命中的公开能力说明，纠正后继续。仅在同一会话仍无法稳定恢复时，才按会话规范整理必要续接信息并考虑切换；资料数量或会话长度本身不是强制停止条件。

**正例**：AI 错用了旧版 SDK 方法，核对项目依赖及当前公开说明后修正调用，继续完成验证。

**反例**：明知版本不符仍继续编写调用；或只因能力文档较长，就要求用户新开会话并重填全部入参。

**检查方式**：失真有具体表现和纠正证据；纠正后的实现仍指向当前能力契约，没有无故中断已授权工作。
