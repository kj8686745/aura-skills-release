# 06-常见任务使用流程

**状态**：候选规范  
**适用对象**：使用 AI 辅助 AURA 应用开发的研发人员

## 一、通用流程

### AURA-AI-FLOW-001：AI 开发任务必须先分析再修改

**必要性**：必须

AI 开发任务应先依据当前目标和项目事实判断修改点、影响及验证方式，再在授权范围内实施。以下是可合并执行的工作环节，不要求逐步停下等待确认；只有实质性选择缺口才提问：

```text
说明任务
→ 定位必要上下文并分析
→ 有实质性选择时确认方案或边界
→ 生成或修改
→ 按影响审查并执行相称验证
→ 记录结果
```

**正例**：用户已明确要求修复指定接口，AI 核对相邻实现和影响后直接修改、验证并报告。

**反例**：未查现有代码就生成整套实现；或每完成一个环节都要求用户批准，即使任务边界已经明确。

**检查方式**：改动前能说明所依据的当前事实和影响；实施与验证没有因重复确认而中断。

## 二、新增后端功能

### AURA-AI-FLOW-002：新增后端功能应按最小改动路径执行

**必要性**：应当

建议流程：

1. 从当前请求与项目资料确认业务目的、目标模块和接口契约，缺失关键事实时再提问；
2. 依据已加载的项目规则，读取目标模块及相邻实现；
3. 判断最小改动路径及实际涉及的权限、租户、事务、缓存或消息边界；
4. 生成代码；
5. 执行编译、测试或接口最小调用；
6. 审查是否符合 AURA 后端规范。

涉及下列行为时，以任务命中的后端基础编码规范和接口规范为准，不在本流程重定义第二套后端规则：

- Controller 不应承载业务流程；
- 输入输出模型应清晰；
- 数据访问结果不应直接暴露；
- 写操作必须考虑权限和数据范围；
- 查询和命令用例应区分。

| 项目 | 要求 |
| --- | --- |
| 允许 AI 做 | 分析相邻实现、生成候选代码、给出验证建议 |
| 不允许 AI 做 | 未经授权改变公开契约、权限信任边界或生产数据 |
| 需要决定时确认 | 当前任务未授权的破坏性契约或数据变化、能力包例外 |
| 验证方向 | 按改动选择相关编译、测试或接口最小调用；未执行的行为如实标注 |
| 完成判断 | 改动范围符合授权，命中的契约与权限边界已核对，验证结果有据可查 |

**正例**：新增查询接口时先核对同模块的分层和响应模型，按既有权限方式实现并运行相关测试。

**反例**：凭示例生成独立 Controller、Service、Mapper 全套代码，却不检查当前模块已有封装；或未授权修改公开响应契约。

**检查方式**：目标、相邻实现、实际命中的后端规则和验证证据可定位；未命中的缓存或消息要求没有被当成必做项。

## 三、新增前端页面

### AURA-AI-FLOW-003：新增前端页面应先读取相邻页面和接口封装

**必要性**：应当

建议流程：

1. 从需求和现有页面确认页面目标、路由、接口及交互；
2. 读取相邻页面、API 封装和当前组件用法；
3. 判断页面结构，以及实际命中的权限、字典、表单或分页要求；
4. 生成代码；
5. 执行构建或页面最小访问；
6. 审查是否符合 AURA 前端规范。

涉及下列行为时，以任务命中的前端基础编码规范为准，本节仅说明任务路径：

- 不直接写死权限和字典；
- 不绕过统一请求封装；
- 不把复杂业务状态散落在页面里；
- 简单页面避免过度分层。

| 项目 | 要求 |
| --- | --- |
| 允许 AI 做 | 分析相邻页面、生成页面结构、补充接口调用和表单校验 |
| 不允许 AI 做 | 写死权限、绕过统一请求、引入与项目不兼容或超出任务范围的依赖、擅自改变全局路由体系 |
| 需要决定时确认 | 当前需求未明确、且会实质改变用户行为的路由或权限设计 |
| 验证方向 | 按改动选择构建、组件检查或页面最小访问，说明未验证行为 |
| 完成判断 | 页面实现与现有封装一致，实际命中的交互要求和验证结果明确 |

**正例**：新增列表页时复用相邻页面的请求封装、分页和权限模式，完成页面访问验证。

**反例**：没有表单的纯展示页也强制创建表单校验；或为新页面自行绕开项目统一请求封装。

**检查方式**：相邻实现、实际命中的交互规则及验证方式可定位；未把示例字段清单当成必填输入。

## 四、接入能力包

### AURA-AI-FLOW-004：能力包接入必须使用公开入口和最小验证路径

**必要性**：必须

建议流程：

1. 从当前需求确认业务场景；已指定适用能力时不重复做选型确认；
2. 通过公开的能力包索引定位适用能力与使用说明；
3. 读取能力包使用规范和示例；
4. 确认版本、配置、公开入口和限制条件；
5. 确定最小接入路径；
6. 实现接入；
7. 按能力包最小验证路径验证。

必须注意：

- 使用当前版本公开且适用的入口；
- 不依赖能力包内部实现；
- 不自行复制能力包逻辑；
- 不把能力包示例业务当成项目业务模板。

| 项目 | 要求 |
| --- | --- |
| 允许 AI 做 | 判断适用性、读取使用规范、生成最小接入方案 |
| 不允许 AI 做 | 绕过公开入口、复制内部实现、擅自将未发布能力当作正式能力接入 |
| 需要决定时确认 | 未确定的能力选型、申请例外或改变公开契约；已指定能力的常规接入可继续 |
| 验证方向 | 按能力包示例或当前业务的最小场景验证 |
| 完成判断 | 公开入口、配置版本和实际限制可查，验证结果与未验证项明确 |

**正例**：任务已指定接入公开 SDK，AI 从能力包索引定位适用版本和示例，接入后验证当前业务路径。

**反例**：跳过索引直接调用能力包内部类；或每次使用既定 SDK 都要求用户重新批准选型。

**检查方式**：能力来源、公开入口、适用版本与实际验证可定位；未把能力示例的业务模型当成项目要求。

## 五、修改已有功能

### AURA-AI-FLOW-005：修改已有功能必须先定位原因和影响范围

**必要性**：必须

建议流程：

1. 从当前问题与现有资料确定目标行为、可用的复现线索；
2. 定位现有实现、相关调用和影响边界；
3. 基于证据确定最小修改点；无法完整复现时标明已证实与推断的部分；
4. 修改代码；
5. 验证原问题和相关边界；
6. 输出变更说明。

必须注意：

- 不在缺少影响分析时大范围重构；
- 不改变无关行为；
- 不绕过现有异常、权限和数据处理。

| 项目 | 要求 |
| --- | --- |
| 允许 AI 做 | 分析现有实现、定位调用链、提出最小修改点 |
| 不允许 AI 做 | 未核对原因和影响就大范围重构、改变无关行为、绕过现有边界 |
| 需要决定时确认 | 超出修复目标的行为或公开契约变化、未授权的数据或权限边界变化 |
| 验证方向 | 优先复现原问题并验证受影响边界；不可复现时说明替代证据与限制 |
| 完成判断 | 改动范围和依据清楚，修复效果已验证或未验证原因明确 |

**正例**：根据失败测试定位条件分支，做局部修复并运行原失败用例与相邻回归。

**反例**：未看现有实现就重写整个模块；或无法复现时仍宣称根因与修复效果已确定。

**检查方式**：原因、改动点和验证结果能对应同一问题；推断与已证实事实分开表述。

## 六、代码审查

### AURA-AI-FLOW-006：代码审查默认只输出问题和建议

**必要性**：应当

建议流程：

1. 根据请求、diff 或目标文件确定审查范围；
2. 只加载命中的基础规范和能力包使用要求；
3. 输出问题、证据、影响和建议；
4. 区分必须整改、建议优化和待确认事项。

审查时不要直接修复，除非用户明确要求实现整改。

| 项目 | 要求 |
| --- | --- |
| 允许 AI 做 | 阅读 diff、定位证据、输出问题和整改建议 |
| 不允许 AI 做 | 未授权直接修复、扩大审查范围、把建议当强制结论 |
| 需要决定时确认 | 审查任务需转为未授权的整改，且用户尚未要求实施时 |
| 核对方向 | 问题有文件、代码或命中规范的依据 |
| 完成判断 | 问题、影响和建议可定位，未越权修改或宣称批准 |

**正例**：只读审查 diff，指出有证据的权限缺口和对应规则，不直接改代码。

**反例**：审查中发现问题便擅自修改项目；或把未命中的能力包规则套到普通接口上。

**检查方式**：输出聚焦可复核的问题与证据；审查和实施权限没有混淆。

## 七、问题定位

### AURA-AI-FLOW-007：问题定位必须先基于证据排查

**必要性**：必须

建议流程：

1. 从用户描述和现有环境收集错误现象、日志或复现线索；
2. 按证据判断可能涉及的层，不预设必须逐一排查前后端全部类别；
3. 沿最有信息量的线索查证；
4. 按证据逐步定位；
5. 给出修复建议；
6. 若当前任务包含修复且范围明确，则继续修改并验证；只授权定位时不修改代码。

不得把未核实的猜测当成根因。能从当前项目直接取得证据时先自行查证；若任务只授权诊断，不修改代码。

| 项目 | 要求 |
| --- | --- |
| 允许 AI 做 | 整理现象、分析日志、提出排查路径、定位可能原因 |
| 不允许 AI 做 | 把猜测写成结论、忽略可取得的复现证据或环境差异 |
| 需要决定时确认 | 修复超出已授权范围，或需处理难以恢复的数据时 |
| 核对方向 | 复现路径、日志、代码或配置证据与结论对应 |
| 完成判断 | 原因有证据或明确为待证假设，修复建议及未验证项清楚 |

**正例**：从报错调用栈定位具体配置差异，核对项目当前配置后给出原因；若用户要求修复，则在授权范围内继续。

**反例**：没有查看日志便认定是数据库问题并修改代码；或明明能运行复现却要求用户先提供全量日志。

**检查方式**：结论与当前证据相符，尚未证实的可能原因有明确标记。

## 八、生成文档或汇报

### AURA-AI-FLOW-008：文档和汇报必须区分事实、计划和待确认事项

**必要性**：必须

建议流程：

1. 根据任务或已有资料明确读者、目的和时间范围；
2. 核对当前事实、阶段结果及来源；
3. 区分已完成、进行中、待确认及未验证事项；
4. 生成文档；
5. 审查是否过度承诺；
6. 必要时调整口径。

不得把候选、计划或未验证事项写成已完成。

| 项目 | 要求 |
| --- | --- |
| 允许 AI 做 | 整理事实、提炼阶段成果、生成文档草稿 |
| 不允许 AI 做 | 把计划写成完成、把候选写成确认、夸大验收状态 |
| 需要决定时确认 | 需要替组织作新的对外承诺或无法核实关键结论时 |
| 最低验证 | 来源文件或当前状态可追溯 |
| 完成判断 | 与本次目的有关的事实、计划和未决事项状态清楚，不强制每份文档都有风险和下一步栏目 |

**正例**：周报依据提交和验证记录总结本周完成项，把下周安排单列为计划。

**反例**：把候选规范写成已发布，或在没有证据时把“准备联调”写成“联调通过”。

**检查方式**：关键结论能对应来源和时间范围，完成、计划、候选和待验证状态未混用。
