# 05-AI 输出审查与人工确认

**状态**：候选规范  
**适用对象**：使用 AI 辅助 AURA 应用开发、审查和交付的研发人员

## 一、AI 输出默认是候选结果

### AURA-AI-REVIEW-001：AI 输出默认不得直接视为交付结果

**必要性**：禁止

AI 生成的代码、项目文档、分析、测试建议和审查结论，在被项目采纳前都是待核对内容。使用者应按其用途核实关键事实和结果；普通解释性答复不因此成为项目交付物。

拟交付的产物应完成相称审阅和验证，并遵循项目已有的交付流程；不额外设置一层与项目流程重复的“AI 批准”。

**正例**：AI 修改接口后，开发者核对契约、变更范围和相关验证，再将代码纳入项目交付。

**反例**：直接复制 AI 生成的接口实现并声称已交付；或把一次普通概念解释也要求走代码交付审批。

**检查方式**：拟采纳的内容有与用途相称的事实核对和验证依据，结论没有超出实际完成状态。

## 二、必须审查的内容

### AURA-AI-REVIEW-002：AI 输出必须经过业务、规范和验证审查

**必要性**：必须

对拟采纳的 AI 产物，应核对真实任务、当前项目事实、命中的规范和实际验证。下表是按影响选择的检查角度，不要求每次任务逐项填写：

| 审查项 | 要求 |
| --- | --- |
| 业务意图 | 是否符合真实需求 |
| AURA 规范 | 是否符合命中的基础规范及能力包使用要求 |
| 接口契约 | 请求、响应、错误和兼容是否稳定 |
| 权限安全 | 是否考虑身份、权限、租户、数据范围 |
| 数据影响 | 是否影响数据一致性、批量操作、导入导出 |
| 依赖边界 | 是否依赖未公开实现或内部细节 |
| 验证结果 | 是否经过构建、测试、运行或最小验证 |
| 变更范围 | 是否超出当前任务授权 |

审查范围由产物决定：接口变更关注契约和兼容，权限变更关注身份与数据范围，文档整理关注来源与事实状态。未命中的检查项不需要制造空记录。开发者可在已有评审或交付流程中完成这些核对。

**正例**：审查 AI 生成的查询接口时，核对需求、响应结构、权限数据范围、相关测试和变更文件。

**反例**：只因构建通过就认定业务、权限和兼容都正确；或给纯文档排版修改机械填写租户与数据迁移检查项。

**检查方式**：审查项覆盖产物的真实影响，结论能对应当前项目文件和验证证据；无关项没有被当成必填流程。

## 三、必须人工确认的情况

### AURA-AI-CONFIRM-001：未获授权或仍有关键选择的高影响变更必须人工确认

**必要性**：必须

人工确认的判断依据是**当前授权与决定权**，不是文件类型。下列事项若未被当前任务明确授权，或存在会实质影响结果的方案选择，AI 必须暂停受影响动作并向有决定权的人提出具体问题：

- 改变已有消费者依赖的公开接口、业务流程或能力包公开契约；
- 改变权限、认证、租户或数据范围的信任边界；
- 执行难以恢复的数据迁移、批量覆盖或删除；
- 执行生产环境操作、正式发布或回滚；
- 申请规范例外，或裁定候选规范已确认、已发布。

已明确授权的常规代码、数据库迁移文件、依赖或构建配置修改可按对应规范直接实施并验证，不因涉及这些文件就重复确认。若需要新的业务取舍或外部权限，再就具体缺口提问。

**正例**：已授权新增字段及迁移脚本时，完成实现与自测；发现迁移会删除历史数据时，暂停数据清理并提出选择。

**反例**：用户明确要求增加依赖实现功能，却因为要编辑依赖文件反复请求批准；或未经授权直接修改生产数据。

**检查方式**：核对确认点是否对应未授权的高影响动作或真实决策缺口，且未阻断可独立完成的任务部分。

### AURA-AI-CONFIRM-002：能力包相关关键决策必须人工确认

**必要性**：必须

项目已明确要求接入某个适用的公开能力，且公开契约覆盖当前场景时，AI 可以按能力包说明实施，无需再次确认“要不要使用”。以下决定仍须由有决定权的人作出：

- 项目尚未明确是否选用该能力，而选择会显著改变业务方案或成本；
- 申请偏离项目已确定的能力使用要求，或使用尚未发布、限制使用的能力；
- 改变能力包公开入口、事件、数据或兼容契约；
- 将项目内实现提升为公司级能力包或裁定新的公开技术组合。

能力包示例只说明调用方式，不自动决定项目业务模型。

**正例**：项目已指定使用物联能力包时，按公开 SDK 接入；若要改动其公开事件格式，再提交具体影响供维护者决定。

**反例**：每次调用已选定的公开 SDK 都让使用者重新确认；或擅自把示例中的设备业务模型照搬进项目。

**检查方式**：区分既定能力接入与新增能力治理决策，核对是否有公开契约和当前任务授权。

## 四、必须验证的情况

### AURA-AI-REVIEW-003：AI 生成或修改结果必须完成相称验证

**必要性**：必须

拟采纳的 AI 生成或修改结果应按实际影响选择可执行的验证，优先复用项目已有命令和研发自测要求。下表是常见验证方向，不是“每次修改都要全部执行”的固定门槛：

| 场景 | 按影响选择的验证方向 |
| --- | --- |
| 后端代码变更 | 相关模块编译、测试或最小接口调用，视改动选择 |
| 前端代码变更 | 相关构建、组件检查或页面访问，视改动选择 |
| API 变更 | 受影响的请求、响应、错误及兼容契约 |
| 权限相关变更 | 受影响身份、角色或数据范围的正反向路径 |
| 能力包接入 | 公开入口及当前场景的最小验证路径 |
| 配置变更 | 配置加载或受影响的启动行为 |
| 批处理/导入导出 | 小样本、边界数据及失败处理 |

如验证条件不具备，可完成已授权的实现，但应明确哪些行为未验证、为什么未验证，不得把实现完成写成链路已验证或上线可用。只改措辞、排版等低影响内容时，文件检查可能已足够，无需人为追加运行测试。

**正例**：修改接口响应后运行相关测试并核对示例响应；真实环境不可用时，说明联调尚未执行。

**反例**：编译通过就声称权限和真实环境联调通过；或一处文档标点修改也强制启动完整应用。

**检查方式**：验证项与受影响行为对应；结果区分已执行、未执行和失败，不以一种检查替代整个链路。

## 五、AI 输出不应直接采纳的情况

### AURA-AI-REVIEW-004：缺少依据、事实或验证的输出不得直接采纳

**必要性**：禁止

拟作为项目结论或交付物时，出现以下相关情况，不得在未核实或纠正前直接采纳：

- 关键结论缺少可核实依据；
- 需要当前项目事实，却只引用旧会话或推断；
- 使用了不存在的类、方法、组件或配置；
- 引入与项目版本或任务授权不符的依赖；
- 绕过现有项目结构；
- 修改范围明显过大；
- 对需要验证的行为没有说明实际验证状态；
- 与 AURA 规范或能力包说明冲突。

发现这些问题时可先补证据、缩小范围或修改产物，不必把整项已授权工作全部中止。能力包说明只对实际命中的能力场景生效。

**正例**：AI 引用了不存在的工具方法，开发者核对当前公共模块后改用公开入口，再做相关验证。

**反例**：未核对类和方法是否存在就复制代码；或因解释性答复未附运行命令便一律判为“不得采纳”。

**检查方式**：被采纳的关键事实、引用和验证状态可核实；发现偏差时已纠正或明确保留为未采纳部分。

## 六、审查结果表达

### AURA-AI-REVIEW-005：审查结果必须明确采纳状态

**必要性**：必须

当任务是对 AI 产物作采纳判断时，应明确哪些内容可采纳、需修改、不能采纳或尚待验证/决定。可按问题逐项说明，不要求填写固定表单，也不把“开发者已审阅”写成正式发布批准。

可参考以下表达：

```text
采纳：
需要修改：
不能采纳：
需要人工确认：
需要补充验证：
```

不要只用“看起来可以”作为采纳依据。若审查只是发现问题而无权决定是否合并、发布，应如实说明建议和决策归属。

**正例**：指出某接口实现可采纳，权限分支需修正，联调尚未验证；相关依据附在问题旁。

**反例**：只写“整体没问题”却遗漏未跑的测试；或审查人越权宣布候选规范正式发布。

**检查方式**：采纳状态与具体产物、问题和证据对应；未验证及无权决定的事项没有被表述为已批准。
