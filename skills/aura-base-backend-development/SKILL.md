# AURA 后端开发

负责需求到后端实现、自测和交付的闭环。版本见 `VERSION`，规范和能力来源见[来源记录](references/source.json)。使用方法见 [USAGE.md](USAGE.md)。

## 选路

1. 先确认当前需求、项目依赖和已有契约。从[编码任务路由](references/任务路由.md)选择命中的规则、正反例与检查点；不预读全部规范。
2. 需要框架已有能力时，按[能力使用索引](references/能力使用索引.md)选中模块，再读该模块的路由和接入示例。模块已随包提供，不要求另装能力技能；普通 CRUD 不预读动态数据源、消息、调度或实时协议。
3. 单独工程初始化、技术详细设计、模块接口文档交付分别属于对应入口。本任务涉及接口实现时，直接按随包接口规范执行；只有用户还要求接口设计文档时才组合可用的接口设计技能，不将其他技能作为必装依赖。

## 实现与完成

核对现状和调用方 → 选择已有规范与能力 → 实现当前需求 → 运行与改动相称的构建和自测 → 汇总实际结果。能力包说明框架提供什么，基础规范约束如何开发；不得凭依赖存在推断能力已启用。

内部与对外 HTTP 接口采用同一 `R<T>`、`CommonConstants.SUCCESS=200` 及公共分页对象目标契约。外部响应先按已确认契约适配，不另定 AURA 成功码；框架尚未提供目标分页类型时，报告版本和实现缺口，不虚构 API。

存量改造先识别受影响接口、调用方与兼容约束，再在授权范围内实现。普通开发只做当前任务所需检查；明确要求规范审查时进入独立审查入口，不把全部旧项目开发都变成先审查。

按命中清单检查分层、权限、数据、事务、失败及并发边界；代码完成、构建、自测、联调分别报告。缺少关键契约或版本时只停止相关推断，不改框架规则，不把未运行结果写成通过。
