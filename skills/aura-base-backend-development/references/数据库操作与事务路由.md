# 数据库操作与事务路由

本路由把数据库开发拆成“依赖与配置 → 数据模型 → Mapper/Repository → SQL → Service 事务 → 迁移 → 验证”闭环。它只负责选择要读的规范和执行顺序，不替代数据库正文、能力包公开入口或项目真实模板。

任务涉及缓存时，先按 `AURA-BASE-DATA-018` 判断是否有明确收益，再按 `AURA-BASE-DATA-019` 选择查询缓存、状态投影、认证状态或协调状态，最后按 `AURA-BASE-DATA-020` 完成键、版本、生命周期、失效和故障边界；没有缓存需求时不加载缓存模板。

## 先判断任务类型

| 任务 | 追加读取 |
|---|---|
| 新增表、字段或索引 | 数据访问事务与生命周期、通用数据表达、项目迁移工具说明 |
| 新增 CRUD 或分页查询 | 代码组织与接口入口、基础业务任务路由、数据访问事务与生命周期、接口规范 |
| 复杂查询或多表关联 | 按[数据库操作模板](数据库操作模板.md#查询开发)确定分页单位、count及数据范围，再选读 `DATA-003/013/015/016` 和对应查询示例 |
| 多步写入或状态变更 | 应用用例与业务模型、事务与生命周期、异常失败恢复 |
| 多数据源、跨服务或分布式事务 | 数据基础设施能力包、外部系统集成与调用、详细设计；不得默认扩大为跨服务事务 |
| 存量数据库改造 | 先盘点 Entity/Mapper/SQL/迁移/调用方，按[结构演进](数据库操作模板.md#结构演进)及 `DATA-014/015` 核对新增、回填、切换、约束和恢复，不重新生成已有模块 |

## 标准开发顺序

1. **确认真实依赖**：核对父 POM/BOM、公共数据模块、数据库驱动、连接池和项目统一配置；不重复引入 ORM、连接池或公共实体，不凭示例猜坐标和版本。
2. **确定数据边界**：明确表、字段、主键、审计字段、逻辑删除、租户/组织数据范围、唯一约束、索引和时间精度；Entity 只表达持久化模型，接口请求/响应使用 DTO。
3. **建立访问层**：简单 CRUD 优先使用项目公共 Mapper/Repository；复杂查询使用语义明确的 Mapper 方法和 XML/受控注解 SQL；SQL 不写进 Controller 或 Service。
4. **绑定参数和范围**：所有输入使用参数绑定，禁止字符串拼接 SQL；排序字段使用后端白名单；租户、组织和数据权限由可信上下文进入查询条件，不能直接采用前端传入的范围字段。
5. **落事务边界**：Service/UseCase 负责业务编排和本地事务；同一数据源的主子表写入保持原子性；事务中不放长时间远程调用；异常传播和回滚条件按实际事务管理器核对。
6. **处理提交后动作**：缓存失效、消息投递、审计或外部通知不能被误当作数据库事务的一部分；需要一致性时按可靠消息、提交后回调或补偿方案设计。
7. **登记迁移和交付**：表结构变更必须有项目既有迁移脚本或受控 SQL，并能从迁移脚本追溯到 Entity、Mapper、Service 和接口/任务；记录向前、回滚或不可逆边界。
8. **执行验证**：静态检查后执行项目可用的编译、迁移、正常读写、约束失败、事务回滚、租户边界和分页上限验证；未运行的数据库行为只能写未证实。

## 禁止直接判定为完成的写法

- Service 中直接拼接 SQL 或直接创建数据源；
- Controller 直接调用 Mapper 并返回 Entity；
- 用 `Map` 接收任意查询条件，绕过 DTO 和参数约束；
- 只新增 Entity/Mapper 不提供迁移脚本或验证表结构；
- 只凭 `@Transactional` 注解存在就宣称回滚已生效；
- 只凭依赖或 import 存在就宣称已经复用 AURA 数据能力；
- 把数据库写入成功、缓存失效、消息投递和外部调用成功混成一个事务结论。

## 最小交付证据

查询或迁移文件已明确时，用 `inspect-database-changes.ps1` 只检查本次 SQL/Mapper XML 文件，输出候选后回到上述条款核对。工具不判断索引最优、分页业务单位或真实租户生效；没有 SQL 文件的查询构造器不为运行工具临时编造一份 SQL。

```text
依赖/BOM/驱动与配置版本
→ Entity/DTO/Mapper/SQL/迁移脚本路径
→ Service 事务方法和数据范围入口
→ 正常读写与失败回滚命令/结果
→ 分页、约束、租户/权限和未验证边界
```

若项目没有数据库功能，不要求强行引入数据库依赖；在初始化或普通业务任务中记录“不适用依据”，不要把未触发能力误写成缺陷。
