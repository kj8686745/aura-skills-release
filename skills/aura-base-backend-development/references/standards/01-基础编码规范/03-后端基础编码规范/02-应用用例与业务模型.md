## 一、规则

### AURA-BASE-BE-008：应用服务必须围绕业务用例组织

**必要性**：必须

应用服务方法应表达一个明确业务动作，例如创建、提交、审核、撤销、同步、批处理、状态变更或查询。

不得把应用服务设计成只转发 Mapper 或 Client 的薄壳，也不得把多个无关业务流程塞进一个方法中。

**为什么需要**：应用服务是业务动作的组织边界，明确用例可以让流程、测试和失败处理具有稳定入口。

**正确写法**：`CreateDeviceGroupApplicationService.create(command)` 组织校验、持久化和结果转换。

**错误写法**：`DeviceService.doEverything()` 根据多个无关参数分支执行创建、删除、导出和同步。

**判断要点 / 验证方式**：方法是否表达单一业务动作；是否只是转发一个 Mapper 或 Client；是否混入无关流程；人工检查用例边界；通过用例级测试验证业务动作和失败结果。

**例外**：纯查询且无业务编排的简单用例可以保持较薄，但仍要有清晰查询语义。

### AURA-BASE-BE-009：应用用例负责业务编排

**必要性**：必须

涉及多步骤处理时，应用用例负责协调业务规则、数据访问、外部调用、事务边界和失败处理。

Mapper、Client、工具类、消息监听器和定时任务入口不得替代应用用例承载主业务流程。

**为什么需要**：统一由应用用例编排，才能集中管理顺序、事务、外部依赖和失败路径。

**正确写法**：`提交审核用例 → 校验状态 → 保存结果 → 发布事件 → 返回业务结果`。

**错误写法**：消息监听器直接改库，定时任务直接调用多个 Mapper，Controller 另外实现相同流程。

**判断要点 / 验证方式**：主流程是否只有一个可识别编排入口；入口适配器是否承载了业务顺序；人工检查调用链和依赖方向；使用成功、失败和重复执行测试验证编排结果。

**例外**：仅做协议转发且不包含业务动作的适配器可以不建立独立用例。

### AURA-BASE-BE-010：事务边界应由业务用例控制

**必要性**：应当

需要事务保护的业务写操作，应在应用用例或明确的业务服务边界控制事务。

不得在接口入口、Mapper、工具类或无法说明业务语义的底层方法中随意开启事务。涉及外部调用、消息发送或长时间任务时，不得简单把全部步骤包进一个大事务。

**为什么需要**：事务边界应保护同一业务一致性，过大的事务会造成锁占用、超时和外部副作用无法回滚。

**正确写法**：事务只包住本地一致性写操作，外部调用通过状态记录、事件或补偿处理衔接。

**错误写法**：在 Controller 或 Mapper 上开启事务，并在事务内等待远程服务和长时间文件处理。

**判断要点 / 验证方式**：事务是否与业务动作一致；外部调用、消息和长任务是否错误纳入本地事务；测试提交、回滚、超时和外部失败路径；人工确认事务边界和补偿语义。

**例外**：跨系统事务方案必须有明确协议和专项人工确认。

**边界说明**：本规则约束事务注解、应用用例和后端代码的落点；本地数据原子性、外部副作用衔接和事务一致性语义由 `BASE-08` 进一步定义。

### AURA-BASE-BE-011：应用用例必须显式处理失败路径

**必要性**：必须

应用用例应明确处理校验失败、数据不存在、状态不允许、重复提交、外部调用失败、超时、部分成功和并发冲突等适用情况。

不得只实现正常路径，也不得用默认值、空对象或忽略异常的方式掩盖失败。

**为什么需要**：失败路径决定调用方能否重试、补偿和追踪业务结果。

**正确写法**：针对状态不允许、重复提交、超时、部分成功和并发冲突分别定义结果。

**错误写法**：捕获所有异常后返回空列表，或在批处理失败时仍把任务标记为成功。

**判断要点 / 验证方式**：失败是否有明确结果；部分成功和重试是否有可识别状态；异常是否被吞掉；为主要失败路径编写测试，并保留失败结果和日志证据；人工确认业务语义。

**例外**：明确约定的“无数据”只能表示查询为空，不能表示执行异常。

### AURA-BASE-BE-012：业务规则应集中表达

**必要性**：应当

决定业务状态、资格、金额、数量、时间窗口、状态流转和关键约束的规则，应在可识别的业务对象、领域服务或应用用例中集中表达。

不得把核心业务规则散落在 Controller、Mapper XML、SQL 条件、前端页面、配置字符串或多个工具方法中。

**为什么需要**：集中表达业务规则可以避免不同入口实现不一致，降低修改和审查成本。

**正确写法**：将状态转换、资格判断和金额计算放入可命名的业务对象或领域服务。

**错误写法**：前端限制一次，Controller 再判断一次，SQL 再隐藏判断一次，三处语义不一致。

**判断要点 / 验证方式**：规则是否有唯一主要表达位置；不同入口是否复用同一业务判断；人工追踪规则来源；通过跨入口测试验证规则结果一致。

**例外**：纯格式校验可以留在请求模型或入口层，但不得把业务资格判断当作格式校验。

### AURA-BASE-BE-013：状态和枚举必须语义清晰

**必要性**：必须

后端状态、类型、来源、结果和错误分类应使用语义明确的枚举、常量或值对象表达。

不得在业务代码中散落魔法数字、魔法字符串、隐式状态值或只在注释中说明含义的字段。

**为什么需要**：明确状态语义可以避免状态流转、接口兼容和数据迁移中的歧义。

**正确写法**：使用 `ReviewStatus.PENDING`、`ReviewStatus.APPROVED` 等语义明确的枚举或值对象。

**错误写法**：在多个方法中直接比较 `status == 2` 或 `status.equals("Y")`。

**判断要点 / 验证方式**：状态值是否有唯一含义、允许转换和终态定义；是否存在无法追溯的魔法值；静态扫描可发现部分魔法值；人工确认状态表、兼容范围和转换规则。

**例外**：外部协议绑定的值可以保留在适配层，但进入业务层前必须转换为内部语义。

### AURA-BASE-BE-014：不同边界的模型不得无条件复用

**必要性**：禁止

请求模型、响应模型、应用命令、业务模型、持久化实体、外部调用模型和事件模型具有不同责任时，应分别表达。

只有字段语义、生命周期、安全边界和变更影响完全一致时，才可以复用同一类型。

**为什么需要**：无条件复用模型会把数据库、接口、事件和外部系统的变化互相传递。

**正确写法**：请求使用 Command，持久化使用 Entity，公开响应使用 Response，并通过转换表达边界。

**错误写法**：Controller 接收 Entity，保存后直接把 Entity 返回前端，同时作为外部事件载荷。

**判断要点 / 验证方式**：模型的生命周期、字段权限、变更来源和安全边界是否一致；人工检查模型依赖和转换位置；通过契约测试验证公开模型不会随内部模型变化。

**例外**：稳定且经过人工确认的内部只读模型可以复用，但不能跨越公开边界。

### AURA-BASE-BE-015：内部模型不得穿透公开边界

**必要性**：禁止

数据库实体、Mapper 查询对象、外部客户端响应、内部异常对象、配置对象和缓存对象不得未经转换直接出现在公开 API、跨模块契约、事件载荷或前端响应中。

公开边界使用的模型必须经过业务项目自身转换。

**为什么需要**：转换是公开契约和内部实现之间的隔离层，可以阻断内部字段、异常和外部协议泄漏。

**正确写法**：`Entity → DeviceGroupResponse`，只映射公开字段，并按业务语义处理状态和空值。

**错误写法**：`return entity`、`return rawClientResponse` 或将内部异常直接序列化返回。

**判断要点 / 验证方式**：公开接口、跨模块接口和事件载荷中是否出现 Entity、内部 DTO、原始响应或内部异常；检查公开签名和序列化结果；人工核对字段来源、敏感字段和兼容要求。

**例外**：经过明确契约和版本管理的内部公共模型可以复用，但必须有人工确认记录。

### AURA-BASE-BE-031：业务校验必须分层表达

**必要性**：必须

字段格式、必填和长度等输入校验应在请求模型或入口适配层完成；跨字段、状态和业务资格校验应在应用用例或业务规则中完成。不得只依赖数据库异常或前端校验保证业务合法性。

**为什么需要**：分层校验可以让错误位置清晰，并避免前端或数据库成为唯一防线。

**正确写法**：请求模型校验格式和必填，用例校验状态和资格，数据库约束负责最终数据完整性。

**错误写法**：只在前端判断，后端直接写库；或把所有业务规则堆在 Controller 参数校验中。

**判断要点 / 验证方式**：校验是否放在能理解该语义的层；是否存在只依赖前端或异常兜底的情况；测试格式错误、跨字段错误、业务状态错误和数据库约束错误；人工检查校验职责。

**例外**：纯展示性校验可以由前端提前提示，但后端仍需执行必要校验。

### AURA-BASE-BE-032：空值和缺失必须有明确语义

**必要性**：必须

后端代码应区分“未提供”“明确为空”“不存在”“默认值”和“查询无结果”。不得用 `null`、空字符串、零值或空集合在不同场景下随意替代多种语义。

**为什么需要**：空值语义不清会导致更新误覆盖、查询条件错误和接口兼容问题。

**正确写法**：使用明确的可选字段、操作命令或结果类型区分未提供、清空和查询无结果。

**错误写法**：所有缺失字段都转成空字符串，或用 `null` 同时表示不存在、清空和系统异常。

**判断要点 / 验证方式**：输入、持久化、响应和查询结果是否分别定义空值语义；测试字段缺失、明确为空、默认值和无结果场景；人工确认兼容行为。

**例外**：已有公开契约明确规定的空值表达可以沿用，但不得在新代码中随意扩展含义。

### AURA-BASE-BE-033：时间处理必须统一来源和时区

**必要性**：必须

业务时间应明确来源、精度、时区和序列化方式。不得直接依赖服务器本地时区、在业务代码中散落格式化字符串，或用字符串比较替代时间比较。

**为什么需要**：统一时间来源和时区，才能保证跨环境、跨服务和跨地区结果一致。

**正确写法**：使用统一时间源和明确时区的时间类型，在边界统一序列化。

**错误写法**：直接调用服务器本地时间，或使用字符串大小比较判断时间先后。

**判断要点 / 验证方式**：时间来源、时区、精度和序列化格式是否明确；在不同时区和边界时间下测试；人工确认业务时区和精度要求。

**例外**：展示层可按用户时区格式化，但内部业务比较必须使用统一语义。

### AURA-BASE-BE-034：金额、数量和精度必须使用合适类型

**必要性**：必须

金额、计费、比例、测量值和其他有精度要求的数据必须使用能够表达其精度和舍入规则的类型。不得用二进制浮点直接承载金额，也不得在多个位置重复定义舍入规则。

**为什么需要**：精度和舍入不一致会造成账务、计费和统计结果偏差。

**正确写法**：使用明确精度的 decimal 类型和值对象，并集中定义舍入规则。

**错误写法**：用 `double` 累加金额，或在 Controller、Service 和 SQL 中分别舍入。

**判断要点 / 验证方式**：类型能否表达所需精度；舍入、单位和溢出边界是否统一；测试临界小数、负数、溢出和多次计算；人工确认业务精度规则。

**例外**：仅用于展示的近似测量值可以使用浮点，但不得进入计费或持久化金额语义。

## 二、典型开发场景

以下示例用于说明多条规则如何组合，不构成新的接口契约，也不绑定具体框架、目录名或业务模型。

### 状态流转

**适用任务**：后端业务用例、数据访问、异常与日志  
**关联规则**：BE-008、BE-009、BE-011、BE-013、BE-024、BE-027  
**示例级别**：完整示例

#### 场景目标

实现审核单从待审核到已通过或已驳回的状态流转，确保后端控制合法转换、重复提交和并发冲突。

#### 输入条件

- 状态只能由后端根据当前状态决定；
- 提交人必须具备操作权限；
- 已通过和已驳回状态不能再次提交；
- 并发修改必须能够识别版本冲突。

#### 状态定义与合法转换

```text
PENDING_REVIEW
  ├─ approve → APPROVED
  └─ reject  → REJECTED

APPROVED / REJECTED
  └─ 不允许再次提交
```

#### 推荐调用结构

```text
SubmitReviewCommand
  → ReviewApplicationService
    → 查询当前状态
    → 校验状态是否允许提交
    → 校验提交人和数据范围
    → 执行状态转换
    → 记录业务结果
```

#### 完整正确示例

```java
public ReviewResult submit(SubmitReviewCommand command) {
    var review = repository.findById(command.reviewId())
        .orElseThrow(() -> new ReviewNotFoundException(command.reviewId()));

    review.ensureOwner(command.operatorId());
    review.requireTransition(command.version());
    ReviewStatus target = switch (command.action()) {
        case APPROVE -> ReviewStatus.APPROVED;
        case REJECT -> ReviewStatus.REJECTED;
    };
    int changed = repository.updateStatusIfVersionAndState(
        review.id(), command.operatorId(), command.version(),
        ReviewStatus.PENDING_REVIEW, target);
    if (changed != 1) {
        throw new ConcurrentReviewModificationException();
    }
    return ReviewResult.changed(review.id(), target);
}

public void requireTransition(long expectedVersion) {
    if (status != ReviewStatus.PENDING_REVIEW) {
        throw new InvalidReviewStateException(status);
    }
    if (version != expectedVersion) {
        throw new ConcurrentReviewModificationException();
    }
}
```

持久层的关键条件写入如下；参数必须绑定，不能拼接请求值：

```sql
UPDATE review
SET status = :targetStatus, version = version + 1
WHERE id = :reviewId
  AND owner_id = :operatorId
  AND status = :expectedStatus
  AND version = :expectedVersion;
```

状态转换由后端根据批准或驳回动作决定。Repository 更新必须同时限定对象、操作人/数据范围、旧状态和旧版本，在数据库中递增版本；影响行数为零时不能返回成功。内存校验用于表达业务语义，不能替代持久层条件写入。

#### 错误示例

```java
public void updateStatus(long id, String status) {
    mapper.updateStatus(id, status); // 直接接受前端状态
}

if (mapper.updateStatus(id, "APPROVED") == 0) {
    return SuccessResult.ok(); // 未更新也返回成功
}
```

问题：前端可以传入任意状态，未检查当前状态、操作权限和版本冲突，更新失败也被伪装成成功。

#### 验证步骤与预期结果

1. 待审核单提交通过，预期状态变为 `APPROVED`。
2. 已通过单再次提交，预期返回状态不允许错误，状态不变。
3. 两个请求使用同一版本并发提交，预期只有一个成功，另一个返回并发冲突。
4. 无权限用户提交，预期返回权限错误，不改变状态。

#### 人工确认点

- 状态集合和合法转换是否覆盖完整业务流程；
- 操作权限和数据范围是否由对应安全规范定义；
- 并发冲突是拒绝、重读还是进入待处理状态；
- 状态变更是否需要记录审计或业务事件。

反例：前端传入任意状态字符串，后端执行无条件更新；更新影响行数为零时仍返回成功。

### 主子表业务

**适用任务**：后端业务用例、数据访问  
**关联规则**：BE-008、BE-009、BE-010、BE-011、BE-014、BE-027  
**示例级别**：完整示例

#### 场景目标

修改一张“工单”及其明细项。主单与明细的业务校验、差异计算、写入顺序和失败语义由同一个应用用例编排，不能由 Controller、Mapper 或多个异步入口分别保存。

#### 输入条件

- 请求包含主单字段、明细列表和版本号；
- 明细项具有唯一业务键，例如物料编码或条目编号；
- 修改场景允许新增、修改和删除既有明细；
- 主单与明细需要在同一业务事务中保持一致；
- 并发修改、明细重复、主单状态不允许修改和部分写入失败需要有明确处理结果。

#### 推荐调用结构

```text
WorkOrderController
  → UpdateWorkOrderCommand
  → WorkOrderApplicationService
    → 校验主单状态、当前用户和明细唯一性
    → 加载既有主单及明细（修改时）
    → 计算新增、更新、删除的明细差异
    → 在业务事务中保存主单和差异明细
    → 返回公开工单结果
```

#### 完整正确示例

```java
@Transactional
public WorkOrderResult update(UpdateWorkOrderCommand command, UserContext context) {
    var order = workOrderRepository.findVisibleById(command.id(), context.scope())
        .orElseThrow(() -> new WorkOrderNotFoundException(command.id()));
    order.requireEditable(command.version());

    var requestedItems = command.items().stream()
        .map(itemMapper::toCommandItem)
        .toList();
    itemValidator.requireUniqueMaterialCode(requestedItems);
    itemValidator.requireAllowedItems(requestedItems, context.scope());

    var changes = itemDiffCalculator.compare(order.items(), requestedItems);
    int changed = workOrderRepository.updateHeaderIfVersionAndStatus(
        order.id(), context.scope(), command.version(), WorkOrderStatus.EDITABLE,
        command.title(), command.remark());
    if (changed != 1) {
        throw new ConcurrentWorkOrderModificationException(order.id());
    }
    workOrderItemRepository.applyChanges(order.id(), changes);
    return WorkOrderResult.from(
        workOrderRepository.findVisibleWithItems(order.id(), context.scope()));
}
```

主单更新至少包含以下条件；Repository 返回实际影响行数：

```sql
UPDATE work_order
SET title = :title, remark = :remark, version = version + 1
WHERE id = :orderId
  AND scope_id = :scopeId
  AND status = :editableStatus
  AND version = :expectedVersion;
```

```text
既有明细：A、B、C
请求明细：A'、C、D

差异结果：更新 A；保留 C；删除 B；新增 D
```

应用用例先校验主单状态和版本，再计算明细差异。`updateHeaderIfVersionAndStatus` 必须在数据库中同时限定主单标识、当前数据范围、旧版本和可编辑状态并递增版本；只有影响一行后才写入明细。示例的 `scope_id` 代表实际项目的数据范围条件，不要求各项目采用同名字段。所有主子表修改入口均须经过同一主单并发门槛，且主单条件更新与明细差异写入处于同一本地事务；明细写入失败时整体回滚。事务的原子性不能代替版本冲突检查。若必须触发外部动作，应先完成本地状态记录，再按异步、幂等和补偿规则处理，不能把不可控远程调用简单包进数据库事务。

#### 错误示例

问题：没有校验主单状态、版本、数据范围和明细唯一性；更新时只会追加明细，无法识别删除和修改；任一步骤失败会留下不一致数据；Mapper 被迫承担业务差异逻辑。

#### 验证步骤与预期结果

1. 提交重复物料编码的明细，预期在写入前被明确拒绝，主单和明细均不改变。
2. 更新不可编辑状态的工单，预期返回业务失败，不执行任何明细写入。
3. 两个用户基于同一版本修改，后提交的一方预期得到明确并发冲突结果，而不是覆盖前一方数据。
4. 请求包含新增、修改、删除三类明细，预期最终明细与请求差异一致，不残留已删除项或重复项。
5. 模拟明细保存失败，预期主单和所有明细整体回滚；如果有外部后续动作，预期可追踪其未执行、待执行或补偿状态。

### 带校验与精度约束的业务操作

**适用任务**：后端业务用例、后端接口  
**关联规则**：BE-012、BE-015、BE-031、BE-033、BE-034  
**示例级别**：完整示例

#### 场景目标

创建一条设备服务计费规则：请求负责字段格式校验，应用用例负责生效时间、计费金额、数量范围和业务资格校验；业务对象集中维护金额精度与时间窗口规则；公开响应只返回稳定的计费规则模型。

#### 输入条件

- 请求包含服务标识、生效开始与结束时间、单价、计费数量和币种；
- 金额使用十进制精确类型，数量使用具有明确单位与精度的类型；
- 时间使用统一时钟和明确时区，不能用服务器本地时间或字符串比较；
- 已存在相同服务标识和时间窗口的规则，需要防止重叠；
- 数据库实体与公开响应字段不同，且响应不应暴露内部审计、租户和存储字段。

#### 推荐调用结构

```text
CreateBillingRuleController
  → CreateBillingRuleRequest（必填、格式、长度、数值范围）
  → CreateBillingRuleCommand
  → BillingRuleApplicationService
    → 解析用户数据范围、统一时钟与时区
    → 校验服务资格、时间窗口和既有规则重叠
    → BillingRule.create（金额、数量和业务不变量）
    → Repository 保存
    → BillingRuleResponse（公开模型转换）
```

#### 完整正确示例

```java
public BillingRuleResponse create(CreateBillingRuleCommand command, UserContext context) {
    var range = billingPeriod.of(command.startsAt(), command.endsAt(), businessClock.zone());
    billingRuleRepository.requireNoOverlap(command.serviceId(), range, context.scope());
    serviceCatalog.requireBillable(command.serviceId(), context.scope());

    var rule = BillingRule.create(
        command.serviceId(), range,
        Money.of(command.unitPrice(), command.currency()),
        Quantity.of(command.quantity(), command.unit()),
        businessClock.now());
    billingRuleRepository.save(rule);
    return BillingRuleResponse.from(rule);
}
```

```java
public record Money(BigDecimal amount, Currency currency) {
    public static Money of(BigDecimal amount, Currency currency) {
        if (amount == null || amount.signum() < 0) throw new BusinessValidationException("INVALID_AMOUNT");
        return new Money(amount.setScale(currency.defaultFractionDigits(), RoundingMode.HALF_UP), currency);
    }
}
```

请求模型处理“字段有没有、格式是否正确”；应用用例处理“当前用户能否为该服务创建规则、时间窗口是否重叠”；业务对象处理“金额、数量和时间是否构成合法计费规则”。实体、持久化字段和内部异常均在响应转换前止步。

#### 错误示例

```java
public Map<String, Object> create(CreateRuleRequest request) {
    var entity = new BillingRuleEntity();
    entity.setPrice(Double.parseDouble(request.price()));
    entity.setStartsAt(LocalDateTime.now().toString());
    mapper.insert(entity);
    return Map.of("data", entity);
}
```

问题：金额使用浮点数和字符串解析；时间依赖本地时区并保存为字符串；没有业务资格、时间重叠和数量规则；实体直接作为公开响应，内部字段和后续存储变化会穿透接口。

#### 验证步骤与预期结果

1. 缺少必填字段、金额格式错误或数量超出输入范围，预期在请求边界返回可理解校验结果，不进入业务写入。
2. 生效结束时间早于开始时间，或与既有规则重叠，预期由业务用例明确拒绝，不依赖数据库唯一键碰撞作为业务反馈。
3. 使用不同服务器时区或夏令时边界输入，预期按业务规定时区计算同一时间窗口，不因运行节点不同而改变结果。
4. 输入小数金额和数量，预期按唯一的币种精度、单位和舍入规则处理，响应中可追溯其公开表达。
5. 检查公开响应，预期不包含 Entity、内部租户字段、审计字段、数据库状态或内部异常信息。
6. 变更持久化字段名称或内部存储方式，预期对外响应契约不受直接影响。

#### 人工确认点

- 计费金额、数量单位、币种精度和舍入规则是否符合业务与财务口径；
- 生效时间的业务时区、闭区间/开区间语义、重叠规则和历史修订方式；
- 字段校验、跨字段校验、权限校验和最终业务裁决分别归属何处；
- 公开响应中允许暴露的时间、金额和状态字段，以及向前兼容要求。
