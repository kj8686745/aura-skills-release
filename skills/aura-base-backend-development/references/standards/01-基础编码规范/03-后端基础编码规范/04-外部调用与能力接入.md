## 一、规则

### AURA-BASE-BE-020：外部调用必须封装在客户端或适配器边界

**必要性**：必须

调用其他服务、第三方系统或基础平台能力时，应通过可识别的 Client、Adapter、Port 或能力公开入口封装。

业务用例不得散落 HTTP 地址、SDK 初始化、协议细节、认证细节、重试细节和原始响应解析。

若能力包的公开入口已经承担调用边界和结果转换职责，业务用例可直接使用该入口；不为满足分层形式再增加无职责的包装类。

**为什么需要**：适配器边界可以隔离外部协议和内部业务语义，避免第三方变更扩散到业务代码。

**正确写法**：`DeviceApplicationService → DeviceClient → 外部 HTTP/SDK`，Client 负责协议适配和基础错误转换。

**错误写法**：在业务用例中拼接 URL、创建 SDK 客户端、设置认证头并解析外部 JSON。

**判断要点 / 验证方式**：外部地址、认证、协议字段和 SDK 类型是否集中在适配边界；业务用例是否只依赖内部接口；自动扫描可发现业务层对 HTTP 客户端和 SDK 的直接依赖；人工确认适配边界和替换成本。

**例外**：一次性的内部探针可以直接调用，但不得作为业务模块的实现范例。

### AURA-BASE-BE-021：外部响应必须转换为业务可理解结果

**必要性**：必须

外部系统的原始响应、错误码、异常、状态值和分页结构不得直接穿透到业务用例、公开 API 或前端响应中。

适配边界应把外部结果转换为业务项目能够理解的结果、失败原因和状态。

**为什么需要**：外部系统的状态码和错误结构通常不等于本业务的状态语义，直接透传会形成不稳定的隐式契约。

**正确写法**：将外部 `200/404/429` 和供应商错误码转换为本业务的成功、未找到、限流或暂不可用结果。

**错误写法**：把外部响应对象直接作为应用服务返回值，或把供应商错误码原样暴露给前端。

**判断要点 / 验证方式**：业务层是否依赖外部字段名和错误码；失败原因是否能被本业务理解和处理；使用成功、空结果、错误、超时和不完整响应进行适配测试；人工核对转换契约。

**例外**：明确版本化且本业务已承诺透传的公开协议可以保留原字段，但必须有契约和兼容说明。

### AURA-BASE-BE-022：能力调用不得绕过 AURA 公开入口

**必要性**：禁止

业务后端使用 AURA 能力时，只能通过对应能力包公开的 API、Starter、SDK、组件服务、事件或配置入口接入。

不得直接依赖能力包内部实现类、内部包结构、内部数据库表、内部缓存键、未公开配置项或未公开消息格式。

**为什么需要**：能力包公开入口是兼容边界，绕过它会把内部实现绑定到业务项目，导致升级和替换不可控。

**正确写法**：通过能力包公开 API、Starter、SDK、组件服务、事件或配置入口接入，并只使用公开模型和公开字段。

**错误写法**：引入能力包内部实现类、读取内部缓存键、查询内部表或复制未公开消息格式。

**判断要点 / 验证方式**：依赖是否落在公开入口；是否存在内部包、内部表、内部缓存或未公开配置的引用；依赖扫描和包访问检查可以提供辅助；人工核对能力包公开文档和版本兼容范围。

### AURA-BASE-BE-023：外部调用失败必须显式处理

**必要性**：必须

后端代码调用外部系统或 AURA 能力时，必须处理失败、超时、拒绝、不可用、版本不兼容和返回不完整等情况。

不得默认外部调用总是成功，也不得在失败后伪造成功继续执行业务流程。是否重试、如何补偿、是否降级，应按公开契约和业务语义决定。

**为什么需要**：外部依赖失败是常态，明确失败结果可以避免数据错误、状态错乱和错误成功提示。

**正确写法**：区分超时、拒绝、不可用、版本不兼容和返回不完整，并根据业务语义决定重试、补偿或降级。

**错误写法**：捕获所有异常后返回默认成功，或外部失败后继续写入“已完成”状态。

**判断要点 / 验证方式**：失败是否可观察、可追踪、可重试；是否存在伪造成功、无限重试或无边界降级；通过超时、拒绝、不可用和异常响应测试失败路径；人工确认重试、补偿、降级和最终状态。

**例外**：明确允许的只读降级必须说明数据时效和一致性影响，不得用于写操作成功判定。

### AURA-BASE-BE-038：依赖调用必须有超时边界

**必要性**：必须

数据库、HTTP、RPC、消息、文件和其他外部资源调用必须有可解释的超时边界。不得使用无限等待，也不得为了掩盖慢调用盲目延长超时时间。

**为什么需要**：没有超时的依赖调用会占用线程、连接和任务资源，最终拖垮整个服务。

**正确写法**：按连接、读取、整体操作和任务级别分别设置超时，并记录超时后的业务结果。

**错误写法**：使用无限等待，或发现外部服务变慢后直接把超时时间改成很大的值。

**判断要点 / 验证方式**：超时是否覆盖所有等待边界；时间是否与业务 SLA、重试和资源容量匹配；使用延迟、无响应和部分响应测试；检查线程、连接和任务是否能在超时后释放。

**例外**：确需长时间执行的异步任务必须脱离同步请求，并提供任务状态和取消边界。

### AURA-BASE-BE-039：重试必须限制次数和范围

**必要性**：必须

需要重试的调用必须明确可重试错误、次数、间隔、总耗时和幂等前提。不得对所有异常无差别重试，也不得在多层调用中重复叠加重试。

**为什么需要**：无边界重试会放大故障、造成重复副作用，并形成调用链级联拥塞。

**正确写法**：只对明确的瞬态错误重试，限制次数和总耗时，并在一层统一控制重试。

**错误写法**：Controller、Service、Client 各重试三次，或对业务校验失败和权限拒绝也重试。

**判断要点 / 验证方式**：检查可重试错误、幂等前提及多层叠加风险；模拟瞬态错误、永久错误和重复副作用，核对重试次数、间隔、总耗时和最终结果。本规则约束已确认可重试的调用如何执行，不替代 `AURA-BASE-BE-024` 对重复副作用、唯一性和最终状态的判断。

**例外**：只读且无副作用的查询可以采用有限重试，但仍需有超时和总次数边界。

**边界说明**：本规则只约束后端调用代码不得无边界重试；异步消费者、消息投递和外部集成的重试策略与最终失败状态遵循 `BASE-10`，异常公开表达遵循 `BASE-09`。

## 二、典型开发场景

以下示例用于说明多条规则如何组合，不构成新的接口契约，也不绑定具体框架、目录名或业务模型。

### 外部服务或能力调用

**适用任务**：外部调用、异步与批处理、后端接口  
**关联规则**：BE-020、BE-021、BE-022、BE-023、BE-038、BE-039、BE-040  
**示例级别**：通用边界示例；具体能力的依赖、配置和公开方法以对应能力包为准

#### 场景目标

查询远端设备在线状态，展示业务用例、适配边界、超时预算、有限重试和外部结果转换。使用 AURA 已公开能力时，按对应能力包提供的入口和契约接入，不从本示例推导能力 API。

#### 输入条件

- 业务用例只依赖项目内的设备状态语义，不依赖远端协议模型；
- 适配器使用项目已确认的远端公开契约；接入 AURA 能力时只使用对应能力包公开入口；
- 连接、读取和整体超时均受项目调用预算约束；
- 本例是只读查询，只对明确的瞬态错误在总预算内有限重试；
- 外部响应和错误必须转换为本业务可理解的结果。

#### 推荐调用结构

```text
QueryDeviceStatusService
  → DeviceStatusPort（项目内业务接口）
    → DeviceStatusAdapter（仅在需要协议适配时设置）
      → 已确认的远端公开契约 / AURA 能力包公开入口
      → 连接、读取、整体超时与有限重试
      → 将远端响应和错误转换为 DeviceStatus 或稳定失败分类
```

#### 正确示例

下列 `DeviceStatusPort`、`RemoteStatusTransport`、结果类型和异常均为业务项目自行定义的示意类型，不是 AURA 框架 API。`RemoteStatusTransport` 的实现只负责接入已核对的远端公开契约，并在该边界配置连接、读取超时及认证；若能力公开入口已完成适配，不必再增加空的 `DeviceStatusAdapter`。

```java
record DeviceStatus(String deviceId, boolean online) {}
record RemoteStatusReply(Boolean online) {}

interface DeviceStatusPort {
    DeviceStatus query(String deviceId);
}

final class QueryDeviceStatusService {
    private final DeviceStatusPort deviceStatusPort;

    QueryDeviceStatusService(DeviceStatusPort deviceStatusPort) {
        this.deviceStatusPort = deviceStatusPort;
    }

    DeviceStatus queryStatus(String deviceId) {
        return deviceStatusPort.query(deviceId);
    }
}

final class DeviceStatusAdapter implements DeviceStatusPort {
    private final RemoteStatusTransport remoteStatusTransport;
    private final ReadOnlyRetryPolicy retryPolicy;

    DeviceStatusAdapter(RemoteStatusTransport transport, ReadOnlyRetryPolicy retryPolicy) {
        this.remoteStatusTransport = transport;
        this.retryPolicy = retryPolicy;
    }

    public DeviceStatus query(String deviceId) {
        // 两次是总尝试次数，包含首次调用；整个过程不得超过三秒。
        RemoteStatusReply reply = retryPolicy.executeReadOnly(
            () -> remoteStatusTransport.query(deviceId, Duration.ofSeconds(1)),
            2, Duration.ofSeconds(3),
            error -> error instanceof RemoteTimeoutException
                || error instanceof RemoteBusyException);

        if (reply == null || reply.online() == null) {
            throw new DependencyContractException("设备状态响应不完整");
        }
        return new DeviceStatus(deviceId, reply.online());
    }
}
```

`retryPolicy` 是项目内策略抽象，必须在总预算内限制每次等待及退避，不代表框架现成方法。远端权限拒绝、参数错误和契约不兼容由适配器转换为稳定失败分类并立即终止；超时或限流仅在只读、预算充足时最多再试一次。若为创建、控制等有副作用操作，先按外部集成规范确认幂等或远端结果，不能照搬此处的只读重试。

#### 错误示例

```java
public Object queryStatus(String deviceId) {
    var client = new InternalStatusClient("http://status-internal:8080");
    try {
        return client.rawQuery(deviceId);
    } catch (Exception ignored) {
        return Map.of("success", true);
    }
}
```

问题：业务代码直接初始化内部客户端、写死内部地址、依赖未公开方法、没有超时边界，并把失败伪造成成功。

#### 验证步骤与预期结果

1. 外部调用成功，预期返回本业务的设备状态模型，不暴露远端原始字段。
2. 外部响应超时，预期在整体超时内结束并返回明确失败结果，且不叠加第二层重试。
3. 外部返回瞬态错误，预期总尝试次数不超过两次；业务失败和永久错误不得重试。
4. 外部返回版本不兼容或字段不完整，预期进入明确不兼容或不可用结果。
5. 扫描依赖和包访问，预期业务层不引用能力内部实现类、内部配置和内部缓存。

#### 人工确认点

- 远端公开契约；使用 AURA 能力时核对对应能力包的入口、模型和兼容版本；
- 连接、读取、整体超时与退避是否都落在业务响应预算内；
- 重试是否具备幂等和副作用安全性；
- 外部失败时业务是拒绝、降级还是进入待处理状态。

反例：在 Controller 中直接调用能力内部类，读取未公开配置，捕获所有异常后返回空结果。

### 跨服务聚合查询

**适用任务**：后端业务用例、外部调用、异常与日志  
**关联规则**：BE-009、BE-011、BE-020、BE-021、BE-023、BE-030、BE-038、BE-039  
**示例级别**：完整示例

#### 场景目标

查询设备总览：设备基础信息必须存在，位置与视频状态属于可降级信息。应用用例明确每个依赖的超时、并发方式和失败语义，再将多个公开 Client 的结果组装为稳定的总览响应；不将下游原始响应、异常和地址直接暴露给调用方。

#### 输入条件

- 设备服务提供设备基础信息，缺失时整个查询不可成立；
- 位置服务和视频服务只补充展示信息，暂时不可用时允许返回“暂不可用”；
- 每个 Client 已封装公开契约、认证上下文、超时和基础错误转换；
- 调用链需要关联 TraceId，并能观察每个依赖的耗时、结果和降级原因；
- 聚合响应需要明确字段可用性，不能以 `null` 或空字符串混淆“无数据”和“依赖失败”。

#### 推荐调用结构

```text
QueryDeviceOverview
  → DeviceOverviewApplicationService
    → DeviceClient（必要依赖）
    → 并行调用 LocationClient、VideoClient（项目内可降级依赖接口）
    → 将客户端结果转换为业务可理解状态
    → 记录依赖耗时、TraceId 和降级原因
    → DeviceOverviewResponse（稳定公开模型）
```

#### 完整正确示例

```java
public DeviceOverviewResponse query(DeviceOverviewQuery query, RequestContext context) {
    var device = deviceClient.getRequired(query.deviceId(), context)
        .orElseThrow(() -> new DeviceNotFoundException(query.deviceId()));

    var locationFuture = asyncExecutor.submit(() -> locationClient.getLatest(device.id(), context));
    var videoFuture = asyncExecutor.submit(() -> videoClient.getAvailability(device.id(), context));

    var location = dependencyResultResolver.optional(
        "location", locationFuture, Duration.ofSeconds(1), context);
    var video = dependencyResultResolver.optional(
        "video", videoFuture, Duration.ofSeconds(1), context);

    return DeviceOverviewResponse.of(
        deviceMapper.toSummary(device),
        locationMapper.toSection(location),
        videoMapper.toSection(video));
}
```

```text
必要依赖失败：设备不存在 / 无权访问 → 返回明确业务错误，不继续调用可选依赖
可选依赖超时：位置服务超时 → location = 暂不可用（TIMEOUT），设备总览仍可返回
可选依赖拒绝：视频服务拒绝 → video = 暂不可用（DEPENDENCY_DENIED），记录关联日志
```

`dependencyResultResolver` 只将超时、拒绝和不可用转换为预定义的业务依赖状态，并记录依赖名、耗时、结果分类与 TraceId；它不吞掉必要依赖失败，也不把异常堆栈、内部地址或下游错误原文带入公开响应。

#### 错误示例

```java
public Map<String, Object> overview(String id) {
    return Map.of(
        "device", deviceClient.rawGet(id),
        "location", locationClient.rawGet(id),
        "video", videoClient.rawGet(id));
}
```

问题：没有区分必要与可选依赖；任何一个下游失败都会以不确定方式中断或伪造空结果；客户端原始模型、错误结构和版本变化直接穿透给调用方；没有超时、调用预算、关联日志和部分失败语义。

#### 验证步骤与预期结果

1. 设备不存在或当前用户无权访问，预期立即返回稳定业务错误，且不调用位置和视频依赖。
2. 位置服务超时、视频服务正常，预期设备与视频信息正常返回，位置区块明确为暂不可用并可通过 TraceId 定位。
3. 两个可选依赖同时失败，预期总览仍返回必要设备信息，两个区块分别表达失败分类，不互相覆盖。
4. 必要设备服务超时或返回异常，预期返回明确失败，不将结果伪装成“设备信息为空”。
5. 检查日志、指标或追踪记录，预期能识别每个依赖的名称、耗时、结果分类和关联 TraceId，且不包含敏感凭据与完整下游响应。
6. 下游响应新增内部字段或错误结构变化，预期公开总览模型保持稳定，转换影响收敛在对应 Client/Mapper。

#### 人工确认点

- 哪些依赖为必要依赖、哪些允许降级，以及降级后页面或调用方应如何提示；
- 单次请求总超时预算、各依赖超时、并发数和重试策略；
- 部分失败是否允许缓存旧值，以及旧值的时效、来源和展示标识；
- 聚合结果的数据一致性要求、数据所有权和公开字段边界；
- 日志、指标和追踪中允许记录的标识、错误分类与敏感信息范围。
