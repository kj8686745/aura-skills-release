**规则域**：`BASE-00`  
**规范对象**：使用 AURA 开展业务应用开发的团队和开发人员  
**文档性质**：面向业务应用开发者的基础规范正文

## 一、这份规范解决什么问题

AURA 基础编码规范规定业务应用项目在工程组织、代码编写、接口对接、配置运行、质量验证和交付过程中必须遵守的共同要求。

它的目标是让不同项目具备一致的工程入口、清晰的代码边界、稳定的对接方式和可复现的交付结果。

这份规范不描述某个具体业务领域的实现方式，也不要求业务项目了解 AURA 内部框架是如何实现的。

## 二、哪些项目适用

以下项目使用 AURA 时适用本规范：

- AURA 前端业务应用；
- AURA 后端业务服务；
- 前后端一体化业务应用；
- 多模块业务应用；
- 使用 AURA 公开能力的业务工具和管理端。

项目同时使用某个 AURA 能力包时，应在遵守本规范的基础上，继续遵守该能力包已发布的使用规范。

## 三、基础规范和能力包的关系

AURA 的使用内容分为两层：

| 层次 | 解决的问题 |
| --- | --- |
| 基础编码规范 | 所有 AURA 业务项目共同遵守的工程和编码底线 |
| 能力包使用规范 | 某一类具体能力如何接入、配置、调用和验证 |

基础编码规范适用于所有项目；能力包使用规范只在项目实际使用对应能力时适用。

能力包可以增加专项要求，但不能降低基础编码规范已经规定的共同要求。

例如：

- 工程目录、命名、分层、接口表达和基础测试属于基础编码规范；
- 物联设备、消息主题、视频播放、模型调用和地图组件属于对应能力包；
- 业务项目不需要为了使用某个能力包而了解该能力的内部实现。

## 四、业务开发者可以依赖什么

业务项目只能依赖 AURA 已公开并且与当前项目版本匹配的内容，包括：

- 已公开的 API；
- 已公开的组件和类型；
- 已公开的 Starter 或接入依赖；
- 已公开的配置项；
- 已公开的事件、数据和错误契约；
- 已公开的示例和使用说明。

业务项目不得把未公开的类、内部包、内部配置、缓存键、拦截器、过滤器或其他实现细节当作依赖依据。

## 五、基础规范覆盖范围

本规范体系覆盖以下共同基础：

1. 工程结构、文件归并和项目文档；
2. 命名、格式和代码表达；
3. 架构分层、依赖方向和模块边界；
4. 后端基础编码；
5. 前端基础编码；
6. API、数据和跨模块契约；
7. 配置、依赖、环境和构建；
8. 安全、身份、权限和敏感信息的通用要求；
9. 异常、日志、审计和可观测性的通用要求；
10. 数据访问、事务和数据生命周期的通用要求；
11. 测试、质量和验证；
12. 版本控制、变更和交付基础。

AI 协作过程与产物采纳要求由 `02-AI开发运用规范` 承载，本基础编码规范不重复定义。

具体能力的业务语义不在本规范展开，由相应能力包说明。

## 六、规则等级

规范正文使用以下等级：

| 等级 | 对业务项目的含义 |
| --- | --- |
| 必须 | 适用项目必须执行 |
| 禁止 | 适用项目不得采用 |
| 应当 | 默认执行；确需偏离时，应说明技术原因和影响 |
| 建议 | 推荐执行，用于提升一致性和可维护性 |
| 可以 | 在满足规定前提下允许采用 |

规则等级表达的是开发要求，不是项目评分或人员考核等级。

每条规则在标题下标出“必要性”，使用上述五级之一。必要性仅在规则适用时生效；“按任务阅读”不等于该规则可选。规则的适用条件和原文位置可从[基础编码规范矩阵](./规范矩阵.md)定位，具体要求仍以规则正文为准。

## 七、默认使用方式

业务项目采用 AURA 时，默认使用当前 AURA 版本中的基础编码规范和项目实际使用的能力包规范。

开发者不需要重复填写或确认已经明确的通用规则。开始开发时，应先确认：

1. 项目属于哪种应用类型；
2. 当前任务涉及哪些基础规范域；
3. 项目实际使用哪些 AURA 能力包；
4. 当前项目和能力包的版本是否匹配；
5. 是否存在规范未覆盖的技术组合或明确偏离。

如果项目不采用 AURA 默认方式、修改公开契约、使用未覆盖的技术组合或需要偏离明确规则，应在项目技术方案中说明影响、替代方案和验证方式。

## 八、项目使用规范的基本要求

业务项目在开发过程中应做到：

- 按基础规范组织工程和代码；
- 按能力包公开说明进行接入；
- 使用与项目版本匹配的公开 API、组件、配置和示例；
- 对正常、异常和边界行为进行验证；
- 保持代码、接口、配置、文档和测试的一致；
- 记录影响后续使用和升级的公开变更。

## 九、阅读顺序

业务开发者按照以下顺序使用 AURA 基础规范：

```text
确认项目适用范围
  → 阅读工程结构和命名要求
  → 阅读前端或后端基础编码要求
  → 阅读接口、配置、安全和测试要求
  → 按实际使用情况阅读能力包规范
  → 按示例和验证要求完成开发与交付
```

## 十、正例与反例

### 正例：按任务加载规范

新增后端设备查询时，先阅读工程结构、架构分层、后端基础编码和接口规范；如果使用视频或消息能力，再按实际接入的能力包加载对应使用规范。

### 反例：无差别加载或依赖内部实现

把整个规范库和所有能力包一次性提供给开发者，或者直接依赖未公开的内部类、缓存键和配置名，都会造成边界混乱和版本不可控。

### 正例：保持契约同步

接口字段发生变化时，同步更新实现、接口文档、示例和测试，并说明兼容方式。

### 反例：只改代码不改契约

代码已经改变请求字段和响应结构，但仍保留旧文档和旧测试，让调用方依据过期信息开发。

## 十一、总则规则

### AURA-BASE-GEN-001：适用的 AURA 业务项目必须遵守基础编码规范

**必要性**：必须

**为什么需要**：统一适用范围，避免项目在工程、接口和交付边界上自行解释规范是否生效。

属于 AURA 业务应用、服务、工具或平台工程的项目，必须按本基础编码规范组织工程、代码、接口、配置和交付。

**正确写法**：项目入口明确适用的 AURA 版本，并按基础规范加载工程、命名、分层和接口要求。

**错误写法**：项目使用 AURA 公开能力，却以项目自定义方式绕过基础工程和接口约束。

**判断要点 / 验证方式**：检查项目类型、AURA 依赖和入口文档，确认适用项目已关联基础规范。

### AURA-BASE-GEN-002：使用能力包时必须同时遵守对应的公开使用规范

**必要性**：必须

**为什么需要**：能力包具有专项约束，只有与基础规范一起使用，才能保证通用工程要求和专项能力要求不互相遗漏。

项目实际接入物联、消息、视频、模型、地图等能力时，必须按对应能力包的公开使用规范开发和验证。

**正确写法**：只加载项目实际使用的能力包规范，并按其中的公开 API、配置和示例接入。

**错误写法**：接入能力包后直接阅读或依赖其内部实现，或把未使用的全部能力包混入项目规范。

**判断要点 / 验证方式**：检查依赖、调用、配置和任务路由，确认能力包识别完整且与实际使用一致。

### AURA-BASE-GEN-003：业务项目禁止依赖未公开的 AURA 内部实现

**必要性**：禁止

**为什么需要**：限制依赖公开契约可以避免内部改造直接破坏业务项目，并让升级和问题定位有稳定依据。

业务项目只能依赖已经公开、版本化并有使用说明的 API、组件、配置、事件和类型。

**正确写法**：通过公开客户端、公开组件和公开配置接入框架能力。

**错误写法**：直接引用内部包、缓存键、拦截器、过滤器或未公开配置名。

**判断要点 / 验证方式**：扫描依赖和代码引用，核对公开契约清单，确认没有内部实现依赖。

### AURA-BASE-GEN-004：能力包专项要求不得降低基础编码规范共同要求

**必要性**：禁止

**为什么需要**：能力包只能补充领域要求，不能让设备、消息或模型场景绕过基础的接口、安全、数据和交付约束。

能力包可以增加领域要求，但不得以专项能力为理由降低工程、接口、安全、数据和交付的基础要求。

**正确写法**：能力包专属调用同时遵守基础接口、异常、权限和日志规则。

**错误写法**：因为是设备或视频能力，就跳过权限校验、错误契约或敏感信息处理。

**判断要点 / 验证方式**：对照基础规则和能力包规则，确认专项规则没有覆盖或削弱基础要求。

### AURA-BASE-GEN-005：业务项目必须使用版本匹配的公开能力和契约

**必要性**：必须

**为什么需要**：版本匹配是保证接口、客户端和运行行为一致的前提，避免“能够编译但运行不兼容”。

项目、AURA 基础规范、能力包、客户端和公开契约必须处于兼容版本组合。

**正确写法**：在项目入口登记框架、能力包和公开契约版本，并按兼容矩阵选择依赖。

**错误写法**：混用不同版本的客户端和服务端，仅凭本地能够编译判断兼容。

**判断要点 / 验证方式**：检查版本登记、依赖锁定、构建结果和关键接口联调结果。

### AURA-BASE-GEN-006：修改公开契约或偏离明确规则时应说明影响和验证方式

**必要性**：应当

**为什么需要**：公开行为变化会影响多个调用方，提前说明影响和验证方式可以减少隐式破坏和无法恢复的变更。

修改公开 API、配置、事件、组件或偏离已适用规则时，应按实际影响说明受影响范围、替代或迁移方式、兼容处理及已执行的验证；已有专项强制规则的，仍按其要求执行。

**正确写法**：接口字段变更同步更新实现、文档、示例、测试和迁移说明。

**错误写法**：只改代码，要求调用方自行适应变化，也不记录兼容影响。

**判断要点 / 验证方式**：检查变更说明、受影响调用方、兼容验证和回退方式。

### AURA-BASE-GEN-007：代码、接口、配置、文档和测试应保持一致

**必要性**：应当

**为什么需要**：只有所有事实来源同步，开发者和维护者才能依据同一版本理解、使用和验证系统行为。

一次研发变更涉及的代码、接口契约、配置、示例、文档和测试应保持同步，不应保留相互矛盾的事实源；主文档与示例、入口的更新分别按 `AURA-BASE-DOC-006` 和 `AURA-BASE-DOC-019` 执行。

**正确写法**：提交前按变更清单核对实现、契约、配置、文档和测试，并执行对应验证。

**错误写法**：代码已经修改，但接口文档、示例或测试仍描述旧行为。

**判断要点 / 验证方式**：按规则 ID 检查变更关联文件，执行构建、接口测试和文档链接检查。
