## 一、数据访问、事务与数据生命周期

### 1. 数据访问与模型

### AURA-BASE-DATA-001：数据访问必须经过明确边界

**必要性**：必须

业务用例通过 Repository、Mapper 或公开数据客户端访问数据，禁止在 Controller、页面、公共工具或跨模块代码中直接操作数据库连接和内部表。

**为什么需要**：统一数据访问入口，避免协议层和跨模块代码绑定数据库实现。

**正确写法**：

```java
Device device = deviceRepository.findById(deviceId).orElseThrow();
```

**错误写法**：

```java
Connection connection = dataSource.getConnection();
return connection.prepareStatement("select * from device where id=?");
```

**判断要点 / 验证方式**：检查 Controller、页面和公共工具是否直接获取连接或访问内部表，确认调用经过 Repository、Mapper 或公开客户端。

### AURA-BASE-DATA-002：数据模型必须表达所有权和用途

**必要性**：必须

实体、查询模型、命令模型、响应模型和报表模型应按用途定义。跨模块不得无条件复用对方 Entity 或内部字段。

**为什么需要**：隔离持久化结构与公开契约，避免一个模块的字段变化扩散到调用方。

**正确写法**：`DeviceQuery`、`DeviceEntity` 和 `DeviceResponse` 分别用于查询、持久化和响应。

**错误写法**：跨模块直接把 `DeviceEntity` 作为接口响应返回。

**判断要点 / 验证方式**：检查模型命名、引用方向和跨模块字段依赖，确认每个模型都有明确用途。

### AURA-BASE-DATA-003：查询必须有规模和排序边界

**必要性**：必须

列表、导出和批量查询必须限制页大小或批次，排序字段使用白名单，结果顺序需要稳定。不得默认把全表读入内存。

**为什么需要**：控制查询资源和结果稳定性，避免数据量增长导致超时、内存溢出或排序注入。

**正确写法**：分页查询设置业务允许的最大页大小，排序字段通过白名单映射；按创建时间分页时再追加唯一标识作为同时间记录的稳定次序。导出按固定批次或游标读取，不一次载入全表。

**错误写法**：调用 `selectAll()` 后在内存排序，直接拼接请求中的 `sort` 字段。

**判断要点 / 验证方式**：使用超大页、非法排序和大数据夹具验证是否拒绝或受控。

**边界说明**：本规则约束数据访问层必须保证查询规模、排序和结果稳定；接口参数和公开响应边界遵循 `BASE-05`，后端查询方法的职责落点遵循 `BASE-03`。

### AURA-BASE-DATA-004：写入必须表达业务结果

**必要性**：必须

新增、更新、删除和状态变更必须根据实际影响行数、版本条件和业务状态返回真实结果，不得无条件返回成功。

**为什么需要**：让调用方能够区分成功、对象不存在、并发冲突和重复提交。

**正确写法**：条件更新影响行数为 0 时返回版本冲突或对象不存在。

**错误写法**：无论影响行数是否为 0 都返回“操作成功”。

**判断要点 / 验证方式**：模拟对象不存在、版本冲突和重复提交，检查响应及业务状态。

### 2. 事务与一致性

### AURA-BASE-DATA-005：事务边界应覆盖本地一致性用例

**必要性**：应当

事务应由应用用例控制，覆盖必须一起成功或失败的本地数据变更。事务内不得长时间等待外部网络、文件处理或人工操作。

**为什么需要**：确保本地数据原子性，同时避免事务长时间占用连接和锁。


**正确写法**：审核状态和审核记录在同一应用用例事务内提交。

**错误写法**：在 Controller 事务中等待远程服务和文件处理完成。

**判断要点 / 验证方式**：注入中途失败，确认本地变更整体回滚且事务内无外部长等待。

**边界说明**：本规则约束本地数据变更的原子性和外部副作用边界；事务代码应放在业务用例的具体位置由 `BASE-03` 的 `BE-010` 规定。

### AURA-BASE-DATA-006：外部副作用不得伪装成本地事务

**必要性**：禁止

数据库事务不能自动回滚已经发送的消息、调用的外部服务或写出的文件。需要通过事件、状态记录、补偿或幂等策略衔接。

**为什么需要**：明确本地事务与外部副作用的边界，避免出现“本地回滚但外部已成功”。

**正确写法**：需要保证外部操作最终执行时，在同一本地事务内保存业务状态和待执行记录；事务提交后由任务或消息投递程序读取记录、重试并使用幂等键防重。若外部操作失败，保留可查询的失败状态和补偿路径。

**错误写法**：数据库事务内调用远程服务并假定回滚能够撤销远程副作用。

**判断要点 / 验证方式**：分别模拟本地提交失败、提交成功但投递失败、外部成功但回执丢失，检查待执行记录、幂等重试、补偿和最终状态；单纯“提交后调用一次”不能证明消息不会丢失。

### AURA-BASE-DATA-007：并发写入必须有一致性策略

**必要性**：必须

并发修改根据业务选择版本号、唯一约束、条件更新、锁或串行化策略，并明确冲突时的结果。不能只依赖前端按钮禁用。

**为什么需要**：防止并发覆盖和重复操作造成数据错误。

**正确写法**：更新使用 `version` 条件，冲突时返回明确的并发修改结果。

**错误写法**：先查询再无条件更新，仅依靠前端禁用按钮防重复。

**边界说明**：本规则约束数据库写入的一致性机制；接口层如何公开冲突响应遵循 `BASE-05`，后端用例如何组织冲突处理遵循 `BASE-03`。

**判断要点 / 验证方式**：并发提交同一版本的两个请求，确认只有一个成功且冲突可见。

### AURA-BASE-DATA-008：删除必须说明语义

**必要性**：必须

删除、作废、停用和归档必须区分。涉及审计、恢复或关联数据时，应按业务保留要求选择状态、软删除或物理删除，并说明默认查询和恢复行为。

**为什么需要**：避免误删、无法恢复和关联数据失去解释。

**正确写法**：需要恢复的设备使用 `archived` 状态区分归档，默认查询排除归档并提供受控恢复入口；明确无需保留的临时数据按期限物理清理。

**错误写法**：直接物理删除且未说明关联数据和审计影响。

**判断要点 / 验证方式**：验证默认查询、恢复、关联记录和审计结果。

### 3. 缓存与数据同步

### AURA-BASE-DATA-009：缓存只能作为明确的加速边界

**必要性**：必须

用于加速持久数据读取的缓存必须说明键、事实来源、有效期、失效、回源和不可用时的处理方式；不得把这类缓存当作唯一事实来源。独立的短期状态存储应按其实际数据责任设计，不套用“可丢失的查询缓存”语义。

**为什么需要**：保证缓存只是可控的加速边界，不把临时数据误当作业务事实。

**正确写法**：在缓存适配器中集中定义键、来源、TTL 和失效规则；读取缓存失败时按业务允许的方式回源或明确失败。

**错误写法**：多个业务方法自行拼接缓存键并把缓存当作唯一数据来源。

**判断要点 / 验证方式**：清空缓存、缓存服务不可用和过期后检查回源与降级。

### AURA-BASE-DATA-010：缓存更新必须考虑一致性窗口

**必要性**：必须

写入、删除和状态变更后必须说明缓存刷新、失效或延迟同步策略。不能只更新数据库却假定所有缓存立即一致。

**为什么需要**：控制数据库与缓存之间的可见性差异和一致性窗口。

**正确写法**：数据库提交后删除旧缓存，读取 miss 时回源并重建；失效失败时记录并重试，或由受控的过期时间限制旧值可见窗口。

**错误写法**：只更新数据库却假定所有缓存立即一致。

**判断要点 / 验证方式**：在写入、提交失败、失效失败和并发读取场景检查可见性窗口，确认回源和失败处置符合约定。

### 4. 生命周期与数据责任

### AURA-BASE-DATA-011：数据必须有生命周期

**必要性**：必须

数据应说明创建、使用、更新、归档、恢复和删除阶段。临时数据、任务数据和导入文件不得无限期保留。


**为什么需要**：防止临时数据无限增长，并让恢复和清理行为可预期。

**正确写法**：导入文件和失败任务分别约定保留期限、查询方式与到期清理动作；需要恢复的数据同时约定恢复期限。

**错误写法**：临时文件和任务记录永久保留，没有清理任务或期限。

**判断要点 / 验证方式**：检查生命周期字段、清理任务、恢复入口和到期行为。

### AURA-BASE-DATA-012：敏感和审计数据必须按用途保留

**必要性**：必须

敏感数据、审计数据和业务主数据的保留期限、访问范围和删除方式必须分别定义，不得用一个默认清理策略覆盖所有数据。

**为什么需要**：让数据保留与业务用途、审计责任和敏感等级相匹配。

**正确写法**：审计记录按审计期限保留，敏感字段按用途最小化并到期删除。

**错误写法**：所有数据使用同一永久保留策略，敏感字段和审计数据不区分。

**判断要点 / 验证方式**：核对保留配置、访问权限、脱敏和到期删除结果。

### AURA-BASE-DATA-013：跨模块数据必须有事实来源

**必要性**：必须

每个共享字段、状态和统计结果必须明确事实来源、同步方式和冲突处理。下游不得通过读取上游内部表来替代公开契约。

**为什么需要**：避免多个模块各自解释同一状态，形成不可收敛的数据事实。

**正确写法**：设备状态以设备服务为事实源，下游通过公开查询或事件同步。

**错误写法**：报表模块直接读取设备模块内部表并自行解释状态值。

**判断要点 / 验证方式**：检查契约、同步路径、冲突策略和事实源唯一性。

### AURA-BASE-DATA-014：数据迁移必须可验证并具备恢复路径

**必要性**：必须

字段、表、索引或数据格式变更必须说明适用的兼容读写、迁移步骤、校验口径和失败处置。恢复路径应依据历史数据和版本并存情况选择旧结构保留、前向修复、补偿或受控数据恢复等可行方式；不能安全反向迁移时，不得把反向脚本或重部署旧代码当作恢复保证。不可逆变更应先完成适用的备份和恢复验证。未完成验证不得删除仍被使用的旧数据结构。

**为什么需要**：保证数据结构变更可验证、可恢复，并支持按实际消费者分阶段切换。

**正确写法**：先增加新字段并兼容读取旧值，按批迁移并核对数量与关键值；切换写入前验证适用的恢复路径，确认旧实例、消费者和恢复窗口均已结束后再清理旧字段。

**错误写法**：直接删除旧字段并在未验证数据完整性前发布。

**判断要点 / 验证方式**：执行样例迁移，核对数量、关键值和消费者读取结果；验证所选恢复路径，并按 `AURA-BASE-VC-014` 判断是否需要可控环境演练。

### AURA-BASE-DATA-015：表结构与数据库约束必须承载关键数据不变量

**必要性**：必须

新增或变更表结构时，字段类型、精度、可空性、唯一性、外键或等效关联约束应与业务数据含义一致。对必须由数据库保证的唯一键和非空字段，不得仅依赖页面或先查后写校验；索引应依据实际过滤、关联和排序查询设计，避免为每个字段盲目建索引。

**为什么需要**：应用层校验无法阻止并发写入或其他入口写入错误数据，不合理的索引又会增加写入和维护成本。

**正确写法**：业务编号由唯一约束兜底，必填字段设置非空约束；根据高频查询的过滤条件和排序设计索引，并确认写入成本可接受。

**错误写法**：创建业务编号时只先查询“是否存在”，表中没有唯一约束；为所有字段各建一个索引而不检查查询路径。

**判断要点 / 验证方式**：核对表结构与模型约束；并发插入相同业务编号，确认数据库约束生效；用实际查询条件核对执行计划、索引使用与查询成本。

### AURA-BASE-DATA-016：SQL 查询必须参数化并验证数据规模

**必要性**：必须

SQL 值参数使用绑定参数；无法参数化的表名、列名和排序方向只能从受控映射中选择，不得直接拼接外部输入。复杂查询、分页、聚合和批量写入应按实际数据量检查执行计划、扫描范围、锁范围及超时边界。

**为什么需要**：外部输入拼接会造成注入风险；只在少量测试数据上运行正常，不能说明真实数据规模下的查询成本可控。

**正确写法**：按业务查询字段构造参数化条件，排序键由白名单映射到受控列；对高频慢查询使用代表性数据检查执行计划后调整索引或查询方式。

**错误写法**：把请求中的 `name` 或 `sort` 直接拼进 SQL；在大表上无过滤地查询全部记录，再由应用内存分页。

**判断要点 / 验证方式**：检查 SQL 构造与参数绑定；输入引号、非法排序字段和大数据量查询，核对拒绝结果、执行计划及资源占用。

## 二、典型使用示例：设备审核与异步通知

**场景目标**：用户审核设备时，在服务端完成租户范围查询、版本条件更新、审核记录写入和待通知记录写入；事务提交后再投递通知，缓存只作为可失效的加速边界。

**输入条件**：请求只携带 `deviceId`、审核结果和业务说明；当前用户与租户来自受信任上下文；设备记录包含 `version` 和状态字段；通知服务可能暂时不可用；设备详情存在查询缓存。

**正确调用链**：

```text
Controller 解析审核命令
  → 应用用例按可信租户查询设备
  → Repository 按 deviceId、tenantId、version 条件更新
  → 同一事务写入审核记录和待通知记录
  → 提交成功后由投递任务按幂等键发送通知
  → 失效设备缓存并按需回源
  → 返回实际更新结果和可查询的通知状态
```

事务只覆盖设备状态、审核记录和待通知记录等本地变更，不在事务中等待通知服务或执行文件处理。条件更新影响行数为 0 时返回对象不存在或并发冲突；通知发送失败保留待处理状态并按幂等键重试，不能把本地回滚当成远程撤销。缓存失效失败时记录并重试，不能把缓存当作设备状态的唯一事实源。

**错误调用链**：先查询设备再无条件更新；只依据前端按钮禁用防止重复审核；事务内同步调用通知服务；通知失败后仍返回“已通知”；只更新数据库却假定缓存立即一致。

**验证步骤与预期结果**：

1. 两个请求使用同一 `version` 并发审核，预期只有一个成功，另一个得到明确的并发冲突结果。
2. 模拟本地提交失败、提交成功但通知投递失败、通知成功但回执丢失，预期本地状态、待通知记录、幂等重试和最终状态均可查询。
3. 使用其他租户设备、无权限设备和不存在的设备 ID，预期查询、更新和审计路径都执行同一数据范围约束。
4. 清空缓存、使缓存不可用或让失效操作失败，预期按约定回源或进入可观察的失败处置，不改变数据库事实。

## 三、典型使用示例：历史字段迁移与生命周期清理

**场景目标**：为设备表增加归档时间和导入文件关联字段，在仍有旧实例和历史数据时完成兼容迁移，并对临时导入文件和失败任务执行有期限的清理。

**正确迁移链**：

```text
增加可空新字段和必要索引
  → 旧代码仍可读写旧字段
  → 新代码兼容读取旧值并双写或按批补齐
  → 校验记录数量、关键值、索引和消费者读取结果
  → 切换默认读取新字段
  → 观察旧消费者和恢复窗口
  → 完成备份/恢复验证后再清理旧字段
  → 按保留期限清理临时文件和失败任务
```

首次定义且没有旧数据或旧消费者的字段，不虚构兼容对象；已经存在历史数据时必须记录迁移批次、校验口径和失败处置。临时文件、成功任务和失败任务分别定义保留期限、查询方式和清理动作；清理任务按批处理并可重复执行，不能用一次无限事务删除全部数据。

**错误迁移链**：直接删除旧字段并发布新代码；未校验历史数据就声明迁移完成；把所有任务和文件永久保留；清理任务一次读入全部记录并在单个长事务中删除。

**验证步骤与预期结果**：

1. 使用代表性旧数据执行迁移，核对总数、关键字段、空值和关联文件数量。
2. 在新旧代码并存期间分别读取和写入，预期双方都能按兼容契约处理。
3. 中途停止迁移，预期可从已记录批次继续或按已选恢复路径恢复，不产生无法解释的半迁移状态。
4. 到达保留期限后执行清理，预期只清理到期且未被保护的数据，保留审计数据和仍可恢复的数据。

### 5. 开发者自检

- 数据访问是否经过明确边界；
- 查询、导出和批处理是否有规模、排序和进度边界；
- 事务是否只覆盖本地一致性；
- 外部副作用是否有事件、补偿或幂等策略；
- 并发写入、删除和归档语义是否明确；
- 缓存是否有失效、回源和一致性策略；
- 数据生命周期、保留期限和迁移回退是否可验证。
- 表结构、数据库约束和索引是否与数据含义及实际查询相符；SQL 值是否参数化，动态标识符是否受控。
