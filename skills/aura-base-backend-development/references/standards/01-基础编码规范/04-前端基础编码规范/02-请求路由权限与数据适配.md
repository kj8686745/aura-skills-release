## 一、请求、路由和权限



### AURA-BASE-FE-006：请求集中封装

**必要性**：必须

API 地址、请求方法、参数转换、响应转换和错误处理应在可发现的请求封装中维护。页面不得散落内部服务地址、重复 Axios 配置或直接依赖底层响应结构。

**为什么需要**：集中封装请求可以稳定接口入口、统一错误处理，并阻断服务地址和底层响应结构向页面扩散。

**正确写法**：

```ts
// views/device/api/deviceApi.ts
import { request } from '@/services/request'
import { devicePageAdapter } from '../adapters/device-page-adapter'
import type { DeviceQuery, DevicePage, DevicePageResponse } from '../model/device'

export async function queryDevices(query: DeviceQuery): Promise<DevicePage> {
  const response = await request.get<DevicePageResponse>('/devices', { params: query })
  return devicePageAdapter.fromResponse(response)
}
```

页面只调用 `queryDevices`，不拼接内部地址、不创建请求客户端，也不直接访问原始响应包装结构。

**错误写法**：

```ts
axios.get(`http://internal-device:8080/api/devices?sort=${sort}`)
  .then(response => response.data.data)
```

**判断要点 / 验证方式**：服务地址、认证、拦截器、参数和响应转换是否集中；页面是否直接依赖底层 HTTP 响应；搜索页面组件中的请求客户端、内部地址和原始响应字段；人工确认领域 API 的输入输出类型是否稳定。

**例外**：本地开发探针可以调用固定测试地址，但不得进入业务页面和生产构建。



### AURA-BASE-FE-007：前端权限不是后端授权

**必要性**：必须

菜单、路由、按钮和页面隐藏只能控制展示和交互，不能替代后端接口和数据权限校验。前端不得根据按钮可见性推断操作必然成功。

**为什么需要**：前端控制只影响用户界面，无法阻止绕过页面直接调用接口；真正的授权和数据范围必须由后端保障。

**正确写法**：前端根据菜单和按钮权限决定是否展示入口；提交后仍按后端返回的权限、数据范围或业务失败结果处理。

**错误写法**：因为按钮不可见就认为接口不需要后端鉴权，或后端拒绝后仍提示操作成功。

**判断要点 / 验证方式**：页面是否把前端可见性当作授权依据；后端拒绝、无权限和数据范围不足是否有真实反馈；使用无按钮权限、直接访问路由和直接调用接口等场景进行联调；人工确认前后端职责边界。

**例外**：纯展示性开关可以只在前端控制，但不得影响任何写操作和敏感数据访问判断。



### AURA-BASE-FE-008：路由来源明确

**必要性**：必须

前端固定路由、后端菜单路由或模块联邦路由必须明确项目采用的模式。不得在同一应用中无说明地混用多套路由来源，造成登录、菜单、权限和刷新行为不一致。

**为什么需要**：路由来源不清会使菜单、权限、刷新恢复和模块加载出现不可预测的差异。

**正确写法**：

```text
固定系统页 → 静态路由
业务菜单页 → 后端菜单路由
独立远程模块 → 模块联邦路由入口
```

每一种来源明确注册时机、权限依据、刷新恢复策略和错误页面处理方式。

**错误写法**：同一业务页既在静态路由注册，又由后端菜单动态注入；远程模块直接修改宿主内部路由而没有公开入口。

**判断要点 / 验证方式**：每条路由能否说明来源、注册时机、权限依据和刷新恢复方式；是否存在重复注册和无来源路由；检查首次登录、菜单切换、直接刷新、无权限访问和远程模块加载结果；人工确认路由模式与项目架构一致。

**例外**：临时演示页面可以使用静态路由，但不得伪装成正式菜单或绕过项目既有路由治理。

## 二、接口模型与 Mock

### AURA-BASE-FE-010：接口数据必须经过领域适配

**必要性**：必须

接口响应进入前端领域代码时，必须转换为业务项目定义的领域类型，统一处理公开字段、枚举、空值和错误语义；不得把后端内部对象、数据库字段、未公开响应字段或第三方原始响应当作领域模型。领域模型到页面展示模型的边界另按 `AURA-BASE-FE-012` 处理。

**为什么需要**：接口字段和外部协议变化不应扩散到各个页面，领域适配提供统一的语义入口。

**正确写法**：

```ts
type DeviceResponse = { id: string; online: number; lastSeenAt?: string }
type Device = { id: string; onlineState: 'online' | 'offline' | 'unknown'; lastSeenAt?: string }

const toDevice = (source: DeviceResponse): Device => ({
  id: source.id,
  onlineState: source.online === 1 ? 'online' : source.online === 0 ? 'offline' : 'unknown',
  lastSeenAt: source.lastSeenAt,
})
```

**错误写法**：领域 API 直接返回原始 HTTP 响应，调用方自行读取包装字段、猜测枚举值或处理供应商错误码。

**判断要点 / 验证方式**：检查领域 API 是否返回稳定领域类型，字段、枚举、空值和错误是否集中转换；用接口字段变化及未知枚举值验证适配边界。

**例外**：接口公开模型与领域语义完全一致时可以不建立单独转换文件，但仍须由领域 API 明确输出类型与错误语义。



### AURA-BASE-FE-011：Mock 有明确边界

**必要性**：必须

Mock 只能支持页面开发、演示或局部联调，不得作为真实接口契约、权限证据、数据范围证据和生产验收证据。Mock 路径和真实路径必须可区分。

**为什么需要**：Mock 可以提升前端开发效率，但它不能证明真实服务、授权、数据范围和异常行为已经可用。

**正确写法**：

```text
mock/device.ts      → 本地开发或演示数据
views/device/api → 真实请求封装
环境开关            → 明确选择 mock 或真实接口
测试报告            → 分别记录 Mock 结果与真实联调结果
```

**错误写法**：页面默认始终读取 Mock 数据，或将 Mock 成功截图标记为真实接口和权限验证通过。

**判断要点 / 验证方式**：Mock 与真实路径是否能明确区分；验收证据是否说明真实接口、真实权限和真实环境状态；在 Mock 与真实环境分别执行页面流程；检查构建配置和报告是否正确标识数据来源。

**例外**：后端尚未提供接口时可以持续使用 Mock 开发，但相关集成验证必须标记为未完成或环境阻断。



### AURA-BASE-FE-012：页面展示模型与领域模型分离

**必要性**：必须

页面组件应从稳定领域模型得到页面所需的展示字段、格式和交互状态，不得把展示文本、组件临时状态或页面默认值写回领域模型，也不得直接使用原始接口响应。简单页面可以在组件边界完成少量展示转换，不要求每个页面建立 Presenter 文件。

**为什么需要**：展示格式随页面变化，而领域语义应保持稳定；混用模型会让页面展示需求反向污染领域数据。

**正确写法**：领域 API 返回 `Device.onlineState: 'online' | 'offline' | 'unknown'`；页面 Presenter 将其映射为“在线/离线/未知”文本，页面只处理展示和交互。

**错误写法**：为了表格显示，把“在线”文本写进共享的 `Device.onlineState` 字段，其他页面再依赖这段文本判断业务状态。

**判断要点 / 验证方式**：检查展示转换是否局限于页面边界，领域类型是否仍表达业务语义；切换展示语言或页面格式时确认领域模型和请求封装不随之改变。

**例外**：字段含义和展示形式一致的简单只读页面可直接使用领域字段，但不得因此跳过 `AURA-BASE-FE-010` 的接口适配边界。

## 三、典型开发场景示例

### 路由、菜单与前后端权限边界

**适用任务**：前端路由权限、前端页面  
**关联规则**：FE-007、FE-008  
**示例级别**：完整示例

#### 场景目标

为“设备分组管理”建立清晰的路由和菜单入口，并在页面中按已获得的前端权限信息控制操作入口。前端负责可见性与交互体验，后端仍是接口操作和数据范围的最终授权方。

#### 输入条件

- 当前应用已明确采用一种路由来源：固定路由、菜单下发路由或模块路由；
- 登录后的用户上下文可提供页面访问标识和按钮操作标识；
- “创建设备分组”接口由后端校验操作权限和数据范围；
- 页面需要在无页面访问权时阻止进入，并在无创建权限时隐藏或禁用创建入口。
- 项目已有 `Forbidden` 路由、已初始化的权限 Store，以及设备分组创建页；这里仅展示路由和入口的权限接线。

#### 推荐结构

```text
app/router/device-group-routes.ts          明确声明本领域路由来源与页面入口
stores/permission.ts                    读取已初始化的前端权限上下文
views/device-group/DeviceGroupListPage.vue  页面访问与操作入口呈现
views/device-group/api/...          不依赖前端按钮状态，正常调用后端公开接口
```

#### 完整正确示例

```ts
// app/router/device-group-routes.ts：固定路由模式示例
export const deviceGroupRoutes = [
  {
    path: '/device-groups',
    name: 'DeviceGroupList',
    component: () => import('@/views/device-group/DeviceGroupListPage.vue'),
    meta: { pagePermission: 'device-group:read' },
  },
  {
    path: '/device-groups/new',
    name: 'DeviceGroupCreate',
    component: () => import('@/views/device-group/DeviceGroupCreatePage.vue'),
    meta: { pagePermission: 'device-group:create' },
  },
]
```

```ts
// app/router/guard.ts：前端页面访问控制
import type { Router } from 'vue-router'
import { usePermissionStore } from '@/stores/permission'

export function installPermissionGuard(router: Router) {
  router.beforeEach((to) => {
    const permission = to.meta.pagePermission as string | undefined
    if (permission && !usePermissionStore().has(permission)) {
      return { name: 'Forbidden' }
    }
    return true
  })
}
```

```vue
<!-- views/device-group/DeviceGroupListPage.vue -->
<script setup lang="ts">
import { computed } from 'vue'
import { usePermissionStore } from '@/stores/permission'

const permissionStore = usePermissionStore()
const canCreate = computed(() => permissionStore.has('device-group:create'))
</script>

<template>
  <main>
    <h1>设备分组</h1>
    <RouterLink v-if="canCreate" :to="{ name: 'DeviceGroupCreate' }">新建设备分组</RouterLink>
    <!-- 列表查询与展示属于本页面的业务实现，不作为权限判断依据。 -->
  </main>
</template>
```

页面路由来源在路由模块中明确；守卫只处理前端页面访问体验；按钮是否显示由同一前端权限上下文决定。即使用户通过地址栏进入或伪造前端权限状态，后端仍必须独立拒绝未授权的创建请求。

#### 错误示例

```vue
<script setup lang="ts">
const canCreate = route.query.admin === 'true'
async function create() {
  if (!canCreate) return
  await createDeviceGroup(form)
}
</script>
```

问题：权限依据来自可伪造的 URL 参数；页面按钮逻辑与路由入口没有统一来源；代码将“不显示按钮”误当成“接口已授权”。如果后端未独立校验，用户可绕过页面直接发起写操作。

#### 验证步骤与预期结果

1. 无页面访问标识进入路由，预期前端进入无权限页或既定替代入口。
2. 有页面访问权、无创建操作标识，预期可查看列表但不显示创建入口。
3. 修改前端状态或直接构造创建请求，预期后端仍按自身权限与数据范围拒绝未授权操作。
4. 刷新页面和重新登录，预期路由来源、菜单展示和权限上下文恢复逻辑一致。
5. 新增本领域页面时，预期在同一既定路由来源中登记，不混入第二套未说明的动态或固定路由机制。

#### 人工确认点

- 当前项目采用的路由来源及其初始化时机；
- 页面访问、菜单可见、按钮操作与后端权限标识之间的对应关系；
- 无权限时应跳转、隐藏还是展示受限说明；
- 后端接口是否已对操作权限、租户和数据范围完成独立校验。

### Mock 与真实联调切换

**适用任务**：前端请求、前端测试交付、前端页面  
**关联规则**：FE-005、FE-006、FE-010、FE-011  
**跨分类规则**：FE-005 见[工程组织与页面状态](./01-工程组织与页面状态.md)。  
**示例级别**：完整示例

#### 场景目标

在后端接口尚不可用时，用 Mock 支持页面开发；接口具备联调条件后，使用相同的领域 API 切换到真实服务验证。页面不感知 Mock 地址或真实地址，也不得以 Mock 成功代替接口、权限和异常链路的验证。

#### 输入条件

- 设备分组列表页面已通过领域 API 请求数据；
- Mock 只用于本地开发或明确的演示环境；
- 真实接口可用后，需要验证字段、空值、错误码、权限和数据范围；
- 切换方式必须在统一请求入口或开发代理中可追溯，不能散落在页面判断中。

#### 推荐结构

```text
services/request/                 唯一请求入口，读取当前运行环境配置
views/device-group/api/      始终调用稳定领域 API
services/request/mocks/mock-request.ts            仅提供本地开发所需的受控模拟响应
.env.development.mock           明确声明本地 Mock 开关
.env.development                明确声明真实联调地址或代理配置
```

#### 完整正确示例

```ts
// services/request/runtime-config.ts
export const runtimeConfig = {
  useMock: import.meta.env.DEV && import.meta.env.VITE_API_MODE === 'mock',
}
```

```ts
// services/request/index.ts
import { runtimeConfig } from './runtime-config'
import { httpRequest } from './http-request'

export const request = {
  async get<T>(path: string, options?: unknown): Promise<T> {
    if (runtimeConfig.useMock) {
      const { mockRequest } = await import('./mocks/mock-request')
      return mockRequest.get<T>(path, options)
    }
    return httpRequest.get<T>(path, options)
  },
}
```

```ts
// views/device-group/api/device-group-api.ts：页面和 Mock/真实环境共用
import { request } from '@/services/request'
import type { DeviceGroupListResult } from '../model/device-group-model'

export async function queryDeviceGroups(): Promise<DeviceGroupListResult> {
  const response = await request.get<{
    records: Array<{ id: string; group_name: string }>
    total: number
    size: number
    current: number
    pages: number
  }>('/device-groups')
  return { items: response.records.map((item) => ({ id: item.id, name: item.group_name })) }
}
```

```ts
// services/request/mocks/mock-request.ts：仅由开发模式的请求入口动态加载
export const mockRequest = {
  async get<T>(path: string, _options?: unknown): Promise<T> {
    if (path !== '/device-groups') throw new Error(`未定义的 Mock 路径：${path}`)
    return {
      records: [{ id: 'demo-group-1', group_name: '演示分组' }],
      total: 1,
      size: 20,
      current: 1,
      pages: 1,
    } as T
  },
}
```

```text
本地页面开发：VITE_API_MODE=mock 且 import.meta.env.DEV → Mock 响应 → 页面状态与交互验证
接口联调阶段：VITE_API_MODE=remote → 真实服务 → 契约、权限、数据范围与异常验证
生产构建：即使误设 VITE_API_MODE=mock，useMock 仍为 false；还须检查构建产物未包含 Mock 数据
```

示例沿用项目已有的 `httpRequest`，其 `get<T>` 将内部接口的 `R<T>` 解包后返回 `data`；Mock 返回的是同一分页数据结构，而不是另造响应外壳。模拟入口只覆盖本例的 GET 路径，其他方法和响应场景应按项目实际契约补齐。示例中的泛型断言只为匹配模拟请求的调用签名，不能证明真实接口字段符合该类型。切换只发生在统一请求入口；领域 API 和页面代码不改变调用方式。Mock 数据必须明确标识为模拟结果，不得伪造真实租户、权限、生产数据或“线上已验证”结论。

#### 错误示例

```ts
async function loadGroups() {
  if (location.hostname === 'localhost') {
    return [{ id: '1', name: '演示分组' }]
  }
  return axios.get('http://internal-service/device-groups')
}
```

问题：Mock 判断、模拟数据和内部服务地址散落在页面；页面在不同环境返回不同模型；没有明确切换记录，开发者无法判断当前验证的是页面交互还是实际接口行为。

#### 验证步骤与预期结果

1. 使用 Mock 模式进入页面，预期只验证页面展示、查询交互、加载、空数据和失败状态，不把结果记录为接口联调通过。
2. 切换到真实接口模式，预期领域 API 和页面调用不变，仅请求入口改变。
3. 真实接口返回字段缺失、空数据、业务错误或未授权，预期页面按真实契约展示对应状态，不由 Mock 默认值掩盖问题。
4. 检查生产构建，预期不加载本地 Mock 处理器、不包含模拟内部地址，也不使用 Mock 数据替代真实请求。
5. 联调记录应区分“Mock 页面验证”与“真实接口验证”，后者才可作为契约、权限和数据范围的证据。

#### 人工确认点

- 哪些环境允许启用 Mock，以及由谁维护开关；
- Mock 是否覆盖了必要的正常、空数据、失败和无权限交互，而没有伪造真实服务能力；
- 真实接口联调的字段契约、错误语义、权限和数据范围是否已逐项验证；
- 构建和发布配置是否确保生产环境无法意外启用 Mock。
