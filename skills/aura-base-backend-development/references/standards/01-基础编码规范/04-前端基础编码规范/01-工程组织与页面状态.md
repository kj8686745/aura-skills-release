## 一、前端工程结构

### AURA-BASE-FE-001：按职责和领域组织

**必要性**：必须

前端工程按 `BASE-01` 的统一目录承载职责。页面或领域专属的组件、API、类型和组合逻辑就近放在 `views/<domain>/`；只有跨页面稳定复用的实现才放入对应公共目录：

```text
src/
├─ views/<domain>/  # 领域页面及其专属组件、API、类型和组合逻辑
├─ app/             # 应用启动、路由、菜单和全局配置
├─ components/      # 跨页面稳定复用的组件
├─ composables/     # 跨页面稳定复用的组合逻辑
├─ services/        # 统一请求入口和外部服务封装
├─ stores/          # 跨页面共享状态
└─ types/           # 跨模块共享类型
```

`layouts/`、`assets/`、`styles/` 等其余统一目录及项目既有测试入口按 `BASE-01` 使用，不为本规则另建一套顶层目录。领域专属内容不得因文件类型被机械分散到公共目录；公共基础设施也不得混入某个领域页面。没有真实内容的空目录、单函数目录和一对一转发文件不得为了形式保留。

**为什么需要**：职责可发现才能让页面、请求、状态和公共能力在变更时各自收束，避免单一目录承载所有业务实现。

**正确写法**：

```text
src/
├─ app/router/             # 路由与菜单入口
├─ views/device/           # 页面入口、领域 API、类型和局部组件
├─ services/request/       # 统一请求入口
├─ components/             # 跨领域稳定组件
└─ stores/                 # 明确的跨页面状态
```

**错误写法**：

```text
src/
├─ components/  # 所有页面、弹窗、领域组件混放
├─ utils/       # 所有请求、类型、转换、业务校验混放
└─ index.ts     # 巨型入口转发全部功能
```

**判断要点 / 验证方式**：页面入口、请求入口、状态来源和公共能力能否被快速定位；目录是否反映真实职责而不是空壳或机械拆分；检查新增模块的依赖路径与文件职责；人工确认目录是否降低跨领域耦合和理解成本。

**例外**：小型项目可以不创建尚无代码的职责目录，但已有代码仍须按统一职责归属，不得改用自定义同义目录。



### AURA-BASE-FE-002：领域聚合优先

**必要性**：必须

同一业务领域的 API、类型、页面和局部组件应保持可发现的领域关联；通用组件和工具只有在跨领域复用语义稳定后才抽取。不得把所有业务请求、所有页面状态或所有表单逻辑堆入一个巨型文件。

现有项目可以作为统一职责目录落地时的事实样本，但不改变本规范的统一目录要求。业务领域只能作为统一职责目录下的模块组织方式，不能新增另一套顶层职责目录。

**为什么需要**：领域聚合能让同一业务的页面、类型、请求和局部交互一起演进，避免修改一个功能时跨大量无关目录寻找实现。

**正确写法**：

```text
views/device/
├─ api/deviceApi.ts
├─ model/device.ts
├─ components/DeviceForm.vue
├─ composables/useDeviceList.ts
└─ adapters/devicePresenter.ts
```

跨领域稳定的请求基础设施放入 `services/`，通用组件放入 `components/`；通用转换只有在语义稳定后才提升为公共代码，不将设备领域规则提前抽成万能工具。

**错误写法**：

```text
api/allApi.ts
stores/globalStore.ts
utils/common.ts
views/  # 所有领域页面混放
```

**判断要点 / 验证方式**：同一领域的 API、类型、页面和局部组件是否可发现；公共抽取是否具有跨领域稳定语义；检查一次领域功能修改需要跨越的目录和依赖；人工确认抽取的组件、Store 和工具是否真正通用。

**例外**：框架约定的全局路由、请求基础设施和应用级主题可以集中维护，但不能承载领域业务逻辑。

## 二、页面、组件和状态



### AURA-BASE-FE-003：页面负责组合，组件负责明确职责

**必要性**：必须

页面负责业务场景组合和路由上下文；可复用组件负责明确的展示、交互或数据输入输出。不得把一个页面全部写成无边界的大组件，也不得为了几个标签或一段简单逻辑拆出无复用价值的组件文件。

**为什么需要**：页面与组件职责清晰，才能在业务组合变化和局部交互复用时控制修改范围。

**正确写法**：

```text
DeviceListPage.vue
  ├─ 负责路由参数、查询条件、页面状态和动作编排
  ├─ DeviceFilter.vue      # 明确输入与筛选事件
  ├─ DeviceTable.vue       # 明确展示与选择事件
  └─ DeviceFormDialog.vue  # 明确表单输入和提交事件
```

**错误写法**：一个页面组件内同时创建请求客户端、管理全部表单、绘制表格、处理路由、拼接权限和实现领域转换；或只为了一个静态标签拆出独立组件。

**判断要点 / 验证方式**：检查页面是否承担场景组合、组件是否有清晰输入输出和职责，以及拆分是否有复用或隔离价值；核对 Props、事件和依赖方向，确认拆分后业务流仍可理解。状态归属另按 `AURA-BASE-FE-004` 判断，状态展示另按 `AURA-BASE-FE-005` 判断。

**例外**：简单静态页面可以保持单组件，但一旦出现可复用交互、复杂表单或独立状态，应按职责拆分。



### AURA-BASE-FE-004：状态来源单一

**必要性**：必须

同一业务状态必须有明确的唯一来源。不得同时在页面变量、全局 Store、浏览器存储和组件内部维护互相可能冲突的副本，除非明确说明同步关系和失效策略。

**为什么需要**：多个状态副本会导致页面展示、提交内容和缓存数据不一致，问题通常难以定位和复现。

**正确写法**：

```text
列表查询结果 → useDeviceList() 局部状态
登录用户与菜单 → 用户 Store
可恢复筛选条件 → 明确序列化到路由或浏览器存储
```

同一份设备列表只由一个 Composable 或 Store 维护，组件通过 Props 和事件读取或更新，不复制为第二份可变数据。

**错误写法**：页面 `ref`、全局 Store、`localStorage` 和子组件各保存一份设备列表，并依赖人工同步。

**判断要点 / 验证方式**：确认每个业务状态的唯一维护者及缓存同步、失效策略；切换路由、刷新页面、修改筛选条件和并发提交时检查状态一致性，并核对跨页面共享是否必要。临时草稿可作局部副本，但不能成为第二个长期事实来源；展示方式另按 `AURA-BASE-FE-005` 判断。

**例外**：为编辑提供的临时草稿可以是局部副本，但必须明确提交、放弃和失效时机。



### AURA-BASE-FE-005：页面状态真实表达

**必要性**：必须

页面必须根据真实请求和任务结果维护加载中、已受理、执行中、成功、失败、部分成功和最终完成等适用状态，不得把请求已受理当作最终成功，或使用无依据默认值掩盖真实结果。具体空数据、失败和无权限时的展示与恢复入口按 `AURA-BASE-FE-016` 处理。

**为什么需要**：页面状态是用户理解请求结果和下一步操作的依据，模糊状态会导致重复提交、错误判断和遗漏处理。

**正确写法**：

```text
loading    → 请求尚未完成
accepted   → 异步任务已受理，但尚未完成
running    → 任务执行中
partial    → 有成功项和失败项，等待用户处理
completed  → 根据最终结果确认成功
failed     → 根据最终结果确认失败
```

**错误写法**：提交接口仅返回任务编号就提示“处理成功”，或任务最终失败后页面仍停留在成功状态。

**判断要点 / 验证方式**：检查页面状态是否来自真实请求与任务结果，是否区分受理、执行、部分成功与最终结果；使用请求延迟、异步受理和最终失败等结果验证状态转换。状态由谁持有按 `AURA-BASE-FE-004` 判断，展示与恢复动作按 `AURA-BASE-FE-016` 判断。

**例外**：同步完成的操作可以没有受理和执行中状态，但不得在真实结果返回前显示最终成功。

## 三、典型开发场景示例

### 领域页面开发与列表查询

**适用任务**：前端页面、前端组件、前端状态、前端请求  
**关联规则**：FE-001、FE-002、FE-003、FE-004、FE-005、FE-006、FE-010、FE-012、FE-014  
**跨分类规则**：FE-006、FE-010、FE-012 见[请求路由权限与数据适配](./02-请求路由权限与数据适配.md)；FE-014 见[表单异步与资源反馈](./03-表单异步与资源反馈.md)。  
**示例级别**：完整示例

#### 场景目标

为“设备列表”建设一个可查询、可展示状态、可追踪请求边界的领域页面。页面负责用户交互和展示；领域 API 负责请求与模型适配；页面不直接依赖后端原始 DTO。

#### 输入条件

- 已存在统一请求入口；
- 后端提供分页查询接口，响应字段可能与页面展示字段不同；
- 页面需要处理首次加载、查询中、查询失败、空数据和正常结果；
- 列表展示可先在页面内实现；抽成可复用组件时，组件不承担领域请求和页面状态编排。

#### 推荐结构

```text
views/device/DeviceListPage.vue        页面入口、查询交互和状态呈现
views/device/api/device-api.ts       领域请求和响应转换
views/device/model/device-model.ts   页面使用的稳定模型
views/device/composables/use-device-list.ts  查询状态与操作
```

#### 完整正确示例

示例沿用项目已有的 `@/services/request`，其 `get<T>` 将内部接口的 `R<T>` 解包后返回 `data`；本例的 `T` 是包含 `records`、`total`、`size`、`current`、`pages` 的框架分页数据。下列模型、查询逻辑和页面代码构成一个可衔接的列表场景。

```ts
// views/device/model/device-model.ts
export type DeviceListQuery = { keyword: string; page: number; pageSize: number }
export type DeviceListItem = {
  id: string
  name: string
  status: 'online' | 'offline' | 'unknown'
}
export type DeviceListResult = { items: DeviceListItem[]; total: number }
```

```ts
// views/device/api/device-api.ts
import { request } from '@/services/request'
import type { DeviceListItem, DeviceListQuery, DeviceListResult } from '../model/device-model'

type DeviceListResponse = {
  records: Array<{ id: string; device_name: string; online_status: number }>
  total: number
  size: number
  current: number
  pages: number
}

export async function queryDeviceList(query: DeviceListQuery): Promise<DeviceListResult> {
  const response = await request.get<DeviceListResponse>('/devices', { params: query })
  return {
    total: response.total,
    items: response.records.map((item): DeviceListItem => ({
      id: item.id,
      name: item.device_name,
      status: item.online_status === 1 ? 'online' : item.online_status === 0 ? 'offline' : 'unknown',
    })),
  }
}
```

```ts
// views/device/composables/use-device-list.ts
import { ref } from 'vue'
import { queryDeviceList } from '../api/device-api'
import type { DeviceListItem, DeviceListQuery } from '../model/device-model'

export function useDeviceList() {
  const items = ref<DeviceListItem[]>([])
  const total = ref(0)
  const loading = ref(false)
  const errorMessage = ref('')
  let latestRequest = 0

  async function load(query: DeviceListQuery) {
    const requestId = ++latestRequest
    const currentQuery = { ...query }
    loading.value = true
    errorMessage.value = ''
    try {
      const result = await queryDeviceList(currentQuery)
      if (requestId !== latestRequest) return
      items.value = result.items
      total.value = result.total
    } catch {
      if (requestId !== latestRequest) return
      items.value = []
      total.value = 0
      errorMessage.value = '设备列表加载失败，请稍后重试。'
    } finally {
      if (requestId === latestRequest) loading.value = false
    }
  }

  return { items, total, loading, errorMessage, load }
}
```

```vue
<!-- views/device/DeviceListPage.vue -->
<script setup lang="ts">
import { computed, onMounted, reactive } from 'vue'
import { useDeviceList } from '@/views/device/composables/use-device-list'
import type { DeviceListItem, DeviceListQuery } from '@/views/device/model/device-model'

const query = reactive<DeviceListQuery>({ keyword: '', page: 1, pageSize: 20 })
const { items, total, loading, errorMessage, load } = useDeviceList()
const pageCount = computed(() => Math.max(1, Math.ceil(total.value / query.pageSize)))

function statusText(status: DeviceListItem['status']) {
  return { online: '在线', offline: '离线', unknown: '未知' }[status]
}

function search() {
  query.page = 1
  return load(query)
}

function changePage(page: number) {
  query.page = page
  return load(query)
}

onMounted(() => { void load(query) })
</script>

<template>
  <form @submit.prevent="search">
    <label for="device-keyword">设备名称</label>
    <input id="device-keyword" v-model="query.keyword" type="search" />
    <button type="submit">查询</button>
  </form>
  <p v-if="loading" role="status">加载中</p>
  <div v-if="errorMessage" role="alert">
    {{ errorMessage }} <button type="button" @click="load(query)">重试</button>
  </div>
  <p v-if="!loading && !errorMessage && items.length === 0">没有符合条件的设备</p>
  <table v-if="!loading && !errorMessage && items.length > 0">
    <thead><tr><th>名称</th><th>状态</th></tr></thead>
    <tbody>
      <tr v-for="item in items" :key="item.id">
        <td>{{ item.name }}</td><td>{{ statusText(item.status) }}</td>
      </tr>
    </tbody>
  </table>
  <nav v-if="!errorMessage && total > query.pageSize" aria-label="设备列表分页">
    <button type="button" :disabled="loading || query.page <= 1" @click="changePage(query.page - 1)">上一页</button>
    <span>第 {{ query.page }} / {{ pageCount }} 页</span>
    <button type="button" :disabled="loading || query.page >= pageCount" @click="changePage(query.page + 1)">下一页</button>
  </nav>
</template>
```

此处用原生表单和表格展示场景，实际项目可按 `AURA-BASE-FE-003` 将稳定的交互抽为组件。页面只组合查询输入、状态和展示；请求路径、响应字段转换集中在领域 API；`loading`、失败和空数据分别表达。查询序号确保较旧的响应或失败不会覆盖较新的查询结果与加载状态。

#### 错误示例

```vue
<script setup lang="ts">
import axios from 'axios'
const rows = ref([])
async function load() {
  const response = await axios.get('http://internal-device-service/devices')
  rows.value = response.data.records || {}
}
</script>
```

问题：页面直接创建请求边界并写入内部地址，直接依赖原始响应字段；失败、空数据和成功结果混在一起，后续字段变化会扩散到页面。

#### 验证步骤与预期结果

1. 首次进入页面，预期显示加载状态，成功后展示经领域模型转换的列表。
2. 接口返回空记录，预期显示空数据状态，而不是错误或成功占位对象。
3. 接口失败，预期显示可理解的失败提示，不展示过期结果为本次成功数据。
4. 快速搜索与翻页，并让旧请求晚于新请求返回，预期查询条件只由页面状态维护，页面最终只展示最新条件的结果，旧请求不关闭新请求的加载状态。
5. 变更后端字段名，预期只需在领域 API 的转换位置评估和修改，页面展示模型保持稳定。

#### 人工确认点

- 查询条件、排序和分页参数是否符合业务语义；
- 空数据、无权限和请求失败是否需要不同的用户提示和交互；
- 页面模型中哪些字段可公开展示，哪些字段必须在领域 API 中脱敏或转换；
- 复用组件的职责是否仍限于展示与交互，而没有重新承接领域请求。
