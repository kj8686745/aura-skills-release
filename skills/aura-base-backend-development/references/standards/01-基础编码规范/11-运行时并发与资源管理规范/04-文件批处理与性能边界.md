**规范对象**：使用 AURA 开展业务应用、服务、工具和平台工程开发的团队和开发人员

**跨规范边界**：本文件约束文件流、循环、批处理、接口输出和性能优化的规模与释放边界；异步任务与重试遵循 `BASE-10`，数据访问遵循 `BASE-08`，公开接口契约遵循 `BASE-05`。具体框架组件的接入方式以对应能力包为准。

## 一、文件、批处理与性能边界

### AURA-BASE-RUNTIME-016：文件和流必须采用受控的生命周期

**必要性**：必须

文件上传、下载、解析和流式处理必须限制大小、路径、并发和处理时间，并在成功、失败、超时和取消路径关闭流、连接和临时文件。

生成文件时必须区分业务提供的写入流、表格Writer、压缩容器和底层文件的所有者：当前文件完成后先结束表格Writer，再结束对应压缩条目，全部条目完成后结束压缩容器；公共组件提供的底层流由公共组件统一关闭。不能用`finish`替代压缩资源的实际释放，也不能让某个分片关闭整个ZIP输出流。发生异常时保留原失败原因，收尾失败作为补充证据，不把部分生成物标为成功。

**为什么需要**：文件资源通常跨越请求和任务边界，泄漏或无界读取会迅速耗尽内存、磁盘和句柄。

**正确写法**：限制上传大小，使用流式复制，临时文件放入专用目录并在终态或期限到达后清理。

**分片正例**：逐份结束XLSX和ZIP条目，最终释放压缩资源；读取/写入失败时停止后续批次，结果保持不可下载并登记清理，原始失败仍可定位。

**错误写法**：把用户上传内容一次性读入内存，使用用户输入直接拼接文件路径，异常时不关闭流。

**分片反例**：每个Writer都关闭同一个ZIP流；只调用压缩`finish`却长期保留压缩器；finally中的二次异常覆盖真正的数据读取失败；发生异常后交付半个ZIP。

**判断要点 / 验证方式**：使用超大文件、非法路径、断点和中途取消，检查内存、句柄、临时文件和权限边界。

### AURA-BASE-RUNTIME-017：循环、递归和批处理必须有规模边界

**必要性**：必须

处理外部输入或持续增长数据的循环、递归、分页和批处理必须有最大次数、深度、批次、结果量或时间边界；已由有限集合和确定性退出条件约束的普通循环不需另设任意次数上限。重试边界遵循 `BASE-10`。

分页回调必须明确排序、偏移量或游标含义，以及空页/短页/下一游标何时表示结束。只能在所用读取契约承诺短页即末尾时据此结束；分页后再进行权限过滤造成的短页，不证明源查询已结束。不得通过反复返回同一页满足批次接口，或依赖事先读取完整结果实现“分页”。

**为什么需要**：数据增长和异常输入会把无界算法变成超时、栈溢出或内存耗尽。

**正确写法**：分页处理设置最大页数和批次大小，递归设置深度或改用显式队列。

**分页正例**：查询条件和授权范围在请求阶段确定，按唯一排序或稳定游标逐批推进，并按公开契约判断结束；记录实际处理行数及边界拒绝结果。

**错误写法**：读取全部数据后在内存循环处理，或递归遍历关系数据而没有深度限制。

**分页反例**：同一页重复导出；短页只是应用过滤结果却提前结束；为了分片先将全表读入List，再对List做subList。

**判断要点 / 验证方式**：使用空集、超大集、循环引用和异常深度输入，确认系统会受控完成或明确拒绝。

### AURA-BASE-RUNTIME-018：避免在循环中重复访问外部资源

**必要性**：必须

对数据库、网络服务、文件和缓存的访问若随输入条数成倍增长，必须通过批量查询、预加载、缓存、分批策略或经验证的调用预算控制；小规模且明确有界的逐项调用不要求为批量而增加复杂度。

**为什么需要**：循环内重复访问会形成 N+1 请求，放大延迟、连接和外部依赖压力。

**正确写法**：批量导入先按标识分批查询所需数据，再完成关联；必须逐项调用的接口限定批量大小、并发和总耗时。

**错误写法**：遍历 10,000 条记录时逐条查询数据库和调用远程服务。

**判断要点 / 验证方式**：使用代表性数据量统计查询、调用次数、延迟和资源使用，确认调用量随输入增长仍受预算约束。

### AURA-BASE-RUNTIME-019：接口和任务输出必须限制数据规模

**必要性**：必须

列表、导出、日志、消息和任务结果必须设置最大记录数、分页、流式或文件化边界；不得把不可预测的大结果直接放入响应、内存或单条消息。

Excel导出必须分别限制查询批次、总记录数和单文件规模；超出单文件容量或可读规模时，按已确认的交付策略拆为多份Excel并压缩成一个ZIP，不继续堆入同一工作表。分片还须限制文件数量及总体资源消耗；格式行数上限必须扣除表头占用，不能把总行数配置当作单工作表可容纳行数。具体公共方法和依赖版本由能力包定义，本规则不指定统一业务阈值。

#### 导出容量如何计算

| 约束 | 必须明确的内容 | 失败处理 |
| --- | --- | --- |
| 单批查询 | 每次最多读取多少条、排序/游标和单批内存预算 | 拒绝超批次返回，不把已全量读取的List视为合规分页 |
| 单个XLSX | 数据行、表头层数、标题/空白占用行、列数和文件可读规模 | 在写入前核对可用容量，不能依赖表格库到最后才溢出 |
| 整体结果 | 累计数据行数、最大分片数、总文件字节/临时磁盘及处理时间预算 | 超限明确失败或按已确认策略拒绝，不静默截掉尾部数据 |
| 任务交付 | 分片结束、ZIP完整关闭、元数据关联和上传成功的顺序 | 全部完成才可发布结果；失败只保留排障/清理引用 |

单文件允许的数据行数取“业务配置上限”和“格式可用数据行数”的较小值。格式可用数据行数等于总行容量减去实际表头、标题及其他占用行；多行表头不能一律只减一行。列数也必须按实际导出字段核对。

对于XLSX工作表，格式总容量为1,048,576行、16,384列；这不是推荐业务规模。一个表头占一行时，数据行理论上限为1,048,575；实际还应受项目验证过的单文件预算约束。来源见[Microsoft Excel规格与限制](https://support.microsoft.com/en-us/excel/excel-specifications-and-limits?re=true)。其他格式按自身限制处理，不能套用XLSX数值。

ZIP分片按同一查询顺序连续划分，批次可跨分片边界，不能因切文件重复查询、丢行或重复写入。空结果仍应有约定的可读表头；恰好到达分片容量时不得再生成一个无意义的尾部空文件。按行数分片不等于已限制字节、磁盘或耗时，未覆盖的预算须明确说明。

**为什么需要**：结果规模增长会导致响应超时、序列化耗时、内存占用和消息失败。

**正确写法**：列表强制分页，导出转为异步文件任务，消息按批次发送并记录进度。

**导出正例**：按固定查询范围和唯一排序逐批读取；按单文件行数拆分Excel，全部分片结束并完成ZIP后作为一个结果交付；用文件读取器核对各分片的表头、数据行、字段值和跨文件连续性。

**错误写法**：接口默认返回全表数据，或将数十万条记录拼成一个 JSON 响应。

**导出反例**：配置数千万行却只写一个工作表；先查询全量List再分文件；ZIP里存在若干xlsx文件名就认定数据完整；分片失败后仍把不完整ZIP标为成功。

**判断要点 / 验证方式**：核对配置有效值与格式容量，使用空结果、单条、批次前后、分片前后、恰好满片、最大值及超过最大值的输入。逐份读取生成的XLSX，验证表头、字段值、数据行数、总量与顺序；跨分片的唯一标识不得遗漏或重复。大规模验证可使用流式解析和汇总校验，不能为了验证再全量读入内存。注入读取/写入异常，检查结果不可发布及资源释放。另使用慢客户端和代表性数据量核对字节、内存、磁盘和耗时，不用小样本断言替代压测。

### AURA-BASE-RUNTIME-020：性能优化必须保持可验证的业务语义

**必要性**：必须

缓存、批量、并行、预加载和异步优化不得改变权限、事务、顺序、幂等和错误语义；优化前后必须验证业务结果一致性和资源收益。

**为什么需要**：只追求耗时下降可能引入旧数据、越权、重复副作用或错误吞掉等问题。

**正确写法**：批量查询后对比权限过滤、排序和空值行为，再用实际数据量验证延迟和资源变化。

**错误写法**：为了减少查询直接跳过租户条件，或为了并行处理而忽略原有顺序和失败结果。

**判断要点 / 验证方式**：对比优化前后的功能结果、权限、错误、顺序、延迟和资源指标，确认优化没有改变契约。

## 二、完整场景示例

### 正例：有界分页生成多个Excel并交付一个ZIP

收到任务记录导出请求后，业务冻结筛选条件、授权范围和稳定排序；公共生成器每次最多读3条，每份Excel最多写2条数据。本例5条输入按顺序生成2、2、1条数据的3份文件，每份使用同一表头；单批返回的第3条进入下一份文件，不回到数据库重新取前2条。

```text
准备查询范围与公开字段
→ 读取批次[1,2,3] → 文件1写[1,2]并结束 → 文件2写[3]
→ 读取批次[4,5] → 文件2追加[4]并结束 → 文件3写[5]并结束
→ 结束ZIP → 保存文件名/类型/大小 → 上传和结果提交 → 一个下载结果
```

示例值仅用于验证边界，不是项目容量默认值。复核时读取三个文件，逐条核对编号、名称和状态；仅ZIP内文件名正确不算完成。范围还需明确调用走到了哪一层：构造ExportJob、实际写出文件、注解执行、任务持久化、上传与下载分别需要对应证据。

### 反例：打包成功但业务数据没有导出

行模型虽然能编译，但不被所用表格库按预期读取，输出只有表头或空行；测试仅断言ZIP大小大于零和存在3个xlsx条目，就宣称5条任务完整导出并已接入下载中心。该测试没有证明字段写出、总量或任务链路，必须补充文件内容验证。

### 正例：批量导入服务的启动、受理与停止

假设服务提供批量导入接口，后台消费者处理已受理任务；数据库是关键依赖，推荐服务是非关键依赖。

```text
必需配置缺失 → 启动失败，并指出配置项
数据库暂时不可达 → 进程存活、服务未就绪，不接收导入任务
数据库恢复 → 服务就绪；推荐服务异常只影响推荐功能
任务队列达到上限 → 拒绝新导入并说明未受理，不返回虚假的完成结果
收到停止信号 → 停止新请求和新消费；已完成任务先持久化再确认消息
等待期届满 → 未完成任务保留可接管状态；关闭执行器和连接
实例重启 → 依据任务状态、租约和幂等键接管，不重复写入
```

该场景将启动、就绪、容量、停止和恢复串成同一业务结果；任务状态与消息确认的细节仍遵循 `BASE-10`。

### 反例：进程存在但导入结果失控

```text
缺少配置仍返回就绪
→ 无界队列继续接收导入并返回“成功”
→ 数据库故障只写一条告警，继续受理新任务
→ 停止时先确认消息、随后直接退出
→ 重启后两台实例同时重做未完成任务
```

该实现既无法反映实际承载能力，也会造成任务丢失、重复写入和资源持续积压。

## 三、开发者自检

- 文件和流是否限制大小、路径、并发和处理时间，并在所有路径释放；
- 循环、递归、分页和批处理是否有实际规模边界；
- 是否避免循环内重复访问数据库、网络、文件和缓存；
- 接口、日志、消息和任务结果是否限制输出规模；
- Excel单文件是否扣除真实表头/标题占用，分片是否连续、空结果是否可读、恰好满片是否没有空尾片；
- 是否实际读取每份结果文件核对表头、数据行、字段值和顺序，而不仅检查ZIP条目；
- 性能优化是否验证权限、事务、顺序、幂等、错误语义和资源收益。
