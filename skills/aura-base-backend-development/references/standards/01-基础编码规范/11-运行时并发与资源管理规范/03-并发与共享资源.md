**规范对象**：使用 AURA 开展业务应用、服务、工具和平台工程开发的团队和开发人员

**跨规范边界**：本文件约束共享状态、锁、线程池、连接池、队列等并发与共享资源边界；异步任务与重试遵循 `BASE-10`，数据一致性遵循 `BASE-08`。具体框架组件的接入方式以对应能力包为准。

## 一、并发与共享资源规则

### AURA-BASE-RUNTIME-013：共享状态必须具备明确的并发保护

**必要性**：必须

多个线程、请求、任务或实例会读写的状态，必须通过不可变对象、原子操作、锁、数据库版本条件或其他明确策略保护；不得依赖调用顺序或前端按钮禁用保证安全。跨实例共享状态不能只用单进程内锁保护。

**为什么需要**：并发请求可能同时读取和修改同一状态，顺序假设无法防止竞态和覆盖。

**正确写法**：进程内计数使用原子操作；跨实例业务状态使用数据库版本条件更新，并在冲突时返回明确结果。

**错误写法**：先读取共享变量、计算新值再无条件写回，认为两个请求不会同时执行。

**判断要点 / 验证方式**：并发执行相同操作，检查结果是否满足业务不变量，并确认冲突不会静默覆盖。

### AURA-BASE-RUNTIME-014：锁必须有边界、顺序和释放保证

**必要性**：必须

锁的保护对象、粒度、获取顺序和最大等待时间必须明确；锁必须在正常、异常和取消路径释放，不得在锁内执行长时间网络调用或人工等待。

**为什么需要**：无边界锁会导致死锁、长时间阻塞和吞吐下降。

**正确写法**：按固定顺序获取有限范围的锁，使用 `try/finally` 释放，锁内只执行本地短操作。

**错误写法**：多个方法按不同顺序获取锁，或持锁调用远程服务并等待返回。

**判断要点 / 验证方式**：并发执行相反顺序操作和远程延迟场景，确认无死锁、无限等待和锁泄漏。

### AURA-BASE-RUNTIME-015：共享资源必须按相互干扰风险隔离与限额

**必要性**：必须

共享线程池、连接池或队列的任务必须有容量、等待和超限处理边界；某类工作会因耗时、优先级或故障依赖占尽共享资源并阻断关键业务时，应使用独立执行器、并发配额或其他隔离方式。无需为每类任务机械创建资源池。

**为什么需要**：低优先级或故障依赖占满共享资源，会阻塞核心业务。

**正确写法**：外部分析与核心请求共用连接资源时对分析调用设置独立并发配额；持续阻塞仍会影响核心请求时，再拆分执行器或连接池，并设置容量与超限行为。

**错误写法**：所有定时任务、消息消费和 HTTP 请求都提交到一个无界线程池。

**判断要点 / 验证方式**：制造单一任务类型持续积压，检查核心请求是否仍能获得资源；资源耗尽时核对等待、拒绝、恢复和监测行为。

## 二、典型使用示例：跨实例审核的并发与资源隔离

**场景目标**：多个实例同时处理设备审核和外部分析任务时，业务状态不会被静默覆盖；高耗时分析不能占满核心请求资源，锁和连接在异常路径也能释放。

**输入条件**：设备审核使用数据库版本条件；外部分析可能长时间等待；核心查询和分析任务共享部分连接资源；应用运行多个实例。

**正确处理链**：

```text
审核更新按 deviceId、tenantId、version 条件提交
  → 只有一个实例成功，其他实例得到明确冲突
分析调用使用独立并发配额和总耗时预算
  → 超限时排队或拒绝，不占满核心请求资源
需要短锁时固定获取顺序并在 finally 释放
  → 不在锁内调用远程服务
```

跨实例状态不能只靠进程内锁；共享线程池、连接池和队列必须有容量、等待和超限行为。小范围本地计数可以使用原子操作，但不能把进程内计数当作跨实例业务事实。

**错误处理链**：先查询后无条件覆盖；用一个全局静态锁保护所有租户；所有请求、分析和定时任务共用无界线程池；持锁等待外部服务；异常 return 导致锁和连接不释放。

**验证步骤与预期结果**：

1. 两个实例并发提交同一版本审核，预期一个成功、一个冲突且业务不变量不被破坏。
2. 让分析任务持续积压，预期核心查询仍能获得线程和连接，超限行为可观察且可恢复。
3. 以相反顺序并发执行需要多资源的操作并注入远程延迟，预期无死锁、无限等待或资源泄漏。

## 三、开发者自检

- 共享状态是否使用了与并发范围匹配的保护策略；
- 锁的对象、粒度、顺序、等待和释放路径是否明确；
- 共享线程池、连接池和队列是否有容量、配额和超限行为；
- 单一任务类型积压时，关键业务是否仍能获得必要资源。
