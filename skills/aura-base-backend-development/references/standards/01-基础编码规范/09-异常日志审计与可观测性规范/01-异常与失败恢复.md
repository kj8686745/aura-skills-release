**适用对象**：使用 AURA 开展业务应用、服务、工具和平台工程开发的团队和开发人员

**规范目标**：让失败类型、定位上下文、公开错误和恢复结果能够被正确表达。

**边界说明**：本文件负责异常分类、上下文保留、公开错误和失败恢复；日志、审计、指标和链路分别见本目录其他分类文件。公开错误结构遵循 `BASE-05`，身份与敏感信息边界遵循 `BASE-07`，异步重试和最终状态遵循 `BASE-10`。

## 一、异常表达

### AURA-BASE-OBS-001：异常必须区分业务失败和系统故障

**必要性**：必须

**为什么需要**：不同失败类型对应不同处理方式，明确区分才能正确返回、重试、提示和定位问题。

业务规则不满足、输入不合法、权限不足、外部依赖失败和程序故障必须能够区分，并分别映射到接口契约规定的结果。不可重试的业务拒绝不得伪装成系统故障，可重试的依赖故障也不得伪装成普通“无数据”。

**正确写法**：参数错误、权限拒绝、外部超时和未预期异常分别进入已定义的错误类别；调用方能依据稳定错误码判断提示、重试或终止。

**错误写法**：所有失败都抛出同一个 `Exception` 并返回相同结果。

**判断要点 / 验证方式**：分别触发业务、权限、依赖和系统故障，检查类型和公开结果。

### AURA-BASE-OBS-002：异常必须保留定位上下文

**必要性**：必须

**为什么需要**：保留原始原因、业务标识和链路上下文，才能把公开结果、日志和具体故障关联起来。

异常转换和重新抛出时必须保留原始原因及定位所需的业务标识、请求标识；记录这些信息时同时遵守敏感信息边界。禁止捕获后静默忽略、只打印字符串或伪造成功结果。

**正确写法**：内部异常保留原始 `cause`，受控日志记录业务对象标识和 `traceId`，对外只返回可安全展示的错误和请求标识。

**错误写法**：`catch` 后只记录“失败”并返回空结果。

**判断要点 / 验证方式**：检查异常链、日志字段和错误响应关联关系。

### AURA-BASE-OBS-003：公开错误必须遵循接口契约

**必要性**：必须

**为什么需要**：稳定错误契约可以让调用方按错误类别处理，同时避免内部堆栈、SQL 和凭据暴露给外部使用者。

对外错误码、消息、字段和 HTTP/WebSocket 结果遵循 `BASE-05`。同一故障在响应和日志中使用可关联的请求标识；内部堆栈、密钥、SQL、Token 和敏感数据不得直接返回给调用方。

**正确写法**：对外返回 BASE-05 稳定错误结构，内部堆栈只保留在受控日志。

**错误写法**：把 SQL、堆栈、Token 或供应商异常原文返回前端。

**判断要点 / 验证方式**：触发未知异常和外部异常，检查响应字段和敏感内容。

### AURA-BASE-OBS-004：失败处理必须说明恢复语义

**必要性**：必须

**为什么需要**：明确重试、补偿、降级和人工处理边界，才能避免无限重试、静默失败或把未完成操作伪装成成功。

涉及自动重试、降级或补偿的业务动作，必须说明可重试错误、幂等前提、次数和总时限，以及处理耗尽后的失败、补偿或人工处理状态。普通失败仍须返回明确结果；降级结果必须与真正成功区分，不能通过无限重试或吞掉异常掩盖不可恢复故障。异步执行细节按 `BASE-10` 落地。

**正确写法**：只对满足幂等前提的瞬态错误有限重试；超时预算耗尽后记录最终失败或待补偿状态，调用方看到的结果与实际状态一致。

**错误写法**：无限重试或把不可恢复失败标记为成功。

**判断要点 / 验证方式**：模拟持续超时和不可用，确认重试次数、退避和最终状态。

## 二、典型使用示例：设备审核的失败分类与有限恢复

**场景目标**：设备审核入口能够区分参数、权限、并发、外部依赖和程序故障；对满足幂等前提的瞬态依赖故障有限重试，最终结果与实际状态一致。

**输入条件**：请求已通过身份和权限校验；审核更新使用版本条件；通知服务可能超时；调用方需要根据稳定错误码决定刷新、重试或终止。

**正确处理链**：

```text
解析并校验审核命令
  → 版本条件更新并区分影响行数
  → 参数/权限/对象不存在/版本冲突分别映射公开错误
  → 通知超时仅在幂等键存在时有限退避重试
  → 到达次数或总时限后记录待补偿/最终失败状态
  → 响应携带可关联的 requestId，不返回堆栈和供应商原文
```

内部异常保留原始 `cause`、设备标识和 `requestId`；对外只返回 BASE-05 约定的稳定错误码和安全消息。通知已经成功但回执丢失时，以幂等键查询或补偿，不重复生成审核结果；不可重试的权限拒绝和参数错误不进入自动重试。

**错误处理链**：所有异常都返回同一个“系统异常”；捕获后返回空结果；无限重试通知；把外部异常原文、SQL 或 Token 写入响应；通知最终失败仍把审核标记为已完成。

**验证步骤与预期结果**：

1. 分别触发参数错误、无权限、对象不存在、版本冲突、通知超时和未预期异常，预期错误类别、状态和 `requestId` 可区分。
2. 让通知连续超时，预期只按约定次数和总时限重试，耗尽后进入可查询的失败或待补偿状态。
3. 模拟通知已成功但回执丢失，预期按幂等键收敛，不重复执行业务副作用。
4. 检查响应、日志和异常链，预期能关联故障但不暴露堆栈、SQL、凭据或敏感请求体。

## 三、开发者自检

- 异常是否区分业务失败、权限拒绝、依赖故障和程序故障；
- 异常链、业务对象标识和请求标识是否保留；
- 对外错误是否遵循接口契约且不泄露内部细节；
- 重试、补偿、降级和人工处理是否有明确的最终状态。
