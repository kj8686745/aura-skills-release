# aura-base-backend-development 任务路由与执行指南

仅在当前任务需要选择能力章节、接入检查或示例时读取本文件。先命中任务，再打开对应能力文档；不要把路由表当作新的规范。

## 按任务读取

先确认需求涉及哪些环节，再在《能力详细说明》中定位相应章节，不默认加载全文。

| 任务 | 优先阅读的章节 | 对应能力包接入要点 |
| --- | --- | --- |
| 新建需要公共数据访问的业务模块 | 0～0.5、6～7、15～17 | `AURA-CAP-COMMON-BIZ-001` |
| 新增或修改 HTTP 接口 | 1、4、10、22.1 | `002`、`005` |
| 实现 CRUD、列表和分页 | 8、11、18～19、22.1 | `002`、`003`、`006`、`007` |
| 实现主子表或多步写入 | 3、9、20、22.1 | `003`、`004` |
| 编写 Entity、Mapper 和自定义 SQL | 15～22.1 | `001`、`003`、`006`、`007` |
| 准备自测、联调和交付 | 14、22、23.6 | 本次命中的规则及完整场景结果 |

表内三位数字均接在 `AURA-CAP-COMMON-BIZ-` 后。第 23 节的设备配置示例用于理解完整组合，不把示例中的业务名、表名或权限编码直接套到其他项目。

## 执行顺序

1. 从需求中确定业务对象、角色、动作、状态、数据范围、成功和失败结果。是否编写完整或简化的技术详细设计，按详细设计规范 `AURA-DES-001/002` 判断，不为局部改动机械补文档；需要设计时必须关注方案取舍、配置/依赖/部署变更、跨模块联调和编码准入结论。
2. 核对项目使用的 AURA 版本、父 POM/BOM、已有依赖、接口契约和数据库配置，再确定 DTO/VO、Entity、Mapper、Service、Controller 的实际落点。缺少公开依赖或契约时先说明缺口，不按示例猜测。
3. 按基础编码规范确定 Controller、Service、Mapper 的共同职责；再从命中的能力接入要点选择 `@HasPermission`、`R<T>`、`BaseEntity` 等实际需要的公开入口和组合示例。
4. 若需求涉及当前用户、缓存、日志、审计、幂等或服务调用，再按同版技能 `aura-base-backend-development` 所指向的基础通用支撑规范选择能力；跨数据源事务、分布式序列和动态数据源进入对应专项能力包。本地数据库事务不能被表述为远程调用或缓存操作的原子性保证。
5. 按本次实际改动验证合法、非法、跨租户、零行更新、部分写入失败和回滚等相关场景，核对接口响应与数据库结果。只报告实际完成的自测与联调证据。

## 停止条件

规范目录不可访问、当前项目的 AURA 版本与候选文档不匹配，或权限、租户、接口响应、事务范围无法从项目与规范确定时，不继续推断实现；列出缺失事实并等待对应契约明确。本模块不制定新规则、不读取内部治理或评分资料，也不替代真实项目的构建、自测和联调。
