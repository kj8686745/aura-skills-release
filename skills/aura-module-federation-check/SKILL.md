# AURA 模块联邦检查

当前版本：`1.1.7`。

普通请求如“检查当前项目的模块联邦配置”，默认完成检查、修复和复检。用户要求只读、审计、评审、只出报告、采集改前基线或仅复检时，按该阶段取证并交付发现。同一请求包含后续修复时，先保留基线，再实施已授权阶段。

## 首次调用提示

简要说明目标项目、检查范围和本次是否包含修复；已有项目路径和需求时直接执行。只有用户询问用法时读取 [使用说明](USAGE.md)。

## 执行与按需读取

1. 运行 `scripts/check-module-federation.ps1 -ProjectPath <项目路径>`。需要机器结果加 `-Json`，指定构建清单加 `-ManifestPath`，核验菜单传真实 `-ComponentPath`。
2. 仅 `Integrated` 进入完整审计；`Provider` / `Consumer` 报告类型证据及专项审计尚未支持；`Unknown` 报告不足或冲突证据并停止，不猜测。
3. 综合端审计读取 [规则矩阵](references/integrated-rule-matrix.md)，按 [验证清单](checklists/integrated-validation.md) 补充构建、独立运行和宿主加载检查。只报告实际执行结果。
   涉及 resolver、公共组件、依赖升级或菜单首次进入重载时，按 [预构建检查](references/prebuild-check.md) 核对实际入口与冷启动证据；后续发现的公共入口持续登记。
4. 对每项发现核对适用规则、当前生效的源码或配置、依赖和实际影响。格式化差异、别名、工厂或 spread 生成的配置、过期产物都可能影响静态结果。能从项目取得的证据先自行补齐，包括脚本遗漏但在本次范围内的确定偏差。
5. 在默认修复模式下，违规已证实且项目现有契约能确定改法时，首次编辑前使用 `aura-web-develop`，执行全部适用规范，直接作最小修复。例：有效 federation 配置漏写某项共享依赖的 singleton，而当前项目与消费契约均要求单例，可在现有 shared 定义补齐。修复配置源，按项目流程重建受影响的产物。
6. 仍有多个合理方案、缺少关键事实或需要扩大写入范围时，先完成其他确定项，再集中请用户抉择。给出规则、位置、已有证据、可选方案及影响。例如部署清单给出两个有效的 manifest 地址，当前环境的目标尚未确定，应请用户选目标；选择前保留该项现状。缺少可运行的宿主等验证条件时，说明待补证据及获取方式。
7. 修复后用相同项目、范围及适用输入重跑探针；若原 manifest 已过期，先用改后产物复检。核对原发现及新增发现，并按影响验证构建、宿主加载或冷启动。仍有确定偏差则继续处理；用户待选与环境缺证分别报告。类型、退出码及交付字段见[报告契约](references/audit-report-contract.md)。
8. 综合端需要交付提供方接入参数且复检无确定错误时，按[对外接入说明](references/provider-consumer-handoff.md)交付。修改其他消费方、后台菜单或部署环境以用户指定的目标和授权为准。

## 规范依据

优先级：用户要求 → 项目源码、类型、实际依赖和产物 → [正式规范](knowledge/PIGX前端开发规范/模块联邦开发技术规范.md) → 规则矩阵与脚本。出现规范冲突或配置细节疑问时读取正式规范。

本技能对消费项目执行的 `@fxft/aura-web-kit` 实装下限为 `1.12.1`。核对项目声明、所属锁文件条目的解析版本、实际安装及所用公开入口；较高的合规版本按实际契约核验。低于门槛记录偏差，升级目标与接入范围按项目依据或用户选择确定。Element Plus `2.14.6` singleton 和 Node.js ≥22.12.0 沿用现有规则。

随包[aura-web-kit 清单](knowledge/PIGX前端开发规范/aura-web-kit能力清单与接入规范.md)与[升级来源记录](references/framework-upgrade-source.json)保留历史版本证据；其中 `1.9.0` 用于追溯。审查现有项目按上述下限与实际契约判断。
