**规范对象**：使用 AURA 开展业务应用、服务、工具和平台工程开发的团队和开发人员

**跨规范边界**：本规范负责异步任务、消息和外部调用的运行行为；本地事务与数据一致性遵循 `BASE-08`，后端代码落点遵循 `BASE-03`，公开请求、响应和错误契约遵循 `BASE-05`，异常日志与链路信息遵循 `BASE-09`。

**本文件内容**：异步任务边界、消息语义、状态、幂等、顺序、重试、并发、上下文与批量任务。

## 一、异步任务与消息处理

### 1. 任务与消息边界

### AURA-BASE-ASYNC-001：异步处理必须有明确的业务任务边界

**必要性**：必须

当操作转为后台执行且调用方需要获知最终结果时，必须定义任务标识、受理结果、当前状态、最终结果和查询或通知方式；不得把受理伪装成同步完成。耗时或跨服务调用是否转为异步，应结合业务响应要求和资源边界决定。

**为什么需要**：调用方需要知道请求只代表受理，还是已经完成业务结果。

**正确写法**：提交设备分析返回 `taskId` 和“已受理”，通过任务查询或事件获取完成、失败和取消结果。

**错误写法**：接口立即返回“分析成功”，实际工作仍在后台排队，失败时没有可查询状态。

**判断要点 / 验证方式**：检查受理响应、状态模型、结果入口和失败表达，确认调用方能区分受理与完成。

### AURA-BASE-ASYNC-002：消息必须表达唯一业务含义

**必要性**：必须

每类消息必须明确事件、命令或结果中的一种语义，并说明生产者、消费者、关键字段和处理后的业务变化，不得使用同一消息同时承担互相冲突的语义。

**为什么需要**：消息语义不清会导致消费者自行猜测，形成重复处理或状态覆盖。

**正确写法**：`DeviceReviewRequested` 表示请求审核，`DeviceReviewCompleted` 表示审核完成，两者由不同状态转换产生。

**错误写法**：使用 `device-message`，由不同消费者自行判断字段决定是请求、通知还是结果。

**判断要点 / 验证方式**：阅读消息名称、载荷和消费代码，确认每种消息只有一个可解释的业务语义。

### AURA-BASE-ASYNC-003：任务状态必须覆盖适用的生命周期

**必要性**：必须

任务必须区分受理、处理中、成功、失败等实际适用的状态，并规定状态转换条件、终态和重复操作行为；只有支持取消时才定义取消状态与生效时点。允许重试的任务还需说明重试中是否回到待执行态。

**为什么需要**：只有明确状态机，调用方和运维人员才能判断任务是否仍会继续变化。

**正确写法**：普通任务定义 `ACCEPTED → RUNNING → SUCCEEDED/FAILED`；支持取消的任务另定义 `CANCEL_REQUESTED`、`CANCELED` 及与完成竞态时的处理，失败重试保留尝试次数和最终原因。

**错误写法**：只有一个布尔字段 `done`，无法区分排队、处理中、失败和取消。

**判断要点 / 验证方式**：逐项执行正常、失败、取消、超时和重复操作，确认状态不会跳过必要语义或回到非法状态。

### 2. 幂等、顺序与一致性

### AURA-BASE-ASYNC-004：消息处理必须具备业务幂等性

**必要性**：必须

可能重复投递的消费者必须使用业务唯一键、消息标识或版本条件识别重复处理，并把幂等判断与业务状态变更放在一致性边界内；同一业务操作重复执行不得产生重复结果或错误覆盖。若处理还会调用外部系统，必须把幂等键或结果确认延伸到该副作用边界。

**为什么需要**：网络重试、消费者重启和消息重复投递都是正常情况，不能依赖“只投递一次”的假设。

**正确写法**：以 `reviewId + operation` 作为幂等键，与审核状态写入一起保证唯一；重复消费读取已完成结果，涉及外部创建时复用同一幂等键或查询远端结果。

**错误写法**：每消费一次消息就新增一条审核记录，不检查消息标识和业务状态。

**判断要点 / 验证方式**：重复投递、并发消费和消费者重启后检查数据、状态和外部副作用是否只产生一次。

### AURA-BASE-ASYNC-005：有顺序要求的消息必须携带顺序依据

**必要性**：必须

依赖前后顺序的状态变更必须携带版本号、序列号或其他可比较依据，并在乱序、重复或缺失前序消息时按业务契约拒绝、等待、补拉或补偿。无需严格顺序的处理不必人为引入全局排序，但仍须满足幂等要求。

**为什么需要**：异步传输和多消费者处理可能造成延迟消息先到，直接覆盖新状态。

**正确写法**：设备状态更新携带递增版本；连续状态流只接受预期下一版本，允许跳版本的状态快照只接受高于当前版本的新值，相同版本按幂等结果处理。

**错误写法**：按消息到达顺序无条件更新状态，晚到的旧消息覆盖最新状态。

**判断要点 / 验证方式**：交换消息顺序、重复发送旧版本，确认系统能够识别并正确处理乱序。

### AURA-BASE-ASYNC-006：本地事务与消息发布必须保持可解释的一致性

**必要性**：必须


需要保证消息最终投递的业务动作，必须在同一本地事务内持久化业务状态和待发布记录，或采用能证明同等可靠性的机制；提交后由投递程序发送、记录投递结果并允许幂等重试。仅在事务提交后直接调用一次发送接口，不足以保证进程中断或发送失败时消息不丢失。

**为什么需要**：业务数据和消息状态不一致会造成任务永远不处理或重复处理。

**正确写法**：在本地事务中同时写入审核状态和待发布事件；提交后投递，发送失败保留待发送状态，重复投递由消费者幂等处理。

**错误写法**：事务中直接发送远程消息，发送成功后数据库回滚，或数据库提交后直接异步发送但无失败记录。

**判断要点 / 验证方式**：模拟提交失败、发送失败、进程中断和重复发布，检查最终状态和补偿路径。

### 3. 超时、重试与失败

### AURA-BASE-ASYNC-007：异步处理必须有超时或终止条件

**必要性**：必须

任务、重试和等待外部依赖必须有明确的超时、最大执行时长或终止条件。达到边界后应按任务契约进入可查询的失败、待确认或待人工处理状态；只有已确认取消生效时才标记为取消，不得把本地等待超时直接解释为远端操作失败。

**为什么需要**：没有终止条件的任务会长期占用资源并让调用方无法判断结果。

**正确写法**：外部分析按约定次数和总时限重试；无法确认远端写入结果时进入 `PENDING_CONFIRMATION` 并查询或人工处理，确认未完成后再进入 `FAILED`。

**错误写法**：失败后无限重试，任务一直保持“处理中”，没有终止或人工处理入口。

**判断要点 / 验证方式**：阻断外部依赖并等待超时，确认任务终态、资源释放和错误信息可查询。

### AURA-BASE-ASYNC-008：重试策略必须区分可重试和不可重试失败

**必要性**：必须

网络暂时不可用、限流和服务忙等暂态失败可在满足幂等及调用预算前提下按退避策略重试；参数错误、权限失败、数据不合法等确定性失败应终止当前尝试，只有输入或授权条件变化后才重新执行。远端结果不确定时先按 `INTEG-011` 确认结果，不盲目重复写入。

**为什么需要**：对不可重试错误无限重试会放大故障并产生重复副作用。

**正确写法**：对超时采用指数退避和上限，对权限不足直接记录失败并返回明确原因。

**错误写法**：不区分错误类型，所有异常每秒重试，或遇到业务校验错误继续发送相同消息。

**判断要点 / 验证方式**：分别注入暂态和确定性错误，检查重试次数、间隔、终止状态和资源使用。

### AURA-BASE-ASYNC-009：失败信息必须支持定位和处理

**必要性**：必须

任务和消息处理失败必须记录业务标识、尝试次数、失败分类、关键原因和下一步处理方式；不得只保存“处理失败”这一不可行动的文本。

**为什么需要**：可定位的失败信息才能支持自动重试、人工处理和问题复盘。

**正确写法**：记录 `taskId`、依赖名称、超时分类、受控的远端响应摘要和是否允许重试；完整响应及敏感内容不进入普通日志或任务结果。

**错误写法**：捕获异常后只记录 `failed=true`，丢失原始原因和关联任务。

**判断要点 / 验证方式**：构造不同失败场景，确认日志、任务状态和接口结果能够相互关联。

### 4. 资源与可观察行为

### AURA-BASE-ASYNC-010：异步任务必须限制并发和资源占用

**必要性**：必须

线程、连接、队列、文件、内存和外部调用次数必须有并发、批次、大小或速率边界，并在容量耗尽时明确拒绝、延迟受理或降级行为；不得因任务堆积无限创建线程或读取全部数据。执行器、关闭和资源释放细节遵循 `BASE-11`。

**为什么需要**：异步只是延后执行，不会消除资源消耗；无界并发会把局部故障扩大为系统故障。

**正确写法**：限制消费者并发和单批大小，队列积压超过阈值时暂停接收或降级。

**错误写法**：每条消息创建新线程，并把整个数据集一次性加载到内存处理。

**判断要点 / 验证方式**：增加消息积压和大批量数据，观察线程、内存、连接、延迟和拒绝行为是否受控。

### AURA-BASE-ASYNC-011：任务和消息必须可关联到请求上下文

**必要性**：必须

请求触发的异步处理应携带任务标识、原请求关联标识及执行所需的最小租户或授权范围；系统触发的任务应建立自身的执行主体和任务标识。不得把用户 Token 或完整请求上下文长期放入消息，消费时必须按可信来源重建并校验执行权限。

**为什么需要**：没有关联上下文，无法从请求追踪到消息、任务和最终结果；直接传播凭据又会扩大泄露范围。

**正确写法**：用户触发消息携带 `taskId`、原请求关联标识、可信的租户和操作范围；消费者按受信执行身份及当前授权规则校验。系统定时任务记录系统执行主体，不伪造用户身份。

**错误写法**：消息没有任务或请求标识，或把完整用户 Token 长期写入持久化队列。

**判断要点 / 验证方式**：从请求追踪到消费者和结果，检查上下文完整性、敏感字段和权限重新校验。

### AURA-BASE-ASYNC-012：消费者处理结果必须可观测

**必要性**：必须

异步处理必须能够观察接收、开始、成功、失败、重试和积压等实际适用的结果；消息被拒绝、进入死信或主动丢弃时还要记录原因和处理入口。任务/消息标识用于日志和状态定位，指标使用低基数结果分类，不把单个任务标识作为指标标签。


**为什么需要**：只观察生产端发送成功，无法判断消息是否被处理或是否持续失败。

**正确写法**：记录任务状态和处理耗时，统计成功率、失败率、重试次数和队列积压。

**错误写法**：只记录“消息已发送”，消费者失败和队列积压没有任何可查询结果。

**判断要点 / 验证方式**：注入消费失败、重试和积压，确认日志、指标、任务状态和告警入口能够互相定位。

### 5. 批量任务与结果生命周期

### AURA-BASE-ASYNC-025：批量异步任务必须表达进度与结果

**必要性**：必须

批量异步任务必须记录总量、已处理量、成功量、失败量、当前阶段和最终状态；业务允许部分成功时应保留失败项及可重试依据，要求整体原子成功时则说明回滚范围，不得把已处理量当作成功量。

**为什么需要**：进度和结果语义明确，调用方才能判断任务是否仍在运行，以及失败后能否继续处理。

**正确写法**：允许部分成功的导入任务返回 `total`、`processed`、`succeeded`、`failed` 和失败项查询入口；整体原子任务在失败时返回明确回滚结果。

**错误写法**：批量任务只显示“处理中/完成”，失败项和已处理范围不可查询；部分数据已入库却返回“全部失败”。

**判断要点 / 验证方式**：让不同批次失败、取消和恢复，核对进度不倒退、成功失败数量与实际数据一致，重复查询结果稳定且重试范围明确。

### AURA-BASE-ASYNC-026：任务结果必须有保留和清理期限

**必要性**：必须

异步任务结果、失败明细和临时文件必须按用途明确可查询期限、访问权限和清理方式；到期后应返回明确的过期或不可用结果，不能无限保留，也不能仅凭任务 ID 绕过权限继续访问。

**为什么需要**：无限保留任务结果和文件会造成敏感数据扩散、存储增长和权限失控。

**正确写法**：导出任务按业务期限保留结果文件，到期后停止访问并按权限允许重新生成；失败明细按其敏感级别独立约定期限。

**错误写法**：任务文件永久保留，任何持有旧任务 ID 的用户都可以继续下载。

**判断要点 / 验证方式**：模拟到期、清理失败和过期地址访问，确认结果不可越权继续使用；核对期限与项目数据生命周期约定一致。

### 6. 开发场景

### 正例：可重试且幂等的异步任务

```text
提交审核 → 返回 taskId/ACCEPTED
       → 消费者按 reviewId 幂等处理
       → 暂态超时按退避重试
       → 超过上限进入 FAILED
       → 查询接口返回最终状态和失败原因
```

该流程明确了受理与完成边界、幂等键、重试上限、终态和可查询结果。

### 反例：无状态、无边界的后台线程

```text
请求收到后直接 new Thread()
→ 调用外部服务失败后无限重试
→ 不记录 taskId、版本和失败原因
→ 接口始终返回成功
```

该实现无法判断任务结果，重复执行会产生副作用，失败也无法恢复或定位。

#### 典型使用场景：设备分析异步任务

**场景目标**：用户提交设备分析后立即得到受理结果，后台任务按租户范围执行；外部分析服务发生超时或重复投递时，任务仍能通过幂等键、有限重试和结果查询收敛到可解释终态。

**输入条件**：请求已通过身份和权限校验；任务记录包含 `taskId`、业务幂等键、租户范围和原请求关联标识；外部服务支持按同一幂等键查询结果；分析结果文件有明确保留期限。

**正确调用链**：

```text
提交接口保存任务与待发布记录 → 返回 taskId/ACCEPTED
  → 消费者接收并按业务键幂等领取
  → 状态变为 RUNNING，调用外部分析服务
  → 暂态超时按总预算有限重试，结果不确定时先查询幂等键
  → 成功写入结果并变为 SUCCEEDED
  → 确定性失败变为 FAILED，超过预算进入 PENDING_CONFIRMATION 或待人工处理
  → 查询接口返回状态、进度、失败原因和结果访问入口
```

消息只携带 `taskId`、原请求关联标识和最小授权范围，不持久化用户 Token；消费者重新建立受信执行上下文。任务进度、成功量、失败量、重试次数、积压和结果文件按约定观察与清理；重复消息读取已完成结果，不重复产生外部副作用。

**错误调用链**：提交接口直接返回“分析成功”；消息没有任务标识；每次消费都新建分析任务；外部超时后盲目重复创建；任务无限保持处理中；结果文件永久保留且只凭任务 ID 下载。

**验证步骤与预期结果**：

1. 重复提交和重复投递同一业务键，预期只产生一个逻辑任务和一个外部分析副作用。
2. 模拟消费者重启、消息乱序、外部超时、远端已成功但响应丢失，预期任务按幂等键查询或进入明确待确认状态。
3. 让任务超过执行时长、重试次数或队列容量，预期进入定义的终态/拒绝状态并释放资源，不能无限堆积。
4. 在任务成功、失败、过期和无权限下载时查询结果，预期状态、权限和文件生命周期一致。

### 7. 开发者自检

- 异步请求是否明确区分受理、处理中和完成；
- 消息语义、生产者、消费者和状态变化是否清晰；
- 任务生命周期、幂等键、顺序依据和一致性策略是否明确；
- 是否区分可重试与不可重试失败，并设置超时和上限；
