# AURA（天玑）基础编码规范：启动与服务生命周期

**规范对象**：使用 AURA 开展业务应用、服务、工具和平台工程开发的团队和开发人员

**跨规范边界**：本文件约束启动、就绪、运行降级、后台任务、停止、恢复、版本识别等服务生命周期行为；存活和就绪入口的环境适用性遵循 `BASE-06`，异步任务与消息结果遵循 `BASE-10`，身份和敏感信息遵循 `BASE-07`，版本交付标识遵循 `BASE-13`。具体框架组件的接入方式以对应能力包为准。

## 一、启动与就绪

### AURA-BASE-RUNTIME-001：启动必须校验必需配置和运行前提

**必要性**：必须

应用启动时必须校验必需配置和可确定的兼容前提；缺失密钥、配置格式错误或已确认的数据结构不兼容等不可恢复问题应明确失败。关键外部依赖暂时不可用时，应保持未就绪并按有边界的策略恢复，不得把暂态故障伪装成启动成功后可接收业务流量。

**为什么需要**：启动阶段尽早失败比运行中持续产生错误更容易定位和恢复。

**正确写法**：启动时校验数据库连接配置和必要密钥格式；配置缺失时说明配置项并终止启动，数据库暂时不可达时保持未就绪，恢复后再接收工作。

**错误写法**：缺少地址时使用空字符串，服务仍然启动，直到第一个请求才抛出空指针。

**判断要点 / 验证方式**：分别注入配置缺失、结构不兼容和关键依赖短时故障，核对启动结果、就绪变化及错误信息。

### AURA-BASE-RUNTIME-002：启动过程不得执行不可控的业务副作用

**必要性**：禁止

启动初始化只能执行幂等、边界明确且与服务可用直接相关的动作；数据迁移、批量发送、全量同步和长时间业务处理不得隐式绑定每次启动。

**为什么需要**：服务重启可能频繁发生，启动副作用会造成重复数据、启动超时或流量放大。

**正确写法**：启动只注册客户端和加载必要缓存，数据迁移和批处理通过独立、可追踪的任务执行。

**错误写法**：每次进程启动都扫描全库并向外部系统重新发送全部数据。

**判断要点 / 验证方式**：重复启动和并发启动，检查是否产生重复写入、重复消息或无法控制的启动耗时。

### AURA-BASE-RUNTIME-003：就绪状态必须随服务承载能力变化

**必要性**：必须

向外接收流量或工作的服务，只有在必需初始化完成且关键资源足以处理目标请求时才能报告就绪；运行期间关键能力失效时应撤销就绪，恢复后再重新就绪。非关键依赖故障可保持核心功能就绪，但受影响功能必须表达降级；不得用暂态依赖故障误导存活判断。一次性任务以退出状态或任务结果表达，不要求提供服务探针。

**为什么需要**：调用方需要区分进程还活着、正在启动和已经可以承担业务流量。

**正确写法**：服务在数据库连接池和必要配置可用后进入就绪；运行中关键数据库失效时暂停接收依赖该库的新工作，恢复后重新就绪；非关键推荐服务故障只影响推荐能力。

**错误写法**：进程一启动就返回健康，实际请求仍会因连接池和配置未完成而失败。

**判断要点 / 验证方式**：在启动延迟、运行中关键依赖故障、非关键依赖故障和恢复时，核对就绪、存活、降级状态与实际业务结果；探针部署条件遵循 `AURA-BASE-ENV-003`。

## 二、运行、停止与恢复

### AURA-BASE-RUNTIME-005：运行时降级必须保持可解释

**必要性**：必须

非关键依赖不可用时，应用可以进入明确的只读、排队、受限功能或待恢复状态；降级范围、恢复条件和对外结果必须可识别。

**为什么需要**：无边界降级会让使用者误以为业务已完成，造成错误数据和错误决策。

**正确写法**：推荐服务不可用时标记推荐结果暂不可用，核心查询仍可用，并记录恢复后的重建行为。

**错误写法**：依赖失败时返回空数据并标记成功，让调用方无法区分“没有数据”和“服务故障”。

**判断要点 / 验证方式**：阻断非关键依赖，确认受影响功能、响应结果和恢复过程均有明确表达。

### AURA-BASE-RUNTIME-006：后台线程和任务必须受生命周期管理

**必要性**：必须

应用创建的线程、定时任务、消费者、连接和临时资源必须有明确的启动、停止与释放路径；支持暂停或重新加载时还须定义相应状态。不得创建脱离应用生命周期、无法关闭或无法定位失败的后台工作。

**为什么需要**：失控后台任务会在服务停止后继续操作数据，或在重复启动时产生多个消费者和定时器。

**正确写法**：通过统一任务管理器注册定时任务，停止时取消调度、等待执行结束并释放资源。

**错误写法**：在业务方法中直接 `new Thread()`，不保存引用，也没有停止和异常处理方式。

**判断要点 / 验证方式**：启动、重载、停止和重复启动应用，检查线程、任务、连接和消费者数量是否回收并保持稳定。

### AURA-BASE-RUNTIME-007：停止过程必须优先完成可安全收尾的工作

**必要性**：必须

收到停止信号时，应用应先停止接收新工作，在约定时限内完成可安全收尾的请求和任务；未完成的工作须保留可恢复状态，消息确认不得早于受保护的处理结果持久化。超过时限时应明确放弃、接管或重试方式，不能仅依赖进程正常退出。

**为什么需要**：直接终止会造成半写入、消息丢失和任务状态永久停留。

**正确写法**：先停止接收新消息，再有限等待当前任务；已完成并持久化的消息才确认，未完成的任务保留待接管状态，随后释放连接和执行器。

**错误写法**：收到停止信号立即关闭进程，不保存处理中任务，也不释放外部资源。

**判断要点 / 验证方式**：在请求、消息和批处理执行期间停止应用，检查新任务、当前任务、状态记录和资源释放。

### AURA-BASE-RUNTIME-008：重复启动和恢复必须保持幂等

**必要性**：必须

服务重启、故障恢复或实例替换后，初始化、任务接管、消息消费和缓存构建不得重复产生业务副作用；需要恢复的任务必须依据状态和幂等键继续处理。多实例并行接管时，还须使用共享的租约、版本条件或等效机制防止同一工作被同时认领。

**为什么需要**：重启和实例替换是正常运行场景，不应依赖人工清理重复结果。

**正确写法**：消费者依据任务状态和共享租约接管未完成任务，重复执行复用幂等键；索引初始化核对版本与存在性，避免重复创建。

**错误写法**：每次启动都重新创建定时任务、重复发送未确认消息或重建全部业务记录。

**判断要点 / 验证方式**：连续重启、异常退出后恢复，检查数据、任务、消息和缓存结果是否一致。

### AURA-BASE-RUNTIME-009：运行时版本和能力必须可识别

**必要性**：必须

应用应能在不泄露敏感信息的前提下提供当前版本、构建标识和启用能力的可识别信息，用于定位交付内容和行为差异。

**为什么需要**：同名服务可能运行不同版本或能力组合，无法识别会导致排障和兼容判断失真。

**正确写法**：提供受保护的版本信息，包含源码标识、构建时间和能力版本，不返回密钥和内部凭据。

**错误写法**：所有实例都显示 `latest`，或调试接口直接暴露环境变量和 Token。

**判断要点 / 验证方式**：核对运行信息与 BASE-13 交付物标识，确认内容可定位且不包含敏感数据。

## 三、典型使用示例：关键依赖恢复与后台任务接管

**场景目标**：服务启动时区分存活与就绪，运行中关键数据库短暂故障时停止接收相关工作；恢复或重启后，后台任务按照状态和租约安全接管，不重复产生业务副作用。

**输入条件**：数据库是关键依赖，推荐服务是非关键依赖；导入任务由消费者处理；任务记录包含状态、租约和幂等键；实例可能在任务处理中收到停止信号。

**正确生命周期**：

```text
缺少必需配置 → 启动失败
数据库暂时不可达 → 进程存活但未就绪，不接收新导入
推荐服务不可用 → 核心能力保持就绪，推荐功能明确降级
数据库恢复 → 重新检查连接池与任务能力后恢复就绪
收到停止信号 → 停止新接收，有限等待当前任务并持久化状态
实例重启 → 按租约、状态和幂等键接管未完成任务
```

启动初始化只注册客户端和任务管理器，不扫描全库或批量发送；后台消费者、定时器和连接在停止和取消路径释放。未完成任务不能在停止时提前确认消息，恢复时也不能仅按“未确认”无条件重复写入。

**错误生命周期**：进程启动即报告健康和就绪；数据库不可用仍接收导入；推荐服务失败返回空结果并标记成功；停止时立即退出且不保存任务状态；重启后多个实例同时执行同一任务。

**验证步骤与预期结果**：

1. 注入缺少配置、数据库不可达、推荐服务不可用和数据库恢复，预期存活、就绪、降级和业务结果分别表达实际状态。
2. 在导入执行、消息等待和定时任务运行期间停止服务，预期新工作停止，已完成结果持久化，未完成工作可接管。
3. 连续重启并启动多个实例，预期租约和幂等键阻止重复执行，线程、连接、消费者和定时器数量最终稳定。

## 四、开发者自检

- 启动是否校验必需配置和运行前提；
- 启动初始化是否幂等且没有不可控业务副作用；
- 存活、就绪和依赖状态是否按 `BASE-06` 分开表达；
- 后台线程、任务、消费者和连接是否纳入生命周期管理；
- 停止和恢复时是否能保存、接管或重试未完成工作；
- 版本和能力是否可定位且不暴露敏感信息。
