# AURA（天玑）基础编码规范：身份上下文与权限边界

<!-- 规范编号：BASE-07 -->
<!-- 规范版本：0.1.0-draft -->
<!-- 模板版本：基础编码规范模板 v3 -->

**适用对象**：使用 AURA 开展业务应用、服务、工具和平台工程开发的团队和开发人员

**规范目标**：统一身份来源、上下文传递、权限判断与租户隔离的开发边界。

**边界说明**：本规范规定业务项目的使用方式，不描述统一认证平台或权限中心的内部实现。接口字段和错误响应遵循 BASE-05。

## 一、身份与上下文

### AURA-BASE-SEC-001：身份必须来自受信任的认证上下文

**必要性**：必须

**为什么需要**：只有来自受信任上下文的身份才能作为授权和审计依据，避免调用方伪造用户、服务或租户信息。

用户或服务身份必须来自框架已验证的认证上下文；租户选择、组织和数据范围还必须与该身份的有效权限对应。`TENANT-ID` 等请求字段用于按接口契约传递上下文，不因出现在请求头中就自动成为授权依据；链路标识只用于追踪，不能用于授权。业务代码不得仅凭请求参数、页面字段或客户端自报值建立身份。


**正确写法**：从框架认证上下文取得当前用户，再按框架权限与租户上下文确认所选租户；请求体中的 `userId` 不参与授权。

**错误写法**：直接信任 `userId`、`tenantId` 或 `role` 请求参数。

**判断要点 / 验证方式**：替换请求身份字段，确认服务端结果仍以认证上下文为准。

### AURA-BASE-SEC-002：身份上下文必须按公开契约传递

**必要性**：必须

**为什么需要**：统一传递身份、租户和链路上下文，可以避免不同服务自行解释字段并造成权限和审计断裂。

跨层、跨模块和服务间调用只传递公开契约允许的身份上下文。不得复制、拼接或自行解释未公开的 Token、内部标识和认证载荷。


**正确写法**：服务间调用按 `BASE-05` 的统一客户端获取服务身份，只传递公开契约要求的租户、用户委托和链路上下文。

**错误写法**：拼接内部 Token 载荷或复制认证平台私有字段到下游。

**判断要点 / 验证方式**：检查调用客户端、请求头和上下文对象字段来源。

### AURA-BASE-SEC-003：身份缺失和失效必须明确失败

**必要性**：必须

**为什么需要**：身份无效时明确拒绝可以防止系统错误降级为匿名、默认租户或高权限身份。

身份缺失、过期或凭证无效时，受保护入口必须终止业务处理并返回接口契约规定的未认证结果；已认证但无权限或租户范围无效时，返回相应的禁止访问结果。不得降级为匿名高权限、默认租户或调用方传入的备用身份。新接口按 `BASE-05` 状态码基线设计，已有特殊状态码按模块契约记录兼容行为。

**正确写法**：令牌过期时按接口契约返回未认证结果；已登录用户选择无权访问的租户时拒绝访问，而非改用默认租户。

**错误写法**：身份解析失败后使用默认用户、默认租户或匿名管理员继续处理。

**判断要点 / 验证方式**：分别使用缺失、过期、无效凭证及无权限租户执行请求，核对状态码与业务处理是否符合契约。

## 二、权限与租户

### AURA-BASE-SEC-004：权限校验必须位于服务端真实边界

**必要性**：必须

**为什么需要**：服务端是数据和业务操作的真实边界，只有在此校验才能防止绕过前端页面直接调用接口。

前端菜单、按钮和路由控制只改善用户体验，不能替代后端授权。每个需要保护的服务入口必须在服务端完成权限判断。


**正确写法**：后端入口执行资源权限判断，前端只负责隐藏无权操作。

**错误写法**：因为按钮在前端隐藏，就删除后端接口鉴权。

**判断要点 / 验证方式**：绕过页面直接调用接口，确认未授权请求被拒绝。

### AURA-BASE-SEC-005：权限判断必须对应业务动作和资源

**必要性**：必须

**为什么需要**：权限与具体动作、资源和数据范围对应，才能准确表达允许什么操作，而不是依赖页面显示或角色名称猜测。

权限标识应表达稳定的业务动作、资源或数据范围。不得只按页面可见性、前端传入角色名称或接口路径字符串决定授权。


**正确写法**：设备审核入口使用权限中心已登记的“设备审核”权限编码，并结合目标设备资源判断；不根据按钮文字临时生成权限标识。

**错误写法**：使用页面位置、按钮文本或客户端角色名称作为唯一授权依据。

**判断要点 / 验证方式**：更换页面文案和路由，确认授权语义不变。

### AURA-BASE-SEC-006：租户和数据范围必须在查询与写入中生效

**必要性**：必须

**为什么需要**：租户和数据范围若只在页面或单个入口处理，其他查询、导出和写入路径就可能造成数据越界。

涉及租户或数据范围的项目，必须在服务端查询、更新、删除和导出路径中施加与当前有效身份一致的隔离条件。不能只在列表接口过滤，而遗漏详情、批量、异步和导出路径；请求中的租户标识不能替代对用户租户关系的判断。


**正确写法**：查询、更新、删除、导出和异步任务都从可信上下文取得租户条件。

**错误写法**：只给列表查询加租户过滤，详情或导出接口直接按请求 ID 查询。

**判断要点 / 验证方式**：跨租户访问各类入口，确认全部路径隔离。

### AURA-BASE-SEC-007：跨服务调用不得扩大调用方权限

**必要性**：禁止

**为什么需要**：服务间转发如果扩大权限，会让低权限调用方通过内部服务间接执行不被允许的操作。

服务间调用必须使用与调用场景匹配的服务身份和权限上下文。下游服务不得无条件信任上游传入的用户、租户或数据范围字段；以服务身份执行系统任务时，必须明确被允许的租户与资源范围，不得默认为全局管理员。

**正确写法**：下游验证服务身份，并按公开调用契约确认用户委托或服务任务允许的租户和数据范围。

**错误写法**：下游无条件信任上游传入的 `role=admin` 或租户字段。

**判断要点 / 验证方式**：伪造上游上下文，确认下游拒绝权限扩大请求。

## 三、典型使用示例：带租户范围的设备审核

**场景目标**：用户从浏览器提交设备审核，服务端依据认证上下文、租户关系、资源权限和业务状态完成审核，不信任请求体中的身份字段。

**输入条件**：请求携带框架认证上下文和 `TENANT-ID`；设备记录属于某个租户；审核动作需要已登记的设备审核权限；服务间调用可能由异步任务代为执行。

**正确调用链**：

```text
浏览器请求
  → 公共认证/租户上下文
  → Controller 仅解析审核命令
  → 应用用例校验用户与租户关系、资源权限、设备状态
  → 按租户条件读取并更新设备
  → 返回公开业务结果并记录关联请求标识
```

请求体只包含 `deviceId`、审核结果和业务说明；`userId`、`role`、`tenantId` 等身份与授权字段不作为可信来源。异步任务使用明确的服务身份和已登记的租户、资源范围，不默认提升为全局管理员。

**错误调用链**：直接按请求体的 `tenantId` 查询设备，或由前端隐藏按钮代替后端权限判断；服务间转发时无条件信任上游传入的 `role=admin`。

**验证步骤与预期结果**：

1. 使用合法用户访问所属租户设备，预期按接口契约完成审核。
2. 修改请求体 `userId`、`tenantId` 或 `role`，预期授权结果不改变且越权请求被拒绝。
3. 使用其他租户设备 ID、无权限用户和失效凭证分别调用详情、审核、批量和异步结果入口，预期全部执行相同的数据范围与身份校验。
4. 伪造上游服务上下文，预期下游拒绝权限扩大请求并保留可关联的失败记录。

## 四、开发者自检

- 身份和租户是否来自受信任上下文，而非请求体或前端状态；
- 查询、写入、批量、导出和异步路径是否使用同一数据范围约束；
- 服务间调用是否使用匹配的服务身份和最小权限；
- 未认证、无权限和租户无效是否按接口契约明确失败。
