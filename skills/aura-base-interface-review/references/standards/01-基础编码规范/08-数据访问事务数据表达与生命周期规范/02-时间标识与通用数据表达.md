## 二、时间、标识与通用数据表达

### 1. 时间与时区

### AURA-BASE-DATAEXP-001：前端时间必须使用统一的中国区表达

**必要性**：必须

中国区业务系统返回前端的时间，通常使用统一的日期时间字符串，例如 `2026-09-22 10:30:00`，由接口约定和前端公共组件按中国标准时间解析与展示。数据库可以保存带时区语义的时间值；是否输出偏移量或 UTC 形式，应由接口场景明确决定，不能要求所有前端统一接收 `Z` 格式。

**为什么需要**：现有中国区系统的使用者习惯直接查看 `YYYY-MM-DD HH:mm:ss`，强制改成 UTC 会增加无意义的前端转换；但如果没有统一的中国区解析约定，不同浏览器仍可能产生时区偏移。

**正确写法**：数据库保存带时区语义的时间；接口按项目统一约定返回 `2026-09-22 10:30:00`，前端通过公共时间组件按中国标准时间处理。只有需要表达跨时区瞬间的特定接口，才使用 `+08:00` 或 `Z` 等带时区格式。

**错误写法**：同一项目有的接口返回 `2026-09-22 10:30:00`，有的返回 UTC，有的返回时间戳，且前端页面各自猜测和换算。

**判断要点 / 验证方式**：检查接口是否遵守项目统一时间格式、前端是否使用公共解析方式，以及数据库时区语义是否保留；在不同浏览器环境中确认中国区时间展示不发生意外偏移。

### AURA-BASE-DATAEXP-002：存储、计算和展示的时间职责必须分开

**必要性**：必须

数据库可以保存带时区语义的时间，服务内部按业务约定计算；中国区对外接口通常输出统一的本地日期时间字符串，前端由公共组件解析和展示。不得把前端展示格式直接当作持久化事实。

**为什么需要**：把本地展示时间作为事实会导致跨区域排序、过期判断和审计时间错误。

**正确写法**：数据库保留时间的时区语义，接口统一输出 `2026-09-22 10:30:00`，前端公共组件按中国标准时间展示；需要跨区域比较的接口再明确输出带偏移量的格式。

**错误写法**：把前端格式化后的显示字符串直接保存，或让不同页面分别把接口时间按浏览器本地时区解析。

**判断要点 / 验证方式**：核对数据库时区、服务计算、接口格式和前端公共解析方式；确认切换浏览器环境不会导致统一中国区时间被重复换算。

### AURA-BASE-DATAEXP-003：日期、时间和时长不得混用

**必要性**：禁止

只有日期含义的字段使用日期类型；服务内部和持久化层表示瞬间时必须保留时区语义，对前端的字符串格式按接口契约转换；表示持续时间的字段使用明确单位的数值或时长类型。不得用一个含糊的字符串字段承载三种语义。

**为什么需要**：日期、瞬间和时长的计算规则不同，混用会产生跨日和夏令时错误。

**正确写法**：`effectiveDate` 表示业务日期，`createdAt` 表示瞬间，`timeoutMs` 表示毫秒时长。

**错误写法**：所有字段都使用 `String time`，由各调用方自行猜测格式和单位。

**判断要点 / 验证方式**：检查字段类型、命名和边界计算，确认日期、瞬间和时长可被明确区分。

### 2. 标识、数值与单位

### AURA-BASE-DATAEXP-004：业务标识必须稳定且不可依赖展示顺序

**必要性**：必须

实体、任务、消息和幂等操作必须使用稳定、唯一且具有明确责任的标识；不得把数据库自增值的大小顺序、数组下标或展示名称当作跨边界业务语义。数据库生成的标识可以作为公开标识，但必须有稳定契约，不能依赖其递增含义。

**为什么需要**：展示顺序和名称可能变化，不能承担关联、幂等和审计责任。

**正确写法**：使用 `deviceId`、`taskId` 和 `idempotencyKey`，并说明生成方和生命周期。

**错误写法**：以列表第 3 行、设备名称或当前时间字符串作为后续更新和关联依据。

**判断要点 / 验证方式**：改变排序、重命名和数据迁移后，检查关联、幂等和审计是否仍准确。

### AURA-BASE-DATAEXP-005：金额和精确数值必须使用可保持精度的表达

**必要性**：必须

金额、计费计量、比例和其他需要精确累计或比较的数值必须明确精度、舍入方式和单位，并使用能满足该精度要求的类型或契约表达。

**为什么需要**：浮点误差会在累计、比较和跨语言传输中形成不可接受的业务差异。

**正确写法**：金额使用 `BigDecimal` 并明确 2 位小数和舍入规则，接口传输使用字符串或约定精度的数值。

**错误写法**：使用 `double` 累计金额，或由不同前端分别决定四舍五入方式。

**判断要点 / 验证方式**：执行边界金额、累计、负数和跨语言序列化，核对精度和舍入结果。

### AURA-BASE-DATAEXP-006：数值单位必须由字段或契约明确表达

**必要性**：必须

长度、重量、时间、速率、容量和角度等数值必须在字段命名、类型或契约中明确单位，内部转换后不得继续使用含糊名称。

**为什么需要**：同一个数字在毫秒和秒、米和公里之间可能相差数量级。

**正确写法**：使用 `timeoutMs`、`distanceMeters`、`speedKph`，或在契约中明确统一单位。

**错误写法**：字段名为 `timeout`、`size`、`speed`，不同模块按自己的理解传值。

**判断要点 / 验证方式**：跨模块传递边界值，检查单位转换、命名和序列化结果是否一致。


### AURA-BASE-DATAEXP-007：枚举和状态值必须有稳定语义

**必要性**：必须

枚举、状态、类型和原因码必须定义稳定值、显示文本和未知值处理；调用方不得只依赖展示文本或数组顺序。

**为什么需要**：展示文字可变，多语言和新增状态不能破坏已有判断。

**正确写法**：使用 `RUNNING`、`SUCCEEDED` 等稳定代码，并为未知值提供兼容分支。

**错误写法**：根据“处理中”“完成”等中文文本判断业务，或以 `0/1/2` 的顺序推断状态含义。

**判断要点 / 验证方式**：切换语言、增加未知值和调整展示文本，确认业务判断仍按稳定代码执行。

### 3. 空值、编码与集合

### AURA-BASE-DATAEXP-008：空值、缺省值和空集合必须区分

**必要性**：必须

字段必须明确区分未提供、明确为空、默认值和空集合等语义；调用方不得把所有情况统一转换成空字符串、零或 `false`。

**为什么需要**：不同空值语义可能代表“不修改”“清空”“未知”或“没有结果”。

**正确写法**：需要区分“保持不变”和“清空”的部分更新接口，使用能区分字段缺失与显式 `null` 的请求模型并写明两者含义；列表无结果返回空数组。

**错误写法**：把缺失字段、`null`、空字符串和零都当成“清空并写入默认值”。

**判断要点 / 验证方式**：分别提交缺失、`null`、空集合和默认值，检查存储、响应和业务行为。

### AURA-BASE-DATAEXP-009：集合顺序和重复语义必须明确

**必要性**：必须

列表、集合、映射和批量参数必须说明是否有序、是否允许重复以及空集合的含义；调用方不得依赖未约定的数据库或对象遍历顺序。

**为什么需要**：未定义顺序和重复行为会导致分页、签名、批处理和界面展示不稳定。

**正确写法**：接口明确按 `createdAt,id` 排序，标签集合去重，批量操作说明重复标识的处理方式。

**错误写法**：直接返回数据库无排序结果，或默认认为输入数组没有重复项。

**判断要点 / 验证方式**：改变数据插入顺序、重复输入和分页边界，确认结果符合明确契约。

### AURA-BASE-DATAEXP-010：文本编码和规范化必须统一

**必要性**：必须

跨边界文本必须使用项目约定的字符编码、换行和 Unicode 规范化方式；文件名、搜索和签名场景必须明确是否进行大小写和空白处理。

**为什么需要**：编码和规范化差异会造成乱码、重复数据、搜索不一致和签名校验失败。

**正确写法**：接口和文件统一使用 UTF-8，比较前按约定处理 Unicode 和空白，不把展示文本直接作为唯一键。

**错误写法**：不同服务使用默认系统编码，或把肉眼相同但编码不同的文本当成相同标识。

**判断要点 / 验证方式**：使用中文、组合字符、换行和不同平台文件进行读写、搜索和签名校验。

### 4. 转换与兼容

### AURA-BASE-DATAEXP-011：数据转换必须在边界处完成并可验证

**必要性**：必须

单位、时区、精度、枚举和空值转换应在明确的边界层完成，转换规则必须可测试；不得让多个业务模块分别进行隐式转换。

**为什么需要**：集中转换可以避免同一数据在不同模块被重复或不一致地解释。

**正确写法**：适配器将外部秒数转换为内部毫秒，业务层只使用统一的 `Duration` 语义。

**错误写法**：Controller、Service 和前端各自把同一字段乘以 1000 或转换时区。

**判断要点 / 验证方式**：检查边界转换代码和测试，使用零值、最大值、未知枚举和跨时区数据验证。

### AURA-BASE-DATAEXP-012：新增表达不得破坏旧数据和未知值处理

**必要性**：禁止

新增状态、字段、单位或格式时，读取方必须对旧数据、缺失字段和未知值保持契约规定的安全行为；可忽略的扩展字段不应使整个任务失败，必须理解的状态或字段则应明确拒绝，不得误判为成功。

**为什么需要**：生产环境中的数据和调用方通常不会同时升级。

**正确写法**：新增状态时保留默认展示和安全分支，未知状态进入可观察的兼容路径，不误判为成功。

**错误写法**：遇到未知枚举时把任务误判为已完成，或把缺失的关键字段悄悄补成成功状态。

**判断要点 / 验证方式**：构造旧数据、缺失字段和未来未知值，检查读取、展示、存储和业务状态。

### AURA-BASE-DATAEXP-013：前端时间解析和展示必须统一

**必要性**：必须

前端不得在页面、组件或业务方法中自行猜测接口时间格式和时区。项目必须通过统一的时间解析和展示方式处理接口返回的中国区日期时间字符串，并区分只展示中国区业务时间、需要跨时区转换的瞬时时间和仅表示日期的字段。

**为什么需要**：同一接口时间被不同页面分别解析时，容易出现部分页面多 8 小时、少 8 小时或跨日的问题。

**正确写法**：公共请求或日期工具统一按中国标准时间解析 `2026-09-22 10:30:00`；页面只声明展示格式，不自行追加 `Z`、加减小时或重复转换。

**错误写法**：在某个页面中对接口日期字符串追加 `Z`、手工加 8 小时，或直接使用浏览器 `new Date()` 猜测其时区。

**判断要点 / 验证方式**：检查公共解析工具和页面调用方式，在中国区浏览器及其他时区浏览器中分别验证同一时间的展示结果。

### 5. 序列化、批量与跨边界兼容

### AURA-BASE-DATAEXP-014：序列化格式必须由契约统一决定

**必要性**：必须

接口、消息、缓存和文件的序列化格式、字段命名、日期格式、数字精度和字符编码必须遵循对应契约；业务代码不得在不同入口自行配置互相冲突的序列化规则。

**为什么需要**：同一个模型在不同入口采用不同格式，会造成字段丢失、时间偏移和前后端解析差异。

**正确写法**：统一由公共配置和边界转换决定 JSON 字段格式，内部模型不直接暴露数据库字段命名。

**错误写法**：某个 Controller 单独启用另一种日期格式，或在页面中根据响应内容猜测字段名称。

**判断要点 / 验证方式**：从接口、消息、缓存和文件分别读取同一类数据，核对字段、时间、精度和编码是否符合统一契约。

### AURA-BASE-DATAEXP-015：未知字段必须按兼容策略处理

**必要性**：必须

读取外部响应、消息或历史数据时，可忽略的新增字段不应导致处理失败；对于必须理解的字段变化，应明确拒绝并给出可定位原因。接收写入请求时，未知字段应按接口契约明确拒绝或忽略，不得误写为其他字段或假称该字段已更新。

**为什么需要**：提供方和调用方不会同时升级，未知字段是兼容演进中的正常情况。

**正确写法**：读取响应时忽略不影响当前业务的未知字段；关键字段缺失时明确失败；写入请求中的拼错字段按契约返回参数错误，或在已约定允许扩展字段时忽略该字段且不声称其已生效。

**错误写法**：只要响应增加一个无关字段就反序列化失败，关键字段缺失仍按默认成功处理，或写入请求中的拼错字段被静默接受并造成预期更新未发生。

**判断要点 / 验证方式**：向请求、响应和消息中增加未知字段、删除非关键字段和删除关键字段，检查处理结果是否符合策略。

### AURA-BASE-DATAEXP-016：字段转换必须保留业务语义

**必要性**：必须

数据库实体、内部模型、接口模型、消息模型和前端视图模型之间的转换必须明确字段来源、默认值、空值和枚举映射；不得通过无条件复制隐藏语义差异。

**为什么需要**：不同模型的字段可能具有不同的安全、精度、生命周期和展示含义。

**正确写法**：将数据库 `deleted_at` 转换为内部归档状态，将内部状态代码转换为接口稳定枚举。

**错误写法**：使用反射把数据库实体全部字段直接复制到公开响应，包含内部权限和审计字段。

**判断要点 / 验证方式**：检查字段映射、默认值、敏感字段和未知值，确认转换前后业务含义一致且没有越界字段。

### AURA-BASE-DATAEXP-017：批量数据必须采用可控的分批和结果表达

**必要性**：必须

批量查询、写入、导入和导出必须说明批次大小、顺序、失败范围和重复执行行为；业务选择原子成功或允许部分成功时，应分别明确回滚范围、失败记录与恢复方式。不得把大批量处理当作单次无限事务。

**为什么需要**：大批量操作需要控制锁、内存、连接和失败恢复范围。

**正确写法**：按受控批次处理导入，允许部分成功时记录成功和失败标识并支持重复执行；要求整批原子成功时在约定规模内失败回滚，不对外声称部分数据已成功。

**错误写法**：一次性读取和写入全部数据，任何一条失败都只返回“失败”，无法知道已处理范围。

**判断要点 / 验证方式**：使用空批次、超大批次、中途失败和重复执行，检查数据一致性、进度和失败明细。

### AURA-BASE-DATAEXP-018：查询结果必须避免暴露内部数据结构

**必要性**：必须

公开查询、导出和跨模块读取必须使用面向用途的查询模型和响应模型，不得直接暴露内部表名、内部状态、数据库主键生成规则或未授权字段。数据库主键若已被明确纳入稳定的公开标识契约，可按该契约返回其值。

**为什么需要**：内部结构一旦成为外部契约，后续迁移和权限控制都会受到约束。

**正确写法**：报表返回面向业务的 `deviceCode` 和状态说明；未进入公开契约的内部表主键与审计字段不返回。

**错误写法**：直接序列化 Entity 或 `select *` 结果作为接口响应和导出文件。

**判断要点 / 验证方式**：逐字段检查接口、导出和跨模块结果，确认只包含用途所需且已授权的数据。

### AURA-BASE-DATAEXP-019：既有数据格式变更必须保留兼容与恢复路径

**必要性**：必须

已有历史数据或旧消费者的字段重命名、类型变化、枚举调整和格式升级，必须采用适用的兼容读写、版本标识或分阶段切换，并在切换期间保留旧数据读取与可执行的恢复路径。首次定义且没有旧数据和旧消费者的格式不虚构兼容窗口；无法安全反向转换的数据按 `AURA-BASE-DATA-014` 选择前向修复、补偿或受控恢复。


**为什么需要**：数据格式通常比代码版本存活更久，直接替换会使历史数据和旧调用方不可用。

**正确写法**：新增字段并兼容读取旧字段，完成数据校验和消费者迁移后再清理旧字段。

**错误写法**：直接修改字段类型和枚举含义，未验证历史数据就删除旧字段。

**判断要点 / 验证方式**：对实际存在的旧数据、旧客户端和新数据执行读写与迁移验证，并按所选恢复路径检查切换或失败后的结果；无旧消费者时不虚构测试对象。

## 三、典型使用示例：设备列表与导出数据表达

**场景目标**：设备列表和导出任务在数据库、服务、接口和前端之间保持一致的数据语义；中国区页面展示统一的日期时间，跨模块关联使用稳定标识，批量导出不一次性加载全量数据。

**输入条件**：列表支持按创建时间、状态和设备编号筛选；接口返回设备状态、创建时间和导出任务标识；导出可能达到百万级记录；前端和服务均可能在不同运行环境中执行。

**正确数据链**：

```text
数据库保存带时区语义的瞬间和稳定设备标识
  → 查询层按受控字段排序并按批次/游标读取
  → 服务边界将状态代码、单位和时间转换为统一模型
  → 接口按契约返回中国区日期时间字符串与 taskId
  → 前端公共时间工具解析并展示，不追加 Z 或手工加减小时
  → 导出任务按批次写入受控文件并返回可查询的任务状态
```

列表排序使用 `createdAt,id` 等稳定组合键，分页和导出不依赖数据库默认顺序；金额、容量和时长等字段在名称或契约中明确单位和精度；任务关联使用 `taskId`，不使用列表下标、设备名称或当前时间字符串。接口返回的 `2026-09-22 10:30:00` 由公共组件按中国标准时间处理，只有跨时区瞬间才按契约输出带偏移量的形式。

**错误数据链**：查询无排序后在前端自行排序；把 `createdAt` 转成字符串后作为持久化事实；不同页面分别追加 `Z` 或加 8 小时；一次性 `selectAll()` 后在内存生成导出文件；以状态显示文本或数组序号判断业务状态。

**验证步骤与预期结果**：

1. 改变数据库插入顺序、同一时间的记录数量和分页边界，预期列表与导出顺序稳定。
2. 在中国区和其他时区浏览器中查看同一接口时间，预期中国区业务时间不被重复换算；跨时区接口按契约保留瞬间语义。
3. 使用大数据量、超大页、非法排序和导出中途失败，预期查询受控、排序字段被拒绝或映射、任务保留失败明细且可重试。
4. 改变设备名称、状态显示文本和列表排序，预期 `deviceId`、`taskId`、幂等和审计关联不受影响。

## 四、典型使用示例：批量导入与兼容扩展

**场景目标**：导入任务接收新旧版本文件和未知扩展字段，按明确的空值、枚举、单位和批次策略处理，既不误写业务数据，也不把未知状态误判为成功。

**正确处理链**：

```text
读取文件并校验 UTF-8、字段名和必填项
  → 在边界层转换日期、单位、枚举和空值
  → 按受控批次写入并记录批次序号、成功数和失败明细
  → 对已处理批次使用幂等键防止重复写入
  → 对非关键未知字段按契约忽略，对关键字段缺失明确失败
  → 返回可查询的导入任务状态和结果明细
```

缺失字段、显式 `null`、空字符串、零和空集合按契约分别处理；新增状态保留未知值兼容分支，不能把未知状态补成成功；字段重命名或格式升级时，已有历史数据和旧消费者采用兼容读写、版本标识或分阶段切换。部分成功和整批原子成功必须分别说明回滚范围、失败记录和恢复方式。

**错误处理链**：把所有空值转为空字符串或零；遇到一个未知扩展字段就让整批失败；按数组顺序推断状态含义；一次大事务处理全部文件；重复执行时不记录已处理批次，导致重复数据。

**验证步骤与预期结果**：

1. 分别提交字段缺失、显式 `null`、空集合、零值、未知枚举和新增扩展字段，预期结果与契约一致。
2. 在第 N 批失败后重新执行，预期已成功批次不重复，失败批次可定位、可重试或按策略回滚。
3. 使用旧格式文件、旧消费者和新格式文件并存，预期兼容窗口内读写均可解释；关键字段变化明确拒绝而不是默认成功。
4. 使用中文、组合字符、不同换行和不同平台文件，预期 UTF-8、规范化、签名和搜索结果稳定。

### 6. 开发者自检

- 瞬时时间的时区语义是否明确，日期、瞬间和时长是否分开；前端时间格式是否符合接口约定；
- 标识是否稳定且不依赖展示顺序或名称；
- 金额、精确数值和单位是否有明确精度与表达；
- 枚举、状态和未知值是否有稳定语义；
- 缺失、空值、默认值和空集合是否区分；
- 集合顺序、重复和文本编码是否明确；
- 转换是否集中在边界并覆盖旧数据和未知值。
- 前端是否通过统一方式解析和展示接口时间，未在页面中自行修正时区。
- 序列化、字段转换和未知字段是否遵循统一契约；
- 批量数据是否有批次、进度、失败明细和重复执行边界；
- 公开结果是否隔离内部数据结构；
- 格式变更是否保留兼容窗口和回退路径。
