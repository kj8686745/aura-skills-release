## 一、规则

### AURA-BASE-BE-024：重试和幂等不能默认成立

**必要性**：禁止

创建、修改、删除、批处理、外部调用、消息发送和任务执行不得默认可以安全重试。

需要重试或防重复时，应明确幂等依据、业务唯一性、重复提交处理和最终状态。

**为什么需要**：网络超时、消息重复和任务重入都可能导致同一动作执行多次，重试不等于天然安全。

**正确写法**：使用业务唯一键、幂等记录或状态机判断是否已处理，并限制重试次数和范围。

**错误写法**：对所有异常统一重试三次，或在没有幂等依据时重复执行扣款、创建设备和发送命令。

**判断要点 / 验证方式**：检查重复执行结果、幂等键稳定性和重复副作用；模拟超时后重试、重复消息和并发提交，确认唯一性、最终状态和补偿策略。是否具备安全重试依据由本规则判断；确认可重试后，次数、间隔、错误范围和总耗时另按 `AURA-BASE-BE-039` 约束。

**例外**：纯查询或明确无副作用的操作可以重试，但仍需有超时和次数边界。

### AURA-BASE-BE-052：写操作必须明确幂等和重复请求结果

**必要性**：必须

创建、更新、删除、状态变更和触发任务的后端入口必须说明重复请求的业务结果，并通过幂等键、唯一约束、版本条件或状态机避免重复副作用。

**为什么需要**：网络重试、用户重复点击和消息重复投递都会让同一写操作执行多次。

**正确写法**：创建审核任务使用业务幂等键，重复请求返回已有任务或明确冲突结果。

**错误写法**：每次请求都新增记录，只依赖前端按钮禁用防止重复提交。

**判断要点 / 验证方式**：检查重复请求、并发请求和超时重试下的数据、消息和外部副作用；使用相同幂等键连续提交并并发提交，确认最终只产生一个业务结果。

### AURA-BASE-BE-025：异步任务必须有最终状态

**必要性**：必须

后端异步任务、消息消费、批处理、导入导出和后台作业必须能够表达提交成功、执行中、成功、失败、部分成功、取消或超时等适用状态。

不得把“请求已提交”直接当作业务最终成功。

**为什么需要**：异步提交和业务完成是两个不同状态，混淆会造成错误提示、重复提交和无法追踪。

**正确写法**：任务记录 `处理中`、`成功`、`失败`、`部分成功`、`取消` 或 `超时`，并提供查询或回调依据。

**错误写法**：消息放入队列后立即把订单、导入或设备控制标记为成功。

**判断要点 / 验证方式**：是否区分受理结果和最终结果；失败和部分成功是否能被查询；任务是否可重入或取消；测试正常完成、消费失败、超时、重试和取消；人工核对状态转换和交付证据。

**例外**：明确属于“仅受理、不保证完成”的通知接口可以只返回受理结果，但必须在契约中说明。

**边界说明**：本规则只约束后端代码必须保留受理与最终结果的表达；任务状态模型、消息语义、重试和结果保留的完整要求遵循 `BASE-10`，接口公开字段遵循 `BASE-05`。

### AURA-BASE-BE-026：资源使用必须有释放边界

**必要性**：必须

文件流、网络连接、线程任务、临时文件、锁、批处理游标和外部资源必须有明确释放或关闭边界。

不得依赖不确定的对象回收来释放关键资源，也不得在异常路径遗漏释放。

**为什么需要**：资源泄漏会造成连接耗尽、线程堆积、临时文件残留和任务长期占用。

**正确写法**：使用明确的关闭、取消、超时和清理边界，并为成功、失败和取消路径分别处理释放。

**错误写法**：打开文件或连接后直接返回；异常时跳过临时文件删除和线程任务取消。

**判断要点 / 验证方式**：资源的创建者和释放者是否明确；异常、超时和取消路径是否执行清理；通过资源泄漏、超时和异常测试观察连接、线程和临时文件；人工检查生命周期。

**例外**：由框架完全托管且有明确生命周期证明的资源可以不在业务代码重复关闭。

### AURA-BASE-BE-027：并发修改必须有一致性策略

**必要性**：必须

涉及状态流转、库存、额度、审批、任务执行、设备控制或其他可能并发修改的业务时，必须明确一致性策略。

不得只依赖前端按钮禁用、页面刷新或偶然的执行顺序来保证后端一致性。

**为什么需要**：并发请求、消息重复和多实例部署会使前端控制失效，后端必须自己保证一致性。

**正确写法**：根据业务选择乐观锁、唯一约束、状态条件更新、分布式锁或串行化策略，并说明失败结果。

**错误写法**：先查询状态再无条件更新，或仅依靠前端按钮禁用阻止重复审批。

**判断要点 / 验证方式**：并发窗口是否明确；一致性策略是否与数据和业务结果匹配；冲突是否返回可处理结果；执行并发提交、重复消费和多实例测试；人工确认锁范围、顺序、超时和降级行为。

**例外**：明确无共享状态且无业务副作用的只读操作可以不设置并发控制。

### AURA-BASE-BE-036：批处理必须有边界和进度

**必要性**：必须

批量写入、导入、导出、同步和后台处理应明确批次大小、失败处理、进度和重入方式。不得在单次请求中无边界处理不可控数量的数据。

**为什么需要**：批处理边界决定内存、事务、耗时和失败恢复能力。

**正确写法**：按批次读取和提交，记录进度、失败明细和最终状态，并支持安全重入。

**错误写法**：一次请求读取全部文件和数据，循环写库，异常后无法知道已处理范围。

**判断要点 / 验证方式**：批次大小、进度、失败处理、重入方式和资源释放是否明确；测试大数据量、部分失败、重试和中断恢复；人工核对进度和最终状态。

**例外**：受控的小批量同步可以同步执行，但仍需有数量和超时边界。

### AURA-BASE-BE-053：批量后端操作必须返回可处理的部分结果

**必要性**：必须

批量接口和后台处理必须表达成功数量、失败数量、失败标识和是否可重试；不能把部分成功压缩为一个无法解释的布尔结果。

**为什么需要**：批量处理失败时，调用方需要知道哪些数据已完成以及下一步如何处理。

**正确写法**：返回批次标识、成功项、失败项和失败原因，重复执行按幂等键跳过已完成项。

**错误写法**：处理 1000 条数据时只返回“操作失败”，调用方无法判断是否需要全部重做。

**判断要点 / 验证方式**：检查批量事务边界、结果模型、失败明细和重试策略；在中途失败、重复执行和空批次场景检查结果是否可追踪。

### AURA-BASE-BE-040：线程和异步执行必须有归属

**必要性**：必须

创建线程、线程池、异步任务或并发执行单元时，必须明确其生命周期、命名、容量、拒绝策略和关闭方式。不得在请求处理中随意创建无法管理的线程。

**为什么需要**：线程和异步任务失去归属会导致线程泄漏、队列堆积、请求超时和服务无法关闭。

**正确写法**：使用有 Owner 的线程池或任务执行器，定义容量、命名、拒绝策略、上下文传递和关闭方式。

**错误写法**：在接口方法中直接 `new Thread()`，或无界创建异步任务和队列。

**判断要点 / 验证方式**：执行单元由谁创建和关闭；容量、拒绝、取消和异常处理是否明确；进行并发压力、队列满、取消和应用关闭测试；检查线程命名和资源释放。

**例外**：框架托管且生命周期明确的执行器可以直接使用，但仍需确认容量和异常策略。

### AURA-BASE-BE-041：锁的范围和顺序必须可说明

**必要性**：必须

使用锁、分布式锁或其他互斥机制时，必须说明保护对象、持有时间、超时和释放方式。涉及多个锁时应保持一致的获取顺序，避免把网络调用和长时间处理放在锁内。

**为什么需要**：锁边界不清会造成死锁、长时间阻塞和吞吐下降。

**正确写法**：明确锁保护对象、范围、超时和释放方式，按统一顺序获取多个锁，并在锁外执行网络和长任务。

**错误写法**：持锁调用远程服务，或不同方法以相反顺序获取同一组锁。

**判断要点 / 验证方式**：锁保护对象是否必要；持有时间、超时、释放和顺序是否可说明；执行并发和锁超时测试；人工检查死锁风险、锁粒度和降级处理。

**例外**：短小、纯内存且无外部等待的临界区可以使用本地锁，但仍需说明保护对象。

## 二、典型开发场景

以下示例用于说明多条规则如何组合，不构成新的接口契约，也不绑定具体框架、目录名或业务模型。

### 批量与异步任务

**适用任务**：后端业务用例、异步与批处理、后端测试交付  
**关联规则**：BE-011、BE-024、BE-025、BE-026、BE-036、BE-040、BE-050  
**示例级别**：完整示例

#### 场景目标

实现设备文件导入：接口快速受理并返回任务标识，后台按批次处理数据，记录成功和失败明细，最终更新任务状态。

#### 输入条件

- 文件大小和数据行数有上限；
- 任务状态包括 `PENDING`、`RUNNING`、`SUCCEEDED`、`PARTIAL_FAILED`、`FAILED`、`CANCELLED` 和 `TIMEOUT`；
- 同一业务幂等键不能重复创建有效任务，文件必须先落到可恢复的持久位置；
- 后台执行单元由应用统一管理，资源必须在成功、失败和取消时释放；
- 任务受理后即使进程中断，也能从持久任务记录恢复执行。

#### 推荐调用结构

```text
ImportDeviceRequest
  → ImportApplicationService
    → 校验文件和数据范围
    → 原子创建或复用持久导入任务并返回任务标识
    → 后台工作者原子领取待执行任务
    → 按批次幂等处理和记录进度
    → 记录成功数、失败数和失败明细
    → 更新任务最终状态
```

#### 任务状态

```text
PENDING → RUNNING → SUCCEEDED
                  ├→ PARTIAL_FAILED
                  ├→ FAILED
                  ├→ CANCELLED
                  └→ TIMEOUT
```

#### 完整正确示例

```java
public ImportAccepted submit(ImportDeviceRequest request) {
    importLimits.requireFileSize(request.fileSize());
    fileStore.requireDurable(request.fileRef());
    var key = IdempotencyKey.from(request.fileHash(), request.operatorId());
    var task = taskRepository.createPendingIfAbsent(
        key, request.fileRef(), request.operatorId(), clock.instant().plus(importLimits.maxDuration()));
    return ImportAccepted.of(task.id(), task.status());
}

public void runDueTasks() {
    // 由受控工作者领取 PENDING 或租约已过期的 RUNNING 任务；领取与状态变更必须是原子操作。
    for (var claim : taskRepository.claimDueTasks(20, Duration.ofMinutes(2))) {
        process(claim);
    }
}

public void process(TaskClaim claim) {
    var task = taskRepository.requireClaimed(claim);
    long rowCount = 0;
    try (var rows = fileStore.open(task.fileRef())) {
        for (var batch : rows.batchesOf(500)) {
            if (taskRepository.markCancelledIfRequested(claim)) {
                return;
            }
            taskRepository.requireBeforeDeadline(claim, clock.instant());
            rowCount += batch.size();
            importLimits.requireRowCount(rowCount);
            batchService.importAndRecordOnce(claim, batch.number(), batch.rows());
            taskRepository.renewClaim(claim);
        }
        taskRepository.finishFromRecordedProgress(claim);
    } catch (TaskDeadlineExceededException e) {
        taskRepository.markTimeoutIfClaimed(claim);
    } catch (Exception e) {
        taskRepository.markFailedIfClaimed(claim, FailureCode.classify(e));
    }
}
```

`createPendingIfAbsent` 依靠持久层唯一约束原子创建或读取同一幂等键的任务，不是“先查再插”；受理响应只表示任务已持久化。工作者以有容量上限的领取循环执行，进程重启后可重新领取待执行或租约过期的任务。`importAndRecordOnce` 以任务标识和批次号去重，在同一本地事务中保存本批业务结果、成功/失败明细和进度；重新领取时跳过已提交批次。领取、续租和终态更新均校验领取凭证，避免旧工作者覆盖新结果；单批执行时间必须受控并短于租约或支持续租。`finishFromRecordedProgress` 根据已记录的成功数与失败数区分 `SUCCEEDED`、`PARTIAL_FAILED` 和 `FAILED`。取消只停止后续批次，已提交结果仍可查询；任务失败只记录稳定错误分类，不把原始异常文本直接公开。

#### 错误示例

```java
public String importFile(MultipartFile file) {
    var rows = file.getInputStream().readAllBytes();
    for (var row : rows) {
        mapper.insert(row);
    }
    return "导入成功";
}
```

问题：一次性读入全部文件，接口同步执行无边界批处理，异常和部分失败没有状态，无法重入，也没有明确资源释放和任务归属。

#### 验证步骤与预期结果

1. 顺序及并发提交同一幂等键，预期由持久唯一约束保证只创建一个任务，并返回同一个任务标识。
2. 导入包含部分错误数据的文件，预期任务为 `PARTIAL_FAILED`，并能查询失败明细。
3. 处理过程中取消任务，预期停止后续批次并释放文件和执行资源。
4. 在任务持久化后、工作者领取前中断进程，预期重启后仍能领取；在批次提交后中断并重新领取，预期已完成批次和进度不重复计算。
5. 模拟超时、领取租约过期、执行异常和取消，预期旧工作者不能覆盖新状态，任务进入可查询的终态或安全重入。
6. 重复运行构建、静态检查和相关测试，保留命令与结果。

#### 人工确认点

- 批次大小、文件大小和任务超时上限；
- 失败行是跳过、回滚还是进入补偿队列；
- 任务重入和幂等键的业务定义；
- 任务状态是否需要对外查询、通知或审计。

反例：一次请求把全部文件读入内存，循环逐条写库，异常被忽略，接口直接返回“导入成功”。

### 文件导入导出

**适用任务**：异步与批处理、后端接口、数据访问  
**关联规则**：BE-011、BE-024、BE-025、BE-026、BE-036、BE-040、BE-050  
**示例级别**：完整示例

#### 场景目标

发起设备列表导出，并以异步任务方式分批读取、生成受控文件、记录进度和结果。调用方获得任务状态或受限下载引用，而不是等待接口把全量数据读入内存后直接返回文件。

#### 输入条件

- 导出请求包含经定义的筛选条件，不接受任意 SQL、文件路径或原始查询表达式；
- 当前用户的数据范围、租户和可导出字段可解析；
- 导出规模可能超过同步接口的时间或内存预算；
- 文件可能包含敏感字段，需要按授权范围脱敏或禁止导出；
- 任务需要支持可观察的排队、执行、成功、失败、取消和过期清理状态。

#### 推荐调用结构

```text
ExportDeviceController
  → ExportDeviceCommand
  → ExportDeviceApplicationService
    → 校验权限、数据范围、筛选条件和导出规模
    → 创建带查询快照和发起人信息的导出任务
    → 提交后台执行

ExportDeviceWorker
  → 按页或游标读取受控数据范围
  → 转换为导出行并脱敏
  → 分批写入临时文件，更新任务进度
  → 完成后存储受限文件引用，或记录失败原因并清理临时文件
```

#### 完整正确示例

```java
public ExportTaskResult create(ExportDeviceCommand command, UserContext context) {
    var scope = scopeProvider.resolve(context);
    var query = exportQueryValidator.validate(command.query(), scope);
    exportPolicy.requireAllowedColumns(command.columns(), context);

    var task = exportTaskRepository.create(new ExportTaskDraft(
        context.userId(), context.tenantId(), query.snapshot(), command.columns()));
    exportDispatcher.submit(task.id());
    return ExportTaskResult.accepted(task.id(), task.status());
}
```

```java
public void execute(ExportTaskId taskId) {
    var task = exportTaskRepository.start(taskId);
    try (var writer = temporaryFileStore.open(task.outputName())) {
        var cursor = ExportCursor.start(task.querySnapshot());
        while (cursor.hasNext()) {
            var page = deviceRepository.scan(task.querySnapshot(), cursor, 500);
            writer.write(page.records().stream()
                .map(record -> exportRowMapper.toRow(record, task.allowedColumns()))
                .toList());
            cursor = page.nextCursor();
            exportTaskRepository.updateProgress(task.id(), cursor.processedCount());
        }
        var fileRef = fileStore.publishRestricted(task.outputName(), task.owner());
        exportTaskRepository.complete(task.id(), fileRef);
    } catch (Exception exception) {
        temporaryFileStore.deleteQuietly(task.outputName());
        exportTaskRepository.fail(task.id(), exportErrorClassifier.classify(exception));
        throw exception;
    }
}
```

导出任务保存的是经校验的查询快照和可导出字段，不保存前端原始表达式；Worker 每批处理有限记录，持续更新进度；结果文件通过受限引用下载，下载时仍需校验发起人或被授权主体，不能因为获得文件地址就绕过权限。

#### 错误示例

```java
public byte[] export(String where) {
    return excelWriter.write(deviceRepository.findAll(where));
}
```

问题：前端输入直接参与查询，没有数据范围、字段和规模控制；全量结果常驻内存；没有任务状态、失败分类、临时文件清理、敏感字段处理或下载权限校验；大文件容易导致接口超时和重复触发。

#### 验证步骤与预期结果

1. 使用无导出权限或超出数据范围的查询，预期在任务创建前被拒绝，且不创建文件与后台任务。
2. 提交超出同步阈值的大数据量导出，预期快速返回任务标识，后台按受控批次执行而非占用接口线程。
3. 导出数据包含敏感字段，预期按导出策略脱敏、排除或拒绝，不将未授权字段写入文件。
4. Worker 在中途失败，预期任务状态为失败并带稳定失败分类，临时文件被清理，调用方可以按既定策略重试或重新发起。
5. 下载完成任务的文件，预期只有任务发起人或明确授权主体可下载；过期、取消或无权访问时不可获取文件内容。
6. 处理百万级或目标规模数据时，预期进度可查询、内存受批次限制，日志能关联任务标识与 TraceId。

#### 人工确认点

- 哪些规模可以同步返回，哪些必须异步，以及对应超时、文件大小和保留期限；
- 导出字段的授权、脱敏、审计和二次传播限制；
- 查询快照的有效期、数据变更后的导出一致性预期，以及重试是否复用快照；
- 下载授权、一次性链接、文件存储位置、过期清理和删除失败的补偿策略；
- 导入场景是否需要复用同一任务模型，并分别定义模板版本、失败行反馈、幂等和回滚边界。
