**适用对象**：使用 AURA 开展业务应用、服务、工具和平台工程开发的团队和开发人员

**规范目标**：让关键业务过程可度量、告警可处理，并通过完整场景说明异常、日志、审计和指标的协同关系。

**边界说明**：本文件负责指标、告警及跨域示例；异常、日志、链路和审计的单条规则分别见本目录其他分类文件。公开错误结构遵循 `BASE-05`，身份与敏感信息边界遵循 `BASE-07`。

## 一、指标与告警规则

### AURA-BASE-OBS-013：关键业务过程必须有可解释指标

**必要性**：必须

**为什么需要**：指标能够持续反映成功率、耗时、积压和失败趋势，帮助团队在用户反馈前发现业务或系统异常。

对有明确运行影响的接口、任务、消息、外部调用和批处理，应能观察调用量、成功失败、耗时，以及适用时的积压或重试。指标名称、单位和结果分类应稳定；标签使用服务、操作、结果等有限取值，不使用用户、设备、请求标识或敏感数据。

**正确写法**：接口和任务使用固定低基数标签观察调用量、成功率、耗时和积压。

**错误写法**：把用户 ID、设备 ID 或完整请求作为指标标签。

**判断要点 / 验证方式**：按正常、业务失败和系统故障核对计数及耗时；检查指标单位和标签基数，使用大量业务对象确认指标序列不会随对象数量无限增长。

### AURA-BASE-OBS-014：告警必须对应可处理事件

**必要性**：必须

**为什么需要**：告警只有对应明确的影响、责任和处理动作，才能避免无效通知和告警疲劳。

告警应基于可解释的失败率、耗时、积压或关键业务状态，说明阈值与持续时间、影响范围、当前状态、责任入口和处理动作。应约定同类事件的抑制/聚合与恢复条件；不得为每条普通日志、每个用户或每个业务对象创建无处理意义的告警。

**正确写法**：队列积压持续超过约定阈值时发出一次可定位告警，附消费者状态和处理入口；积压恢复后解除告警，持续故障不按每条消息重复通知。

**错误写法**：每次普通参数校验失败都告警，或通知只写“系统异常”，没有影响范围、责任入口和恢复条件。

**判断要点 / 验证方式**：模拟触发、持续和恢复过程，检查阈值、抑制、影响范围、处理入口及告警状态是否正确收敛。

## 二、典型使用示例：设备审核发生版本冲突

某内部业务接口执行设备审核。请求已通过身份和权限校验，应用用例用版本条件更新设备；影响行数为零时，先区分对象不存在、无权访问和版本冲突。本例已确认对象存在且可访问，因此按已登记的“版本冲突”错误契约结束，不能把它当作系统故障或成功。以下标识和业务码仅用于说明字段关系，具体值以模块接口文档为准。

该接口向调用方返回 `BASE-05` 约定的统一 `R<T>` 错误结构，业务码和请求标识让调用方能定位结果，内部异常不进入 `msg`；公开 OpenAPI 只在认证、DTO 和数据范围上做边界控制，不另造响应结构：

```json
{
  "code": 409,
  "msg": "设备状态已变化，请刷新后重试",
  "data": {
    "errorCode": "REVIEW_VERSION_CONFLICT",
    "requestId": "req-1024",
    "retryable": false
  },
  "ok": false
}
```

服务端在受控日志中记录操作、结果和关联标识；本例将设备审核按高风险动作处理，审计记录还保留可信执行主体、对象、失败结果和时间。失败率指标使用固定结果标签，不把设备或用户 ID 放入指标标签。可预期的单次版本冲突不触发系统故障告警。

```text
WARN operation=device_review result=CONFLICT deviceId=dev-1024 requestId=req-1024 durationMs=24
audit actor=u-18 action=device_review object=dev-1024 result=CONFLICT requestId=req-1024 occurredAt=2026-10-10T02:30:00Z
metric operation=device_review result=conflict count=1
```

反例是把版本冲突记录成 `ERROR`，打印 `Authorization` 和完整请求体，响应仍返回“审核成功”，并以 `deviceId` 为指标标签。分别模拟正常审核、版本冲突和未预期故障，核对业务状态、响应、日志、审计和指标；在故障持续时再验证告警触发、抑制及恢复。日志与审计中的对象标识是否可记录，仍需按 `BASE-07` 的敏感数据边界判断。

## 三、开发者自检

- 关键接口、任务、消息、外部调用和批处理是否有低基数、可解释指标；
- 指标是否没有使用用户、设备、请求标识或敏感数据作为标签；
- 告警是否包含阈值、影响、责任入口、处理动作和恢复条件；
- 正常、业务失败和系统故障是否能在响应、日志、审计、指标和告警中保持一致。
