**适用对象**：使用 AURA 开展业务应用、服务、工具和平台工程开发的团队和开发人员

**规范目标**：让日志表达可定位事实、影响匹配的级别和稳定字段，同时阻断敏感信息泄露。

**边界说明**：本文件负责业务日志的事实、级别、脱敏和字段；异常分类见异常与失败恢复，链路上下文与审计见对应分类，指标与告警见指标与告警。身份与敏感信息边界遵循 `BASE-07`。

## 一、日志规则

### AURA-BASE-OBS-005：日志必须表达可定位事实

**必要性**：必须

**为什么需要**：日志只有包含事件、位置、对象和结果等事实，才能支持问题复盘和开发者自助定位。

与业务处理有关的日志应能说明事件、服务或模块、结果，以及适用时的业务对象、耗时和请求/任务标识。无对象的系统事件不强行填业务标识；禁止只记录“失败”“成功”或无业务语义的对象地址。

**正确写法**：设备审核失败日志记录操作名、受控设备标识、结果分类、耗时和请求标识；无业务对象的启动故障记录服务、阶段和失败原因。

**错误写法**：只记录“操作失败”或打印无业务语义的对象地址。

**判断要点 / 验证方式**：根据日志能否定位一次具体业务失败进行检查。

### AURA-BASE-OBS-006：日志级别必须与事件影响匹配

**必要性**：必须

**为什么需要**：合理的日志级别可以区分正常业务信息、可恢复异常和系统故障，避免重要事件被淹没或噪声过多。

调试信息、正常业务记录、可恢复异常和系统故障使用与影响相称的级别。高频正常轮询和可预期业务拒绝不得持续作为系统错误刷屏；同一异常在多层传播时避免重复输出相同堆栈。

**正确写法**：正常拒绝记录业务级别，系统故障记录错误级别，调试信息不进入生产默认日志。

**错误写法**：把所有轮询和业务拒绝都记录为 ERROR。

**判断要点 / 验证方式**：分别触发正常、可恢复和系统故障，检查级别和告警行为。

### AURA-BASE-OBS-007：日志不得泄露敏感信息

**必要性**：禁止

**为什么需要**：日志通常长期保存并被多套系统读取，脱敏可以降低凭据、身份和业务敏感数据扩散的影响。

Token、密码、私钥、完整个人信息、认证载荷和敏感请求体不得写入日志；异常消息、请求/响应对象、重试日志和调试日志同样适用。为定位问题保留的字段应按用途脱敏、截断或使用不可逆标识，不能靠关闭正式日志级别掩盖泄露。

**正确写法**：记录 `taskId`、操作名和失败分类；删除认证头和密码，对确需定位的手机号只记录受控掩码值。

**错误写法**：把完整请求体和认证头打印到错误日志。

**判断要点 / 验证方式**：用含敏感值的请求触发正常、异常、重试和调试路径，检查日志及异常堆栈可关联业务操作但不能还原凭据或敏感原文。

### AURA-BASE-OBS-008：日志格式和字段必须稳定

**必要性**：必须

**为什么需要**：稳定字段让日志能够被检索、聚合和关联，避免每个模块使用不同名称导致排查依赖人工猜测。

项目内对服务、模块、事件类型、结果、耗时、错误标识和链路标识使用稳定字段及类型。业务代码不得为同一事件随意使用多套字段名；日志字段的具体名称以项目统一约定为准。

**正确写法**：统一使用 `service`、`operation`、`result`、`durationMs` 和 `traceId` 字段。

**错误写法**：同一事件在不同模块使用 `cost`、`time`、`elapsed` 多套含义。

**判断要点 / 验证方式**：对比日志样本和字段字典，检查字段类型和语义一致性。

## 二、典型使用示例：受控导出失败的日志记录

**场景目标**：导出任务发生参数拒绝、权限拒绝、依赖超时或程序故障时，日志能够定位操作和任务，又不泄露 Token、密码、完整请求体或敏感字段。

**输入条件**：用户提交导出条件后生成 `taskId`；服务端已完成数据范围校验；任务可能在排队、处理中、失败和成功之间变化；日志由检索系统按固定字段聚合。

**正确日志链**：

```text
提交入口记录 operation=export_submit、taskId、result 和 requestId
  → 任务执行记录 operation=export_run、阶段、durationMs 和失败分类
  → 依赖超时记录可恢复级别并保留重试次数
  → 失败完成记录最终状态和处理入口
  → 所有路径统一脱敏 Authorization、密码、请求体和敏感字段
```

正常完成和用户主动取消使用业务级别；可恢复依赖故障使用与影响匹配的级别；程序故障才进入错误级别并关联异常堆栈。字段使用稳定的 `service`、`operation`、`result`、`taskId`、`requestId`、`durationMs` 和 `traceId`；确需定位时可在受控日志中记录脱敏后的业务对象标识，但不把用户 ID、设备 ID 或请求标识作为指标标签，也不记录完整请求。

**错误日志链**：直接打印完整请求头和请求体；把每次参数拒绝都记为 ERROR；不同模块分别使用 `cost`、`time`、`elapsed` 表示耗时；重试日志重复打印同一堆栈；只记录“导出失败”而没有任务标识和最终状态。

**验证步骤与预期结果**：

1. 分别触发正常、参数拒绝、权限拒绝、依赖超时、重试和未预期异常，预期级别与影响匹配且字段稳定。
2. 使用含 Token、密码、手机号和敏感请求体的输入，预期日志可关联任务但无法还原凭据和敏感原文。
3. 检查同一异常在入口、任务和重试层的输出，预期不会重复打印无法区分的完整堆栈。
4. 按 `taskId` 和 `requestId` 检索一次导出，预期能够还原提交、执行、失败和最终处理结果。

## 三、开发者自检

- 日志是否能定位事件、对象、结果和耗时；
- 日志级别是否与事件影响匹配；
- 正常、异常、重试和调试路径是否都经过脱敏；
- 服务、操作、结果、耗时和链路字段是否稳定统一。
