## 一、规则

### AURA-BASE-BE-001：后端代码必须有可识别的职责边界

**必要性**：必须

后端代码至少应能识别以下职责：

- 接口入口：接收请求、做基础参数校验、调用业务用例、转换公开响应；
- 应用用例：组织一个业务动作的执行过程，协调业务规则、事务、数据访问和外部调用；
- 业务规则：表达业务状态、资格、计算、约束和状态转换；
- 数据访问：读取和写入本服务负责的数据；
- 外部调用：调用其他服务、第三方系统或 AURA 公开能力；
- 技术适配：封装具体客户端、持久化框架、缓存、文件和消息实现。

后端工程目录必须遵循 `BASE-01` 规定的统一职责目录；本规范进一步规定各职责目录中的代码边界。类名、方法名和字段命名由 `BASE-01` 统一约束。不得以项目自定义目录或类名改变职责边界，也不得让一个入口同时承担协议、业务、数据访问、外部调用和展示转换等多种职责。

**为什么需要**：职责边界清晰，才能在接口、业务规则、数据结构或外部依赖变化时控制影响范围。

**正确写法**：

```text
Controller
  → ApplicationService
    → 业务规则
    → Repository / Client
  → Response 转换
```

**错误写法**：

```text
Controller
  → Mapper
  → 拼接业务规则
  → 调用外部服务
  → 直接返回 Entity
```

**判断要点 / 验证方式**：检查入口是否同时承担协议适配、业务编排、数据访问和外部调用；检查每个职责是否能够指出对应的代码归属；自动检查只能辅助识别入口对 Mapper、Client 和 Entity 的直接依赖；人工检查需要确认职责边界和业务语义。

**例外**：极简单的只读工具接口可以合并入口和用例，但不得因此直接暴露持久化模型或绕过公开能力入口。

### AURA-BASE-BE-002：后端模块应围绕业务责任组织

**必要性**：应当

后端模块可以按业务领域、用例集合、数据责任、权限范围或部署单元组织。

不得只按 `controller`、`service`、`mapper` 等技术目录堆积所有业务，也不得把无关业务逻辑放入统一的“大 service”“common service”或“util service”。

**为什么需要**：按业务责任组织模块，可以降低无关功能之间的耦合，避免公共类成为无法维护的逻辑集中点。

**正确写法**：

```text
device-group/
  application/
  domain/
  infrastructure/
  model/
```

**错误写法**：

```text
controller/
service/      # 所有业务共用一个巨大 Service
mapper/
util/         # 混合业务校验、转换和外部调用
```

**判断要点 / 验证方式**：模块是否能用业务责任解释；同一模块内的入口、用例、规则和适配是否围绕同一责任闭环；自动检查包结构只能提供提示；必须人工检查模块边界、依赖方向和跨模块调用理由。

**例外**：确实只有一个业务动作的短期工具可以暂时合并，但应保留后续拆分时的职责边界，并记录不适用原因。

### 后端小型业务的结构适配说明

后端项目是否可以合并职责层级，统一遵循 `BASE-02` 的 `AURA-BASE-ARCH-027`。本规范不再重复维护“小型项目可以合并层级”的独立规则。

合并后仍必须满足本规范的后端边界：接口入口不直接承担数据访问和复杂编排，请求、响应和持久化模型不得无条件混用，业务规则不得散落在技术实现中，且拆分时不能破坏公开契约。

适用的后端判断示例：

```text
短小查询：Controller → QueryService → Repository → Response
```

如果合并后无法独立说明入口、业务判断和数据访问职责，应继续保持职责分离，并按 `ARCH-027` 的规则进行人工确认。

### AURA-BASE-BE-004：接口入口只负责协议适配

**必要性**：必须

Controller、Resource、Resolver、Job 入口、消息消费入口或其他接入入口只负责协议适配和调用业务用例。

接口入口不得直接：

- 访问 Mapper、Repository 或数据库连接；
- 调用多个外部客户端完成复杂业务流程；
- 拼接复杂查询和业务计算；
- 控制跨系统事务；
- 直接返回持久化实体、外部原始响应或内部异常。

**为什么需要**：入口层是协议边界。将业务编排、数据访问和外部调用塞入入口，会让接口难以测试，也会让协议变化直接影响业务代码。

**正确写法**：

```text
POST /device-groups
  → CreateDeviceGroupRequest
  → DeviceGroupApplicationService.create(command)
  → DeviceGroupResponse
```

**错误写法**：

```text
Controller
  → 读取 Mapper
  → 拼接查询条件
  → 调用多个 Client
  → 捕获异常并返回空对象
```

**判断要点 / 验证方式**：入口是否只做协议解析、基础校验、用例调用和响应转换；是否存在直接数据库访问、外部编排或内部模型泄漏；可通过依赖扫描辅助发现 Controller 对 Mapper、DAO 和底层 Client 的直接依赖；必须人工确认入口职责和失败处理。

**例外**：完全无业务逻辑的健康检查或只读探针可以采用简单入口，但仍不得泄漏内部实体和异常。

### AURA-BASE-BE-005：接口输入必须先形成明确请求模型

**必要性**：必须

接口入口应使用明确的请求模型、查询对象或命令对象表达输入。简单接口可以直接使用少量基础参数，但不得出现大量散乱参数、未命名 Map 或无法说明语义的对象。

请求模型应表达字段含义、必填关系、基础格式和空值语义。复杂业务校验由应用用例或业务规则承担，不应全部塞进接口入口。

**为什么需要**：明确请求模型可以稳定接口契约，区分协议校验和业务校验，避免 Map、参数顺序或隐式默认值造成歧义。

**正确写法**：

```text
CreateDeviceGroupRequest
  - name
  - deviceIds
  - description
```

入口将请求模型转换为 `CreateDeviceGroupCommand`，由应用用例完成业务校验。

**错误写法**：

```text
create(String name, String type, String status, Map<String, Object> options, ...)
```

**判断要点 / 验证方式**：输入字段是否有稳定名称和语义；基础格式校验与业务规则是否分层；是否使用无法说明含义的 Map 或散乱参数；自动检查接口签名和请求模型结构；人工确认字段语义、必填关系、空值语义和兼容影响。

**例外**：只有一个基础参数且无复杂语义的内部工具接口可以直接使用基础类型，但仍需保持参数名称清晰。

### AURA-BASE-BE-006：接口输出必须经过公开响应模型

**必要性**：必须

对外接口、前端接口和跨模块接口不得直接返回数据库实体、内部领域对象、外部系统原始响应或原始 Map。分页记录必须转换为公开响应模型；新接口按 `BASE-05` 使用统一的 `R<PageResult<Response>>` 目标契约，浏览器、内部模块和对外 OpenAPI 不再各定义一套分页返回对象。公共 `PageResult` 类型尚未落地的存量模块须记录实际返回类型与调用方，并按兼容迁移方案改造，不得将目标契约误写为当前实现。

公开响应模型只包含使用方需要且语义稳定的字段。响应结构、错误表达和分页规则的完整要求由 `BASE-05` 定义。

**为什么需要**：公开响应模型可以阻断持久化结构、内部状态和外部系统字段向调用方泄漏，降低数据结构变化的影响。

**正确写法**：

```text
DeviceGroupResponse
  - id
  - name
  - deviceCount
  - status
  - version（需要支持并发修改时公开）
```

**错误写法**：

```java
return deviceGroupEntity;
return externalClientResponse;
return Map.of("data", entity, "raw", rawResponse);
return R.ok(pageOfDeviceGroupEntity);
```

**判断要点 / 验证方式**：响应是否只包含稳定的公开语义；是否泄漏 Entity、内部字段、原始外部响应或内部错误对象；自动检查 Controller 返回类型只能作为辅助；必须人工核对公开契约和字段来源。

**例外**：内部同模块调用也不得默认复用持久化实体；只有明确约定且经过人工确认的内部契约才可以复用稳定模型。

### AURA-BASE-BE-007：接口入口不得吞掉异常或伪造成功

**必要性**：禁止

接口入口不得把业务失败、权限失败、外部调用失败、数据缺失或系统异常伪装成成功结果。

接口入口应把可识别的业务失败转换为公开错误，把不可预期异常交由统一异常处理机制表达。具体错误模型归入 `BASE-05` 和 `BASE-09`。

**为什么需要**：调用方必须能够区分成功、业务失败和系统异常，才能正确重试、提示或记录结果。

**正确写法**：

```text
业务校验失败 → 公开业务错误
权限失败     → 公开权限错误
系统异常     → 统一异常处理 + 可定位日志
```

**错误写法**：

```java
try {
    return service.execute(request);
} catch (Exception ignored) {
    return ApiResponse.success(null);
}
```

**判断要点 / 验证方式**：失败是否仍返回成功状态；是否吞掉异常；是否把内部堆栈、类名、地址或敏感信息直接返回调用方；通过业务失败、权限失败、外部失败和未预期异常测试验证结果分类；人工确认错误模型和日志关联信息。

**例外**：明确约定的幂等查询可以返回“无结果”，但不得将执行失败伪装成业务成功。

## 二、正确和错误结构

### 1. 正确结构

```text
接口入口
  → 应用用例
    → 业务规则
    → 数据访问接口
    → 外部能力接口
      ↑
      技术适配实现
```

接口入口只做协议适配，应用用例表达业务流程，业务规则集中表达，技术适配隐藏实现细节。

### 2. 错误结构

```text
接口入口
  → 直接访问 Mapper
  → 直接拼接 HTTP 地址
  → 直接操作缓存
  → 拼接业务规则
  → 直接返回数据库实体
```

这种结构会导致协议、业务、数据和外部依赖互相穿透，后续接口、数据表或外部能力变化都会影响入口层。

## 三、典型开发场景

以下示例用于说明多条规则如何组合，不构成新的接口契约，也不绑定具体框架、目录名或业务模型。

### 后端模块创建与职责拆分

**适用任务**：架构分层、工程结构  
**关联规则**：BE-001、BE-002；工程结构另见 `AURA-BASE-STRUCT-002/003/004`  
**示例级别**：完整示例

#### 场景目标

新增“设备告警规则”模块。模块围绕告警规则这一业务责任组织，既能让开发者快速定位请求入口、业务动作、数据读写和外部适配，也不会为了形式化分层制造只转发一次的空壳文件。

#### 输入条件

- 模块需要提供规则创建、查询、启停和测试触发等业务动作；
- 规则需要持久化，测试触发可能调用公开消息能力；
- 业务规则、权限和状态变化必须可定位；
- 项目已有统一的异常、请求、响应和基础设施约定；
- 对于仅一个简单查询的内部工具，可减少文件，但不能把协议、业务和数据访问混入同一职责不清的方法。

#### 推荐结构

```text
alert-rule/
├─ api/
│  ├─ AlertRuleController.java          协议适配、请求与响应
│  └─ model/                            请求与公开响应模型
├─ application/
│  └─ AlertRuleApplicationService.java  创建、启停、测试触发等业务用例
├─ domain/
│  ├─ AlertRule.java                    状态与业务规则
│  └─ AlertRuleRepository.java          业务所需的数据读写契约
└─ infrastructure/
   ├─ persistence/                      持久化实现
   └─ messaging/                        公开消息能力适配
```

#### 完整正确示例

```java
public AlertRuleResponse enable(EnableAlertRuleCommand command, UserContext context) {
    var rule = repository.findVisible(command.ruleId(), context.scope())
        .orElseThrow(() -> new AlertRuleNotFoundException(command.ruleId()));
    rule.enable(context.userId());
    repository.save(rule);
    return AlertRuleResponse.from(rule);
}
```

```text
Controller：解析请求、调用 enable、转换公开响应
ApplicationService：组织查询、状态变更、权限上下文和持久化
AlertRule：判断当前状态是否可启用，维护业务不变量
Repository：读取和保存规则，不决定是否可启用
消息适配器：调用公开消息能力，不承载告警规则业务流程
```

对于只有“按标识读取一条只读配置”的内部工具，可以在一个清晰的查询用例中合并领域对象和应用服务；但 Controller 仍不能直接拼接数据访问、权限判断和外部调用，也不能把“文件少”当作职责混合的理由。

#### 错误示例

```java
@PostMapping("/alert-rule/{id}/enable")
public AlertRuleEntity enable(@PathVariable Long id) {
    var entity = mapper.selectById(id);
    entity.setStatus("ENABLED");
    mapper.updateById(entity);
    messageClient.send("alert-rule-enabled", entity);
    return entity;
}
```

问题：入口层直接读取与更新数据、修改状态、调用外部能力并返回实体；看不出状态变更是否合法、数据范围在哪里校验、外部失败如何处理，也无法独立演进公开响应与持久化结构。

#### 验证步骤与预期结果

1. 新增业务动作时，预期能在应用用例中定位流程，在领域对象或业务规则中定位状态约束，在 Repository/适配器中定位外部边界。
2. 修改表结构或持久化实现，预期不要求修改 Controller 的公开响应模型和业务动作表达。
3. 新增消息能力调用，预期只增加公开能力适配与应用编排，不在入口层散落地址或底层客户端。
4. 对单一、简单只读功能合并文件，预期仍能从方法名、输入输出和依赖关系识别其唯一职责。
5. 检查模块目录，预期按业务责任聚合，没有跨领域的万能 `util`、`service` 或按技术类型堆放所有业务模块的目录。

#### 人工确认点

- 模块边界是否对应稳定业务责任，而不是当前表名或临时页面名称；
- 哪些动作属于同一用例集合，哪些已需要拆成独立模块或服务；
- 简化层级后是否仍能清楚区分协议、业务、数据和外部适配；
- 模块间数据所有权、公开契约和依赖方向是否明确。

### 标准 CRUD

**适用任务**：后端接口、后端业务用例、数据访问  
**关联规则**：BE-004、BE-005、BE-006、BE-008、BE-011、BE-014、BE-016、BE-018、BE-027  
**示例级别**：完整示例

#### 场景目标

实现设备组的新增、查询、修改和分页列表，展示入口、应用用例、业务校验、数据访问和公开响应之间的边界。

#### 输入条件

- 新增接口接收名称、设备 ID 集合和描述；
- 名称不能为空，设备 ID 不得重复；
- 修改请求携带读取时取得的版本号，不能覆盖并发修改；
- 列表查询页码从 1 开始，页大小为 1～100，排序字段使用白名单；
- 持久化实体不能直接作为接口响应。

#### 推荐目录结构

```text
Controller
  → CreateDeviceGroupCommand / UpdateDeviceGroupCommand / DeviceGroupQuery
  → DeviceGroupApplicationService
    → 业务校验
    → DeviceGroupRepository
    → DeviceGroupResponse 转换
  → 公开响应
```

#### 完整正确示例

```java
@PostMapping("/device-groups")
R<DeviceGroupResponse> create(@Valid @RequestBody CreateDeviceGroupRequest request) {
    return R.ok(DeviceGroupResponse.from(service.create(request.toCommand())));
}

@GetMapping("/device-groups/{id}")
R<DeviceGroupResponse> get(@PathVariable long id) {
    return R.ok(DeviceGroupResponse.from(service.get(id)));
}

@PutMapping("/device-groups/{id}")
R<DeviceGroupResponse> update(@PathVariable long id,
                              @Valid @RequestBody UpdateDeviceGroupRequest request) {
    return R.ok(DeviceGroupResponse.from(service.update(id, request.toCommand())));
}

@GetMapping("/device-groups")
R<PageResult<DeviceGroupResponse>> list(@Valid DeviceGroupQuery query) {
    IPage<DeviceGroupResponse> page = service.list(query).convert(DeviceGroupResponse::from);
    return R.ok(toPageResult(page));
}

public DeviceGroup create(CreateDeviceGroupCommand command) {
    DeviceGroupRule.validate(command);
    return repository.save(DeviceGroup.create(command));
}

public DeviceGroup get(long id) {
    return repository.findById(id)
        .orElseThrow(() -> new DeviceGroupNotFoundException(id));
}

@Transactional
public DeviceGroup update(long id, UpdateDeviceGroupCommand command) {
    DeviceGroupRule.validate(command);
    var group = get(id);
    group.requireVersion(command.version());
    int changed = repository.updateIfVersion(id, command.version(), command);
    if (changed != 1) {
        throw new ConcurrentDeviceGroupModificationException(id);
    }
    return get(id); // 读取已提交到当前事务的最新字段和版本
}

public Page<DeviceGroup> list(DeviceGroupQuery query) {
    if (query.page() < 1 || query.size() < 1 || query.size() > 100) {
        throw new InvalidPageRequestException();
    }
    var sort = SortWhitelist.resolve(query.sort());
    return repository.findPage(query.page(), query.size(), sort);
}
```

入口只负责协议适配；应用服务负责业务动作；Repository 只负责数据读写。`updateIfVersion` 必须在持久层以 `id` 和旧 `version` 为条件更新并递增版本，根据影响行数报告冲突，不能实现成先查后无条件 `save`。`DeviceGroupResponse` 包含供修改请求使用的公开版本号；列表先把每条内部记录转换为该响应模型，再转换为 `PageResult`，保留 `records`、`total`、`size`、`current`、`pages` 字段，统一使用 `R.ok(...)` 返回。示例中的 `toPageResult` 表示目标转换步骤，公共类型及转换 API 尚须由框架落地；不得把这段目标示例当作现有依赖可直接编译的代码。列表在访问数据库前限制页码、页大小并校验排序字段。

#### 错误示例

```java
public Object create(Map<String, Object> body) {
    var entity = mapper.insert(body);
```

#### 验证步骤与预期结果

1. 提交空名称、重复设备 ID，预期返回明确业务错误且不写入数据。
2. 新增后按标识查询，再携带查询所得版本修改，预期只返回公开响应字段，不出现数据库内部字段。
3. 两个修改请求使用同一版本，预期仅一个成功，另一个返回并发冲突。
4. 使用非法排序字段、零页码和超大页大小，预期在查询前被拒绝。
5. 运行 Repository、应用用例和接口测试，确认各层职责和错误结果。

#### 人工确认点

- 设备组名称和设备 ID 的业务唯一性；
- 数据范围和权限条件是否需要在查询中加入；
- 分页上限是否满足实际业务；
- 响应字段是否构成稳定公开契约。
