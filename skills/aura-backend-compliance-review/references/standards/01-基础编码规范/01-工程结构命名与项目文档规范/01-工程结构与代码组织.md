## 工程结构目标

本规范规定业务项目如何组织工程、模块、目录、文件和项目文档，使开发者能够快速找到职责入口，理解变更影响，并在项目持续扩展时保持结构清晰。

文件数量不是目标。项目既不能把所有内容堆进少数巨型文件，也不能为了形式把一个完整职责拆成大量难以理解的小文件。

## 工程组织总要求

### AURA-BASE-STRUCT-001：项目必须有清晰的工程入口

**必要性**：必须

项目根目录必须能够让开发者找到：

- 项目用途和适用范围；
- 本地启动方式；
- 主要模块；
- 配置和环境入口；
- 项目文档入口；
- 构建、测试和交付方式。

工程入口应保持稳定，不应依赖个人口头说明。

**为什么需要**：没有稳定入口时，开发者和 AI 无法判断项目边界、启动方式和文档事实源，后续目录审查也没有统一起点。

**正确写法**：根 `README.md` 指向根 `docs/README.md`，并明确启动、模块、配置、测试和交付入口。

**错误写法**：项目只有一个无说明的代码目录，启动方式和模块关系依赖聊天记录或个人经验。

**判断要点 / 验证方式**：入口是否唯一、是否能独立说明项目用途和操作路径、链接是否有效；检查根 `README.md`、根 `docs/README.md` 及其中列出的入口；人工按入口完成一次定位。

**例外**：无。代码生成项目也必须提供生成后的工程入口。

### AURA-BASE-STRUCT-002：目录必须表达真实职责

**必要性**：必须

目录、模块和文件应按业务领域、技术职责或稳定边界组织。目录名称应能帮助开发者判断其内容、依赖和变更范围。

不得仅因为以下原因新增目录或模块：

- 代码暂时变长；
- 个人习惯不同；
- 预计未来可能复用；
- 希望所有模块看起来完全一致；
- 脚手架生成了空目录。

**为什么需要**：真实职责能够稳定表达依赖和变更范围，避免目录数量增长却没有可维护边界。

**正确写法**：按统一工程结构将页面、领域、请求、状态、应用和基础设施放入对应职责目录。

**错误写法**：把所有内容放入 `common`、`utils` 或 `components`，再通过文件名猜测真实职责。

**判断要点 / 验证方式**：目录是否符合统一职责结构，名称是否能解释内容，是否存在同义目录；按目录职责检查新增文件的归属，并检查是否出现未登记的平行目录。

**例外**：只能在统一职责目录下增加业务模块，不得通过新增同义顶层目录规避本规则。

### AURA-BASE-STRUCT-003：拆分必须有真实边界

**必要性**：必须

文件、类、组件、函数和模块可以拆分，但拆分后必须存在至少一种真实边界：

- 职责不同；
- 依赖不同；
- 生命周期不同；
- 测试方式不同；
- 发布或复用范围不同；
- 权限或数据边界不同。

如果多个内容职责相同、通常一起修改、没有独立依赖或复用边界，应优先保留在同一清晰入口中。

**为什么需要**：无边界拆分会增加跳转、引用和同步成本，使 AI 和人工都难以还原一次业务变更的完整范围。

**正确写法**：仅在职责、依赖、生命周期、测试、发布、复用、权限或数据边界独立时拆分。

**错误写法**：把一个短方法、一个 DTO 或一个仅被单处调用的转换单独拆成文件，只为了保持目录看起来完整。

**判断要点 / 验证方式**：拆分后是否能独立理解、独立测试或独立变更；如果不能，优先归并；审查变更涉及的文件数量、调用关系和共同修改情况；人工确认拆分理由。

**例外**：框架要求的固定扩展点可以独立存在，但必须说明其扩展职责和生命周期。

### AURA-BASE-STRUCT-004：禁止无意义的空壳结构

**必要性**：禁止

项目不得保留没有实际职责的：

- 空目录；
- 空接口；
- 空服务；
- 空组件；
- 一对一转发类；
- 仅为“看起来完整”而创建的重复层级。

框架要求的扩展点、代码生成入口或独立发布单元可以保留必要结构，但其用途必须能从工程入口或名称中看出。

**为什么需要**：空壳和转发层会制造虚假边界，增加维护路径并误导 AI 判断真实实现位置。

**正确写法**：删除无职责目录和一对一转发；保留的框架扩展点在 README 或目录说明中标明用途。

**错误写法**：创建空的 `service`、`utils`、`components` 目录，或保留只调用另一个同名方法的转发类。

**判断要点 / 验证方式**：结构是否有真实实现、入口或发布责任；保留是否有可追溯理由；静态扫描空目录、空类型和一对一转发；人工确认框架扩展点。

**例外**：代码生成、框架注册和独立发布要求的空入口可以保留，但必须有说明和生成/发布依据。

### AURA-BASE-STRUCT-005：公共能力应在语义稳定后抽取

**必要性**：应当

代码只有在多个真实场景中具有稳定一致的语义，并且输入、输出、依赖和维护边界明确时，才应抽取为公共工具、组件或模块。

只使用一次的代码不得因为形式相似就提前公共化。公共抽取不能把业务语义隐藏在难以发现的通用模块中。

**为什么需要**：过早公共化会把尚未稳定的业务语义扩散到多个模块，后续修改成本高且容易产生隐式耦合。

**正确写法**：先在业务领域内验证，确认多个场景语义一致后，再抽取到统一公共目录并补充使用边界。

**错误写法**：两个页面都出现相似代码，就立即抽成名为 `commonUtil` 的万能方法，参数和语义依赖调用方猜测。

**判断要点 / 验证方式**：是否存在多个真实调用、稳定输入输出、明确依赖和公共维护责任；检查调用数量、语义一致性、依赖方向和公共目录归属；人工确认抽取后是否仍能定位业务含义。

**例外**：公司统一基础库或框架公开扩展点可按其发布契约接入，但不能把业务逻辑混入其中。

### AURA-BASE-STRUCT-006：目录层级应服务于发现和变更

**必要性**：应当

目录层级应帮助开发者定位职责和影响范围。出现以下情况时，应优先考虑归并或减少层级：

- 目录只有一个短小文件，且没有独立边界；
- 目录名称无法说明内容；
- 同一需求需要在多个无关目录中同步修改；
- 目录只是下一层目录的一对一转发。

出现以下情况时，可以保留独立目录：

- 代表稳定业务领域；
- 具有独立依赖、权限、生命周期或发布边界；
- 是公开扩展点或代码生成入口；
- 能显著缩小变更影响范围。

**为什么需要**：层级应降低发现和变更成本，而不是单纯增加路径深度。

**正确写法**：稳定领域、独立依赖或发布边界使用独立目录；短小且共同变更的内容归并到已有职责入口。

**错误写法**：连续创建只有一个文件的多级目录，或使用多个目录分别保存同一业务的页面、请求和状态而没有清晰关联。

**判断要点 / 验证方式**：目录是否帮助定位职责和影响范围；是否存在一对一层级、同义目录或重复归属；检查目录树、依赖路径和变更涉及范围；对新增目录记录归并/拆分理由。

**例外**：统一框架要求的目录层级不得删除，但仍需在目录说明中标明职责，不得继续扩展无意义层级。

## 前端工程结构

### 1. 统一组织方式

AURA（天玑）前端工程以当前 nexus 模板的真实目录和入口为准：

```text
src/
├─ api/                 # 按业务域封装请求和接口类型
├─ assets/              # 参与 Vite 构建的静态资源
├─ components/          # 项目公共组件和框架组件适配
├─ config/              # 站点、远程入口和模块联邦配置
│  └─ aura/             # 请求、Pinia、i18n 等项目实例绑定
├─ directive/           # 项目指令扩展；公共指令从 web-kit 引入
├─ hooks/               # 项目联邦资源入口与跨页面业务 Hook
├─ i18n/                # 公共语言、页面语言和联邦语言聚合
├─ router/              # 静态路由、补充路由与菜单接入
├─ stores/              # 项目 Pinia 状态
├─ styles/              # 全局、主题与远程隔离样式
├─ types/               # 环境、全局和远程模块类型声明
├─ utils/               # 确有需要的项目工具，不复制公共包实现
└─ views/               # 页面入口和页面私有组件
```

应用入口为 `src/main.ts` 与 `src/App.vue`。业务 API 和接口类型放在 `api/<业务域>/`，页面入口及私有组件放在 `views/<业务域>/<页面>/`；公共包需要的项目依赖绑定在 `config/aura/`。后台主布局与主题通过 `aura-core/theme-core` 消费，不另建本地布局副本。

页面私有组件放在页面的 `components/`；已有模板目录不批量改名。新增稳定跨页面的业务 Hook 使用 `hooks/`，跨项目 TS 能力先查 `aura-web-kit` 公开入口。不得新增同义顶层目录替代模板现有职责。具体页面与公共能力约束见前端工程组织。

### 2. 前端归并与拆分

- 同一页面内关系紧密的短小逻辑可以保留在同一文件；
- 页面组件不得承担大量跨页面通用逻辑；
- 组件只有在存在复用、独立交互或独立生命周期时才单独抽取；
- 地图、视频、实时消息等具有独立依赖或运行协议的内容，应通过相应能力包接入，不与普通页面逻辑混成无法区分的大文件；
- 页面、组件、请求和状态命名应能互相对应，避免同一业务使用多套名称。

## 后端工程结构

### 1. 统一组织方式

后端项目应按业务领域和技术职责组织，不得仅按类数量机械复制目录。

```text
src/main/
├─ java/
│  └─ <项目包名>/
│     ├─ <领域>/              # 业务领域入口
│     │  ├─ controller/       # 接口适配
│     │  ├─ application/      # 用例编排
│     │  ├─ domain/           # 领域模型和规则
│     │  ├─ infrastructure/   # 数据、外部服务和技术实现
│     │  └─ dto/              # 对外或跨层数据模型
│     └─ common/              # 项目内确实跨领域复用的基础内容
└─ resources/
   ├─ application*.yml
   ├─ mapper/
   └─ db/
```

后端项目必须使用本规范规定的领域、应用、领域模型、基础设施和数据模型职责目录。不得以项目自定义分层名称替代标准目录；确需增加内容时，必须归入已有职责目录。

### 2. 后端归并与拆分

- 简单用例可以在同一应用服务中保留私有校验、转换和编排方法；
- 数据访问、外部调用、事务边界或公开接口具有独立职责时，应拆成清晰的对象；
- DTO、VO、Entity 和持久化模型不得因文件少而混为同一对象；
- 公共模块必须具有真实跨领域语义，不得把单一业务逻辑包装成通用工具；
- Controller 不应直接承担数据访问和复杂业务编排；
- 模块之间不得通过内部实现细节互相耦合。

## 典型开发场景示例

### 新项目初始化

**适用任务**：工程结构、项目初始化、文档管理  
**关联规则**：AURA-BASE-STRUCT-001、AURA-BASE-STRUCT-002、AURA-BASE-DOC-001、AURA-BASE-DOC-002、AURA-BASE-DOC-003  
**示例级别**：完整示例

#### 场景目标

创建一个符合 AURA 统一工程结构的前后端项目，使开发者能够从根入口定位模块、配置、测试和文档。

#### 输入条件

- 项目尚未创建业务模块；
- 已确定前端、后端和公共模块边界；
- 项目需要纳入版本管理并支持后续扩展。

#### 推荐目录

```text
project/
├─ README.md
├─ docs/
│  ├─ README.md
│  ├─ 快速开始.md
│  └─ 架构说明.md
├─ frontend/
│  └─ docs/README.md
├─ backend/
│  └─ docs/README.md
└─ shared/
   └─ docs/README.md
```

#### 完整正确示例

根 README 链接到 `docs/README.md`，根 docs 说明快速开始、架构和模块入口；存在独立模块文档时，在该模块建立 `docs/README.md`，只记录本模块职责、启动和使用约束。

#### 错误示例与问题说明

```text
project/
├─ src/
├─ 项目说明-最终版.md
└─ backend说明.md
```

问题：没有统一根入口、没有根 docs、模块没有文档入口，后续无法判断文档事实源。

#### 验证步骤与预期结果

1. 从根 README 定位根 docs；
2. 从根 docs 定位所有模块；
3. 对有独立文档的模块，进入对应模块并找到 `docs/README.md`；无独立文档的模块从项目入口定位职责；
4. 预期所有入口都能通过相对链接到达，且不存在第二套顶层目录。

#### 人工确认点

- 模块边界是否已经确定；
- 是否有遗漏的公共或工具模块；
- 根 docs 与模块 docs 的影响范围是否清楚。

### 新增后端业务模块

**适用任务**：工程结构、后端模块创建、文档管理  
**关联规则**：AURA-BASE-STRUCT-002、AURA-BASE-STRUCT-003、AURA-BASE-STRUCT-006、AURA-BASE-DOC-003、AURA-BASE-DOC-004  
**示例级别**：完整示例

#### 场景目标

在既有后端工程中新增设备业务模块，并将代码、测试和模块文档放入统一职责目录。

#### 输入条件

- 项目已有统一后端工程目录；
- 新模块具有独立业务领域和接口入口；
- 新模块不应新增自定义顶层分层。

#### 推荐目录

```text
backend/<领域>/
├─ controller/
├─ application/
├─ domain/
├─ infrastructure/
├─ dto/
├─ test/
└─ docs/README.md
```

#### 完整正确示例

将设备接口放入 `<领域>/controller`，用例放入 `application`，数据和外部适配放入 `infrastructure`，模块接口与配置说明放入该领域的 `docs/`。

#### 错误示例与问题说明

```text
backend/deviceService/
├─ service2/
├─ manager/
├─ helper/
└─ README.md
```

问题：自定义同义分层，职责无法和统一目录对应，README 也没有位于模块 docs 入口。

#### 验证步骤与预期结果

1. 检查模块是否位于统一领域目录；
2. 检查职责是否归入规定目录；
3. 检查模块 docs/README.md 是否存在；
4. 预期不出现新的顶层分层名称。

#### 人工确认点

- 模块是否确实具有独立业务边界；
- 是否误把单一功能拆成独立模块；
- 模块文档是否只描述该模块。

### 新增前端业务页面

**适用任务**：工程结构、前端页面、文档管理  
**关联规则**：AURA-BASE-STRUCT-002、AURA-BASE-STRUCT-003、AURA-BASE-DOC-003、AURA-BASE-DOC-004  
**示例级别**：完整示例

#### 场景目标

在统一前端工程中新增设备列表页面，并保持页面、领域请求、局部组件和状态的可发现关系。

#### 输入条件

- 项目已有统一前端职责目录；
- 页面属于已有设备领域；
- 页面不引入新的同义组件、请求或状态目录。

#### 推荐目录

```text
src/views/device/
├─ DeviceList.vue
├─ components/
├─ api/
├─ model/
└─ docs/README.md
```

#### 完整正确示例

页面入口位于 `views/device`，设备请求和模型位于设备领域目录，跨页面稳定组件才提升到统一公共目录，页面使用说明放在 `views/device/docs/README.md`。

#### 错误示例与问题说明

```text
src/components/DeviceList.vue
src/utils/deviceApi.ts
src/store/device.ts
```

问题：页面、请求和状态分散到无关公共目录，无法快速判断领域边界，也容易把设备逻辑误当成公共能力。

#### 验证步骤与预期结果

1. 从页面入口找到领域请求、模型和局部组件；
2. 检查公共目录是否只包含稳定跨领域能力；
3. 检查模块 docs/README.md 是否存在；
4. 预期页面变更不需要遍历无关领域目录。

#### 人工确认点

- 组件是否确实跨页面复用；
- 状态和请求是否属于设备领域；
- 是否错误创建了同义公共目录。

### 文件拆分与归并评估

**适用任务**：工程结构、重构、文件治理  
**关联规则**：AURA-BASE-STRUCT-003、AURA-BASE-STRUCT-004、AURA-BASE-STRUCT-006  
**示例级别**：反例对照

#### 场景目标

判断一个变长文件应该拆分还是归并，避免因为文件数量或目录形式进行机械重构。

#### 输入条件

- 文件包含多个方法或组件；
- 需要评估职责、依赖、生命周期、测试和变更范围；
- 重构不能改变业务行为。

#### 推荐判断结构

```text
先识别真实边界
  → 有独立职责/依赖/生命周期/测试/发布边界：拆分
  → 无独立边界且总是一起修改：归并
  → 仅一对一转发或空壳：删除
```

#### 完整正确示例

将同时包含设备查询、导出任务和外部通知的模块，按独立生命周期和失败处理拆分；将仅包含一个短方法且没有独立依赖的转换类归并回用例入口。

#### 错误示例与问题说明

```text
DeviceService.java
DeviceValidator.java
DeviceConverter.java
DeviceHelper.java
DeviceManager.java
```

问题：每个文件只有少量转发或重复逻辑，拆分没有真实边界，增加了理解和同步成本。

#### 验证步骤与预期结果

1. 列出每个文件的职责和依赖；
2. 检查是否独立测试、发布或生命周期；
3. 检查共同修改历史或变更范围；
4. 预期拆分理由可说明，无法说明的内容归并或删除。

#### 人工确认点

- 拆分是否改变依赖方向；
- 归并后职责是否仍可识别；
- 是否存在框架要求的扩展点。

### 公共能力抽取

**适用任务**：工程结构、公共模块、重构  
**关联规则**：AURA-BASE-STRUCT-005、AURA-BASE-STRUCT-006  
**示例级别**：完整示例

#### 场景目标

判断重复代码是否已经具备稳定公共语义，避免过早抽取万能工具。

#### 输入条件

- 至少出现两个相似实现；
- 需要比较输入、输出、依赖和业务语义；
- 公共模块必须有明确维护责任。

#### 推荐判断结构

```text
比较多个真实调用场景
  → 语义、输入输出和依赖稳定一致：抽取公共能力
  → 仅表面相似或业务语义不同：保留在领域内
```

#### 完整正确示例

多个领域都使用同一套无业务含义的日期格式化函数，确认输入输出和时区语义一致后，抽取到统一公共工具，并在公共模块 docs 中说明适用范围。

#### 错误示例与问题说明

```java
CommonUtil.convert(Object value, String mode, Map<String, Object> options)
```

问题：参数和语义依赖调用方猜测，实际隐藏了多个领域规则，无法确认公共能力是否稳定。

#### 验证步骤与预期结果

1. 列出真实调用方和语义；
2. 检查输入、输出、依赖和维护责任；
3. 检查公共模块 docs/README.md；
4. 预期公共能力可以脱离单一领域解释和测试。

#### 人工确认点

- 是否已经有多个真实场景；
- 抽取后是否隐藏业务语义；
- 公共模块的维护责任和兼容范围。

## 工程结构自检

提交工程结构或文档变更前，开发者至少应自行确认：

- 新增目录、文件或模块是否有清晰职责；
- 是否存在可以直接归并的短小内容；
- 是否产生空壳、一对一转发或重复公共模块；
- 根 `README.md` 和项目级 `docs/README.md` 是否可用；
- 模块文档是否放在对应模块 `docs/`；
- 是否存在重复主文档、失效链接或临时命名；
- 代码、接口、配置和文档是否同步。
