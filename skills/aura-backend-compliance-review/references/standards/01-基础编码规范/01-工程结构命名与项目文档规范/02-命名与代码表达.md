## 命名与代码表达目标

本规范规定工程、模块、目录、文件、代码、接口、配置、事件和文档的命名、格式与基本表达方式。

命名和代码表达必须让开发者能够判断对象的业务领域、职责、输入输出、状态和稳定性。规范的目标是降低理解成本和沟通成本，不是强制个人偏好。

## 通用命名规则

### AURA-BASE-NAME-001：名称必须表达职责或领域

**必要性**：必须

**为什么需要**：稳定名称直接影响代码检索、协作沟通和后续维护，明确职责可以减少开发者对实现含义的猜测。

工程、模块、目录、文件、类、组件、方法、函数、变量、常量、接口、事件、配置键和文档名称必须能够表达职责、领域或稳定技术含义。

不得将以下宽泛或临时名称作为稳定生产代码的唯一名称：

```text
CommonUtil
Helper
Manager
Data
Info
Result
Temp
New
Old
Final
test2
```

需要使用通用词时，应增加明确限定，例如 `UserPermissionService`、`CacheInvalidationEvent`、`DeviceQueryResult`。


**正确写法**：使用 `DevicePermissionService`、`deviceQuery` 和 `DeviceQueryResult` 表达领域与职责。

**错误写法**：使用 `CommonUtil`、`Data`、`test2` 作为稳定生产对象的唯一名称。

**判断要点 / 验证方式**：检查名称是否能说明领域、职责和稳定技术含义。
### AURA-BASE-NAME-002：同一概念必须使用同一术语

**必要性**：必须

**为什么需要**：统一术语可以避免前后端、接口、日志和文档对同一业务概念产生多个事实名称。

同一业务概念在前端、后端、接口、日志、事件和文档中必须保持统一名称。

不得让 `userId`、`memberId`、`operatorId` 在没有明确语义差异时表示同一概念，也不得让同一名称在不同模块表达不同概念。


**正确写法**：用户标识在接口、代码和日志中统一使用 `userId`，操作人另使用 `operatorId`。

**错误写法**：同一用户在不同模块交替使用 `userId`、`memberId` 而没有语义差异。

**判断要点 / 验证方式**：检索同一概念的字段、事件和文档，确认术语唯一。
### AURA-BASE-NAME-003：名称必须区分对象类型

**必要性**：必须

**为什么需要**：区分单体、集合、查询条件和结果类型，可以降低参数传错、返回值误用和模型转换错误。

名称应明确区分单个对象和集合、查询条件和查询结果、当前状态和目标状态、类型和值、原始数据和转换后的数据、请求模型和响应模型。

```text
device
devices
deviceQuery
devicePage
deviceStatus
targetStatus
deviceType
```

不得让所有对象都使用 `data`、`result`、`info` 或 `items` 作为唯一名称。

**正确写法**：使用 `device`、`devices`、`deviceQuery`、`devicePage` 区分对象、集合、条件和分页结果。

**错误写法**：所有对象都命名为 `data`、`result` 或 `items`。

**判断要点 / 验证方式**：检查单体、集合、查询和结果类型名称是否可区分。

## 各类载体的命名风格

### AURA-BASE-NAME-004：同一工程内必须保持风格一致

**必要性**：必须

**为什么需要**：统一命名风格可以减少代码阅读和检索成本，也能避免新代码与既有公开契约产生不必要的差异。

命名风格可以受语言、框架和已有公开契约约束，但同一工程内不得无说明地混用。

| 对象 | 默认风格 | 示例 |
| --- | --- | --- |
| 工程名称 | 小写短横线 | `device-service` |
| Java 包名 | 小写点号 | `com.example.device` |
| 目录 | 小写短横线或稳定领域名 | `user-center`、`device` |
| Java 类、接口、枚举 | UpperCamelCase | `DeviceService` |
| Java 方法、变量 | lowerCamelCase | `findDeviceById` |
| Java 常量 | UPPER_SNAKE_CASE | `DEFAULT_TIMEOUT_SECONDS` |
| TypeScript 类型、接口 | UpperCamelCase | `DeviceQuery` |
| 前端变量、函数 | lowerCamelCase | `loadDeviceList` |
| Vue/React 组件文件 | PascalCase | `DeviceTable.vue` |
| composable 或 Hook | `use` + 领域名称 | `useDeviceQuery` |
| HTTP 路径 | 小写、短横线、资源复数 | `/device-models` |
| JSON 字段 | 使用公开契约既定风格 | `deviceId` |
| 配置键 | 项目统一风格 | `aura.device.timeout` |
| 事件名称 | 领域 + 事实或动作 | `device.created` |
| 文档名称 | 稳定主题名称 | `接口说明.md` |

已有公开 API、组件、字段、配置键和事件名称优先保持兼容。

**正确写法**：Java 类使用 UpperCamelCase，方法使用 lowerCamelCase，Vue 组件使用 PascalCase，项目内保持一致。

**错误写法**：同一工程同时使用 `device_service`、`DeviceService` 和 `deviceService` 表示同一类对象。

**判断要点 / 验证方式**：扫描命名配置和新增文件，确认风格与公开契约一致。

## 格式化与排版

### AURA-BASE-FORMAT-001：项目必须使用统一格式化配置

**必要性**：必须

**为什么需要**：可复现的格式化配置能够让不同开发环境产生一致代码，减少无意义排版差异和合并冲突。

同一项目必须使用仓库内统一的格式化配置和编辑器约定。开发者不得仅依赖个人 IDE 设置形成不同代码风格。

格式化配置至少应能统一：

- 缩进；
- 空格；
- 换行；
- 引号；
- 分号；
- 尾随逗号；
- import 排序；
- 文件末尾换行；
- 文件编码。


**正确写法**：仓库提交 `.editorconfig`、格式化插件配置和统一执行命令。

**错误写法**：只依赖个人 IDE 保存格式，仓库没有可复现的格式化配置。

**判断要点 / 验证方式**：在干净环境执行格式化检查，确认结果一致。
### AURA-BASE-FORMAT-002：源文件格式必须稳定

**必要性**：必须

**为什么需要**：稳定的编码、换行和控制字符约定可以避免构建失败、乱码、工具解析异常和大范围无关变更。

源代码和项目文档默认使用 UTF-8 编码。代码文件必须保留清晰的换行和缩进，不得提交不可见控制字符、混乱的制表符和空格组合。

格式化后的代码不得引入与本次变更无关的大范围排版变化。


**正确写法**：源文件统一使用 UTF-8 和项目约定的换行符，提交前执行格式检查。

**错误写法**：同一仓库混入 GBK 文件、不可见控制字符和不同换行格式。

**判断要点 / 验证方式**：检查编码、换行和格式化扫描结果。
### AURA-BASE-FORMAT-003：代码排版必须服务于阅读

**必要性**：必须

**为什么需要**：清晰排版能够让业务步骤、条件边界和异常路径可见，降低审阅和维护复杂代码的成本。

代码应使用清晰的空行、换行和代码块边界表达逻辑层次：

- 一个代码块只表达一个主要意图；
- 过长表达式应按语义拆行；
- 条件、参数和链式调用应保持可读；
- 不使用连续空行、尾随空格和无意义对齐；
- 不通过压缩排版隐藏复杂逻辑。


**正确写法**：复杂条件拆成有意义的局部变量和分支，代码块层级与业务步骤一致。

**错误写法**：把整段业务逻辑压成一行或连续嵌套多层三元表达式。

**判断要点 / 验证方式**：人工阅读主要路径，确认排版能够区分步骤和边界。
### AURA-BASE-FORMAT-004：声明和导入顺序必须一致

**必要性**：必须

**为什么需要**：稳定的声明和导入顺序可以准确表达依赖关系，避免隐式依赖、循环引用和格式化结果反复变化。

文件内的导入、类型、常量、成员、构造方法和公开方法应按项目约定保持稳定顺序。第三方依赖、项目内部依赖、相对路径依赖和仅类型依赖应能够区分。

不得通过无序导入、重复导入或通配符导入隐藏真实依赖。

**正确写法**：按项目约定排列 import：标准库、第三方、项目内，并保持声明顺序稳定。

**错误写法**：同一文件重复导入、依赖隐式全局对象或每次提交都产生无意义顺序变化。

**判断要点 / 验证方式**：运行 lint 和格式化检查，确认声明与导入顺序稳定。

## 类型、函数与参数表达

### AURA-BASE-TYPE-001：公开边界必须有明确类型

**必要性**：必须

**为什么需要**：明确类型可以让调用方在编译和编辑阶段理解接口结构，减少运行时字段猜测和错误传递。

公开 API、组件属性、事件参数、配置对象、服务方法和跨模块调用的输入输出必须有明确类型。类型名称和结构应能表达业务语义。


**正确写法**：公开方法使用 `DeviceResponse`、`Page<DeviceResponse>` 等明确类型，不返回无结构对象。

**错误写法**：公开接口返回 `Object` 或 `Map<String,Object>`，调用方必须猜字段。

**判断要点 / 验证方式**：检查公开方法签名和序列化模型是否明确。
### AURA-BASE-TYPE-002：禁止用不安全类型掩盖不确定性

**必要性**：禁止

**为什么需要**：限制不安全类型可以把不确定性收敛在适配边界，避免错误结构扩散到业务代码和公开接口。

前端代码不得为了绕过类型检查而滥用 `any`。确实未知的数据应优先使用 `unknown`，并在使用前完成类型判断或转换。

不得使用 `String`、`Number`、`Boolean`、`Object` 等包装类型替代 `string`、`number`、`boolean` 等原始类型。


**正确写法**：对可选字段使用明确联合类型、泛型或领域类型，并在边界处完成转换。

**错误写法**：用 `Object`、裸 `Map` 或 `any` 掩盖未知结构并让不确定性扩散。

**判断要点 / 验证方式**：扫描不安全类型使用，确认不确定性被限制在适配边界。
### AURA-BASE-TYPE-003：空值和可选值必须区分

**必要性**：必须

**为什么需要**：明确空值语义可以区分缺失、未知、默认值和有效值，避免条件判断和序列化结果产生歧义。

类型、接口和方法必须明确区分“字段不存在”“字段为空”“字段有默认值”和“字段不允许为空”。

不得用一个含义不明的空字符串、`0`、`false` 或特殊数字同时表示缺失、未知和有效值。


**正确写法**：区分必有的 `DeviceStatus` 与可缺省的 `Optional<DeviceStatus>` 或 `status?: DeviceStatus`。

**错误写法**：用空字符串、0 和 null 混合表示“没有值”。

**判断要点 / 验证方式**：检查字段类型和序列化结果，确认空值语义唯一。
### AURA-BASE-TYPE-004：类型定义必须与使用边界一致

**必要性**：必须

**为什么需要**：按职责区分请求、响应、领域、持久化和配置类型，可以防止内部字段穿透公开边界并降低变更影响范围。

请求、响应、页面表单、领域对象、持久化对象和配置对象应根据实际职责定义类型。只有字段语义、生命周期和责任一致时，才可以复用同一类型。


**正确写法**：接口响应类型只包含公开字段，数据库 Entity 在 Repository 边界转换为 Response。

**错误写法**：直接把数据库 Entity 作为跨模块公开类型。

**判断要点 / 验证方式**：沿调用链检查类型定义与使用边界是否一致。
### AURA-BASE-CODE-001：函数和方法名称必须表达动作与对象

**必要性**：必须

**为什么需要**：动作和对象明确后，调用方无需阅读实现即可理解方法用途，便于检索、复用和审查。

函数和方法名称应表达“对什么对象做什么动作”：

```text
findDeviceById
createDevice
updateDeviceStatus
disableDevice
loadDeviceList
```

不得使用 `doIt`、`handleData`、`process`、`execute` 等无法说明业务动作的名称作为主要入口。


**正确写法**：使用 `approveDevice`、`loadDeviceList`、`invalidateDeviceCache` 表达动作和对象。

**错误写法**：使用 `doIt`、`handle`、`process` 作为没有对象语义的方法名。

**判断要点 / 验证方式**：检查方法名是否能说明动作、对象和主要结果。
### AURA-BASE-CODE-002：参数名称必须表达角色、含义和单位

**必要性**：必须

**为什么需要**：参数语义和单位清晰可以避免传错对象、误用时间或金额单位，以及调用点难以理解的问题。

参数名称必须说明其业务角色；时间、长度、金额、容量和数量等参数应在名称或类型中体现单位。

```text
timeoutMs
retryCount
fileSizeBytes
amountFen
```

多个具有稳定关系的参数，或参数数量过多导致调用难以理解时，应使用有明确类型和名称的参数对象。


**正确写法**：使用 `timeoutMs`、`pageSize`、`deviceId` 表达参数角色、对象和单位。

**错误写法**：使用 `n`、`value` 或 `timeout` 隐藏参数含义和时间单位。

**判断要点 / 验证方式**：检查调用点和声明，确认参数名称无需猜测即可使用。
### AURA-BASE-CODE-003：返回值必须表达结果语义

**必要性**：必须

**为什么需要**：明确返回结果类型可以让调用方正确处理实体、集合、分页、状态和异步任务，避免依赖无语义字段。

返回值名称和类型应能区分实体、集合、分页、统计、状态、操作结果和异步任务。不能让不同结构的方法都返回无法解释的 `data` 或 `result`。

**正确写法**：返回 `ApprovalResult`、`DevicePage` 或 `boolean isAvailable` 表达结果语义。

**错误写法**：所有方法都返回 `Object`、`data` 或无语义的 `true`。

**判断要点 / 验证方式**：检查返回类型、调用方分支和失败结果是否一致。

## 模块、导入与导出

### AURA-BASE-MODULE-001：模块入口必须明确

**必要性**：必须

**为什么需要**：稳定入口可以隐藏内部目录和实现变化，避免调用方依赖不可兼容的内部文件路径。

模块应有稳定的入口文件或公开导出位置。业务代码只能从明确的公开入口引入跨模块内容，不应依赖模块内部文件路径。


**正确写法**：模块通过 `index.ts` 或公开 `DeviceApi` 作为唯一入口导出能力。

**错误写法**：调用方深入模块目录引用任意内部文件。

**判断要点 / 验证方式**：检查模块入口文件和外部引用路径。
### AURA-BASE-MODULE-002：导出范围必须与使用范围一致

**必要性**：必须

**为什么需要**：控制导出范围可以缩小公开面，防止内部类型、测试工具和临时实现被误用并形成长期兼容负担。

只有需要被其他模块使用的类型、函数、组件和常量才应导出。内部实现不得通过宽泛导出、通配符导出或多层 `index` 文件被无意暴露。


**正确写法**：只导出文档声明的 `DeviceApi`、`DeviceQuery` 和 `DeviceResponse`。

**错误写法**：把测试工具、内部 Entity 和临时函数全部从包入口导出。

**判断要点 / 验证方式**：比较导出清单与实际调用范围，确认没有扩大公开面。
### AURA-BASE-MODULE-003：导入和导出不得制造隐式循环

**必要性**：禁止

**为什么需要**：清晰的单向依赖可以避免初始化顺序问题、构建失败和模块边界逐步失控。

模块导入关系必须能够被开发者理解。不得通过互相导入、跨层反向导入或隐式聚合入口形成循环依赖。

模块之间的总体依赖方向由架构规范进一步规定。

**正确写法**：抽取稳定接口或事件后保持单向依赖，模块 A 不再反向导入模块 B 的内部实现。

**错误写法**：通过聚合入口或全局变量互相导入，形成隐藏循环。

**判断要点 / 验证方式**：运行依赖分析并检查新增 import 是否形成环。

## 常量、枚举和字面量

### AURA-BASE-CONST-001：重要字面量必须有语义名称

**必要性**：必须

**为什么需要**：语义名称可以说明阈值、状态和业务含义，避免修改者无法判断字面量的作用范围。

超时、重试次数、分页大小、容量、状态值、类型值、错误码和业务阈值等不能以无意义的数字或字符串散落在代码中。

```text
DEFAULT_REQUEST_TIMEOUT_MS
MAX_RETRY_COUNT
DEVICE_STATUS_ONLINE
```


**正确写法**：使用 `MAX_DEVICE_BATCH_SIZE` 替代散落的 `1000`。

**错误写法**：在多个方法中直接写 `1000`，调用者无法知道它代表批量上限。

**判断要点 / 验证方式**：扫描重复字面量，确认重要值有集中语义名称。
### AURA-BASE-CONST-002：常量名称必须体现单位和范围

**必要性**：必须

**为什么需要**：单位和范围明确可以减少毫秒/秒、字节/数量等误用，避免配置和业务计算产生隐蔽错误。

涉及时间、长度、容量、金额和比例的常量，名称应体现单位或精度：

```text
REQUEST_TIMEOUT_MS
MAX_FILE_SIZE_BYTES
AMOUNT_SCALE
```


**正确写法**：使用 `REQUEST_TIMEOUT_MS = 5000` 和 `MAX_PAGE_SIZE = 100`。

**错误写法**：使用 `TIMEOUT = 5`，无法判断单位和允许范围。

**判断要点 / 验证方式**：检查常量名称是否包含单位、范围或边界含义。
### AURA-BASE-CONST-003：状态和类型值必须集中表达

**必要性**：必须

**为什么需要**：集中表达可以保证状态值和类型值在代码、接口、日志及文档中保持一致，避免散落字符串造成语义漂移。

同一业务对象的状态、类型和错误值应集中定义并使用统一名称。不得在不同文件中重复定义同一组值，也不得让数字本身成为业务语义的唯一表达。

**正确写法**：集中定义 `DeviceStatus.ACTIVE`、`DeviceStatus.DISABLED`，接口和持久化映射统一使用。

**错误写法**：在不同模块分别用 `1`、`ACTIVE`、`enabled` 表示同一状态。

**判断要点 / 验证方式**：检索状态和类型值，确认定义集中且映射一致。

## 注释、文档与代码说明

### AURA-BASE-COMMENT-001：注释必须解释意图或边界

**必要性**：必须

**为什么需要**：注释只有说明约束、原因和边界才具有维护价值，避免注释与代码重复或在实现变化后失真。

注释应说明代码为什么这样实现、有什么边界、遵守什么外部约束或存在什么重要取舍，不应只重复代码已经表达的内容。


**正确写法**：注释说明“设备审核必须在提交后发布事件”的原因和边界。

**错误写法**：注释只重复 `i++` 或 `save(device)` 这类代码表面行为。

**判断要点 / 验证方式**：检查注释是否解释意图、约束或非显然边界。
### AURA-BASE-COMMENT-002：公开接口必须有必要说明

**必要性**：必须

**为什么需要**：公开接口的调用前提、异常和兼容限制需要被明确记录，避免使用者只能通过阅读内部实现理解行为。

公开服务方法、组件、类型、配置项、事件和复杂业务方法应说明用途、关键参数、返回值、异常或使用限制。

注释格式可以使用项目统一的 Javadoc、TSDoc 或其他约定，但同一项目不得混用无法理解的格式。


**正确写法**：公开 API 注明认证、分页上限、错误码和幂等要求。

**错误写法**：公开方法没有说明参数限制、失败语义和副作用。

**判断要点 / 验证方式**：检查公开接口文档和代码注释是否覆盖调用必需信息。
### AURA-BASE-COMMENT-003：临时注释必须可识别

**必要性**：必须

**为什么需要**：可识别的临时标记便于后续清理和跟踪，避免试验性说明被误认为长期设计或正式契约。

`TODO`、`FIXME`、`NOTE` 等临时标记必须说明待处理事项，不得用“以后处理”“临时方案”等无法判断范围的表述长期代替正式说明。

代码行为发生变化时，受影响注释必须同步修改，不得保留与实际行为冲突的说明。

**正确写法**：使用 `TODO(AURA-123, 2026-10-01): 替换兼容逻辑` 标识临时注释。

**错误写法**：留下没有负责人和期限的 `TODO`、`FIXME`。

**判断要点 / 验证方式**：扫描临时注释，确认包含责任、原因或清理条件。

## 前端专属表达

### AURA-BASE-NAME-FE-001：页面、组件和状态名称必须对应领域职责

**必要性**：必须

**为什么需要**：前端名称与领域职责一致，才能让页面组合、组件复用和状态维护边界保持可发现。

```text
DeviceListView
DeviceEditDialog
useDeviceQuery
loadDeviceList
DeviceQueryRequest
deviceStore
```

不得使用 `Box1`、`Panel2`、`CommonDialog`、`LeftPart`、`TempTable` 等无法表达职责的名称作为稳定页面或组件名称。


**正确写法**：使用 `DeviceReviewPage`、`DeviceTable`、`useDeviceReviewStore` 表达页面、组件和状态职责。

**错误写法**：把所有页面命名为 `Index.vue`，所有状态集中到 `store`。

**判断要点 / 验证方式**：检查前端目录和组件名称能否对应业务领域。
### AURA-BASE-NAME-FE-002：事件和异步方法名称必须表达动作

**必要性**：必须

**为什么需要**：动作名称可以区分加载、提交、刷新和选择等行为，避免事件处理逻辑在页面中难以定位。

事件处理函数、异步方法和状态操作应区分用户事件、数据加载、创建、更新、删除和状态变化：

```text
handleSubmit
onDeviceSelected
loadDeviceList
createDevice
updateDeviceStatus
removeDevice
```

不得使用同一个 `handle`、`change` 或 `action` 名称承载多个无关动作。


**正确写法**：使用 `handleReviewSubmit`、`loadDeviceList`、`onDeviceSelected` 表达动作。

**错误写法**：使用 `clickHandler`、`doAction` 表示多个不同事件。

**判断要点 / 验证方式**：检查事件处理和异步方法名是否说明动作与对象。
### AURA-BASE-NAME-FE-003：路由、菜单、权限和国际化标识必须稳定

**必要性**：必须

**为什么需要**：稳定标识是路由跳转、权限判断、语言切换和自动化验证的共同基础，不能依赖临时文案或视觉位置。

路由名称、菜单标识、权限标识、国际化 key、测试选择器和静态资源名称应表达稳定业务语义，不得使用页面位置、临时序号或视觉文案作为唯一标识。

**正确写法**：路由、菜单、权限和 i18n 使用稳定的 `device.review` 标识。

**错误写法**：把按钮中文文案或页面位置作为权限和国际化键。

**判断要点 / 验证方式**：检查路由、权限和语言包键是否稳定且可追踪。

## 后端专属表达

### AURA-BASE-NAME-BE-001：查询、命令和状态变更名称必须区分

**必要性**：必须

**为什么需要**：区分读取、命令和状态事实可以避免把不同副作用的操作混为一个入口，降低调用和审查风险。

方法名称应区分读取、搜索、创建、更新、删除、禁用、归档和状态变更：

```text
findDeviceById
queryDevices
createDevice
updateDevice
disableDevice
archiveDevice
```

不得使用 `save`、`process` 或 `execute` 等模糊动词掩盖不同业务语义。


**正确写法**：使用 `DeviceQuery`、`ApproveDeviceCommand`、`DeviceStatusChanged` 区分查询、命令和状态事实。

**错误写法**：把查询、命令和事件都命名为 `DeviceData`。

**判断要点 / 验证方式**：检查后端模型名称和调用方向是否表达不同语义。
### AURA-BASE-NAME-BE-002：后端类型后缀必须表达层次职责

**必要性**：必须

**为什么需要**：类型后缀与职责一致可以帮助开发者判断对象所处边界，避免 Entity、Response 和 Client 等模型被混用。

Controller、ApplicationService、Repository、Client、Request、Response、Entity、Record、Converter、Assembler 和 Exception 等后缀只能用于对应职责，不得为了命名整齐机械添加。


**正确写法**：使用 `DeviceController`、`DeviceApplicationService`、`DeviceEntity`、`DeviceResponse` 表达层次职责。

**错误写法**：所有后端类型都以 `Manager` 或 `Info` 结尾，无法判断所在边界。

**判断要点 / 验证方式**：检查类型后缀与目录、依赖和公开边界是否一致。
### AURA-BASE-NAME-BE-003：异常名称必须表达失败原因

**必要性**：必须

**为什么需要**：明确失败原因才能决定错误转换、重试、提示和恢复方式，避免所有故障退化为不可处理的通用异常。

异常类、错误类型和错误码名称应说明发生了什么失败，不得统一使用无法区分原因的 `Exception`、`Error` 或 `Fail` 作为唯一表达。

**正确写法**：使用 `DeviceNotFoundException`、`DeviceVersionConflictException` 表达失败原因。

**错误写法**：所有故障都抛出 `BusinessException` 或 `Exception`。

**判断要点 / 验证方式**：检查异常名称能否直接说明失败原因和调用方处理方式。

## 测试代码命名

### AURA-BASE-NAME-TEST-001：测试名称必须表达条件、行为和结果

**必要性**：必须

**为什么需要**：测试名称包含条件、行为和结果后，失败报告可以直接说明验证场景，降低定位和维护成本。

测试类、测试方法和测试用例名称应说明测试对象以及正常、异常或边界结果：

```text
shouldReturnDeviceWhenIdExists
shouldRejectCreateWhenNameIsBlank
shouldRetryWhenRemoteServiceTimesOut
```

不得使用 `test1`、`caseA`、`check` 或 `testSomething` 作为唯一测试名称。


**正确写法**：测试命名为 `approveDevice_whenVersionConflict_returns409`，包含条件、行为和结果。

**错误写法**：测试名称为 `test1`、`shouldWork`，无法说明验证场景。

**判断要点 / 验证方式**：检查测试名能否独立说明前置条件、行为和预期结果。
### AURA-BASE-NAME-TEST-002：测试数据名称必须表达业务含义

**必要性**：必须

**为什么需要**：有业务语义的测试数据便于理解边界和失败原因，避免夹具变化后无法判断其实际用途。

测试数据、fixture、mock、stub 和 fake 的名称应说明对象、场景和状态，不得使用 `data1`、`obj2`、`mockTest` 等无法理解的名称。

**正确写法**：使用 `deviceWithExpiredStatus`、`tenantAUser`、`duplicateApprovalRequest` 表达测试数据语义。

**错误写法**：测试数据全部命名为 `data1`、`user`、`mockObject`。

**判断要点 / 验证方式**：检查夹具和样例数据名称是否能说明业务场景。

## 命名与表达自检

新增或修改名称、格式和代码表达时，至少确认：

- 是否表达职责或领域；
- 同一概念是否在前后端、接口、日志、事件和文档中保持一致；
- 是否区分单对象、集合、状态、类型、布尔量、请求和响应；
- 是否使用了项目统一格式化配置；
- 类型、函数参数和返回值是否表达真实语义；
- 导入导出是否清晰且没有隐式循环；
- 重要字面量、状态和类型值是否有语义名称；
- 公开接口和复杂逻辑是否有必要说明；
- 是否存在临时名称、无意义数字后缀或模糊测试名称；
- 公开名称变更是否影响已有使用方；
- 名称是否暴露了不应依赖的内部实现。

## 与能力包的关系

能力包可以增加自身的领域术语、组件、事件和配置名称，但必须遵守本规范的通用命名、格式和代码表达要求，保持能力包内术语一致，并使用业务可理解的公开名称。
