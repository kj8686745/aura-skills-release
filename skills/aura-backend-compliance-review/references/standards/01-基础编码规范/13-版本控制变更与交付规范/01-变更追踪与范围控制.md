# AURA（天玑）基础编码规范：变更追踪与范围控制

<!-- 文档类型：基础编码规范 -->
<!-- 规范编号：BASE-13 -->
<!-- 规范版本：0.2.0-draft -->
<!-- 模板版本：基础编码规范模板 v3 -->

**规范对象**：使用 AURA 开展业务应用、服务、工具和平台工程开发的团队和开发人员

**规范目标**：让每项变更能够解释来源、目标、范围和受影响消费者。

## 一、变更可追踪与范围控制

### AURA-BASE-VC-001：每项交付变更必须能够定位来源

**必要性**：必须

代码、配置、数据库脚本、接口契约和文档变更必须能够从已有任务、提交记录或变更说明关联到明确的业务需求、缺陷、技术任务或安全修复，不得提交无法说明用途的孤立改动；不要求为每个文件另建登记表。

**为什么需要**：可追踪来源才能判断变更目的、影响范围和验证结果是否对应。

**正确写法**：在变更说明中关联“设备审核重复提交修复”任务，并列出涉及接口、状态表和回归用例。

**错误写法**：提交一批格式、配置和业务逻辑混杂的修改，只写“优化代码”，无法说明每项修改的原因。

**判断要点 / 验证方式**：从交付变更反向检查其来源、目标和验证证据，确认不存在无法解释的修改。

### AURA-BASE-VC-002：一次变更必须保持单一可解释范围

**必要性**：必须

一次交付变更应围绕一个可说明的目标组织，格式化、重命名、无关重构和业务行为修改不得无边界混在同一变更中。

**为什么需要**：范围清晰才能准确审查影响、定位回归并在需要时单独恢复。

**正确写法**：先提交独立的格式化变更，再提交设备审核规则修改，并分别执行对应验证。

**错误写法**：在修改支付状态规则的同时批量重排整个仓库、升级无关依赖和调整页面样式。

**判断要点 / 验证方式**：检查变更清单和差异，确认每项文件修改都与目标直接相关，或有明确的兼容原因。

### AURA-BASE-VC-003：共享边界变更必须说明影响消费者

**必要性**：必须

公共类、组件、配置键、接口、消息、数据库字段和文件格式变更必须从代码引用、公开契约和已知接入方识别受影响的直接消费者及可定位的间接消费者，说明其适配或兼容方式；无法确认的外部消费者须明确未知范围，不得假定不存在。

**为什么需要**：共享边界的影响通常超出当前模块，遗漏消费者会造成跨模块回归。

**正确写法**：修改统一分页响应时，列出后端调用方、前端列表组件、导出接口和历史版本兼容处理。

**错误写法**：只在提供方模块修改公共字段，不检查其他模块的反序列化和空值处理。

**判断要点 / 验证方式**：通过引用、接口消费者和配置使用处反查影响范围，核对已识别消费者的验证或迁移安排，并标出尚不可定位的使用方。

## 二、Git提交说明

本节适用于前端、后端、公共组件、SDK、规范、技能和构建工具的提交消息。人工与AI提交使用相同要求。类型标签不是Git tag、分支名或技能分类，也不能代替制品版本和发布记录。

### AURA-BASE-VC-015：提交必须使用统一类型标签

**必要性**：必须

普通人工提交与最终squash提交从以下11类中选择一个类型。按照主要变更目的分类，不按照文件后缀或新增文件数量分类；一个目标需要实现、SQL、文档和测试配套时可以一起提交，无关变更按VC-002拆分。

| 类型标签 | 适用内容 | 边界与示例 |
| --- | --- | --- |
| `[feat]` | 新功能、新能力或新的公开行为 | `[feat][下载中心] 支持多份Excel压缩为一个ZIP` |
| `[fix]` | 修复已有错误或安全缺陷 | 修复与对应回归测试一起用fix；`[fix][下载中心] 阻止过期任务下载` |
| `[refactor]` | 保持公开行为的内部结构调整 | `[refactor][用户服务] 拆分权限查询与结果组装职责` |
| `[perf]` | 性能和资源效率改进 | `[perf][设备导出] 分批读取设备数据以限制内存占用`；未测收益不填写虚构提升数字 |
| `[docs]` | 文档、规范、模板与说明 | `[docs][接口规范] 统一分页字段说明`；规范正文属于docs |
| `[style]` | 不改变行为的格式、缩进和空白调整 | `[style][用户模块] 统一Java文件缩进`；不是页面视觉样式 |
| `[test]` | 仅调整测试或测试组织 | `[test][下载中心] 补充存储异常场景`；不把业务修复机械拆为fix和test两次提交 |
| `[build]` | 依赖、编译、打包和容器构建定义 | `[build][UPMS] 补齐容器快照依赖层`；修复明确运行缺陷时可选择fix并说明依赖变化 |
| `[ci]` | 持续集成、交付流水线与自动检查流程 | `[ci][后端流水线] 增加候选制品内容检查`；POM和Dockerfile本身归build |
| `[chore]` | 不改变业务或构建行为的仓库维护 | `[chore][仓库] 移除停用的编辑器缓存配置`；不能作为无法分类的兜底标签 |
| `[revert]` | 撤销已有提交的效果 | `[revert][接口响应] 撤销不兼容的分页字段变更`；正文关联被撤销提交 |

不另设release、security或breaking类型。版本配置归build，版本说明归docs，安全缺陷归fix，不兼容变化按VC-018标识。技能执行行为新增或修复分别选feat/fix，纯说明更新选docs；不因文件名是SKILL.md就一律选docs。既有历史中的mod、update、opt不追溯改写，但新普通人工提交不得继续使用这些未定义标签。

**为什么需要**：稳定类型让研发人员快速区分功能、修复和交付影响，也为后续检索提供一致入口。

**正确写法**：`[fix][设备页面] 修复状态颜色与实际状态不一致`。

**错误写法**：`[style][设备页面] 新增设备状态颜色`，或`[feat][fix][下载中心] 更新代码`。

**判断要点 / 验证方式**：标签来自11类白名单，且与差异的主要目的相符；正文与差异证明其含义，不能只检查标签字符串。自动生成提交的例外见VC-020。

**人工确认边界**：新增标签或改变分类语义由规范维护者统一确定；常规类型选择不要求研发逐次申请。

### AURA-BASE-VC-016：标题必须包含范围和具体变更结果

**必要性**：必须

标题统一采用以下格式，类型和范围均必填：

```text
[类型][范围] 动作与具体结果
```

标签为小写英文，范围和摘要默认简体中文，类名、模块名等技术标识保持原名。范围使用稳定业务域或实际工程模块名，如下载中心、设备管理、aura-common-core、后端开发技能；不另设全公司模块码表。一个目标跨模块时选择共同业务域；真正全仓变更可以用工程构建或仓库，不能用“全部”掩盖无关改动。

标题必须具体说明动作、对象及主要结果，不能只写“修改”“更新代码”“修复问题”。建议不超过72个字符，过长细节放正文；该长度作为阅读建议，不作为首版硬性阻断。标题不以句号结尾。

**为什么需要**：不打开完整差异也能识别改动目的，减少仅凭模糊标题猜测变更范围。

**正确写法**：`[fix][下载中心] 下载结束后恢复原租户上下文`。

**错误写法**：`[fix] 修复问题`、`fix(download): 修复下载`、`[chore][全部] 优化所有内容`。后者格式可能适用于别的体系，不属于本规范选定格式。

**判断要点 / 验证方式**：检查类型、范围、分隔空格、非空摘要和具体结果；范围是否真实应与差异核对，不能仅靠正则判定。

**人工确认边界**：范围名称按实际模块选用，无需新增模块就修改规范。调整标题语法或长度阻断政策需统一维护。

### AURA-BASE-VC-017：提交正文必须覆盖实际影响和验证

**必要性**：必须

涉及功能逻辑、接口契约、身份权限、数据或数据库结构、依赖、运行配置、并发资源、跨仓协同及回退的提交，必须在标题后空一行，填写原因、改动、影响、验证四个字段。每项可以一句话，也可以使用简短列表，不以完整日志或逐文件差异充数。

| 字段 | 应说明的内容 |
| --- | --- |
| 原因 | 触发条件、原有行为或需求，以及为何需要本次变更 |
| 改动 | 关键处理方式与本提交真正包含的范围 |
| 影响 | 公开行为、消费者、数据、依赖或配置变化及兼容边界；不适用时明确相关边界即可 |
| 验证 | 实际执行的方法和结果、尚未验证的关键范围；未执行如实说明原因 |

纯错字、失效链接、格式等简单无行为变更可以只有清楚的标题；有重要理解或回退影响时仍应补正文。字段必填不代表必须为了文案额外运行无关测试，也不能用“测试通过”掩盖未执行。

存在已有任务时可加关联；涉及配套、迁移、回退时必须补对应信息。没有任务编号时说明来源，不虚构编号；没有对应事项不机械填写“无”。

| 条件字段 | 触发时说明什么 |
| --- | --- |
| 关联 | 实际需求、缺陷或技术任务，已有编号或稳定链接 |
| 配套 | 关联仓库、精确提交或制品坐标、必须满足的顺序 |
| 迁移 | 前置条件、真实脚本或配置位置、执行顺序及兼容范围 |
| 回退 | 涉及数据、权限、公开契约或多服务时的可恢复范围及限制 |

**为什么需要**：提交说明能支持审查、定位和恢复，而非依赖作者记忆或私有聊天记录。

**正确写法**：

```text
[fix][下载中心] 下载结束后恢复原租户上下文

原因：读取结果文件时启用租户跳过，成功和失败返回后未恢复原值。
改动：移除文件读取中不必要的租户跳过，沿用当前认证上下文。
影响：保持接口路径和响应结构，不重新计算文件生成时的数据范围。
验证：成功读取、存储异常和上下文保留用例通过；未进行真实存储联调。
```

**错误写法**：

```text
[fix][下载中心] 修复下载问题

原因：用户让我修一下。
改动：修改了十几个文件，详见AI聊天。
影响：应该没有。
验证：全部测试通过，已上线。
```

**判断要点 / 验证方式**：先按差异判定是否要求正文；再核对原因、方案、影响和证据是否对应。纯文档链接修复不强制跑业务测试，逻辑修复不能仅写标题。

**人工确认边界**：缺少关键需求、契约或兼容策略时先澄清这些事实，不能用模糊字段代替设计；普通字段填写不新增审批流程。

### AURA-BASE-VC-018：不兼容变更必须在标题和正文同时标识

**必要性**：必须

删除或重命名公共类、字段、接口路径，改变现有字段语义、权限默认行为、运行环境下限、数据/配置读取兼容等，影响既有消费者时，标题在范围后加`!`，正文增加`BREAKING CHANGE:`，说明具体不兼容点、受影响方及迁移办法。任何类型都可能发生不兼容变化，不另设breaking标签。

增加可选字段不自动属于不兼容，也不自动证明兼容，应依据已知消费者契约核对。明确标识不替代已有兼容设计和变更决策。

**为什么需要**：让消费者在读标题时看到风险，并能在正文找到具体适配方法。

**正确写法**：

```text
[build][运行基线]! 将后端最低Java版本提升到25

原因：本次采用需要Java25的运行时能力。
改动：同步编译、测试和运行镜像基线。
影响：Java21消费者不能直接加载该版本制品。
验证：按实际结果记录构建、消费者验证与尚未验证范围。

BREAKING CHANGE: 最低Java版本由21变为25；升级前更新运行镜像和消费者，暂未适配的项目继续使用已维护兼容版本。
```

**错误写法**：只写`[build][依赖] 更新版本`，实际生成Java25字节码，却没有说明旧Java21环境无法加载。

**判断要点 / 验证方式**：对照接口、模型、配置、数据及JDK变化识别消费者影响；触发时标题和正文标识必须配对。仅检查`!`不能判断是否遗漏隐性不兼容变化。

**人工确认边界**：兼容策略或目标运行基线未明确时，先由对应变更负责人决定，再形成提交说明；不能为避免标记而自行降低影响。

### AURA-BASE-VC-019：提交说明必须对应本次提交内容与证据

**必要性**：必须

原因、实现、文件、测试和状态描述必须对应本次暂存差异。未跟踪文件、未暂存改动、其他分支或隔离目录的成果不能当成本提交内容。复用验证证据时必须核对源码及范围一致性；不一致则明确限定，不能挪用另一版本的测试数量。

提交、推送、制品发布、部署和真实运行验收必须分别依据事实描述。提交消息在提交对象创建前编写，不应写“本提交已推送/已上线”作为其完成声明；实际推送和部署结果进入后续交付记录。即使仓库里存在测试，也不等于该测试已执行。

不得写入密码、Token、私钥、完整敏感连接信息、真实用户数据、AI对话或模型思考。需要引用资料时使用仓库内稳定相对路径或已有任务系统链接，不使用维护者本机绝对路径。安全问题说明应足以支持维护，但不通过消息分发敏感内容。

**为什么需要**：提交记录是长期证据，错误状态会误导审查、回归和发布判断。

**正确写法**：“本提交只修复身份类型，其他候选文件未包含。所选模块编译通过，未进行部署验证。”

**错误写法**：“已完成整个下载中心并上线”，实际提交只有两行类型替换，完整实现仍未提交。

**判断要点 / 验证方式**：提交前核对暂存差异、验证日志及输入范围；提交后可对照提交对象复核。不凭提交标题认定发布成功。

**人工确认边界**：无法证实的验证保持未验证，不能由AI猜测补齐；没有敏感信息不需要额外审批。

### AURA-BASE-VC-020：特殊提交必须有明确例外和处理说明

**必要性**：必须

Git自动生成的merge和revert消息可以保留默认标题，不强制改成普通人工格式；人工编写的revert使用`[revert][范围] 摘要`。临时fixup/squash消息仅用于整理过程，进入受控主线前通过最终提交表达完整目标；最终squash提交必须采用本规范标题及适用正文。此处不统一各仓库的分支合并策略。

发生人工冲突处理时，必须补充冲突处理、影响和验证说明，说明保留内容、适配方式以及相关验证；没有冲突的常规自动合并可以保留Git默认消息。自动revert应在生成消息外补充撤销原因、原提交、影响与验证，保留工具产生的原提交关联信息。

本规范只约束生效后新增提交，不因格式要求重写已有共享历史；不自动执行rebase、amend、强推或批量修改历史。

**为什么需要**：兼顾Git工具工作方式，同时避免“自动合并”掩盖人工冲突选择与语义风险。

**正确写法**：

```text
Merge branch 'dev' into candidate/download-java21

冲突处理：保留导出执行流程，将身份类型适配上游AuraUser，不恢复旧身份类。
影响：维持目标Java基线，保留与本目标无关的上游功能。
验证：所选模块编译及相关回归通过，真实运行环境未验证。
```

**错误写法**：只保留默认合并标题，却在冲突时覆盖一侧身份类型，不说明处理选择，也不验证编译；或为补齐标签强制改写已共享提交。

**判断要点 / 验证方式**：识别自动提交类型和父提交，再核对有无人工冲突处理及相关说明。格式例外不免除兼容和构建检查。

**人工确认边界**：需要改写已共享历史时，沿项目既有协作要求单独决定；本规范本身不授权该操作。

### AURA-BASE-VC-021：跨仓配套提交必须能定位实际依赖关系

**必要性**：必须

同一目标涉及多个仓库时，每仓独立提交符合VC-002的变更，在正文配套字段说明关联仓库、必须满足的版本与顺序；已有共同任务编号时关联同一编号，没有时使用明确目标描述。最终交付清单必须记录实际提交号与制品坐标，不能仅写“使用最新版”。

后形成的提交可以引用已存在的前一个提交。前一个提交不得填写尚不存在的后一个哈希；待提交形成后在最终交付清单补齐配套关系即可，不为双向链接反复改写共享提交。涉及循环依赖时先明确构建和发布顺序，不能编造可用坐标。

**为什么需要**：防止只拿到单仓修复、混用旧依赖，或用不存在的哈希形成无法执行的配套说明。

**正确写法**：

```text
[fix][下载中心] 删除任务时保留对象清理依据

原因：任务行物理删除后无法重试清理关联对象。
改动：同事务登记清理意图，进行中任务只隐藏并保留执行租约。
影响：需配套公共任务模型与清理实现，目标库增加清理表。
验证：删除、事务回滚和进行中任务保护用例通过；真实存储未联调。
迁移：先核对并执行仓库内实际存在的下载任务增量脚本。
配套：记录已形成的公共组件提交号和候选版本；最终制品坐标在交付清单核对。
回退：保留新增结构，旧下载入口恢复前重新核对访问边界。
```

上述为写法示例，真实提交必须将脚本、提交和坐标写成实际存在的值，不能原样保留“记录已形成的提交号”等提示语。

**错误写法**：“配套使用common最新版”，或在前一个提交中填写尚未生成的后一个提交号。

**判断要点 / 验证方式**：检查关联提交、坐标、脚本与交付清单的真实性和消费顺序；不能要求首次提交预知后续哈希。

**人工确认边界**：依赖版本或跨仓发布顺序不确定时，由对应维护者明确；已有事实直接引用，不重复确认。

## 三、可复制提交模板

以下为模板，不是已执行的项目结果。填写实际内容后删除不适用的条件字段；不得把占位符、示例路径和未执行验证原样提交。

### 轻量模板

适用于简单无行为变更：

```text
[docs][范围] 说明具体修正结果
```

### 完整模板

```text
[类型][范围] 说明动作和具体结果

原因：触发条件、原有行为或具体需求。
改动：关键处理和本次提交范围。
影响：消费者、契约、数据、依赖或配置的实际影响与兼容边界。
验证：实际执行方法和结果；未验证范围及原因。
关联：实际存在的任务或缺陷编号（有则填写）。
配套：已存在的关联仓库提交或精确制品坐标（涉及则填写）。
迁移：真实脚本/配置位置、前置条件与顺序（涉及则填写）。
回退：可恢复边界、顺序与限制（涉及则填写）。
```

### 不兼容模板

```text
[类型][范围]! 说明不兼容变更的主要结果

原因：为什么需要变更。
改动：实际改变的公开契约或运行基线。
影响：旧消费者受到的影响。
验证：已验证的消费者和仍未验证的边界。
迁移：消费者必须采取的具体迁移办法。

BREAKING CHANGE: 具体不兼容点、适用版本与迁移入口。
```

### 人工撤销模板

```text
[revert][范围] 说明撤销对象和结果

原因：撤销的实际原因。
改动：撤销内容以及保留的不相关修复。
影响：恢复哪些行为，是否涉及数据或兼容限制。
验证：实际执行的撤销后检查与未验证范围。
Reverts: 真实被撤销提交号
```

中文正文的原因、改动等是本规范的阅读格式，不声明兼容Git标准trailer解析；`BREAKING CHANGE:`与`Reverts:`保持明确标识，后续自动化需显式支持本规范的方括号格式，不能直接使用默认Conventional Commits解析器假定可用。

## 四、典型使用示例：统一响应字段变更的范围追踪

**场景目标**：统一分页响应新增可选字段时，研发能够说明变更来源、单一范围、直接和间接消费者，并为已知与未知消费者安排兼容验证。

**输入条件**：变更涉及后端公共响应模型、前端列表组件、导出接口和接口示例；已有多个服务调用该模型，外部消费者范围不能完全确认。

**正确变更链**：

```text
关联明确任务与目标
  → 列出公共模型、提供方、前端组件、导出和文档消费者
  → 只修改响应字段和对应示例，不混入格式化与无关依赖升级
  → 验证旧消费者忽略可选字段，记录无法定位的外部消费者
  → 交付说明列出兼容方式、未确认范围和剩余风险
```

**错误变更链**：在响应字段变更中同时重排全仓库、升级无关依赖和调整页面样式；只验证提供方编译通过，不检查调用方解析；把未知外部消费者假设为不存在。

**验证步骤与预期结果**：

1. 由任务、提交和差异反查每项改动，预期没有无法解释的孤立修改。
2. 通过代码引用、接口文档和配置使用处列出消费者，预期已知消费者有验证或迁移安排。
3. 使用旧调用方和新调用方解析响应，预期可选字段不破坏旧行为；未知消费者明确记录为未知范围。

## 五、开发者自检

- 提交类型与主要目的相符，范围和摘要能独立读懂。
- 按实际影响填写正文和条件字段，不混入无关改动或占位符。
- 不兼容标识与迁移说明一致，Git自动提交例外有明确依据。
- 描述与暂存差异、测试版本一致，不把提交、推送和部署混为一谈。
- 配套提交、制品与脚本实际存在，未暴露凭据和私人路径。
