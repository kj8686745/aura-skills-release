# 基础通用支撑能力包详细说明

**能力包**：通用工具类 / 基础通用支撑能力包  
**版本**：0.1.0-draft  
**适用对象**：AURA 业务应用开发者和 AI 编码助手

## 1. 使用方式

本文件是基础通用支撑能力包的能力使用手册。开发者先根据业务问题选择能力，再按对应章节完成编码；具体规则 ID、正反例和综合场景仍以[基础能力使用规范](./04-基础能力使用规范.md)和[基础能力使用示例](./05-基础能力使用示例.md)为准。

每项能力按照以下顺序阅读：

```text
能力作用
→ 主要入口
→ 适用场景
→ 开发步骤
→ 边界处理
→ 正确/错误用法
→ 完成判断
```

## 2. 统一响应与结果处理

### 2.1 能力作用

统一响应能力让所有 HTTP Controller 和服务间调用使用一致的成功、失败和数据结构，避免每个业务模块定义自己的响应包装。公开 OpenAPI 只通过 DTO、认证和数据范围控制公开内容，不另造响应契约。

### 2.2 主要入口

| 入口 | 用途 |
| --- | --- |
| `R<T>` | 内部业务 Controller 返回成功、失败和数据 |
| `RetOps<T>` | 服务间调用后判断状态、读取数据和转换结果 |

### 2.3 开发步骤

1. 先确定接口的业务数据类型和公开字段范围；
2. 所有 HTTP Controller 返回 `R<T>`、`R<Void>` 或 `R<PageResult<T>>`；公开 OpenAPI 通过 DTO、认证和数据范围控制公开内容；
3. 远程调用收到 `R<T>` 后先判断结果，再读取 `data`；
4. 在接口文档中同步说明 `code`、`msg` 和 `data`；
5. 覆盖成功、业务失败、未授权和参数错误。

### 2.4 正确用法

```java
@GetMapping("/{id}")
public R<DeviceView> detail(@PathVariable Long id) {
    return R.ok(deviceService.detail(id));
}

DeviceView owner = RetOps.of(ownerClient.getOwner(ownerId))
        .assertSuccess(result -> new RemoteCallException(result.getMsg()))
        .getData()
        .orElseThrow(() -> new BusinessException("负责人不存在"));
```

### 2.5 错误用法

```java
public Map<String, Object> detail(Long id) {
    return Map.of("success", true, "data", deviceService.detail(id));
}
```

错误原因：绕过统一响应契约，调用方无法按 AURA 约定处理结果。

### 2.6 完成判断

- 没有新增自定义响应包装类；
- Controller 和 Feign 契约遵循其所属边界的响应模型；
- 远程失败不会被当成业务成功继续执行；
- 接口文档和实际响应字段一致。

## 3. JSON 处理

### 3.1 能力作用

统一 JSON 能力用于业务代码中的特殊转换，例如缓存序列化、消息载荷转换、树模型读取和非 HTTP 边界的数据处理。普通 Controller 请求响应由统一 Web/Jackson 配置处理。

### 3.2 主要入口

| 入口 | 用途 |
| --- | --- |
| `JsonUtils.toJson` | 对象转 JSON 字符串 |
| `JsonUtils.parse` | JSON 字符串转对象 |
| `JsonUtils.parseArray` | JSON 字符串转集合 |
| `JsonUtils.readTree` | 读取树模型 |
| `JsonUtils.toJsonBytes` | 对象转 JSON 字节 |

### 3.3 开发步骤

1. 先判断是否已经由 Spring MVC、Feign 或消息转换器自动完成转换；
2. 只有在边界需要显式字符串或字节时才调用工具；
3. 为目标类型提供明确的 DTO 或命令对象；
4. 保持日期、枚举、空值和未知字段处理遵循统一配置；
5. 对空字符串、非法 JSON 和字段缺失进行处理。

### 3.4 正确用法

```java
String payload = JsonUtils.toJson(command);
DeviceCommand command = JsonUtils.parse(payload, DeviceCommand.class);
```

### 3.5 错误用法

```java
ObjectMapper mapper = new ObjectMapper();
return mapper.writeValueAsString(entity);
```

错误原因：自行创建序列化器，可能造成日期、枚举和字段规则与服务其他接口不一致。

### 3.6 完成判断

- 没有在业务代码中重复创建 `ObjectMapper`；
- JSON 转换目标不是持久化实体的直接暴露；
- 非法输入和空值行为已经明确；
- 需要对外传输的字段经过敏感信息审查。

## 4. 身份、权限与内部调用

### 4.1 能力作用

安全能力提供当前认证对象、当前用户、角色和会话信息的读取方式，并通过权限声明保护业务操作，使用内部调用标识划定明确的服务内部边界。

### 4.2 主要入口

| 入口 | 用途 |
| --- | --- |
| `SecurityUtils` | 获取认证对象、当前用户、角色和会话信息 |
| `AuthUtils` | 处理受约束的客户端认证辅助场景 |
| `@HasPermission` | 为业务方法声明权限编码 |
| `@Inner` | 标识明确的内部服务调用入口 |

### 4.3 开发步骤

1. 判断接口是否需要登录、业务权限或可信内部调用；
2. 为新增、修改、删除、导入、导出和授权定义权限编码；
3. 在方法入口声明权限；
4. 在 Service 中从安全上下文读取当前用户；
5. 仅对经过服务端校验的内部入口使用内部调用能力；
6. 对无令牌、无权限、有效权限和内部调用分别自测。

### 4.4 正确用法

```java
@PutMapping("/{id}")
@HasPermission("device:config:update")
public R<Void> update(@PathVariable Long id, @Valid @RequestBody DeviceUpdateCommand command) {
    deviceService.update(id, command);
    return R.ok();
}

var currentUser = SecurityUtils.getUser();
if (currentUser == null) {
    throw new UnauthenticatedException();
}
String operator = currentUser.getUsername();
```

### 4.5 错误用法

```java
public void update(DeviceUpdateCommand command) {
    entity.setUpdateBy(command.getUserId());
}
```

错误原因：把请求参数当作当前操作人，调用方可以伪造操作主体。

### 4.6 完成判断

- 写接口权限可以单独识别和追踪；
- 当前用户来自服务端安全上下文；
- 内部入口范围最小，外部请求不能自行伪造内部标识；
- 日志和异常信息不包含令牌、密钥或完整认证报文。

## 5. 租户与基础实体

### 5.1 能力作用

租户能力保证业务请求、异步任务和远程调用中的数据边界一致；基础实体能力统一主键、审计字段和逻辑删除字段，减少实体重复定义。

### 5.2 主要入口

| 入口 | 用途 |
| --- | --- |
| `TenantContextHolder` | 读取、设置和清理当前租户上下文 |
| `TenantBroker` | 在受控代码块中临时运行指定租户上下文 |
| `BaseEntity` | 复用公共实体字段 |

### 5.3 开发步骤

1. 判断数据是否具有租户归属；
2. 租户实体优先继承 `BaseEntity`；
3. 请求入口使用项目已验证的租户上下文处理，并核对正常、异常及提前结束时的清理；普通用户业务还须核对上下文租户与已认证用户的租户归属，不能只检查上下文非空；
4. 异步任务明确传递租户并在结束时清理；
5. 缓存 key、远程请求和数据查询都保留租户边界；
6. 覆盖跨租户访问、无租户上下文和异步执行场景。

### 5.4 正确用法

```java
public class DeviceConfig extends BaseEntity {
    private String deviceCode;
    private String configValue;
}

var user = SecurityUtils.getUser();
Long tenantId = TenantContextHolder.getTenantId();
if (user == null || tenantId == null || !tenantId.equals(user.getTenantId())) {
    throw new CustomException("身份与租户上下文不匹配");
}
String key = "aura:device:tenant:" + tenantId + ":detail:" + deviceId;
```

### 5.5 错误用法

```java
executor.submit(() -> {
    TenantContextHolder.setTenantId(tenantId);
    deviceService.refresh();
});
```

错误原因：任务结束没有清理线程上下文，线程复用后可能污染其他租户任务。异步边界应使用框架提供的上下文传播和清理方式。

### 5.6 完成判断

- 已认证用户、请求上下文、查询与写入条件及缓存 key 的租户边界一致；
- 异步任务结束后上下文被清理；
- 公共审计字段没有在业务实体重复定义；
- 例外实体在详细设计中说明原因。

## 6. Redis 缓存与并发控制

### 6.1 能力作用

Redis 能力提供统一的缓存读写、过期、分布式锁、计数、集合和扫描操作。它用于明确的缓存或并发问题，不替代数据库和业务事实来源。

### 6.2 主要入口

| 入口 | 用途 |
| --- | --- |
| `RedisUtils.get/set/delete` | 缓存读写和失效 |
| `RedisUtils.expire/getExpire` | 生命周期控制 |
| `RedisUtils.getLock/releaseLock` | 受控分布式锁 |
| `RedisUtils.increment` | 计数和限次 |
| `RedisUtils.scan` | 非阻塞模式的匹配扫描 |

### 6.3 开发步骤

1. 明确缓存对象、真实数据源和可接受的过期时间；
2. 设计包含业务域和必要租户标识的 key；
3. 写入时设置过期时间；
4. 修改和删除成功后清理相关缓存；
5. 锁设置唯一值和过期时间，释放时校验持有者；
6. 禁止在生产请求中使用全量 `keys` 扫描。

### 6.4 正确用法

```java
String key = "aura:device:tenant:" + tenantId + ":detail:" + deviceId;
DeviceView value = RedisUtils.get(key);
if (value == null) {
    value = deviceMapper.selectView(deviceId);
    if (value != null) {
        RedisUtils.set(key, value, 300);
    }
}
```

### 6.5 错误用法

```java
RedisUtils.set("detail:" + deviceId, value);
RedisUtils.keys("*");
```

错误原因：key 没有业务和租户边界，且 `keys` 可能阻塞 Redis 服务。

### 6.6 完成判断

- key 可以判断所属业务和租户；
- 所有缓存都有有效期或明确的永久性理由；
- 写操作有对应失效策略；
- 锁有过期时间和安全释放逻辑；
- 生产代码没有无范围的全量扫描。

## 7. 操作日志、数据审计与幂等

### 7.1 能力作用

三项能力分别解决三个问题：操作日志记录“谁做了什么”，数据审计记录“数据改了什么”，幂等控制“重复请求如何只生效一次”。

### 7.2 主要入口

| 入口 | 用途 |
| --- | --- |
| `@SysLog` | 记录业务操作描述和扩展类型 |
| `@Audit` | 记录数据修改前后差异 |
| `@Idempotent` | 待项目验证的注解入口；注解存在不代表重复请求已被拦截 |

### 7.3 开发步骤

1. 识别操作是否需要留痕；
2. 对关键写操作增加清晰的日志描述；
3. 对修改操作提供实际存在、带数据边界的旧值和新值查询表达式；
4. 对可重复提交的接口设计稳定幂等键、有效期和重复结果，并确认项目中的幂等切面实际拦截；
5. 对日志、审计内容执行敏感字段检查；
6. 自测正常请求、重复请求、异常回滚和重试。

### 7.4 正确用法

```java
@SysLog("修改设备配置")
@Audit(name = "设备配置更新", spel = "@deviceConfigService.auditSnapshot(#id)")
public R<Void> update(Long id, DeviceUpdateCommand command) {
    deviceService.update(id, command);
    return R.ok();
}
```

### 7.5 错误用法

```java
log.info("token={}, request={}", token, requestBody);
```

错误原因：普通日志不能替代数据审计，并且输出了认证凭据和完整请求内容。

### 7.6 完成判断

- 能区分操作日志、数据审计和幂等的职责；
- 幂等 key 对同一业务请求稳定且有效期合理；
- 不能仅凭 `@Idempotent` 注解类存在就认定幂等已生效；未经项目验证时使用已验证的服务端幂等方案；
- 审计记录能够定位被修改的数据和字段；
- 日志、审计不会泄露令牌、密钥、密码等敏感信息。

## 8. 六项能力的组合顺序

典型的业务写接口可以按以下顺序组合：

```text
统一响应
→ 身份认证
→ 权限判断
→ 租户边界
→ 业务数据处理
→ 日志/审计/幂等
→ 缓存失效
→ 返回统一结果
```

不是每个接口都需要全部能力。开发者应以业务问题为依据选择能力，并在详细设计和自测说明中记录选择结果。
