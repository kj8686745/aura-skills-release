# 网关与流量治理能力清单与边界

| 能力 | 依赖或运行位置 | 当前实现入口 | 接入前提 |
| --- | --- | --- | --- |
| 动态路由 | 可接入网关服务的 `aura-common-gateway`；现有网关工程另有同名实现 | Redis 路由仓储、刷新事件监听、路由健康检查 | 核对实际使用的实现、Reactive Gateway、Redis 连接及路由定义的受控写入来源 |
| 网关灰度 | 网关服务中的 `aura-common-gateway` | `gray.rule.enabled=true` 时的灰度负载均衡 | 服务发现、实例 `VERSION` 元数据、可信的版本标识来源 |
| 服务间灰度 | 业务服务中的 `aura-common-gray` | Feign 版本透传、服务实例选择 | Feign/LoadBalancer；当前版本匹配分支依赖 Nacos 实例类型，还需核对上下文清理与回退策略 |
| Servlet 接口与 Feign 保护 | 业务服务中的 `aura-common-sentinel` | Servlet 阻断处理和 Feign 构建扩展 | 依赖和自动配置生效，项目已提供保护规则并核对返回契约 |
| 网关限流 | 网关工程 | `KeyResolver` 示例 | 另行配置网关限流过滤器、阈值和可信客户端 IP 来源 |

## 1. 已实现与需另行建设的边界

- 动态路由仓储负责读取和保存路由定义，并发送刷新消息；它不是对业务开发者开放的路由管理 API。当前删除实现的刷新消息不保证在 Redis 删除完成后发送，删除与回滚结果必须按实际路由行为核对。路由审批、审计、回滚和发布入口需由接入项目提供并验证。
- `aura-core-gateway` 当前工程存在自身的路由与灰度实现，所查网关业务模块未直接依赖 `aura-common-gateway`；接入时须核对运行中的实际 Bean 与配置，不能把公共模块实现当作该工程的已生效能力。
- 网关和服务间灰度按 `VERSION` 选择实例。当前实现无匹配版本时会回退到普通实例，**不提供严格版本隔离**；需要严格隔离时必须另行设计和验证。
- `aura-common-gray` 的版本匹配分支将实例转换为 `NacosServiceInstance`；非 Nacos 服务发现不能直接按“通用服务发现”使用该分支，须先核对实例类型与实际选择结果。
- 灰度选择器会读取请求头，但不负责证明请求头可信。来自外部的版本头必须在可信入口校验或重写，不能把客户端自行填写的值当成已授权灰度资格。
- `aura-common-sentinel` 的默认阻断处理面向 Servlet；网关 WebFlux 限流需单独配置。仅引入模块或定义 `KeyResolver` 不会自动产生网关限流规则。
- 保护规则、阈值、超时、回退和恢复行为应结合服务容量及业务契约设定；框架组件不替代真实压测、故障演练或业务兜底。

## 2. 与其他能力的边界

网关路由成功不等于业务授权成功。业务服务仍按基础业务与安全能力完成身份、权限、租户、数据范围和状态校验；消息投递、调度补偿、文件导出等任务由各自能力包处理。内部路由仓储、负载均衡器和自动配置类不应被业务代码直接实例化为业务 API。
