# 基础业务能力接入与组合说明

**能力包**：通用工具类 / 基础业务开发能力包  
**适用对象**：业务应用开发者、后端技术负责人和 AI 编码助手  
**使用目标**：按业务开发顺序选择并组合 AURA 已提供的基础入口，完成一个可联调的业务功能

本文中的 Controller、Service、数据库、事务与自测顺序用于串联能力用法，不单独定义工程分层、接口、权限或交付规则；共同要求由[基础编码规范矩阵](../../../01-基础编码规范/规范矩阵.md)所指向的正文决定。示例中的目录和对象只按实际业务需要选用。

## 0. 业务研发闭环

以下是业务功能从需求到交付的完整路径。按本次变更涉及的环节形成可检查的结果；不要求每个局部改动都新建一套文档、目录和代码文件。

```text
需求进入
→ 需求澄清与边界确认
→ 技术详细设计（按触发条件和影响范围）
→ 数据库、接口和权限契约
→ 工程骨架与依赖配置
→ Controller / Service / 数据访问实现
→ 事务、异常和横向能力接入
→ 研发自测与前后端联调
→ 交付、文档和后续维护
```

## 0.1 阶段产物和技术细节

| 阶段 | 涉及时要回答的问题 | 对应产物 | 本文技术内容 |
| --- | --- | --- | --- |
| 需求澄清 | 做什么、不做什么、谁使用、边界是什么 | 需求范围、角色和业务流程 | 业务用例、状态、主子关系 |
| 技术详细设计 | 如何分层、数据如何保存、接口如何协作 | 按详细设计规范的触发条件形成完整或简化设计 | 模块结构、Controller/Service、事务和依赖 |
| 数据与契约设计 | 表怎么建、接口怎么入参出参、权限如何控制 | 表结构/迁移脚本、DTO/VO、API 契约 | Entity、Mapper、XML、分页、权限 |
| 工程初始化 | 依赖、包路径、配置和基础能力是否可用 | 新建模块时形成 POM、配置和实际需要的目录 | Maven 依赖、模块目录、启动配置 |
| 业务实现 | 业务流程是否完整、数据是否一致 | Controller、Service、Mapper、转换器 | CRUD、主子表、查询、写入和事务 |
| 横向能力 | 鉴权、租户、缓存、日志、审计和幂等如何接入 | 能力组合说明和配置 | 通用支撑能力协作 |
| 自测联调 | 正常、失败、回滚和边界是否可观察 | 自测记录、接口联调记录 | 异常、分页、权限、数据范围 |
| 交付维护 | 别人能否构建、部署和继续修改 | 变更说明、迁移脚本、接口/项目文档 | 交付证据和后续变更入口 |

## 0.2 需求进入后的第一步

收到需求后，先把自然语言转换为可开发的业务用例：

1. 明确业务对象、参与角色和触发入口；
2. 列出本次涉及的新增、查询、修改、删除、导入、导出或业务动作；
3. 确定数据状态、状态转换和不可逆操作；
4. 标出主表、子表、关系表和外部服务；
5. 标出权限、租户、数据范围、审计和幂等要求；
6. 明确成功结果、业务失败、权限失败、数据不存在和系统失败；
7. 决定是否需要本地事务、异步任务、缓存或分布式能力。

以上问题帮助定位要接入的框架能力；需求分析和技术详细设计的要求以对应规范为准。

## 0.3 技术详细设计如何承接本能力包

是否需要详细设计、采用完整还是简化设计，按详细设计规范的触发条件和影响范围判断；编写时使用该规范配套模板，不在本能力包另设一套文档门槛。

涉及本能力包时，设计应写明实际选用的公共依赖、Controller/Service/Mapper 落点、数据与权限条件、本地事务及外部副作用边界，以及对应的失败验证。未涉及的缓存、导入导出或异步能力不为填满模板而加入。

## 0.4 按研发阶段查阅技术内容

| 当前阶段 | 优先阅读章节 |
| --- | --- |
| 设计接口入口 | Controller 能力、异常与统一返回、参数校验与对象转换 |
| 设计数据库 | 数据库开发依赖与接入、数据库工程结构、基础实体和字段约定、Mapper 编写方式 |

| 实现主子表 | 主子表业务模式、事务能力、数据库写入 |
| 实现导入导出 | 导入导出在业务闭环中的位置、文件任务与实时交互能力包 |
| 处理权限和租户 | 横向能力协作、基础通用支撑能力包 |
| 准备提交 | 研发自测和交付判据、数据库开发完成判断 |

## 0.5 能力地图与接入选择

| 开发环节 | AURA 提供的基础入口 | 业务模块需要完成什么 | 可观察结果 |
| --- | --- | --- | --- |
| HTTP 入口 | Web 框架、`@HasPermission`、统一参数校验 | 定义本模块 Controller、DTO、权限标识 | 合法请求进入用例；无权限请求不写库 |
| 业务用例 | Service 层与本地事务支持 | 写业务规则、事务边界和失败处理 | 一次写操作完整提交或回滚 |
| 数据映射 | `aura-common-data`、`BaseEntity`、MyBatis-Plus `BaseMapper` | 定义本模块 Entity、Mapper、SQL 和迁移脚本 | 数据按业务条件读写，审计字段可核对 |
| 统一结果 | 公共核心模块的 `R<T>`、`CustomException` | 返回明确的数据模型并抛出可识别业务错误 | 成功与失败均遵循接口契约 |
| 租户与操作人 | 公共租户和安全上下文 | 普通用户用例核对上下文租户与登录用户租户，并在读写中落实数据范围 | 换租户或越权操作不能改动目标数据 |

这些基础入口不替业务模块生成 Controller、Mapper 或 SQL。一个功能需要哪些横向能力，应按实际需求选择；缓存、审计和幂等不因引入数据模块而自动完成。

接口路径、HTTP 方法和响应模型遵循[接口规范](../../../01-基础编码规范/05-接口规范体系/01-接口规范.md)；后端分层和对象职责遵循[后端基础编码分类](../../../01-基础编码规范/总入口.md#三后端基础编码分类)；数据访问与事务边界遵循[数据访问事务规范](../../../01-基础编码规范/08-数据访问事务数据表达与生命周期规范/01-数据访问事务与生命周期.md)。本能力包说明这些约定在一次业务开发中如何组合使用。

## 1. HTTP 入口的能力组合示例

### 能力作用

本示例展示 `@HasPermission`、参数校验和统一接口 `R<T>` 如何与业务用例连接。Controller 的职责和对象边界由 `AURA-BASE-BE-004` 与接口规范决定。

### 正确结构

```java
@RestController
@RequestMapping("/device/config")
@RequiredArgsConstructor
public class DeviceConfigController {

    private final DeviceConfigService service;

    @PutMapping("/{id}")
    @HasPermission("device:config:update")
    public R<Void> update(@PathVariable Long id,
                          @Valid @RequestBody DeviceUpdateCommand command) {
        service.update(id, command);
        return R.ok();
    }
}
```

### 完成判断

- 请求参数使用 DTO/Command；
- 写接口有权限入口；
- Controller 不直接操作 Mapper、Redis 或远程服务；
- 返回统一 `R<T>`。

## 2. Service 与数据入口的组合示例

### 能力作用

本示例展示 Service 如何调用业务 Mapper，并读取框架提供的身份和租户上下文。业务分层与事务边界由基础编码规范决定。

### 正确结构

```java
@Service
@RequiredArgsConstructor
public class DeviceConfigService {

    private final DeviceConfigMapper mapper;

    @Transactional
    public void update(Long id, DeviceUpdateCommand command) {
        Long tenantId = TenantContextHolder.getTenantId();
        var user = SecurityUtils.getUser();
        if (tenantId == null || user == null || user.getTenantId() == null
                || !tenantId.equals(user.getTenantId())) {
            throw new CustomException("身份与租户上下文不匹配");
        }
        int updated = mapper.updateOwned(id, tenantId, command.value(), user.getUsername());
        if (updated == 0) {
            throw new CustomException("配置不存在或无权访问");
        }
    }
}
```

`updateOwned` 是业务模块自行声明的 Mapper 方法，须在 SQL 中同时约束主键、当前租户和逻辑删除状态；完整方法与 SQL 见第 23 节。这里使用的 `CustomException` 来自公共核心模块。`TenantContextHolder` 的值只提供请求上下文，普通用户业务还须与已认证用户的租户归属核对；跨租户管理操作需要另行定义授权范围。

### 完成判断

- 业务规则集中在 Service 或领域对象；
- 事务覆盖完整的本地写操作；
- 异常能够向事务边界传播；
- 不把 Controller 参数直接当作持久化实体。

## 3. 本地事务的接入示例

### 能力作用

Spring 本地事务用于同一数据源中的一组业务写入；这里说明与 Mapper、缓存和异常处理的组合位置，不把通用事务规则重新定义为本包独有要求。事务语义以 `AURA-BASE-BE-010`、`AURA-BASE-DATA-005/006` 为准。

### 接入与组合注意

1. 事务边界优先放在 Service 的业务方法；
2. 读操作明确是否需要只读事务；
3. 异常必须能够触发回滚，不能捕获后静默吞掉；
4. 事务中避免长时间远程调用、文件生成和用户交互；
5. 跨服务一致性需求另行选择分布式事务或可靠消息方案。

### 错误方向

```java
@Transactional
public void update() {
    remoteService.call();
    Thread.sleep(30000);
    mapper.update(...);
}
```

事务中包含长时间远程调用会长期占用连接和锁，失败时也无法天然回滚外部服务。

## 4. 异常与统一返回

```text
参数错误 → 参数校验异常 → 统一错误响应
资源不存在 → 业务异常 → 统一错误响应
业务规则失败 → 业务异常 → 事务回滚 + 统一错误响应
系统异常 → 全局异常处理 → 统一错误响应 + 日志
```

业务层抛出已由本服务异常处理器映射的业务异常，不能在 Controller 中拼装错误字符串，也不能把数据库异常原样返回前端。本文的 `R<T>` 示例适用于所有 HTTP 业务接口；公开 OpenAPI 通过 DTO、认证和数据范围控制公开内容，不另造响应外壳。

## 5. 完整业务示例入口

第 23 节给出一个设备配置更新用例，将 DTO、Controller、Service、Mapper XML、租户条件、事务与自测放在同一场景中。先按第 0.5 节选择能力，再按第 22.1 节逐条检查边界，不应把单个 Controller 代码片段误当成完整业务功能。

这个闭环中，Controller 负责入口，Service 负责业务和事务，数据访问由本能力包的 Mapper/数据库章节承接。若该数据存在缓存，应在事务成功提交后按缓存策略失效，不能在事务尚未提交时把缓存操作误当成数据库提交的一部分。

## 6. 标准业务模块结构

下面按职责展示普通业务模块可能使用的目录。只建立实际需要的目录和对象，不为保持树形完整而生成空接口、空实现或空文件夹；具体拆分遵循[工程结构规范](../../../01-基础编码规范/01-工程结构命名与项目文档规范/01-工程结构与代码组织.md)。

```text
<业务模块>/
├─ controller/       HTTP 入口
├─ service/          业务接口
│  └─ impl/          业务实现、事务和流程编排
├─ dto/              请求、查询和提交对象
├─ vo/               接口返回对象
├─ bo/               业务中间对象（确有需要时建立）
├─ convert/          DTO、Entity、VO 转换
├─ entity/           数据库映射对象
├─ mapper/           数据访问接口
├─ config/           本模块配置
└─ support/          本模块专用支撑代码
```

分层职责保持单向调用：

```text
Controller → Service → Mapper/Repository → Database
                  ├→ 通用支撑能力
                  └→ 受控的外部服务
```

Controller 不直接访问 Mapper；Mapper 不调用外部服务；对象转换不访问数据库。

## 7. 业务功能的标准生命周期

```text
需求与资源定义
→ DTO/VO 和接口契约
→ Entity 与数据访问设计
→ Controller 入口
→ Service 业务规则
→ 事务和异常边界
→ 日志/审计/幂等/缓存协作
→ 联调、自测和交付
```

本次变更涉及的阶段应能找到相应实现、契约或验证结果；目录数量和文件数量不作为完成标准。

## 8. 标准 CRUD 开发模式

标准 CRUD 适用于资源的新增、修改、删除、详情、分页、选项和状态变更。新增、修改、查询 DTO 应分离，Entity 不直接作为复杂接口入参或出参。

### 8.1 推荐结构

```text
controller/DeviceController.java
dto/DeviceCreateDTO.java
dto/DeviceUpdateDTO.java
dto/DevicePageDTO.java
entity/DeviceEntity.java
mapper/DeviceMapper.java
service/DeviceService.java
service/impl/DeviceServiceImpl.java
vo/DeviceVO.java
vo/DeviceOptionVO.java
convert/DeviceConvert.java
```

### 8.2 标准流程

```text
Controller 参数接收和格式校验
→ Service 校验业务状态和权限边界
→ 数据访问能力执行查询或写入
→ Service 处理事务与必要的审计
→ 事务提交后按能力约定处理缓存失效
→ Convert 转换 Entity 与 VO
→ Controller 返回统一响应
```

### 8.3 动作和接口约定

下表是 HTTP 业务接口的 Controller 相对路径示例，不是可直接复制的网关最终路径。实际模块前缀、网关路径、权限编码和分页字段应在接口文档中登记；所有调用边界统一使用 `R<T>` 和 `PageResult<T>`，对外接口仅通过 DTO、认证和数据范围控制公开内容。

| 业务动作 | HTTP 方法 | 路径示例 | 返回结果 |
| --- | --- | --- | --- |
| 分页列表 | `GET` | `/devices/page` | `R<PageResult<DeviceVO>>` |
| 详情 | `GET` | `/devices/{id}` | `R<DeviceVO>` |
| 新增 | `POST` | `/devices` | `R<Long>` |
| 修改 | `PUT` | `/devices/{id}` | `R<Void>` |
| 删除 | `DELETE` | `/devices/{id}` | `R<Void>` |
| 业务动作 | `POST` | `/devices/{id}/enable` | `R<Void>` |

### 8.4 CRUD 完成判据

- 新增、修改、查询 DTO 已分离；
- Entity、VO 和 DTO 职责清晰；
- 修改、删除具备资源存在和状态校验；
- 删除策略已经明确是逻辑删除还是物理删除；
- 列表和导出使用同一数据权限边界；
- 接口、权限、日志和事务可以逐项核对。

## 9. 主子表业务模式

### 9.1 适用场景

订单与明细、配置与规则、任务与明细、流程与节点等一主多子业务使用主子表模式。

### 9.2 输入与输出

```java
public class OrderCreateDTO {
    @NotBlank
    private String orderNo;

    @Valid
    @Size(max = 200)
    private List<OrderItemCreateDTO> items;
}

public class OrderDetailVO {
    private Long id;
    private String orderNo;
    private List<OrderItemVO> items;
}
```

### 9.3 保存和修改流程

```text
校验主表
→ 校验子表数量、字段和业务关系
→ 同一数据源的本地事务内写入主表与子表
→ 事务成功提交
→ 按需失效缓存或触发跨边界后续动作
→ 返回主表标识或聚合详情
```

数据审计和操作日志按对应能力的触发、落库与失败记录约定接入，不把缓存或外部调用视为本地事务的一部分。修改策略按详细设计规范 `AURA-DES-006/007` 说明流程、状态和数据所有权：子表没有独立生命周期且数量较少时可以全量覆盖；子表有独立状态、审计或外部引用时应计算新增、修改和删除差异。

### 9.4 完成判据

- 同一数据源的主表和子表写入在同一本地事务中；
- 子表集合有数量上限；
- 修改策略明确；
- 详情查询不会产生循环单条查询；
- 主子表删除前检查业务引用。

## 10. 参数校验与对象转换

### 10.1 校验分层

- DTO 校验字段必填、长度、格式、数值范围和集合数量；
- Service 校验数据是否存在、状态是否允许、业务关系是否满足；
- 数据访问层不承担面向用户的业务错误提示。

### 10.2 对象职责

| 对象 | 用途 | 禁止事项 |
| --- | --- | --- |
| Entity | 数据库映射 | 直接作为复杂接口入参或出参 |
| DTO | 新增、修改、查询和导入参数 | 混入持久化状态和内部字段 |
| VO | 接口返回 | 暴露密码、令牌、密钥和内部状态 |
| BO | Service 内部业务传递 | 长期作为外部接口契约 |
| Convert | 对象转换 | 查询数据库或产生业务副作用 |

## 11. 分页与查询用例

HTTP 接口分页统一使用 `PageResult<T>` 契约，设置默认页大小与上限，查询条件集中在 Query DTO 中，排序字段使用后端白名单；Controller 或适配层负责把 ORM `Page/IPage` 转换为 `PageResult<T>`，不能把 ORM 类型直接输出。详情、列表、导出和统计必须保持一致的数据权限边界。

`PageResult<T>` 是接口规范要求的公共分页边界，不代表目标依赖版本已经提供该类或转换方法。编码前核对公共类型的包路径、版本和字段；尚未提供时先补齐公共实现，不在业务模块自行创建同名 DTO 冒充框架能力。`Page/IPage` 只用于内部查询。

```text
接收分页参数
→ 规范化页码和页大小
→ 校验查询权限和租户边界
→ 调用数据访问能力分页
→ 转换为 VO
→ 返回统一分页响应
```

不得在 Controller 中构造复杂查询条件，也不得让前端排序字段直接进入 SQL。

## 12. 导入导出在业务闭环中的位置

导入导出是业务模式的扩展，不属于普通 CRUD 的默认流程：

```text
上传与格式校验
→ 解析导入 DTO
→ 行级格式和业务校验
→ Service 选择全量回滚/部分成功/异步任务
→ 数据访问能力批量写入
→ 返回成功数和失败明细
```

导出与列表遵循[身份上下文与权限边界](../../../01-基础编码规范/07-安全身份权限与敏感信息规范/01-身份上下文与权限边界.md) `AURA-BASE-SEC-006` 和[前端会话与文件访问](../../../01-基础编码规范/07-安全身份权限与敏感信息规范/03-前端会话与文件访问.md) `AURA-BASE-SEC-015` 的数据范围和访问校验；大文件进入文件任务与实时交互能力包处理。具体文件和 Excel 入口引用对应专项能力包。

## 13. 横向能力协作

基础业务闭环只定义横向能力在什么位置接入：

| 位置 | 应协作的能力 |

具体 API 读取[基础通用支撑能力包](../03-基础通用支撑能力包/01-总入口.md)，数据库入口读取本能力包第 15 至 22 节。

下表仅用于核对本包示例中实际接入的框架入口，不替代[研发自测范围与验证层级](../../../01-基础编码规范/12-研发自测规范/01-范围与验证层级.md)及[证据、回归与交付结论](../../../01-基础编码规范/12-研发自测规范/03-证据回归与交付结论.md)的要求；未使用的横向能力无需为了填满清单而接入：

| 类别 | 自测场景 |
| --- | --- |
| 接口 | 正常、参数错误、资源不存在；写入动作检查重复提交的实际策略 |

## 15. 数据库开发依赖与接入

数据库能力属于基础业务开发闭环的必备部分。新建后端业务服务时，先确认项目父 POM/BOM 已管理的 AURA 版本与依赖，再按服务职责选择业务服务聚合依赖或所需公共模块，并配置目标数据库驱动与数据源。

### 15.1 推荐依赖组合

普通业务服务先检查是否已引入 `aura-common-service-starter`；当前该聚合依赖包含公共核心、数据、安全、日志等模块。选择按模块引入时，基础数据访问至少需要公共核心与数据模块：

```xml
<dependency>
    <groupId>net.fxft</groupId>
    <artifactId>aura-common-core</artifactId>
</dependency>
<dependency>
    <groupId>net.fxft</groupId>
    <artifactId>aura-common-data</artifactId>
</dependency>
```

当前 `aura-common-data` 模块已经声明 MyBatis-Plus starter 与 SQL 解析器依赖；先核对项目依赖树，不重复声明。数据库驱动和连接池按项目实际数据库与统一配置选择，不因文档示例同时安装多套连接池。业务模块不应自行覆盖公共包版本，也不应为了一个基础查询重复引入多套 ORM 或 SQL 构造框架。

### 15.2 依赖选择原则

| 需求 | 依赖方向 | 处理方式 |
| --- | --- | --- |
| 基础实体、租户和数据工具 | `aura-common-data` | 使用公共实体、数据边界和数据配置 |
| 基础 CRUD、分页和逻辑删除 | MyBatis-Plus starter | 优先使用框架 CRUD 能力 |
| 复杂查询和多表关联 | Mapper XML 或明确 Mapper 方法 | 显式字段、参数绑定和结果映射 |
| 对象转换 | MapStruct 或项目统一转换能力 | 转换类不访问数据库 |
| 数据库连接池 | 项目统一连接池 | 不在业务模块自建连接池 |

## 16. 数据库工程结构

推荐的业务模块结构如下：

```text
src/main/java/<package>/
├─ controller/
├─ service/
│  └─ impl/
├─ dto/
├─ vo/
├─ entity/
├─ mapper/
└─ convert/

src/main/resources/
├─ mapper/
│  └─ DeviceConfigMapper.xml
└─ db/
   └─ migration/          数据库迁移脚本
```

发生数据库变更时，迁移脚本、Entity、Mapper、Service 和接口应能互相追溯：变更字段对应 Entity，Entity 对应 Mapper，Mapper 对应 Service 用例，Service 对应接口或任务入口。

## 17. 基础实体和字段约定

适合使用统一审计与逻辑删除字段的业务实体，可继承公共 `BaseEntity`。当前类包含 `id`、`createBy`、`updateBy`、`createTime`、`updateTime`、`delFlag`；主键使用 `ASSIGN_ID`，逻辑删除字段标记为 `@TableLogic`。字段填充依赖 MyBatis-Plus 处理器及实际持久化操作，不应仅凭继承关系推断自定义 SQL 一定完成填充。

```java
@Data
@TableName("device_config")
public class DeviceConfig extends BaseEntity {

    private Long tenantId;
    private String deviceCode;
    private String configValue;
    private Integer status;
}
```

基础要求：

- 主键使用项目统一主键策略；
- 逻辑删除字段使用统一逻辑删除配置；
- 创建人和修改人从安全上下文或框架填充能力获得；
- 时间字段使用项目统一时间类型和序列化规则；
- 不把密码、token、密钥等敏感字段放入普通 VO；
- 非持久化字段优先放在 VO/BO；确需暂存在 Entity 时，按 `AURA-CAP-COMMON-BIZ-007` 明确排除持久化映射。

如果业务表不适合继承 `BaseEntity`，必须在详细设计中说明公共字段、逻辑删除和审计方案。

## 18. Mapper 编写方式

### 18.1 简单 CRUD

简单 CRUD 优先使用项目统一 Mapper 基础能力：

```java
@Mapper
public interface DeviceConfigMapper extends BaseMapper<DeviceConfig> {
}
```

Service 通过 Mapper 或统一 Service 能力完成基础查询和写入；Controller 不直接构造 Wrapper，也不直接调用 Mapper。

### 18.2 复杂查询

复杂查询使用语义明确的 Mapper 方法和 XML：

```java
@Mapper
public interface DeviceConfigMapper extends BaseMapper<DeviceConfig> {

    Page<DeviceView> selectPageView(Page<DeviceView> page,
                                    @Param("tenantId") Long tenantId,
                                    @Param("query") DevicePageQuery query);
}
```

对应 XML：

```xml
<mapper namespace="com.example.device.mapper.DeviceConfigMapper">
    <select id="selectPageView" resultType="com.example.device.vo.DeviceView">
        select
            id,
            device_code as deviceCode,
            config_value as configValue,
            status,
            create_time as createTime
        from device_config
        <where>
            del_flag = 0
            and tenant_id = #{tenantId}
            <if test="query.deviceCode != null and query.deviceCode != ''">
                and device_code = #{query.deviceCode}
            </if>
            <if test="query.status != null">
                and status = #{query.status}
            </if>
        </where>
        order by create_time desc, id desc
    </select>
</mapper>
```

XML 的 `com.example.device.mapper` 和 `com.example.device.vo` 需替换为业务模块实际包名；`tenantId` 必须由 Service 核对身份与租户归属后传入，不能直接采用前端查询参数。`DevicePageQuery` 的筛选字段应具有可供 MyBatis 读取的属性。

### 18.3 SQL 编写要求

- 查询字段显式列出，禁止默认 `select *`；
- 普通参数使用 `#{}` 绑定；
- `${}` 仅允许用于经过后端白名单转换的动态片段；
- 查询、更新和删除必须有明确条件；
- 逻辑删除、租户和数据权限条件不能遗漏；
- XML 放在 `resources/mapper` 并与 Mapper 接口对应；
- 复杂 SQL 应说明字段别名、关联关系和统计口径。

## 19. Service 中如何使用数据库

Service 负责业务规则和事务，数据库读写通过 Mapper/Repository 完成：

```java
@Service
@RequiredArgsConstructor
public class DeviceConfigServiceImpl implements DeviceConfigService {

    private final DeviceConfigMapper mapper;
    private final DeviceConfigConvert convert;

    @Override
    @Transactional(rollbackFor = Exception.class)
    public Long create(DeviceCreateCommand command) {
        validateBusinessRule(command);
        Long tenantId = TenantContextHolder.getTenantId();
        var user = SecurityUtils.getUser();
        if (tenantId == null || user == null || user.getTenantId() == null
                || !tenantId.equals(user.getTenantId())) {
            throw new CustomException("身份与租户上下文不匹配");
        }
        DeviceConfig entity = convert.toEntity(command);
        entity.setTenantId(tenantId);
        mapper.insert(entity);
        return entity.getId();
    }

    @Override
    @Transactional(readOnly = true)
    public DeviceView detail(Long id) {
        Long tenantId = TenantContextHolder.getTenantId();
        var user = SecurityUtils.getUser();
        if (tenantId == null || user == null || user.getTenantId() == null
                || !tenantId.equals(user.getTenantId())) {
            throw new CustomException("身份与租户上下文不匹配");
        }
        DeviceConfig entity = mapper.selectOne(
            Wrappers.<DeviceConfig>lambdaQuery()
                .eq(DeviceConfig::getId, id)
                .eq(DeviceConfig::getTenantId, tenantId));
        if (entity == null) {
            throw new CustomException("设备配置不存在");
        }
        return convert.toView(entity);
    }
}
```

Service 中禁止直接写 SQL、拼接 SQL 字符串、创建新的数据源或绕过 Mapper 访问数据库。SQL 应该留在 Mapper 注解或 XML 中，业务条件由 Service 组织后以参数传入。上例的 `DeviceConfigConvert` 是业务模块自行实现的转换器，不是公共框架类；示例中的 `DeviceConfig` 须提供 `tenantId` 的 getter。详情和分页除租户外若还有部门、本人或资源归属条件，也须落实到实际查询，不能把仅按租户过滤当作完整授权。

## 20. 事务、数据库写入和横向能力

```text
Service 参数和状态校验
→ 开启本地事务
→ Mapper 写入主表/关系表
→ 按对应能力约定记录数据审计和操作日志
→ 事务成功提交
→ 按需失效缓存；外部事件使用可靠发布或补偿方案
→ 返回业务结果
```

同一数据源内需要一起成功或失败的主子表、关系表和授权表写入，放在同一业务事务中。大批量处理遵循[通用数据表达规范](../../../01-基础编码规范/08-数据访问事务数据表达与生命周期规范/02-时间标识与通用数据表达.md) `AURA-BASE-DATAEXP-017`，按批次和失败语义设计，不能不加限制地放进一个长事务。缓存、消息和外部调用不应被误认为数据库事务的一部分；需要跨边界一致性时，进入分布式事务、可靠消息或补偿设计。

## 21. 数据库开发反例

```java
@Service
public class DeviceService {

    public DeviceConfig find(Long id) {
        return jdbcTemplate.queryForObject(
                "select * from device_config where id = " + id,
                DeviceConfig.class);
    }
}
```

问题包括：

- Service 直接承载 SQL；
- 外部参数拼接 SQL，存在注入风险；
- 使用 `select *`，字段契约不稳定；
- 没有数据权限、租户和逻辑删除条件；
- 返回持久化实体，可能泄露内部字段；
- 没有统一异常、事务和对象转换边界。

## 22. 数据库开发完成判断

- POM 依赖由 BOM 或父 POM 统一管理；
- 数据库迁移脚本、Entity、Mapper、Service 和接口可追溯；
- 基础实体和审计字段遵循公共约定；
- Entity 中的非持久化字段不会被 MyBatis-Plus 误认为数据库列；
- Service 不直接编写 SQL；
- Mapper/ XML 参数安全、字段显式、条件完整；
- 查询、写入、分页、逻辑删除和数据权限边界明确；
- 写操作事务覆盖完整业务用例；
- DTO、Entity、VO 和转换职责清晰；
- 数据库异常不会原样返回前端；
- 按第 14 节对实际涉及的查询、权限、租户、多步写入和批量场景留下研发自测结果，不要求未涉及的场景补做形式化记录。

### AURA-CAP-COMMON-BIZ-001：先确定依赖入口，再使用数据能力

适用场景：新建后端业务模块或接入数据库。使用要求：核对父 POM/BOM、现有聚合依赖和依赖树；缺少数据模块时才按版本引入 `aura-common-data`。

**正确写法**：已有 `aura-common-service-starter` 且依赖树包含数据模块时，直接使用其提供的 `BaseEntity` 与 MyBatis-Plus 能力。**错误写法**：未核对传递依赖，同时手工追加不同版本的公共数据模块、MyBatis-Plus starter 和连接池。**失败与边界**：依赖解析或自动配置失败时，应先核对版本组合与数据源配置，不通过覆盖公共包版本规避。**检查方式**：查看 Maven 依赖树、启动配置和实际数据源连接。

### AURA-CAP-COMMON-BIZ-002：在接口入口组合权限声明与业务用例

适用场景：新增或修改需要权限控制的 HTTP 接口。共同的 Controller 职责和服务端权限要求见 `AURA-BASE-BE-004`、`AURA-BASE-SEC-004`；本要点示范 `@HasPermission` 与业务用例调用的组合位置。

**正确写法**：`@HasPermission("device:config:update")` 的 Controller 调用 `service.update(id, command)` 后返回 `R.ok()`。**错误写法**：Controller 直接注入 Mapper，拼 SQL 或在入口中执行多步业务写入。**失败与边界**：参数错误和无权限请求不得进入写入流程。**检查方式**：检查 Controller 依赖、接口权限和非法请求下数据库是否保持不变。

### AURA-CAP-COMMON-BIZ-003：在 Mapper 读写中落实租户与数据范围

适用场景：详情、列表、修改和删除业务数据。共同的数据边界以 `AURA-BASE-SEC-006`、`AURA-BASE-BE-017` 为准；本要点展示 AURA 数据访问入口中如何将租户、逻辑删除和业务条件落实到实际 Mapper 读写，不把查询拦截器误当作写入保护。

**正确写法**：普通用户业务先核对上下文租户与登录用户租户，再执行 `update ... where id = #{id} and tenant_id = #{tenantId} and del_flag = 0`，并检查受影响行数。**错误写法**：只检查上下文非空，执行 `update ... where id = #{id}`，并假定查询拦截器会保护写入。**失败与边界**：零行更新要按资源不存在或无权访问处理；租户不匹配时拒绝操作，跨租户管理须使用另行授权的用例。**检查方式**：用当前租户、其他租户、租户不匹配和已删除记录分别执行查询与写入自测。

### AURA-CAP-COMMON-BIZ-004：在业务用例中组合本地事务与缓存处理

适用场景：一个业务动作写入一张或多张本地表，并可能涉及缓存。事务和外部副作用的共同规则见 `AURA-BASE-BE-010`、`AURA-BASE-DATA-005/006/010`；本要点展示 AURA Service、Mapper 与缓存能力如何组合，不能把本地事务描述成缓存或远程调用的原子性保证。

**正确写法**：Service 用例方法标注 `@Transactional(rollbackFor = Exception.class)`，同一数据源的主表与子表写入失败时一并回滚；需要失效缓存时，按缓存能力约定在事务提交后处理。**错误写法**：只给某个 Mapper 调用加事务，捕获写入异常后仍返回成功，在事务中长时间等待远程服务，或在提交前清理缓存却声称数据库失败时缓存也会自动回滚。**失败与边界**：本地事务不回滚已发生的远程调用或缓存变更，跨数据源写入不能仅凭一个本地事务保证原子性。**检查方式**：在第二步写入制造异常，核对两张表均未提交；使用缓存时另核对提交成功与回滚后的缓存结果。

### AURA-CAP-COMMON-BIZ-005：选用业务异常与统一响应入口

适用场景：资源不存在、业务状态不允许和接口成功返回。异常与响应的共同规则见 `AURA-BASE-BE-007`、`AURA-BASE-API-014`；本要点说明项目已采用对应公共模块时，`CustomException` 与统一 `R<T>` 如何分工，以及公开 DTO、认证和数据范围如何约束。

**正确写法**：Service 对零行更新抛出 `CustomException("配置不存在或无权访问")`，Controller 按统一契约返回 `R.ok()` 或统一错误 `R<T>`；公开接口通过 DTO、认证和数据范围控制字段。**错误写法**：`catch (Exception e) { return R.ok(); }`，把数据库错误栈直接放进 `data`，或为公开接口另造响应外壳。**失败与边界**：具体 HTTP 状态与业务错误码按接口规范和项目异常处理配置核对。**检查方式**：对照成功、参数错误、资源不存在和数据库异常的实际响应与日志，确认所有 HTTP 边界使用同一响应语义。

### AURA-CAP-COMMON-BIZ-006：自定义 SQL 的审计字段要显式处理

适用场景：业务模块使用 Mapper XML/注解执行自定义写入。使用要求：自定义 SQL 要按表结构写入操作人和修改时间；不要把 `BaseEntity` 自动填充误当成任意 SQL 的保证。

**正确写法**：第 23 节的 `updateOwned` SQL 同时更新 `config_value`、`update_by` 和 `update_time`。**错误写法**：自定义 `update` 只改业务字段，却声称继承 `BaseEntity` 后审计字段必然自动更新。**失败与边界**：后台任务没有登录用户时须明确操作人来源。**检查方式**：核对修改前后数据库审计字段与操作上下文。

### AURA-CAP-COMMON-BIZ-007：Entity 的非持久化字段不得混入数据库映射

适用场景：业务 Entity 需要临时承载展示或计算字段。使用要求：优先将这些字段放入 VO/BO；确需保留在 MyBatis-Plus Entity 中时，使用 `@TableField(exist = false)` 排除框架生成的列映射。

**正确写法**：`DeviceConfig` 的 `displayLabel` 只用于业务展示时放入 `DeviceConfigView`；如必须放在 Entity，声明 `@TableField(exist = false) private String displayLabel;`。**错误写法**：在 Entity 中新增数据库表没有的 `displayLabel` 字段，不标记映射边界，却继续依赖 `BaseMapper` 生成查询和写入 SQL。**失败与边界**：真实持久化字段不能误标为 `exist = false`；自定义 Mapper XML 仍需自行核对查询列和结果映射。**检查方式**：对照表结构、Entity 注解与 Mapper 生成或手写 SQL，检查新增字段是否造成未知列或数据丢失。

## 23. 完整业务场景示例

### 23.1 需求

需求：设备管理员可以修改设备配置值；只有当前租户的配置可修改，修改人和修改时间应被记录。修改成功后，再次查询应看到新值。

### 23.2 需求拆解

| 项目 | 结论 |
| --- | --- |
| 业务入口 | `PUT /device/config/{id}` 修改，`GET /device/config/{id}` 查询；网关最终路径按项目接口文档登记 |
| 输入对象 | `DeviceUpdateCommand` |
| 返回对象 | 修改为 `R<Void>`，查询为 `R<DeviceConfigView>` |
| 权限 | 修改为 `device:config:update`，查询为 `device:config:view` |
| 数据边界 | 当前租户下的设备配置 |
| 事务 | 单库本地事务 |
| 横向能力 | 当前用户、权限声明、操作日志；若启用缓存，还需提交后失效 |
| 数据库变化 | 更新配置值和修改审计字段 |
| 失败场景 | 无权限、上下文租户与登录用户租户不匹配、跨租户资源、资源不存在、数据库异常 |

### 23.3 技术设计

```text
Controller
  └─ 参数校验、权限声明、统一返回
Service
  └─ 当前用户/租户校验、资源状态校验、本地事务
Mapper
  └─ 按 id + tenant + 逻辑删除边界查询或更新配置
横向能力
  └─ 当前用户和操作日志；存在缓存时处理提交后失效
```

### 23.4 工程实现顺序

1. 在 DTO 中定义配置值和字段校验；
2. 在接口文档中登记路径、权限和请求/响应；
3. 确认 Entity 的公共字段和数据库变更脚本；
4. 在 Mapper 中定义带租户和逻辑删除条件的查询、更新方法；
5. 在 Service 中核对当前用户与租户上下文，并开启本地事务；
6. 在 Controller 上声明路径、权限和操作日志；
7. 若详情使用缓存，在事务成功后按缓存规范清理；
8. 补充更新后再次查询、异常场景、自测记录和接口文档。

### 23.5 代码组合

以下为该业务模块的主要代码片段。DTO、Mapper 方法和 Entity 由业务模块定义；`R`、`BaseEntity`、`TenantContextHolder`、`SecurityUtils`、`CustomException` 与 `@HasPermission` 是当前 AURA 公共模块中可核对的入口。实际项目需补全包名、import 和数据库迁移脚本。

```java
public record DeviceUpdateCommand(@NotBlank String value) { }

public record DeviceConfigView(Long id, String value, LocalDateTime updateTime) { }

@Data
@TableName("device_config")
public class DeviceConfig extends BaseEntity {
    private Long tenantId;
    private String configValue;
}

@Mapper
public interface DeviceConfigMapper extends BaseMapper<DeviceConfig> {
    DeviceConfig selectOwned(@Param("id") Long id,
                             @Param("tenantId") Long tenantId);

    int updateOwned(@Param("id") Long id,
                    @Param("tenantId") Long tenantId,
                    @Param("value") String value,
                    @Param("operator") String operator);
}
```

对应 `DeviceConfigMapper.xml` 使用绑定参数，并将租户与逻辑删除条件放进实际写入语句；自定义 XML 不依赖实体自动填充来补齐修改审计字段：

```xml
<mapper namespace="com.example.device.mapper.DeviceConfigMapper">
    <select id="selectOwned" resultType="com.example.device.entity.DeviceConfig">
        select id,
               tenant_id as tenantId,
               config_value as configValue,
               update_time as updateTime,
               del_flag as delFlag
        from device_config
        where id = #{id}
          and tenant_id = #{tenantId}
          and del_flag = 0
    </select>

    <update id="updateOwned">
        update device_config
        set config_value = #{value},
            update_by = #{operator},
            update_time = CURRENT_TIMESTAMP
        where id = #{id}
          and tenant_id = #{tenantId}
          and del_flag = 0
    </update>
</mapper>
```

XML 的 `com.example.device.mapper` 和 `com.example.device.entity` 必须替换为实际包名；数据库时间函数应按项目数据库方言确认。接口、Service 和 SQL 的方法名与参数名应保持一致：

```java
@RestController
@RequestMapping("/device/config")
@RequiredArgsConstructor
public class DeviceConfigController {
    private final DeviceConfigService service;

    @GetMapping("/{id}")
    @HasPermission("device:config:view")
    public R<DeviceConfigView> detail(@PathVariable Long id) {
        return R.ok(service.detail(id));
    }

    @PutMapping("/{id}")
    @HasPermission("device:config:update")
    @SysLog("修改设备配置")
    public R<Void> update(@PathVariable Long id,
                          @Valid @RequestBody DeviceUpdateCommand command) {
        service.update(id, command);
        return R.ok();
    }
}

@Service
@RequiredArgsConstructor
public class DeviceConfigService {
    private final DeviceConfigMapper mapper;

    @Transactional(readOnly = true)
    public DeviceConfigView detail(Long id) {
        Long tenantId = TenantContextHolder.getTenantId();
        var user = SecurityUtils.getUser();
        if (tenantId == null || user == null || user.getTenantId() == null
                || !tenantId.equals(user.getTenantId())) {
            throw new CustomException("身份与租户上下文不匹配");
        }
        DeviceConfig entity = mapper.selectOwned(id, tenantId);
        if (entity == null) {
            throw new CustomException("配置不存在或无权访问");
        }
        return new DeviceConfigView(entity.getId(), entity.getConfigValue(), entity.getUpdateTime());
    }

    @Transactional(rollbackFor = Exception.class)
    public void update(Long id, DeviceUpdateCommand command) {
        Long tenantId = TenantContextHolder.getTenantId();
        var user = SecurityUtils.getUser();
        if (tenantId == null || user == null || user.getTenantId() == null
                || !tenantId.equals(user.getTenantId())) {
            throw new CustomException("身份与租户上下文不匹配");
        }
        int updated = mapper.updateOwned(id, tenantId, command.value(), user.getUsername());
        if (updated == 0) {
            throw new CustomException("配置不存在或无权访问");
        }
    }
}
```

上述读写 SQL 显式处理了当前租户，Service 另外核对请求上下文与已认证用户的租户归属；不能因为上下文有值就认定其具有该租户的数据权限。若业务还有部门、本人或资源归属权限，需把该数据范围落实到本次读写条件或先做受控校验；不能假定查询侧的数据范围拦截器会自动约束写入。项目还需确认 `CustomException` 已被本服务的全局异常处理映射为约定的接口响应；类存在不等于错误契约已生效。若此功能引入缓存、审计或请求幂等，还须按相应能力包补齐配置、触发位置和失败验证，不能只加注解就宣称完成。

### 23.6 自测和交付

| 场景 | 预期结果 | 证据 |
| --- | --- | --- |
| 有权限、当前租户、合法参数 | 更新成功，返回统一成功结构 | 接口响应和数据库记录 |
| 无权限 | 请求被拒绝，不修改数据 | 权限响应和数据库前后对照 |
| 跨租户 ID | 返回资源不存在或无权访问 | 数据未改变 |
| 上下文租户与登录用户租户不匹配 | 拒绝查询和修改 | 接口失败结果和数据库前后对照 |
| Mapper 更新异常 | 事务回滚 | 数据库前后对照和异常日志 |
| 成功后再次查询 | 返回最新配置 | 查询响应与数据库记录；若启用缓存，再核对失效结果 |

该示例展示的是完整研发链路。其他 CRUD、主子表、导入导出和跨服务业务，都应沿用同样的“需求拆解—技术设计—分层实现—横向能力—自测交付”顺序。
