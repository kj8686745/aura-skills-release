# 数据与事务基础设施能力详细说明

**版本**：0.1.0-draft  
**状态**：建设中
**源码依据**：`aura-core-common` `dev@4a2a1f1`

## 1. 动态数据源

### 能力作用

按明确规则在已注册的多个数据源之间切换，使业务能够访问不同数据库或数据域。业务模块引入同版 `aura-common-datasource`；已使用 AURA BOM 的项目可由 BOM 管理版本，其他项目须指定匹配版本：

```xml
<dependency>
    <groupId>net.fxft</groupId>
    <artifactId>aura-common-datasource</artifactId>
</dependency>
```

当前框架提供 `@EnableDynamicDataSource` 作为启用入口；项目未通过其他配置启用时，可在应用配置类上使用该注解，然后在 Service 边界通过 `@DS` 选择已存在的数据源。数据源提供器依赖 `spring.datasource.druid` 的主库配置、`StringEncryptor` 和数据源配置表；默认查询语句面向 `gen_datasource_conf`，项目必须先核对表结构与连接信息。

### 开发步骤

1. 确认本次业务确实需要访问已配置的其他数据源；
2. 列出数据源、用途、读写权限和默认数据源；
3. 核对当前项目的数据源启用方式、主库配置、配置表和加解密能力，避免重复装配；
4. 在 Service 入口用固定、已登记的数据源名称选择目标，不在深层业务代码随意切换；
5. 请求或任务结束后清理数据源上下文；
6. 自测默认数据源、目标数据源、异常回退和并发请求隔离。

### 正例

```java
// 启用入口；项目若已启用，不要再次装配。
@Configuration
@EnableDynamicDataSource
public class DataSourceConfiguration {
}

// report 数据源须已在当前项目注册；方法经 Spring 代理调用。
@Service
public class ReportQueryService {
    private final ReportMapper reportMapper;

    public ReportQueryService(ReportMapper reportMapper) {
        this.reportMapper = reportMapper;
    }

    @DS("report")
    public ReportView load(Long reportId) {
        return reportMapper.selectView(reportId);
    }
}
```

代码分别使用 `net.fxft.aura.common.datasource.annotation.EnableDynamicDataSource` 与 `com.baomidou.dynamic.datasource.annotation.DS`；`ReportMapper` 和 `ReportView` 是业务项目类型。切换方法不要依赖同类内部自调用；目标数据源不存在、连接失败和事务已在错误数据源上开启时，均须在项目中验证实际结果。

### 反例

```java
// 在业务方法中直接修改全局数据源配置
dataSource.setUrl(request.getParameter("url"));
```

这会把外部输入带入基础设施配置，并破坏连接池和请求隔离。也不能把 `@DS` 注解中的数据源名直接改为未经校验的请求参数。

### 完成判断

- 数据源名称和用途可追踪；
- 默认数据源和失败行为明确；
- 切换上下文不会在线程复用中泄漏；
- 业务查询未通过用户输入直接决定数据库连接。

## 2. 分布式序列

### 能力作用

本包当前给出 `Sequence.nextValue()` / `nextNo()` 与 `SnowflakeSeqBuilder` 的接入示例。源码中还存在 Redis、数据库区间构建器，但 Redis 构建器的 `step(int)` 未传入区间管理器，DB 构建器的 `dataSource(DataSource)` 未传入实际取号链路；两者不列为当前可直接照用的业务入口。

### 开发步骤

1. 判断编号是技术主键还是业务编号；
2. 为每类业务定义唯一业务名称；
3. 明确是否要求趋势递增、可读格式或租户隔离；
4. 选择实现并确认多实例节点编号是否冲突；
5. 定义时钟回拨、节点编号冲突和重复生成的处理；
6. 对高并发和多实例同时取号进行验证。

### 正例

```java
Sequence orderSequence = SnowflakeSeqBuilder.create()
        .datacenterId(1)
        .workerId(2)
        .build();
long orderId = orderSequence.nextValue();
```

`datacenterId` 和 `workerId` 取值均为 `0..31`，多实例的组合须避免重复。上例仅说明取号 API；项目若加载 `SequenceAutoConfiguration`，其应用就绪回调会查询序列表，表不存在时尝试创建。项目须核对是否加载该配置，并在加载时验证数据库元数据、建表权限与启动结果，不能因为 Snowflake 取号不使用数据库就忽略这一边界。

### 反例

```java
String orderNo = String.valueOf(System.currentTimeMillis());
```

单纯使用时间戳无法保证多实例并发下的唯一性，也没有业务名称和故障处理。不同实例重复使用同一组 Snowflake 节点编号，同样不能保证唯一性。

### 完成判断

- 编号唯一性和排序要求明确；
- 序列实现的依赖、容量和失败策略明确；
- 业务编号生成与事务提交的关系经过设计；
- 不把序列能力误当作幂等能力。

## 3. 跨服务事务模块的当前边界

### 能力作用

当前 `aura-common-seata` 引入 Seata 依赖并包含数据源代理配置，但模块随附的事务组和协调服务地址不是可供业务项目直接采用的 AURA 部署契约。本包不提供可复制的 `@GlobalTransactional` 业务代码或“接入完成”判断；仅增加依赖也不能保证远程操作一致。

跨服务写入的参与方、原子性要求、可靠消息或补偿、超时与失败语义，按[数据访问、事务与生命周期规范](../../../01-基础编码规范/08-数据访问事务数据表达与生命周期规范/01-数据访问事务与生命周期.md)和[异步任务与消息处理](../../../01-基础编码规范/10-异步任务消息与外部系统集成规范/01-异步任务与消息处理.md)设计。若目标项目没有与其版本匹配的事务组、协调服务、参与方配置和失败回滚证据，应将 Seata 接入标为未验证，不从本包推断实现方案。

## 4. 接入范围判断示例

```text
报表服务需要查询已登记的 report 数据源
→ 核对主库、配置表、目标数据源与启用状态
→ 在受 Spring 代理调用的 Service 边界使用 @DS("report")
→ 在目标项目验证查询、错误数据源和异常后的上下文

订单服务需要跨库写入
→ 按基础规范设计参与方与一致性机制
→ 本包当前没有可照用的跨服务事务入口
→ 保留设计与接入缺口，不把 aura-common-seata 依赖当成完成证据
```
