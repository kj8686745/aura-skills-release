# 数据安全与内容防护能力详细说明

**当前源码依据**：`aura-core-common` `dev@4a2a1f1`。以下示例仅适用于业务项目实际引入同版模块且满足相应启用条件的场景。

## 1. 敏感字段脱敏

### 适用场景

手机号、证件号、邮箱、银行卡、密码、密钥、地址和 IP 等数据在接口展示、日志、审计和导出中不应完整暴露时使用。业务项目引入同版 `aura-common-sensitive`；AURA BOM 可管理模块版本，未使用 BOM 的项目须指定匹配版本。

### 使用方式

```java
// 始终要求输出掩码的日志或导出字段，显式调用工具。
String mobileForLog = DesensitizedUtils.desValue(user.getPhone(), 0, 0, "*");
String emailForExport = DesensitizedUtils.desValue(user.getEmail(), 0, 0, "*");

// 仅对命中的 Jackson 字段序列化生效，是否脱敏由 SensitiveService 判断。
public class UserView {
    @Sensitive(type = SensitiveTypeEnum.MOBILE_PHONE)
    private String mobile;
}
```

`DesensitizedUtils`、`@Sensitive` 和 `SensitiveTypeEnum` 均来自 `aura-common-sensitive`。上例的 `desValue(..., 0, 0, "*")` 用于必须隐藏全部字符的渠道；部分保留的 `mobilePhone`、`email` 等工具方法须先核对输入长度和实际输出，短值可能保留原文。当前默认 `SensitiveService` 在无认证信息时执行掩码；有认证信息时，若权限集合包含配置的豁免标识，就输出原文，否则掩码。该标识的源码默认值为 `*`；项目若覆盖 `SensitiveService`，实际判断以覆盖实现为准。因此，`@Sensitive` 适合按权限展示的 VO，不适合用于“任何情况下都不得输出原文”的日志、审计或导出字段。脱敏也不改变数据库存储内容。

### 反例

```java
// VO 注解不会处理这里的日志参数，仍可能记录完整手机号。
log.info("手机号：{}", user.getPhone());
```

### 完成判断

- 数据库原文保护和展示脱敏已经区分；
- 日志、审计、导出和缓存均已检查；
- 脱敏策略不会误把必需的业务标识完全隐藏；
- 始终禁止原文的渠道已显式脱敏，不能仅依赖 `@Sensitive`；
- 对具有与不具有查看权限的身份分别核对 VO 结果。

## 2. XSS 内容防护

### 适用场景

用户输入包含 HTML、富文本或可能进入浏览器渲染的内容时，按输入和输出的具体位置处理。业务项目引入同版 `aura-common-xss`；当前自动清理的配置键为 `security.xss.enabled`，属性默认值为 `false`，仅引入模块不能证明请求已被清理。源码自动配置在缺少该配置键时仍会装配，但拦截器不会开启 XSS 清理；其 JSON/Form 字符串处理器仍可能按默认 `trimText=true` 裁剪首尾空白。需要保留原始空白的字段，应在目标项目验证这一行为，而不能把“未启用清理”理解为“输入完全不变”。

### 使用规则

- 需要框架自动处理时，显式配置 `security.xss.enabled: true`，核对命中的请求路径、JSON/Form 输入和忽略规则；不需要自动清理时应显式配置 `false`，避免把缺省配置误认为未装配输入处理器；
- 富文本允许的标签与属性以当前 `XssUtil` 实现为准；其白名单不能不经验证就视为适合所有业务渲染场景；
- 仅需一次显式清理时，可调用 `XssUtil.clean`，但不能把清理后的 HTML 当作任意输出上下文均安全；
- 输出到前端时仍按实际渲染位置处理，不能用输入清理替代输出编码。

### 正例

```yaml
security:
  xss:
    enabled: true
```

```java
// 仅在业务允许保留经当前白名单处理的 HTML 时使用。
String cleanedHtml = XssUtil.clean(command.getContent());
```

启用后以当前项目的真实请求验证命中路径：带脚本的 JSON 字段、表单字段、富文本允许标签、未命中路径及需保留首尾空白的字段应分别核对。上例中的 `command` 是业务输入模型。

### 反例

```java
String html = request.getParameter("content");
return R.ok(html);
```

仅依赖引入 `aura-common-xss` 而不启用配置，或把未处理的用户内容直接交给 HTML 渲染，都不能证明已完成防护。

## 3. 字段与实体保护

### 适用场景

证件号、密钥或其他不能以明文落库的字段，需要在实体读写过程中保护时考虑此能力。业务项目引入同版 `aura-common-cipher`；当前模块仅定义 `CipherProvider` 接口，只有项目提供可用实现时，自动配置才创建 `CipherEngine` 等执行组件。没有提供方时，不能把实体注解当成已加密。

### 使用原则

1. 确定需保密和需校验完整性的字段，及签名、篡改标记字段的数据库映射；
2. 核对项目中的 `CipherProvider` Bean、算法与密钥来源，再声明 `@CipherProtectedEntity`；
3. 核对 `aura.cipher.enabled` 与 `aura.cipher.mybatis-auto-enabled`、MyBatis 组件和相关 Bean 是否满足自动处理条件，逐项验证新增、更新、读取、密文条件查询和篡改结果；
4. 设计迁移、密钥轮换和历史密文兼容；
5. 解密后的数据仍须通过业务权限控制，日志、异常、缓存和导出另行核对。

### 正例

```java
// 仅展示实体规则；必须同时具备可用的 CipherProvider 和字段映射。
@CipherProtectedEntity(
        signField = "sign",
        tamperMarkField = "signStatus",
        confidentialFields = {"idCard"},
        integrityFields = {"userId", "idCard"})
public class CustomerRecord {
    private Long id;
    private Long userId;
    private String idCard;
    private String sign;
    private Integer signStatus;
}
```

`CustomerRecord` 是示意业务实体，不是框架自带模型。显式列出的字段必须真实存在；`CipherProvider` 的加解密及签名验签由项目实现并验证。实体加密不会自动替业务决定哪些用户可读取解密结果。

### 反例

```java
// 只有注解，没有 CipherProvider；不能据此宣称数据库已存密文。
@CipherProtectedEntity(confidentialFields = {"idCard"})
public class CustomerRecord {
    private String idCard;
}
```

加密字段不能直接假设普通模糊查询仍可用；需要查询时必须设计经验证的索引、摘要或受控检索方式。完成判断是项目中写入密文、读取受控、篡改可识别、失败不返回原文，不能仅凭注解或 Bean 存在判断。

## 4. API 报文保护

### 适用场景

前后端契约明确要求请求体、响应体或 GET 查询参数使用密文传输时，才启用此能力。业务项目引入同版 `aura-common-encrypt-api`，并显式设置 `security.api.encrypt.enable: true`；默认不开启。当前默认算法为 AES，默认密文 JSON 字段名为 `encryption`，客户端必须使用与服务端一致的协议。

### 使用规则

- 密钥从项目配置渠道注入，不写入源码、日志和接口文档；
- 对应 HTTP 请求体与响应体使用同一算法和 `bodyJsonKey`；当前 GET 过滤器遍历查询参数，但每个参数名仅解密首个值并覆盖为单值。使用多值、数组或明密文混合参数的接口，不能直接套用此协议；
- 方法级 `@NoEncrypt` 和 `skipUrl` 可形成例外，但 GET 过滤器只读取 `skipUrl`，方法注解需经映射路径登记后才会影响 GET；当前路径匹配使用包含判断，动态路径或相似路径须逐项验证。不能只写类级注解就推断全类被跳过；
- Feign 调用和上传请求有独立跳过条件，不能仅凭普通 HTTP 用例验证所有接口；
- 当前实现不能单独证明具备防重放能力，需要该能力时另行定义并验证；
- 未启用报文加密的普通接口不应自行调用 `ApiCryptoUtil` 改造协议。

### 正例

```yaml
security:
  api:
    encrypt:
      enable: true
      default-encrypt-type: AES
      body-json-key: encryption
      aes-key: ${API_AES_KEY}
```

客户端与服务端先约定密钥、算法、`encryption` 字段和例外接口，再验证加密 POST、单值 GET 参数、响应以及错误密文；多值 GET 参数不应在未经额外实现与验证时纳入该协议。环境变量只是示意注入方式；值和管理方式由项目配置确定。

### 反例

```java
// 仅引入依赖并不能启用加密；也不能用工具自行改变单个接口协议。
String result = ApiCryptoUtil.encryptData(body, cryptoInfo);
```

上例中的 `body`、`cryptoInfo` 为示意变量；直接调用工具不等于请求 Advice、响应 Advice、GET 过滤器与客户端已形成一致契约。

## 5. 能力组合示例

```text
用户提交包含手机号的表单
→ 若启用且路径命中，输入边界执行 XSS 清理
→ 权限和租户校验
→ Service 处理业务
→ 配齐 CipherProvider 并验证写入链路后，实体字段加密入库
→ 日志和审计显式输出脱敏值
→ 查询 VO 依据 SensitiveService 的判断展示原文或脱敏值
```

该链路中，认证、租户、加密、脱敏和 XSS 分别承担不同职责，不能只启用其中一项就宣称数据安全完成。

## 6. 失败和交付判断

- 脱敏：分别核对可看原文与不可看原文的用户；日志、审计、导出另行核对；
- XSS：核对启用值、缺省配置下的字符串裁剪、命中路径、忽略规则，以及当前富文本白名单在业务渲染场景下的实际结果；
- 实体保护：核对 `CipherProvider`、写入密文、读取验签和解密、篡改或密钥不可用时的结果；
- 报文保护：核对前后端协议、密文错误、方法级例外、单值 GET 参数和响应体；多值参数须单独设计，启用加密不等于已防重放；
- 权限、租户、缓存和文件导出仍按其自身边界核对，不能由本包任一能力代替。
