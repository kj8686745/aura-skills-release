# 网关与流量治理能力详细说明

**当前源码依据**：`aura-core-common` `dev@4a2a1f1`；网关工程示例为 `aura-core-gateway` `dev@5ef887d`。以下示例只展示接入方式和预期行为。服务名、路径、版本与阈值由项目确定；路由管理、配置下发和保护规则仍需在项目中核实。

## 1. 动态路由

`aura-common-gateway` 的 Reactive 配置包含 Redis 路由仓储、路由刷新监听与健康检查。网关从路由仓储读取定义；保存路由后发布刷新消息，监听器清除本地缓存并触发路由刷新。当前 `aura-core-gateway` 工程有自身的同名路由实现，不能把公共模块的装配结果直接套到该工程。公共模块和网关工程的删除实现均在订阅删除操作后直接发布刷新消息，源码未保证刷新发生在 Redis 删除完成之后；删除成功、已删除路由不再命中及回滚恢复都须在目标网关核对。健康检查只判断路由键是否存在，不能证明每个目标服务可达。

接入时先确定路由 ID、服务发现名、匹配路径、过滤器与权限边界，再由受控的路由管理入口提交和回滚。业务服务不直接改路由 Redis 键。下面是一条**路由定义示意**，不是新的管理 API 或可直接粘贴的生产配置：

```yaml
id: order-query
uri: lb://order-service
predicates:
  - Path=/api/orders/**
```

正例：在受控入口登记以上定义后，检查路由列表已包含 `order-query`，请求能到达目标服务；修改前保留旧定义，失败时回滚并重新检查。删除时还须确认 Redis 中定义已移除、目标网关已刷新且旧路径不再命中。服务端仍校验调用者权限。反例：把目标写成固定环境 IP、路径写成 `/api/**` 后直接投入使用，既扩大匹配范围，也让环境迁移和回滚困难；仅收到删除刷新消息就宣称路由已删除，也不成立。

完成判断是“目标路由实际命中、错误路径不误命中、路由变化在网关生效、回滚后恢复”。仅健康检查为 `UP` 不足以证明以上结果。

## 2. 网关灰度流量

网关灰度负载均衡仅在 `gray.rule.enabled=true` 且 Reactive Gateway 的相关配置生效时启用。实现从请求头 `VERSION` 读取目标版本，与服务实例元数据 `VERSION` 比较：命中则在同版本实例中按权重选择；无版本头时优先选无版本元数据的实例；指定版本不存在时回退到所有可用实例。无可用实例时返回服务不可用错误。

正例：经可信入口确认灰度资格后写入 `VERSION: v2`，目标服务注册实例元数据也包含 `VERSION=v2`；在网关配置中显式开启灰度，分别验证命中、无版本、无匹配版本和无实例四种情况。反例：仅允许客户端自带 `VERSION: v2` 就进入灰度，或把“无匹配版本回退到任意实例”解释为严格隔离。现有组件不会自行验证客户端是否有灰度资格。

如果业务要求“指定版本不存在就拒绝请求”，不能沿用当前回退行为作为完成结果；需另行实现该策略并验证。

## 3. Feign 与非 Web 灰度上下文

`aura-common-gray` 启用时，Feign 拦截器优先读取当前 Web 请求的 `VERSION`，无 Web 请求时读取非 Web 版本上下文，并向下游透传。服务间负载均衡按请求版本和实例元数据选择；目标版本没有实例时也会回退到普通选择。当前版本匹配分支将服务实例直接转换为 `NacosServiceInstance`，因此接入前须核对服务发现返回的实例类型；不能把它描述为适配任意服务发现。非 Web 场景必须由业务确定可信版本并清理上下文：

```java
NonWebVersionContextHolder.setVersion(approvedVersion); // 来自受控任务配置，而非用户原始输入
try {
    remoteOrderClient.refresh();                    // Feign 请求透传 VERSION
} finally {
    NonWebVersionContextHolder.clear();              // 避免后续任务继承旧版本
}
```

正例：一次调度任务仅在获准批次范围内设置版本，调用结束后 `finally` 清理，并在 Nacos 接入环境检查 Feign 请求头与目标实例版本。反例：在共享线程中设置版本但不清理，后续无关任务可能继承旧值；使用非 Nacos 实例却未经验证便开启版本匹配，也不能保证正常选择。`aura-common-gray` 的自动配置在未显式设为 `false` 时也可能生效，接入前需核对项目实际依赖和条件，不能仅凭配置元数据中的默认值推断运行状态。

## 4. Servlet 与 Feign 保护

`aura-common-sentinel` 提供 Servlet 阻断处理、请求来源解析以及 Feign 构建扩展。Servlet 资源被 Sentinel 阻断时，默认处理器返回 HTTP 429 和 `R.failed(...)`；这与网关 WebFlux 的限流不是同一入口。Feign 构建扩展是否生效，还取决于模块、自动配置、`spring.cloud.openfeign.sentinel.enabled` 及项目使用的 Feign 客户端。

正例：为具体接口或下游调用配置可识别的资源与保护规则，按项目统一契约核对阻断时的状态码、失败体和恢复后的正常响应；Feign 调用分别验证成功、超时、阻断和回退结果。反例：只引入 `aura-common-sentinel` 依赖就宣称接口已经限流，或捕获所有下游异常并返回 `R.ok(defaultValue)`，会让调用方把保护失败误判为业务成功。

保护规则与回退结果必须按业务制定。不能从自动配置存在推断已经配置阈值、熔断规则或告警。

## 5. 网关限流

现有网关工程提供按客户端 IP 提取 Key 的 `KeyResolver` Bean；它只是限流维度输入，不包含默认阈值或生效的 `RequestRateLimiter` 路由规则。接入网关限流时应分别核对限流过滤器是否挂到目标路由、Key 是否来自可信代理链、阈值和拒绝结果是否符合项目接口契约。

正例：在受控的网关配置中将限流过滤器绑定到明确的路由和 Key，验证同一 Key 达到阈值时被拒绝、不同 Key 不相互误伤，并检查代理透传的真实来源。反例：只声明 IP Key 解析器就认为所有路由已经限流；或者无条件信任外部传入的 `X-Forwarded-For`，让客户端自行改变限流 Key。

## 6. 联调与完成判断

按“请求入口 → 路由匹配 → 可信版本判定 → 服务实例选择 → 下游接口保护 → 业务权限与响应”逐段核对。至少分别观察正常请求、错误路径、无实例、灰度版本未命中、Servlet 阻断和网关限流（如项目已配置）时的结果。记录实际生效的依赖、配置、服务实例元数据、保护规则和返回结果；未配置或未运行的能力保持为待验证，不写成已启用。
