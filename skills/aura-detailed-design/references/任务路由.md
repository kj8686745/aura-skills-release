# 技术详细设计任务路由

本文件仅组织执行顺序，技术要求以[详细设计规范](standards/02-详细设计规范/01-详细设计规范.md)及其正反例为准；按任务读命中章节，不全文预读全部资料。

## 新建设计

先判断完整或简化设计（001/002）。从需求、现有代码、接口文档及命中能力公开资料取得事实与约束（003），再使用[模板](standards/02-详细设计规范/02-技术详细设计文档模板.md)的适用部分。

完整设计先给总体技术方案、取舍与实现路线，再登记模块和契约，最后填各变更模块实现卡片。一份业务设计横跨多个仓库时登记真实仓库和模块落点，不拆成多份互不关联的主设计（004/005/011）。用“无及原因”处理不适用项，不能用未落实的消息、SDK 或框架类型填空。

写到具体接口时引用已有模块文档；新增/变更契约默认同步该模块文档。详细设计保留影响方案的身份、超时、幂等、失败与兼容决定（008），不替代字段文档。项目代码、接口与需求冲突时记录冲突位置和影响，不自行挑一方当确定事实。

## 修订已有设计

先固定原设计版本、本次需求或代码差异，逐项判断原结论是否仍成立（002/003/004）。沿下面影响链只更新实际相关部分：

```text
技术决策/模块变化
→ 契约与数据所有权
→ 主链路、失败链路、状态和权限
→ 模块卡片、图与部署兼容
→ 实施顺序、验证计划、未决项与准入结论
```

保留有效的 M/C 编号，不因新增模块重排全篇；不把未变模块重写成新方案。接口未变时不机械改模块接口文档；接口变化则同步原文档对应章节。原设计错漏影响本次方案时修正相关结论，说明扩大范围的具体依据，不顺带重构无关内容。

在同文档变更记录中汇总本次版本、原因和影响范围。新增资料只在确有独立职责时创建，不另建“本次修订说明”替代原设计更新。

## 只读复核

先确定用户要复核的设计版本与范围；核对设计所依赖的需求、代码和公开契约。只做文档复核时不改项目、不运行真实联调、不升级成全项目规范审查。

| 复核问题 | 命中规则 | 需要看到的实际内容 |
| --- | --- | --- |
| 关键结论是事实还是假设，为什么选该方案 | 003/004 | 代码或契约来源、技术取舍、需求/风险对应；不是只有“采用异步” |
| 研发能否定位模块与实现文件 | 005/011 | 模块拓扑、真实路径、变更模块卡片、前置条件和实现路线 |
| 失败或结果未知时如何结束 | 006/008/010 | 提交与副作用边界、状态归属、超时/重试/去重前提、恢复和观测；不是“异常后重试” |
| 数据与权限在哪里落实 | 007/009 | 模型与所有权、授权和范围校验、跨模块上下文；不是只列字段或页面权限 |
| 编码和交付条件是否明确 | 002/012 | 适用验证、配置迁移回滚、联调前置、未决项及明确准入范围；计划不冒称执行证据 |

输出一份有界复核结果（可直接答复，用户要求报告时才落盘）：总体准入建议、已确认事实、按重要性排列的问题（位置、规则 ID、证据、影响、建议）、未覆盖与待确认项。无问题时说明实际检查范围与依据；没有检查不能写“通过”。技术风险未消除时不因脚本成功判可进入编码。

## 共用收尾

运行入口中的机械检查，再做上述语义复核。工具不能解析时说明检查缺口，继续人工检查可读内容，不生成迎合脚本的空表。交付或建议准入均使用规范三种结论；有条件时标明能先实施的模块/步骤、未决项负责人、解除条件和复核时点。进入代码实现、项目规范审查或能力建设时分别交给对应任务，不在本技能中展开。
