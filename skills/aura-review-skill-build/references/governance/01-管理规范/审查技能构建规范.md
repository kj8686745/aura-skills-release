# 审查技能构建规范

**版本**：1.2.1
**适用对象**：负责建设前端、后端及接口等规范审查技能的领域负责人。
**配套模板**：[审查结果包模板](../05-技能构建/审查结果包模板.md)。

本规范规定审查技能如何建设、如何验证以及最终报告如何交付。技术判断依据来自对应领域的人工规范；既有审查技能和历史报告只供对照，不能代替规范。构建技能属于内部维护工具，生成的审查技能与开发技能分别维护、分别触发。

## 一、建设输入与交付

从用户提供的位置和仓库入口确定：目标领域、目标技能名称与源码目录、规范版本与提交、适用框架及版本、相邻技能、验证样本及允许执行的验证范围。已经能从仓库确定的信息不要求负责人重复填写。缺少规则或无法核对来源时记录缺口，完成其余可确认部分，不自造技术规则。

交付目标技能的完整目录、同版规则引用、双模式报告模板和一份合并的建设验证记录。记录覆盖来源、规则映射、代表性任务的实际结果、未验证项、版本和发布状态。前端负责人提交前端审查技能；无需同时改写后端审查技能或重建整个发布工具。

### 按审查范围选择交付

| 审查范围 | 基线与取证范围 | 交付形式 |
| --- | --- | --- |
| 日常变更 | 基线提交、目标提交及未提交差异；变更文件与实际受影响调用方、共享契约和配置 | 一份变更审查报告，完整保留范围、规则、证据、候选、整改与未覆盖项 |
| 全项目 | 固定项目版本，盘点全部纳入资产和全部适用规则 | 统一六文件结果包 |
| 接口或其他专项 | 用户限定的模块/接口/规则域及必要关联链路 | 有界局部任务可用单报告；全量专项或用户要求结果包时用六文件，明确专项而非全项目结论 |

审查范围与交付形式分别记录，不靠文件数量推断深度。没有基线或无法确定变更集时，使用已提供的文件清单完成可执行核对，但说明缺口，不宣称变更范围完整。输出形式在任务开始确定，普通执行步骤不反复要求用户选择。

```text
<审查技能名称>/
├─ SKILL.md                       # 触发、自动工作流、选读入口、完成条件
├─ VERSION
├─ USAGE.md
├─ agents/openai.yaml
├─ references/
│  ├─ 审查路由.md                 # 规则域、规则ID、适用条件、证据位置及方法
│  ├─ 审查结果包模板.md
│  └─ standards/                  # 本技能实际必需的规范同版副本
└─ scripts/                       # 仅在有可重复确定性检查时建立
```

构建记录在内部治理区维护；它不进入使用者的审查报告。目标技能的所有必读文件应能从交付包内定位；不得依赖维护者电脑路径、另一个未安装技能或未交付的规范工作区。

## 二、构建规则

### AURA-GOV-REVIEW-001：绑定规范并形成完整规则路由

**必要性：必须。**

从指定版本的规范正文提取规则 ID、必要性和适用条件，形成“规则—检查对象—取证方式—证据边界”的映射。规则矩阵用于定位，正文及正反例用于判断。分组路由表可简写规则范围，但实际项目结果必须逐规则给出状态。全项目覆盖全部适用规则；变更审查覆盖变更和受影响链路命中的规则，列出未纳入域及依据，不把未检查的域计为通过。审查项目自身的代码只能证明现状，不能修改规范要求。

执行入口先核对用户指定技能、当前技能与规则来源是否一致。旧入口缺少资料、指向已失效规则或与现行契约矛盾时，说明具体冲突；不静默混用两套规则，不把旧报告的固定判断带入新审查。可核实的同源部分继续执行；确需更换用户明确指定的规则基线时集中确认。

**正例**：前端请求规则映射到请求封装、页面调用和错误处理；未使用模块联邦的项目依据框架识别结果将相应专项规则列为不适用。
**反例**：只从旧报告复制十条发现项作为全部规则；要求所有前端项目符合某个 Vue 工程的私有目录。
**检查与证据**：核对规范来源提交、规则数量、重复 ID、缺失映射和每个排除项的依据。

### AURA-GOV-REVIEW-002：一次调用连续完成可执行审查

**必要性：必须。**

目标技能应自动完成：冻结版本、范围与交付形式 → 盘点纳入资产 → 规则域取证 → 候选归并及逐项判断 → 适用构建/测试补证 → 报告输出 → 完整性复核。变更审查从差异沿受影响调用/配置链扩展必要对象，不扩成默认全项目审查；全项目审查盘点全部纳入对象。进度消息不作为用户确认节点，不能在每个模块或发现项之后等待“下一步”。明确限制或抽样时如实标明，不冒称全量。

只读指不修改目标业务源码、依赖锁文件、配置和部署状态。构建可以在约定的输出目录或隔离副本生成产物；运行会修改数据或访问外部环境的脚本前核对授权范围。缺少浏览器、依赖、运行环境或业务证据时记录未证实，继续完成其余审查。工作树差异记录文件与摘要，输出目录不计入被审资产。目标不可定位或关键业务边界确需用户决定时集中询问。

大项目在既有执行记录中建立分批队列，按模块、入口或规则域安排有限批次，每批记录规则 ID、单元 ID、完成证据、剩余对象和下一步。完成一批即更新矩阵并自行选择下一批，不以批次边界要求用户继续。上下文续接从同一队列恢复，不重扫已核实对象；版本或规则变化时只失效受影响结论。静态资料仍可读取时不得因无运行环境结束静态审查，也不得自行把全项目降为抽查。发生实际中断时保留检查点及明确剩余工作，不能把检查点称为完成。

**正例**：三个模块按批次自动接续；构建缺依赖时保留错误并继续可读源码核对，中断后从同一队列恢复，不改锁文件。
**反例**：每扫描十个文件就等用户“下一步”；静态目录仍可读却因无联调环境结束；为了通过直接改业务代码。
**检查与证据**：代表性任务具有连续执行记录，目标源码无新增改动，失败原因可复核。

### AURA-GOV-REVIEW-003：命中、偏差和证据不足必须区分

**必要性：必须。**

检索命中先进入候选。结合调用链、框架封装、运行条件和例外依据后，将候选判为确认偏差、排除或待补证。发现项按根因、规则与影响范围归并，保留所有相关位置；单条规则可能产生多个发现，同一发现也可关联多条规则。不得把发现数量等同于违规规则数量。

每条规则的状态为 `通过`、`偏差`、`未证实` 或 `不适用`，另填证据级别：静态源码/配置、构建/测试、运行/联调、人工材料。通过只覆盖已检查范围和相应证据级别。同一规则分多个单元取证时先给出单元行，再按“存在偏差优先，其次未证实，全部适用单元有符合依据才通过，全部不适用才不适用”汇总；统计按唯一规则 ID，不按子行计数。规范允许的合理情形或有有效依据的例外写明适用条件；不能用口头认可豁免明确禁止事项。建议改进但不违反现行规则的内容独立标为建议，不计入规范偏差。

每条规则单元行同时登记执行进度 `待执行/已执行/受阻`，与四种技术结论分别表达。尚未读取或尚未分析填“待执行＋未证实”，不能改写为环境缺口；已完成静态核对但缺运行结果填“已执行＋未证实”，写清静态已证实部分和具体缺口。缺口区分未执行、外部证据缺失、适用性待确认或无。适用单元由规则含义与真实入口确定，不机械采用整个规则域的文件总数，也不要求所有规则与所有文件做笛卡尔积。单元只有其全部适用静态检查完成后才算已检查；词法命中、被候选引用或读取文件一次均不能替代该条件。

**正例**：请求适配层候选沿调用链排除；已读的静态权限配置与待补的运行验证分别记录；未读模块保留待执行及下一批。
**反例**：将全部 `fetch` 命中写为违规；把未读源码统一归因于缺环境；凭候选引用把整个文件算已查；把没有测试报告写成测试失败。
**检查与证据**：使用合规、违规、合理例外及证据不足样本验证，核对假阳性和遗漏；引用文件及行号绑定被审提交。

#### 外部 SDK 与依赖边界

审查项目引用 SDK、Starter、Feign Client 或其他外部制品时，纳入范围只到“项目如何声明、配置、调用和适配该依赖”。可核对依赖坐标与版本、项目内 import/注入/调用、超时与异常映射、请求/响应适配、网关或公开契约的使用方式，以及项目代码对 SDK 能力的重复实现。审查在项目内的 `Client/Adapter` 调用出口停止。

除非用户明确同时提供并授权审查 SDK 源码，否则不得自动进入 Maven/Gradle 缓存、反编译 JAR、跟随源码链接、拉取邻仓库或按依赖关系递归审查 SDK 内部实现、供应商规范和其他项目。SDK 内部线程模型、连接池、重试实现或内部编码风格不计入当前项目偏差；本项目未提供 SDK 内部证据，也不能据此判定本项目不合规。外部契约缺失时，只将本项目可确认的使用事实和对应未证实边界记录下来。

**正例**：项目通过 SDK Client 发起请求，审查本地依赖版本、超时配置、参数适配、异常映射和调用方处理；SDK 内部实现列为范围外。
**反例**：扫描 `.m2` 中的 SDK 源码、反编译依赖 JAR 或跳转邻仓库，把 SDK 内部未遵守 AURA 规则的内容计入项目发现。
**检查与证据**：范围记录列出依赖坐标、项目内使用位置、公开契约来源、停止节点和排除路径；若用户明确扩大范围，另建独立 SDK 审查任务，不并入项目审查统计。

### AURA-GOV-REVIEW-004：按范围交付报告并校验统计

**必要性：必须。**

目标技能须携带并遵循配套模板。变更审查交一份报告，按模板在内部设基线、结论、覆盖、证据、候选和整改章节；全项目交固定六份文件，按模块分节，不按规则或发现无限拆分文档。必要原始证据可放报告旁 `证据/`，先脱敏再保存。单报告用同文件章节及稳定 ID 互引，不保留指向不存在的 `02/03/04/05` 文件的旧引用。

规则总数 = 通过 + 偏差 + 未证实 + 不适用；适用规则数 = 规则总数 − 不适用。已判定适用规则数 = 通过 + 偏差。这里的“适用”是统计纳入且未判不适用的规则，包含适用性仍未证实项，不能把它称为全部已确认适用。检查对象分别登记类型、去重口径、纳入、已检查、未检查和排除数量；同一类别满足 `纳入=已检查+未检查`，排除不混入纳入，抽样不得充当全量。唯一候选数 = 确认偏差 + 排除 + 待补证；原始命中数独立登记。优先级只对确认偏差的唯一 F 编号统计，不把未证实风险、原始命中或规则数计入发现优先级，不自动计算总分。

同一根因、相同触发条件和整改闭合方式可归并发现并保留全部位置；仅规则相同不能强行合并不同根因。所有确认偏差候选关联 F 和 E，排除/待补证有依据及 E；偏差规则回指 F，F 回指纳入的规则和 E，整改清单使用同一 F。零发现仍交覆盖与证据，不自动得出全部合规。

Agent 先给出可复核的逐项判断，脚本仅整理已有判定、计算汇总和检查一致性。禁止按规则域批量填同一观察、缺口或默认状态；没有候选也须处理该规则要求。F 必须引用具体 U/E 及路径:符号；行为链写真实节点、关键分支、期望与实际冲突，不用“遵循关联规则”代替事实。相同证据可支持多条规则，但逐条说明其支持关系；工具对重复笼统依据的提示须人工复核，不能反向认定业务违规。证据类型、置信度与严重性各自填写，不把 S1 当作置信度，不把常量值误写成不存在的响应字段。

多仓审查在既有总入口合并总体风险、共同根因、整改先后及剩余静态工作。范围同时包含真实调用方和提供方时，沿同一业务链静态核对路径、请求/响应字段、权限、分页及错误处理，区分已确认的契约差异与待运行验证项；无联调环境不免除双方源码可比对部分。不要求不在范围的仓库或无关系统一并审查。

**正例**：两文件变更用单报告保留独立规则依据与具体 U/E；全项目报告摘要归并风险，逐规则矩阵可反查真实链路，零发现仍有范围和证据。
**反例**：小改动也强制六份薄文件；按域批量填写相同未证实原因；F 仅写“见证据目录”；依据偏差文件数推算合规率。
**检查与证据**：核对模式对应的文件/章节、稳定 ID、统计闭合、证据互引、归并和脱敏。随包报告自检脚本可检查结构及可解析统计；工具通过不证明取证充分、例外有效或项目合规。

### AURA-GOV-REVIEW-005：完成状态与项目质量分别表达

**必要性：必须。**

审查执行状态统一使用 `阻断`、`部分完成`、`抽查完成`、`变更审查完成`、`静态审查完成`、`发布准入审查完成`。变更审查完成表示已确定变更集及必要关联范围，并处理全部纳入对象和规则，不表示整个项目已审。只有所有纳入对象的静态检查已完成、规则均有状态和依据、候选全部完成判定或明确待补证、对应报告已复核时，才可称相应范围的变更/静态审查完成；运行证据缺口仍逐项保留。存在尚未检查的纳入对象时标部分完成，或明确将范围调整为抽查后交付抽查结论；不能删掉未检查对象来美化覆盖。发布准入审查完成需满足项目已经明确的验收要求，不能由技能自行设定。

总体质量结论另写已确认偏差、严重程度、影响范围和补证项。执行完成不代表项目合规；环境不足不代表代码存在确定偏差。未预先定义评分规则时不生成百分制或合规率。

部分完成是进度事实，不是可提前停止的交付方式。尚有可执行静态批次时继续；只有用户停止、实际会话中断、资料不可取得或需要新增授权等真实限制才保存部分结果并说明下一批。运行补证受阻仅限制对应结论，不阻断其余静态工作。只有明确的用户范围调整才可改为抽查；格式自检通过、发现数量足够或六文件齐全均不是完成依据。

**正例**：“指定变更审查完成；存在 1 项 P2 偏差，关联调用方运行行为未证实”；全项目可写“静态审查完成；存在 2 项 P1 偏差”。
**反例**：“扫描结束，项目通过”；适用规则未逐条处理却宣布全量审查完成。
**检查与证据**：检查状态和矩阵、候选及报告结论是否一致，查验范围限制是否清楚。

### AURA-GOV-REVIEW-006：领域技能先验证再移交

**必要性：必须。**

核对技能结构、内部引用、来源版本、自动/显式触发、相邻任务边界和代表性产物。必须使用至少包含合规、确定违规、合理例外、缺证据四类情况的样本，分别验证单报告与六文件模式；另测试受限范围和环境失败时的结论，以及重复候选归并、未检查对象保留、零发现但有证据缺口。语法或报告格式校验只证明可解析结构和一致性，不代替任务验证。验证样本应有预期依据，不能用刚生成的报告反过来证明自己正确。

建设者提交验证结果和缺口供维护者复核，不能把创建目录、填写 VERSION 或当前项目审查完成作为技能已发布证据。构建技能自身只向内部负责人交付；生成的前端或后端审查技能独立登记方向、版本与发布资格。

验证还应包含：无扫描候选但可由源码确认的偏差、跨批次剩余静态工作、只影响运行结论的环境缺口、按域套话的假矩阵及具体 U/E 关联缺失。分别观察工作流是否继续、结论是否有独立依据、工具是否拒绝确定矛盾或提示需复核。工具夹具通过与独立 Agent 试用分别记录，不互相替代；样本有效不外推大型项目全量能力。

**正例**：前端审查技能在隔离样本识别真实请求边界偏差、排除允许的封装，并对缺少浏览器验证的页面状态标为未证实。
**反例**：只运行技能格式检查就宣称前端审查可正式发布；把后端报告替换标题作为前端审查结果。
**检查与证据**：保留输入样本版本、预期判断依据、实际结果包、差异和未验证项，一份记录随版本更新。

### 审查工作中适合脚本化的事项

脚本只承担可重复、输入边界明确且不需要业务语义裁决的工作；脚本输出是取证输入或报告质检结果，不直接生成“合规/违规”结论。

| 事项 | 处理方式 | 结论边界 |
| --- | --- | --- |
| 项目范围、模块目录、重解析点和文件分类 | 应脚本化；输出纳入、排除、跳过及文件摘要 | 不能替代审查者确认真实适用对象 |
| 构建声明、依赖坐标、SDK 使用候选 | 应脚本化；只读取项目内 `pom.xml`/Gradle 声明及项目源码线索 | 不解析依赖树，不下载或进入 SDK 内部，不判定复用正确性 |
| Controller/API、分页、响应、OpenAPI 和明显重复实现候选 | 保持脚本化；先形成候选 | 命中须沿项目内调用/配置链由 Agent 判定 |
| 结果包结构、规则统计、链接和编号 | 应脚本化 | 只能检查格式闭合，不能证明证据真实或项目合规 |
| 规则适用性、调用链根因、SDK 使用是否符合公开契约、严重性、例外和整改方案 | 保留 Agent 判断 | 必须保留具体 U/E、路径/符号和未证实边界 |
| 运行、联调、权限、事务回滚、消息投递和容量结论 | 保留人工/环境验证 | 静态脚本不得替代真实运行证据 |

新增脚本必须明确 `ProjectPath/ModulePath` 边界、排除规则、输出字段和退出码，并至少用“正常范围、越界路径、依赖声明、外部源码不可见”四类夹具验证。不得为了减少人工判断，把脚本扩展成按域批量填充规则状态的报告生成器。

## 三、前后端负责人如何补充领域内容

以下是规则选路范围，具体必须执行哪些规则由已绑定规范和项目适用条件决定。

| 领域 | 检查对象与取证重点 | 不可直接推断的结论 |
|---|---|---|
| 前端工程与框架 | 工程组织、依赖/锁文件、构建配置、当前框架身份、模块联邦生产/消费关系 | 任意 Vue 项目都属于同一框架 |
| 前端页面与组件 | 页面职责、公共组件复用、样式/资源、类型、表单、加载/空/失败/无权限状态 | 截图可证明所有状态与交互正确 |
| 前端请求与状态 | 请求封装、字段适配、分页、路由菜单、权限上下文、异步竞态、防重、资源释放 | 前端隐藏按钮可证明服务端权限 |
| 前端交付验证 | 类型检查、lint、构建、项目已有测试；条件具备时进行浏览器验证 | 构建成功等于浏览器运行和联调通过 |
| 后端工程与业务 | 工程、Controller/Service/持久层职责、实体/DTO、依赖和配置 | 文件数量或类大小能单独证明违规 |
| 后端数据与运行 | 数据访问、事务、缓存、鉴权/租户、异常日志、外部调用、异步并发及交付 | 注解、依赖或单次编译证明运行安全 |
| 接口跨端契约 | 路径、认证、请求/响应、统一分页、失败语义、兼容及联调证据 | 只看前端或后端一侧就能证明联调成功 |

前端负责人以当前已维护的前端规范和框架事实为准，复用现有前端技能的识别与取证方法；后端技能提供的是工作流参考。新增前端审查技能不得覆盖已有前端开发技能。内部构建规则不随生成的审查技能下发，只提供审查执行必需的规范、路由和结果包模板。

## 四、审查经验沉淀与最终产出要求

审查技能不是扫描命令集合，而是把领域负责人可以重复执行的判断过程固化为一次连续任务。建设者必须把以下信息写入目标技能或其按需参考资料，不能只保留在聊天记录中。

### 1. 先证明覆盖，再报告发现

审查开始先生成纳入范围的对象目录：模块、源码根、配置、接口入口、外部调用、消息或异步入口、测试与交付文件。每个规则域绑定“纳入对象、实际检查对象、未检查对象、排除对象及原因”。没有对象目录的“全量审查”只能标部分完成；变更模式从差异定位入口和必要关联对象，不为单报告省略这一依据。

规则路由必须记录五个关系：`规则 ID → 检查对象 → 检查方法 → 证据 → 结论边界`。规则没有适用对象时，必须依据工程事实判定不适用；无法确认时标为未证实，不得用零命中代替覆盖证明。

### 2. 用调用链和配置链确认根因

涉及接口、权限、事务、缓存、异步、外部调用和数据生命周期的候选，至少追踪到能够解释行为的链路：

```text
入口/触发器 → Controller/Consumer/Job
→ Service/UseCase → Mapper/Client/Adapter
→ 配置/权限/事务/消息边界 → 最终响应或副作用
```

单文件命中只能形成候选。发现卡片必须说明已确认的链路节点、未取得的节点和因此保留的未知边界。同一根因在多个模块出现，且触发条件与关闭方式一致时可归并，并保留全部位置和覆盖数量；不同根因不能仅因规则相同而合并。

### 3. 证据、置信度和严重性分开

证据等级只说明依据是什么，不等同于严重性：

| 证据等级 | 可支持的结论 |
| --- | --- |
| `S1 静态` | 文件、符号、配置或依赖存在/缺失；不能证明运行行为 |
| `S2 构建/测试` | 指定命令在指定环境下的结果；不能外推未执行路径 |
| `S3 运行/联调` | 可复现请求、权限、事务、消息或故障行为 |
| `S4 人工材料` | 已确认的契约、部署、调用方或例外依据；需记录来源和确认人 |

S1～S4 是证据类型，不是由低到高的质量或可信度排名；人工说明不能自动覆盖运行事实。严重性按影响和触发条件判定，置信度按证据是否足够判定。`潜在 P1 + 未证实` 可在补证项记录，但不进入已确认偏差及 F 优先级数量；不能为了提高优先级把未证实改成偏差。

### 4. 两种交付都必须形成闭环

单报告的六个章节或六文件结果包都必须形成“范围与资产 → 规则覆盖 → 扫描候选 → 调用链判定 → 发现/符合/未证实 → 整改关闭条件 → 复核证据”的闭环。单报告的内容对应配套模板首节，六文件分工如下：

- `00` 固定基线、范围、执行状态和未验证边界；
- `01` 只写结论、影响和可执行整改，不重复整张矩阵；
- `02` 保证每条适用规则都有状态，能反查发现和证据；
- `03` 保存可复现命令、资产统计、工具/环境、原始证据和限制；
- `04` 把每个发现转为关闭条件，复核时追加新证据，不覆盖历史结论；
- `05` 保留扫描原始命中、归并关系和排除/待补证理由。

报告至少能回答：审查了什么、没有审查什么、依据哪一版规范、发现是否确认、影响什么、如何修复、何时证明已关闭。没有这些信息，即使六个文件都存在，也只能标部分完成。复核在同一报告或结果包内追加版本与新证据，保留初审基线、稳定 ID 和历史结论，不每轮新建过程报告。

每张统计表标明对应审查基线，复核统计与初审分开，不把历史发现数量与新基线规则状态直接混算。工具无法定位多版本统计时保留待复核，不默认选择其中一份代表当前质量。

### 5. 构建技能时的经验验证

领域技能移交前至少使用四类隔离样本：符合规则、确定偏差、合理例外、证据不足；另加一个跨文件调用链样本和一个构建或运行失败样本。预期结果必须在执行前记录，执行后比较实际结果；不能用技能自己生成的报告反向证明技能正确。

经验应沉淀为可复用的规则路由、证据字段、误报排除条件和复核关闭条件。一次项目的具体路径、业务名称和偶然命中不得直接写成通用规则。真实项目审查报告只作为验证材料，不作为领域规范或技能正文的第二事实源。

### 6. 基础能力包必须复用，专项能力包按需审查

账本按项目实际功能建立预期能力与实际实现的对照，至少说明公开入口/版本、预期复用点、实际依赖/配置/调用链、关键行为差异及证据。只有 import 或依赖不能证明复用，也不能仅凭同名类认定重复建设；缺少公开契约时保留未证实。重复实现须说明已有能力能覆盖什么、项目另建了什么，以及触犯哪条正式规则，不以能力编号直接扣分。

领域审查技能涉及后端业务项目时，必须把该领域已经确认的基础能力包列入默认审查范围。当前后端基础能力基线至少包括 `AURA-CAP-COMMON-BUSINESS`（基础业务开发能力包）和 `AURA-CAP-BASE`（基础通用支撑能力包）。审查范围涉及对应功能时，核对公开入口、实际依赖/配置及调用，确认是否重复实现同类能力；没有对应功能可记录具体不适用依据，不要求项目强装全部基础依赖。变更模式只检查当前变更和受影响链路中的基础功能，不借此默认重审全项目。只看到依赖或类名不能判定已复用，重复实现也必须沿配置、调用入口和行为链确认。

物联中枢云、文件与实时、数据基础设施、任务调度、网关流量、数据安全等专项能力属于按需能力。技能只有在需求、路由、依赖、配置、接口或代码行为触发时才纳入；未触发的专项能力应记录不适用依据，不得因为没有引入而判定偏差。专项能力被触发后，优先核对公开能力入口和版本，再判断接入、替代实现或证据不足。

后端报告必须在模板对应章节提供能力复用账本，至少记录能力包编号、复用级别（`基础必查/按需`）、触发依据、预期入口、实际依赖与调用、重复实现候选、证据编号和结论。按需能力只对已触发或触发性未明的能力建行，其余按已核对能力目录版本及未触发类别说明，不要求罗列所有未接入能力。非后端领域使用自身能力基线；领域没有能力要求时说明不适用，不照抄后端能力表。能力结论与规范规则分开统计但互引，不用“没有专项能力”代替基础复用核查。
