# 模块联邦（综合端）开发边界说明

## 一、为什么要划分开发边界

模块联邦（综合端）同时依赖 `aura-core` 的后台布局、主题和公共能力，并通过统一运行时向其他综合端提供或消费远程模块。部分文件看起来可以直接修改，但实际承担所有综合端共同遵守的协议；单个业务项目私自调整后，通常会出现独立运行正常、远程运行失败，或不同综合端行为不一致的问题。

开发边界分为三个层级：

| 边界 | 处理原则 |
| --- | --- |
| 框架保护区 | 业务只使用，不自行修改、删除或替换；有需求由框架统一实现和发布 |
| 业务配置扩展区 | 按规定修改值或追加配置，保留框架结构和标准入口 |
| 业务自由开发区 | 业务自行设计和实现，但继续遵守公共开发规范 |

同一个文件可能同时包含框架结构和业务配置。例如 `moduleFederationBaseConfig.ts` 的配置结构和辅助函数属于框架，`remoteName`、`remoteEntryName` 和业务 `i18nScanDirs` 属于业务必须维护的配置。

## 二、框架保护区

### 1. 核心依赖和构建链路

以下版本和构建配置由框架统一维护：

- Vue、Vue Router、Vue I18n、Pinia、Element Plus。
- `@module-federation/vite`、`@module-federation/enhanced`、Vite。
- Module Federation `shared`、manifest、`remoteEntry.js`、远程预加载跳过和依赖预构建配置。
- Vite 基础插件顺序、`/@/` 别名和自动导入基础配置。

Element Plus 当前固定为 `2.14.3`，并作为 Module Federation singleton。业务不得自行升级、降级、移出 shared 或设置为非 singleton。

业务可以增加经过项目确认的业务依赖，但不得借安装业务依赖修改核心版本。`@fxft/ui-plus` 是业务按需依赖，不是框架基础依赖，也不加入框架 shared。

### 2. 模块联邦运行时

以下能力属于框架协议，业务不得复制后改造或删除关键逻辑：

- 远程入口标准化、注册、加载和缓存刷新。
- 远程加载失败隔离、重新加载和重试。
- 远程 i18n、页面 CSS、scoped Tailwind 和核心主题样式加载。
- 远程资源根路径识别以及静态资源、public 资源地址转换。
- 远程路由真实 scope 根节点和 `ModuleFederationElementProvider`。

框架标准 expose 不得删除、改名或替换：

```ts
export const utilsExposes = {
	'./utils/mitt': './src/utils/mitt.ts',
	'./moduleFederation/runtime': './src/hooks/moduleFederation.ts',
};

export const styleExposes = {
	'./styles/moduleFederationTailwind.ts': './src/styles/moduleFederationTailwind.ts',
};

export const i18nExposes = {
	'./i18n/langs': './src/i18n/moduleFederation.ts',
};
```

业务只在 `pageExposes`、`apiExposes`、`componentExposes` 和业务工具 expose 中追加自己的模块。

### 3. 应用启动和请求内核

`main.ts` 中以下启动顺序由框架维护：

```text
恢复启动缓存、主题和 Iconfont
→ 从 aura-core manifest 加载核心主题样式
→ 获取系统全局配置
→ 校准 systemId、主题和 Iconfont
→ 创建并挂载 Vue 应用
```

业务不得移除或交换启动缓存、核心主题、系统配置、认证异常处理和 Iconfont 初始化顺序。

请求相关的懒加载入口、请求实例、公共请求头、认证异常、参数序列化和存储前缀同样属于框架。业务只能通过统一请求入口封装 API：

```ts
import request from '/@/utils/request';

export const getOrderPage = (params: OrderPageQuery) =>
	request({ url: '/order/page', method: 'get', params });
```

业务不得直接创建 axios 实例、修改统一认证处理或自行清理登录态。

### 4. 样式、主题和后台布局

以下内容由框架统一维护：

- PostCSS/Tailwind 远程 scope、选择器转换和边框兼容插件。
- 标准 Tailwind 入口及“远程入口不引入完整 Preflight”的隔离策略。
- `aura-core/theme-core` 提供的后台主布局、主题运行时和主题配置面板。
- 顶栏、侧栏、菜单、TagsView、面包屑、内容区容器和移动端适配。

业务不得：

- 把 `aura-core/theme-core` 复制到业务项目后修改。
- 通过 CSS 覆盖或运行时替换实现另一套后台主布局。
- 修改 PostCSS scope 算法、删除边框兼容插件或输出无 scope 的全局 Tailwind。
- 替换框架顶栏、侧栏、菜单、TagsView 或路由内容区结构。

业务页面可以在框架内容区内部实现自己的查询区、表格、卡片、看板、地图、视频、弹窗和抽屉布局。

### 5. 框架组件和生成文件

框架已注册的全局组件、公共 Hooks 和 `ModuleFederationElementProvider` 不能由业务删除或同名替换。需要改变自动解析组件时，使用框架提供的编译期覆盖 Resolver，不修改运行时全局组件表。

以下文件由工具生成，禁止手工修改：

- `src/i18n/moduleFederation.ts`。
- `auto-imports.d.ts` 等自动导入声明。
- 构建目录中的 `remoteEntry.js`、`mf-manifest.json` 和 chunk。

## 三、业务配置扩展区

### 1. 项目身份必须修改

脚手架占位身份不能直接用于真实项目。业务必须同步修改：

- `remoteName`。
- `remoteEntryName`。
- `systemId`。
- `package.json.name`、站点标题和部署前缀。
- PostCSS/Tailwind scope、环境变量和 Nginx 部署目录。

三个身份在同一部署环境中必须唯一，且不能混用各自职责。

### 2. 国际化扫描目录可以追加

框架默认扫描公共组件目录，业务只追加自己的目录：

```ts
const defaultI18nScanDirs = ['src/components'] as const;

export const currentRemoteConfig = {
	i18nScanDirs: ['src/views/order', ...defaultI18nScanDirs] as const,
};
```

不得删除 `src/components`，也不得手工维护生成的 `src/i18n/moduleFederation.ts`。

### 3. 对外 expose 可以追加

```ts
export const pageExposes = {
	'./views/order/list/index.vue': './src/views/order/list/index.vue',
};

export const componentExposes = {
	'./components/OrderStatusTag.vue': './src/components/OrderStatusTag.vue',
};
```

业务 expose key 必须与真实文件路径对应，标准 runtime、i18n 和 Tailwind expose 保持不变。

### 4. 远程消费配置可以扩展

业务可以按需增加：

- 运行时远程名称和 manifest 入口。
- 对应环境变量和开发代理。
- 后端模块联邦菜单。
- 源码静态 import 所需的编译期 remotes 和 TypeScript 声明。

后端菜单动态页面只配置运行时远程，不为动态菜单误加编译期 remotes。

### 5. 组件覆盖项由业务决定

框架提供空的编译期覆盖能力，不预置任何具体组件。业务可以登记自己的覆盖项：

```ts
const componentOverrides: Record<string, string> = {
	ElEmpty: './src/components/ElEmpty/index.vue',
};
```

上例只表示某个业务项目选择覆盖 `ElEmpty`，不代表框架默认提供该覆盖。业务接入其他组件库 Resolver 时，框架覆盖 Resolver 必须放在前面：

```ts
Components({
	dts: false,
	dirs: [],
	resolvers: [createComponentOverrideResolver(pathResolve), FxftUiPlusResolver()],
});
```

### 6. 业务全局组件可以追加

业务可以增加确有跨页面复用价值的全局组件，但不能删除或同名替换框架组件。远程页面不会执行提供方 `main.ts`，因此需要远程使用的组件应通过源码 import、编译期 Resolver 或 expose 接入，不能只依赖运行时全局注册。

## 四、业务自由开发区

业务可以自行设计和实现：

- `src/views/<业务域>` 下的页面、页面私有组件、composables 和 i18n。
- `src/api/<业务域>` 下的接口封装、业务类型和参数模型。
- 业务 Pinia Store、业务 Hooks 和跨页面业务组件。
- 业务图片、SVG、视频、Worker 和其他静态资源。
- 后端菜单、按钮权限、表单规则、页面交互和业务状态。
- 内容区内部的卡片、表格、看板、弹窗、抽屉和局部布局。
- 地图和视频业务组合逻辑。

业务自由开发仍必须遵守：

- 请求统一使用 `/@/utils/request`。
- import 静态资源使用 `getStaticResourceUrl`。
- public 资源使用 `getPublicResourceUrl`。
- 后端相对文件地址使用 `getFileFullUrl`。
- 使用主题变量，不硬编码部署地址或大面积主题色。
- 地图、单路视频和多路视频使用公司 UI 组件公开 API。
- 独立运行和模块联邦远程运行都需要验证。

## 五、后台布局预设边界

### 1. 现有能力

当前 `aura-core` 提供三个后台布局预设：

- 自定义。
- 经典蓝。
- 草木绿。

布局预设是一组完整的主题和布局配置。底层还提供四种布局模式：

- `defaults`。
- `classic`。
- `transverse`。
- `columns`。

布局预设和布局模式不是同一概念。业务可以选择框架已有预设、布局模式和开放的主题配置项。

### 2. 新增布局预设

现有三个预设不能满足业务时，业务可以提出新增后台布局预设需求。新预设统一在 `aura-core` 中开发、维护和发布，各综合端通过升级核心框架获得能力。

业务综合端不得自行：

- 增加 `LayoutTemplateKey`。
- 修改布局预设清单。
- 复制 `aura-core/theme-core`。
- 替换后台布局或主题配置面板。

如果需求涉及顶栏、侧栏、菜单结构等基础结构变化，由框架统一判断属于新增布局预设还是新增底层布局模式。

## 六、框架需求提出方式

框架保护区不能满足业务时，业务可以直接向框架提出需求，由框架统一评估、实现和发布。

业务项目不直接维护框架保护区的长期补丁。框架正式版本发布后，各综合端按对应升级说明统一升级。

## 七、开发前快速判断

| 需求 | 归属 |
| --- | --- |
| 新增业务页面、接口、表单或看板 | 业务自由开发 |
| 增加业务 expose、远程入口或代理 | 业务配置扩展 |
| 安装并使用 `@fxft/ui-plus` | 业务配置扩展 |
| 在 `componentOverrides.ts` 登记业务覆盖组件 | 业务配置扩展 |
| 修改 Module Federation 加载、缓存或重试机制 | 框架需求 |
| 修改统一请求、认证或存储机制 | 框架需求 |
| 修改 Element Plus、Vue 或模块联邦核心版本 | 框架需求 |
| 新增后台布局预设或底层布局模式 | 框架需求 |
| 修改顶栏、侧栏、菜单或 TagsView | 框架需求 |
