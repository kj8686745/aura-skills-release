# AURA（天玑）基础编码规范：构建与交付

<!-- 规范编号：BASE-06 -->
<!-- 规范版本：0.1.0-draft -->
<!-- 模板版本：基础编码规范模板 v3 -->

**适用对象**：使用 AURA 开展业务应用、服务、工具和平台工程开发的团队和开发人员

**规范目标**：让本地、联调和交付构建可重复、可检查、可追溯且入口一致。

**边界说明**：本文件负责构建命令、构建检查和交付产物；配置、依赖和环境启动分别见本目录其他分类文件。

## 一、构建规则

### AURA-BASE-BUILD-001：构建命令必须可重复

**必要性**：必须

**为什么需要**：可重复构建是验证代码、依赖和交付物一致性的基础，避免只能在某台开发机上成功。

项目必须提供从干净环境执行的编译、测试和打包入口，并说明 JDK、包管理器、关键参数和产物位置。构建结果不得依赖开发者本机缓存或未声明文件。

**正确写法**：提供固定的编译、测试、打包命令，并声明 JDK、参数、输入和产物目录。

**错误写法**：只在个人 IDE 中构建，依赖本机缓存或未提交的配置文件。

**判断要点 / 验证方式**：在干净环境执行完整命令并核对产物。

### AURA-BASE-BUILD-002：构建必须覆盖依赖和配置检查

**必要性**：必须

**为什么需要**：在构建阶段尽早发现缺依赖、错配置和不兼容，可以减少问题延迟到联调或运行阶段才暴露。

构建至少应检查依赖收敛、配置格式、敏感信息、测试结果和制品内容。发现版本冲突、敏感值或关键测试失败时，不得以跳过检查方式形成正式产物。

**正确写法**：构建同时执行依赖收敛、配置格式、敏感扫描、测试和制品检查。

**错误写法**：通过跳过测试、忽略冲突或关闭敏感扫描生成正式产物。

**判断要点 / 验证方式**：使用违规依赖、敏感值和失败测试夹具确认构建被阻断。

### AURA-BASE-BUILD-003：构建产物必须可追溯

**必要性**：必须

**为什么需要**：产物能关联源码、依赖和构建环境，才能定位线上版本、复现问题并执行可靠回退。

产物必须能关联源码版本、依赖版本、构建命令和非敏感配置版本或环境标识。日志和产物不得包含敏感值；同一输入在相同环境下应得到可解释的结果。

**正确写法**：产物元数据记录源码提交号、依赖约束摘要、构建命令和非敏感配置版本，不写入 Token、密码或完整连接串。

**错误写法**：只上传一个没有版本信息的 `app.jar`，构建过程依赖本机环境且无法还原输入。

**判断要点 / 验证方式**：检查制品元数据和构建日志，使用同一提交在干净环境重建并比对关键摘要。

### AURA-BASE-BUILD-004：本地、联调和交付构建入口必须一致

**必要性**：必须

**为什么需要**：统一构建入口可以减少“本地通过、交付失败”的差异，让验证结果真实反映最终交付过程。

开发者本地、联调和交付构建必须复用项目中同一份构建定义与版本约束；联调和交付可在该入口上追加环境适用的校验、打包或签名步骤。差异必须通过明确参数、配置和流水线步骤表达，不能复制多套互相漂移的依赖与编译定义。

**正确写法**：本地和流水线调用同一 Maven 或前端包管理器构建定义，流水线另执行适用的扫描和制品发布步骤；参数与制品版本可在项目文档和构建记录中还原。

**错误写法**：本地使用 IDE 构建，联调用另一套脚本，交付时由人工重新执行一组未记录的命令。

**判断要点 / 验证方式**：分别在本地、干净环境和交付环境执行入口，比较版本、参数、检查项和产物结构。

## 二、典型使用示例：同一入口完成构建与交付

**场景目标**：让开发者本地、联调环境和交付流水线复用同一构建定义，并使交付物能够追溯到源码、依赖和非敏感配置版本。

**输入条件**：项目已提供统一的 Maven 或前端包管理器入口；交付需要生成带元数据的制品；环境差异通过参数或受控配置注入。

**正确做法**：

```text
本地验证 ─┐
联调构建 ─┼─> 项目统一构建入口 ─> 依赖/配置/测试检查 ─> 带版本元数据的制品
交付构建 ─┘                         └─> 交付说明与恢复信息
```

```json
{
  "sourceCommit": "<commit>",
  "dependencyConstraint": "<bom-or-lock-summary>",
  "buildCommand": "<project-build-entry>",
  "environmentProfile": "<non-secret-profile>",
  "artifact": "<artifact-name-and-version>"
}
```

Java 项目可由项目统一入口执行 `./mvnw -B clean verify`，前端项目可由项目统一入口执行 `npm ci` 和 `npm run build`；命令必须以项目实际构建定义为准，不能另造一套交付脚本。

**错误做法**：本地依赖 IDE 构建，联调使用另一份脚本，交付时手工上传没有提交号的 `latest.jar`；或把 Token、密码和完整连接串写入制品元数据。

**验证步骤与预期结果**：

1. 在隔离依赖缓存中执行项目统一构建入口，确认依赖、配置和测试检查均执行。
2. 用同一提交分别执行本地、联调和交付参数，确认构建定义、关键检查和产物结构一致。
3. 检查制品元数据能定位源码、依赖、命令和环境标识，且不包含敏感值。
4. 保留构建日志和失败原因；不得通过跳过检查生成正式交付物。

## 三、开发者自检

- 是否提供从干净环境执行的编译、测试和打包入口；
- 构建是否检查依赖收敛、配置、敏感信息、测试和制品内容；
- 产物是否能追溯到源码、依赖、命令和非敏感配置版本；
- 本地、联调和交付是否复用同一构建定义；
- 构建失败时是否保留真实失败原因，而不是跳过检查生成产物。
