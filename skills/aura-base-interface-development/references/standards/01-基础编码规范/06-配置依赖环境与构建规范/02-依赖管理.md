# AURA（天玑）基础编码规范：依赖管理

<!-- 规范编号：BASE-06 -->
<!-- 规范版本：0.1.0-draft -->
<!-- 模板版本：基础编码规范模板 v3 -->

**适用对象**：使用 AURA 开展业务应用、服务、工具和平台工程开发的团队和开发人员

**规范目标**：让依赖版本、公开边界、升级影响和构建输入可追溯、可复现、可控制。

**边界说明**：本文件负责依赖选择和版本约束；配置、环境启动和构建交付分别见本目录其他分类文件。

## 一、依赖规则

### AURA-BASE-DEP-001：依赖版本必须来自统一版本约束

**必要性**：必须

**为什么需要**：统一版本约束可以减少传递依赖冲突和环境差异，保证项目使用的基础库组合可复现。

项目必须使用当前 AURA 版本允许的父工程、BOM 或版本约束。核心框架、序列化、数据访问和通信依赖不得在业务模块随意覆盖。

**正确写法**：依赖版本由项目统一 BOM 管理，业务模块不单独覆盖核心框架版本。

**错误写法**：某个业务模块单独升级框架依赖，导致同一工程出现多套核心版本。

**判断要点 / 验证方式**：检查 effective POM、依赖树和版本收敛报告。

### AURA-BASE-DEP-002：新增依赖必须说明用途和影响

**必要性**：必须

**为什么需要**：记录依赖用途、体积、权限和运行影响，可以避免无必要引入并为后续升级和故障定位提供依据。

新增依赖时，必须在项目的依赖变更说明中写清用途、引入模块、是否已有 AURA 能力可复用，以及版本和传递依赖影响；涉及许可证、已知漏洞、制品体积或运行配置变化时，记录相应检查结果与处理方式。仅在可选场景使用的依赖不得无条件进入所有模块。

**正确写法**：在模块文档或变更说明中记录新增库的用途、坐标和版本、依赖树变化及实际受影响的许可证、漏洞、体积和配置事项。

**错误写法**：只因为示例方便引入重量级库，未评估已有 AURA 能力和安全影响。

**判断要点 / 验证方式**：核对依赖变更说明、依赖树及适用的许可证/漏洞检查；涉及基础模块时检查最小消费者构建和产物体积。

### AURA-BASE-DEP-003：模块依赖必须符合公开边界

**必要性**：必须

**为什么需要**：依赖公开入口而不是内部实现，可以保持模块可替换、可升级，避免内部重构破坏调用方。

消费者只能依赖已公开、已版本化的契约、客户端、组件或能力入口，不得依赖其他业务模块的内部实现、持久化模型或运行配置。跨模块关系遵循 BASE-02 和 BASE-05。

**正确写法**：服务消费者依赖公开 API 或客户端，不直接引用提供方的 Entity、Mapper 或内部配置。

**错误写法**：通过 Maven 依赖其他业务服务的 `*-biz` 并调用其内部 ServiceImpl。

**判断要点 / 验证方式**：检查依赖树、包引用和跨模块公开入口。

### AURA-BASE-DEP-004：依赖和构建输入必须可复现

**必要性**：必须

**为什么需要**：锁定依赖和构建输入才能让不同开发机、联调环境和交付环境得到一致结果。

禁止使用无法确定版本的动态依赖。构建必须能够识别版本冲突、重复类、未声明直接依赖和不受控快照输入；关键版本、JDK、插件和仓库来源必须可追溯。

**正确写法**：锁定 JDK、插件、依赖和仓库来源，使用干净环境执行构建和依赖收敛检查。

**错误写法**：依赖本机缓存成功，使用 `LATEST`、动态版本或未登记 SNAPSHOT。

**判断要点 / 验证方式**：使用隔离的空依赖缓存重复构建，不删除个人或共享缓存；检查版本冲突、重复类和动态输入。

### AURA-BASE-DEP-005：历史依赖必须限定在兼容边界内

**必要性**：必须

**为什么需要**：历史兼容依赖如果没有范围和退出条件，会持续扩大维护成本并阻止基础版本升级。

不能立即替换的历史依赖必须登记使用范围、调用边界、替代方向、责任人、回归方式和退出版本。新增代码不得扩大未批准历史依赖的使用范围。

**正确写法**：历史依赖登记精确坐标、调用 API、消费者、替代方案、Owner 和退出版本。

**错误写法**：以“项目还在用”为理由无限扩大历史依赖使用范围。

**判断要点 / 验证方式**：扫描新增引用并检查兼容台账、回归结果和到期状态。

### AURA-BASE-DEP-006：依赖升级必须先验证直接行为影响

**必要性**：必须

**为什么需要**：版本升级可能改变序列化、线程、连接和安全行为，先验证直接影响可以降低隐式回归风险。

升级依赖、运行时或插件时，必须识别直接和传递依赖变化，并验证序列化、线程、事务、异常、默认配置和构建产物等受影响行为；不能只确认版本号已更新。

**正确写法**：升级序列化库后验证日期、未知字段和枚举解析，检查依赖树和关键接口回归。

**错误写法**：批量更新所有依赖到最新版本，只运行编译，不检查运行时行为。

**判断要点 / 验证方式**：比较升级前后依赖树、锁定文件、关键行为测试和构建产物。

### AURA-BASE-DEP-007：可选依赖不得扩大基础工程体积和边界

**必要性**：禁止

**为什么需要**：限制可选依赖可以避免基础工程被无关能力、额外漏洞和不必要运行时资源拖重。

只服务于特定模块或场景的依赖必须保持可选和局部引入，不得因为示例、调试或单一能力把重量级库和传递依赖带入所有业务模块。

**正确写法**：视频处理依赖只进入视频模块，基础模块不因其存在增加运行时和构建负担。

**错误写法**：为了一个导出功能把完整报表和图形库加入所有服务公共依赖。

**判断要点 / 验证方式**：检查模块依赖树、构建体积和最小模块构建，确认可选能力没有无边界传播。

## 二、典型使用示例：为导出模块增加可选依赖

**场景目标**：为报表导出模块增加库依赖，同时保证基础服务、其他业务模块和最小构建不被该依赖带入。

**输入条件**：项目已有统一 BOM；导出能力只由 `report-export` 模块使用；依赖的许可证、漏洞和运行体积需要在变更说明中记录。

**正确结构**：

```text
project
├─ dependency-management/       # 统一版本约束
├─ report-export/               # 仅此模块声明导出依赖
└─ device-service/              # 不依赖导出库
```

```xml
<!-- report-export/pom.xml：版本由统一约束提供，不在业务模块写死核心库版本 -->
<dependency>
    <groupId>example.report</groupId>
    <artifactId>report-export</artifactId>
</dependency>
```

变更说明同时记录依赖用途、受影响模块、传递依赖摘要、许可证/漏洞检查、构建体积变化和回退方式；`device-service` 的最小构建不应解析该依赖。

**错误结构**：把导出库加入公共父工程或基础 starter，仅因为一个模块需要就让所有服务携带该库；或者在子模块中覆盖统一 BOM 的版本。

**验证步骤与预期结果**：

1. 检查 effective POM 和依赖树，确认版本来自统一约束且没有动态版本或重复核心库。
2. 分别构建 `report-export` 和不使用导出的最小 `device-service`，确认后者不包含导出依赖。
3. 核对依赖变更说明中的许可证、漏洞、体积和恢复信息；任一关键检查缺失时，不形成正式交付物。

## 三、开发者自检

- 依赖版本是否来自统一约束；
- 新增或升级依赖是否记录用途、影响、漏洞和许可证检查；
- 依赖是否只通过公开契约和能力入口使用；
- 历史依赖是否有边界、Owner 和退出版本；
- 最小模块是否没有被可选依赖和传递依赖拖重。
