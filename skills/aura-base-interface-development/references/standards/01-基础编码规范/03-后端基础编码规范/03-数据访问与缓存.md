## 一、规则

### AURA-BASE-BE-016：数据访问层只负责数据读写

**必要性**：必须

Repository、Mapper、DAO 或其他数据访问代码只负责数据读写、查询条件转换和持久化模型映射。

不得在数据访问层编写跨用例业务流程、外部调用、权限判断、接口响应转换或页面展示逻辑。

**为什么需要**：数据访问层只承担持久化适配，才能避免数据库实现反向决定业务流程。

**正确写法**：Repository 接收明确查询条件，完成数据读写和持久化模型映射，将业务判断留在应用用例或业务层。

**错误写法**：Mapper 查询时判断审批权限、调用外部服务或拼装公开响应。

**判断要点 / 验证方式**：数据访问代码是否只处理查询、保存、映射和持久化异常；是否出现业务流程和外部依赖；检查数据访问层依赖方向和方法职责；通过 Repository 测试验证读写边界。

**例外**：数据库特有的查询优化可以保留在数据访问层，但不得改变业务语义或绕过业务规则。

### AURA-BASE-BE-017：查询条件必须有明确来源和语义

**必要性**：必须

后端查询必须能够说明查询条件来自请求、当前用户上下文、业务规则、系统配置还是固定约束。

不得用无来源的默认条件、隐式租户、隐式权限、全局变量或字符串拼接形成查询语义。

**为什么需要**：查询条件来源不清会造成越权、数据遗漏、结果不稳定和难以复现的问题。

**正确写法**：明确区分请求条件、当前用户范围、业务状态、系统配置和固定约束，并在用例中组装查询条件。

**错误写法**：从全局变量读取租户值，或直接把前端传入的 SQL 片段拼接到查询中。

**判断要点 / 验证方式**：每个过滤条件是否能追溯来源、优先级和安全边界；是否存在隐式默认条件；使用不同用户、租户和数据范围进行查询测试；人工确认权限条件和数据范围语义。

**例外**：固定系统条件可以在 Repository 中表达，但必须有明确命名和文档说明。

### AURA-BASE-BE-018：分页、排序和批量查询必须可控

**必要性**：必须

列表查询、批量查询和导出类查询必须明确分页、排序、过滤和最大范围。

不得默认全量查询，也不得把前端传入的排序字段、过滤字段或 SQL 片段未经校验直接传入数据访问层。

**为什么需要**：可控的查询范围可以防止内存、数据库和接口响应被无限放大。

**正确写法**：限制页大小和最大范围，使用白名单映射排序字段，并为批量和导出提供独立边界。

**错误写法**：`select *` 默认查询全部数据，或直接使用前端传入的 `sort`、`where` 和 SQL 片段。

**判断要点 / 验证方式**：是否有最大页大小、最大批量、排序白名单、超时和导出规模限制；使用超大页码、超大批量、非法排序和空过滤条件进行边界测试；保留查询和响应证据。

**例外**：受控的内部统计任务可以采用批量读取，但必须明确规模、执行时间和资源边界。

**边界说明**：本规则约束后端查询代码如何落实接口层的范围要求；公开参数、响应字段和批量契约遵循 `BASE-05`，数据库访问细节和数据生命周期遵循 `BASE-08`。

### AURA-BASE-BE-019：跨模块数据必须通过公开契约获取

**必要性**：必须

后端模块需要其他模块数据时，应通过公开查询接口、公开事件、只读视图或明确的数据共享契约获取。

不得直接访问其他模块数据库表、Mapper、缓存键或内部实体。数据所有权和数据生命周期的完整要求由 `BASE-08` 定义。

**为什么需要**：跨模块直接访问内部数据会破坏所有权，使表结构、缓存实现和内部模型成为隐式公共契约。

**正确写法**：通过公开查询接口、事件、只读视图或明确共享契约获取所需数据，并转换为本模块模型。

**错误写法**：直接引入其他模块 Mapper，读取对方数据库表或拼接对方缓存键。

**判断要点 / 验证方式**：数据来源是否经过拥有方定义的公开边界；是否依赖对方内部表、缓存和实体；检查模块依赖和数据库连接范围；人工确认数据所有权、兼容性和失败处理。

**例外**：经过明确治理的只读共享视图可以使用，但必须有稳定契约和版本管理。

### AURA-BASE-BE-035：集合处理应当考虑规模和顺序

**必要性**：应当

对集合进行过滤、排序、分组、去重和转换时，应明确数据规模、顺序要求和重复元素语义。不得在不确定规模的情况下把全量数据加载到内存，也不得依赖无序集合的偶然顺序。

**为什么需要**：集合操作同时影响性能、结果顺序和重复数据语义。

**正确写法**：明确分页或流式处理，使用稳定排序和有语义的去重键。

**错误写法**：查询全量数据后在内存中排序，或依赖 HashSet 的遍历顺序作为业务结果顺序。

**判断要点 / 验证方式**：规模是否受控；顺序和重复元素是否有明确语义；使用大数据量、重复数据和空集合测试；人工确认性能和结果顺序。

**例外**：已证明规模很小的内部集合可以直接处理，但应有边界依据。

### AURA-BASE-BE-037：后端缓存访问必须集中封装并定义边界

**必要性**：必须

使用缓存时必须说明缓存数据的来源、键、有效期、一致性策略和失效方式。不得把缓存当作唯一事实来源，也不得在业务代码中散落缓存键和失效逻辑。

**为什么需要**：缓存是加速边界，不是默认事实来源；语义不清会导致脏数据、击穿和失效失控。

**正确写法**：定义缓存键、来源、有效期、失效和回源策略，并集中封装缓存访问。

**错误写法**：在多个业务方法中拼接缓存键，把缓存当作唯一数据来源，或永久缓存无失效策略。

**判断要点 / 验证方式**：缓存是否可回源；一致性、失效、容量和降级策略是否明确；测试缓存命中、过期、删除、回源失败和并发击穿；人工确认业务可接受的不一致范围。

**例外**：纯临时计算结果可以采用短期缓存，但仍需明确有效期和失败处理。

## 二、典型开发场景

以下示例用于说明多条规则如何组合，不构成新的接口契约，也不绑定具体框架、目录名或业务模型。

### 数据访问与分页

**适用任务**：数据访问、后端业务用例、异步与批处理  
**关联规则**：BE-016、BE-017、BE-018、BE-019、BE-035、BE-036  
**示例级别**：数据访问示例（导出任务生命周期见场景 3）

#### 场景目标

实现设备列表查询和导出任务中的数据扫描，展示查询条件来源、数据范围、分页上限、排序白名单、跨模块数据契约和大数据量处理边界。导出任务的受理、领取、终态和恢复沿用场景 3 的模式。

#### 输入条件

- 查询条件来自请求、当前用户数据范围和固定业务约束；
- 页大小有明确上限；本例导出总量上限为 50,000 行，而不只是每批 500 行；
- 排序字段只能从白名单中选择；
- 其他模块数据通过公开查询契约获取，不直接访问对方表和缓存。

#### 推荐调用结构

```text
DeviceQueryController
  → DeviceQuery
  → DeviceQueryApplicationService
    → UserScopeProvider
    → DeviceRepository.findPage(query, scope, sort)
    → DeviceResponse 转换

DeviceExportApplicationService
  → 由受控任务工作者领取已持久化的导出任务
  → 重新解析当前操作人的数据范围
  → 按稳定游标读取并限制总量
  → 分批写入临时文件，成功关闭后发布产物
```

#### 完整正确示例

```java
public IPage<DeviceResponse> list(DeviceQueryRequest request, UserContext context) {
    var query = request.toQuery();
    var scope = scopeProvider.resolve(context);
    var sort = SortWhitelist.resolve(request.sort()).withIdTieBreaker();
    var page = PageRequest.requireRange(request.page(), request.pageSize(), 200);

    return repository.findPage(query, scope, sort, page)
        .convert(DeviceResponse::from);
}

public ExportFileRef writeExport(ExportTask task) {
    var scope = scopeProvider.resolveFor(task.operatorId());
    var sort = DeviceSort.byId(); // 游标顺序必须稳定且唯一
    var cursor = ExportCursor.start();
    long total = 0;
    ExportTempRef temporary;
    try (var writer = exportFiles.createTemporary(task.id())) {
        while (true) {
            scopeProvider.requireStillValid(task.operatorId(), scope);
            var batch = repository.readNext(task.query(), scope, sort, cursor, 500);
            if (batch.isEmpty()) break;
            if (total + batch.size() > 50_000) throw new ExportLimitExceededException();
            writer.write(batch.items().stream().map(DeviceExportRow::from).toList());
            total += batch.size();
            cursor = batch.nextCursor();
            exportTasks.recordProgress(task.id(), total);
        }
        temporary = writer.finish();
    }
    return exportFiles.publish(temporary); // 文件关闭成功后才发布
}
```

查询条件、数据范围和排序均由应用用例明确组装；列表将分页记录转换为公开响应模型和统一 `PageResult<T>`，所有 HTTP Controller 再按 `BASE-05` 使用 `R.ok(pageResult)` 返回，不另造分页外壳，也不把 ORM `Page/IPage` 直接暴露给调用方。导出扫描限定每批和总行数，按稳定唯一游标推进，不将全量数据一次性加载到内存；游标不等于一致性快照，业务若要求固定时点结果还需定义数据快照或截止条件。每批复核数据范围，临时文件完成并关闭后才发布；任务工作者取得已发布产物引用后才记录成功终态。文件、进度记录或发布失败时应保留失败结果、清理未发布的临时文件；重入使用新的临时产物，不能把上次的半成品当作成功文件。导出任务的幂等受理、领取凭证、超时与重入遵循场景 3，不能仅凭本段扫描代码宣称整个导出流程完成。

#### 错误示例

```java
public List<?> list(String where, String sort) {
    return jdbc.query("select * from device where " + where + " order by " + sort);
}

public byte[] exportAll() {
    return repository.findAll().toList().toBytes();
}
```

问题：前端输入直接拼接 SQL，没有用户数据范围和排序白名单，默认全量加载，无法控制内存和响应时间。

#### 验证步骤与预期结果

1. 使用非法排序字段、无效页码和超大页大小，预期在查询前被拒绝。
2. 使用不同用户和数据范围查询，预期只能看到授权范围内数据。
3. 使用超过 50,000 行的数据导出，预期触发总量限制；未超限时按稳定游标分批处理，任务状态可查询且内存受控。
4. 导出过程中撤销操作人数据权限、写入失败或进程中断，预期不产生越权文件或伪成功，任务可按已定义的恢复边界处理。
5. 检查跨模块数据来源，预期只依赖公开接口、事件或共享契约。

#### 人工确认点

- 数据范围和租户条件的来源及优先级；
- 页大小、导出规模和任务超时上限；
- 排序字段白名单和稳定排序要求；
- 跨模块数据所有权、缓存和一致性边界。

### 树形数据和层级查询

**适用任务**：数据访问、后端业务用例  
**关联规则**：BE-016、BE-017、BE-018、BE-019、BE-035  
**示例级别**：完整示例

#### 场景目标

查询用户有权访问的设备分组树。调用方只能指定业务允许的根节点和受控深度；应用用例负责校验数据范围、树结构和公开模型转换；数据访问层只在受控条件下读取节点。

#### 输入条件

- 当前用户具有可解析的数据范围；
- 查询允许指定根节点和最大层级，但最大深度由服务端限制；
- 节点存在父子关系和稳定排序字段；
- 数据库可能存在孤儿节点、循环引用或超出授权范围的节点；
- 对外响应只暴露页面需要的树节点模型，不直接返回持久化实体。

#### 推荐调用结构

```text
DeviceGroupTreeController
  → DeviceGroupTreeQuery(rootId, maxDepth)
  → DeviceGroupTreeApplicationService
    → 解析当前用户数据范围
    → 校验根节点可见性与最大深度
    → DeviceGroupRepository.findVisibleTreeNodes(...)
    → TreeAssembler 组装并检测异常关系
    → DeviceGroupTreeResponse 转换
```

#### 完整正确示例

```java
public DeviceGroupTreeResponse queryTree(DeviceGroupTreeQuery query, UserContext context) {
    int depth = Math.min(query.maxDepthOrDefault(), 5);
    var scope = groupScopeProvider.resolve(context);

    if (query.rootId() != null && !repository.isVisible(query.rootId(), scope)) {
        throw new AccessDeniedException("ROOT_NOT_VISIBLE");
    }

    var nodes = repository.findVisibleTreeNodes(query.rootId(), scope, depth);
    var tree = treeAssembler.build(nodes, depth);
    return DeviceGroupTreeResponse.from(tree);
}
```

```java
public DeviceGroupTree build(List<DeviceGroupNodeRecord> records, int maxDepth) {
    var byId = records.stream().collect(toMap(DeviceGroupNodeRecord::id, identity()));
    var roots = new ArrayList<DeviceGroupNode>();
    for (var record : records) {
        if (record.parentId() == null || !byId.containsKey(record.parentId())) {
            roots.add(toTreeNode(record, byId, maxDepth, new HashSet<>()));
        }
    }
    return new DeviceGroupTree(roots);
}
```

查询条件、数据范围、最大深度和排序均由后端控制；组装器在当前路径中检测循环引用，并将异常节点记录为可诊断问题或按既定业务规则拒绝请求。数据库字段如 `parent_id`、内部状态和审计字段不直接穿透至公开响应。

#### 错误示例

```java
public List<DeviceGroupEntity> tree(Long rootId) {
    return repository.findAllChildren(rootId);
}
```

问题：调用方可传任意根节点，查询没有数据范围和深度上限；默认递归读取可能扫全表或造成资源耗尽；持久化实体直接暴露，循环关系与孤儿节点也没有处理语义。

#### 验证步骤与预期结果

1. 使用无权访问的根节点查询，预期返回明确的无权限或不可见结果，且不泄露节点存在性之外的内容。
2. 传入超过上限的深度，预期按服务端上限拒绝或截断，并保留明确行为说明。
3. 构造包含循环引用的测试数据，预期不会无限递归；系统按既定规则记录异常或拒绝该结构。
4. 使用不同数据范围的用户查询，预期树中不包含超出授权范围的节点，且不能通过子节点反推隐藏父节点。
5. 检查公开响应，预期只包含已定义的节点标识、名称、排序和子节点字段，不含持久化内部字段。

#### 人工确认点

- 根节点可见性不足以覆盖的继承、跨组织或共享节点规则；
- 深度、节点数和查询耗时的上限及超限后的业务处理方式；
- 循环引用、孤儿节点和多个根节点属于数据修复、查询降级还是请求失败；
- 树形公开模型中允许展示的字段，以及节点隐藏后的用户体验。

### 受控缓存与并发更新

**适用任务**：数据访问、外部调用、异步与批处理  
**关联规则**：BE-027、BE-037；跨主题参见 DATA-009、DATA-010  
**示例级别**：完整示例

#### 场景目标

读取设备能力配置时使用缓存降低热点查询压力，同时保证数据库仍是事实来源；配置更新以持久层版本条件处理并发，提交后可靠触发缓存失效。此例允许短时读取旧配置，不承诺缓存与数据库立即一致；要求读取最新配置的业务路径直接查询事实来源。

#### 输入条件

- 设备能力配置以数据库记录为最终事实来源；
- 读取是高频操作，业务允许短时旧值；示例缓存有效期为 30 秒，单次回源等待不超过 2 秒；
- 更新必须按旧版本条件写入数据库，并在同一本地事务中记录待执行的缓存失效；
- 缓存不可用时业务应能降级到事实来源，不能把缓存当作唯一数据；
- 缓存未命中时的回源并发有上限；不得为减少击穿而在业务服务中持锁等待数据库或缓存网络调用。

#### 推荐调用结构

```text
DeviceCapabilityQueryService
  → DeviceCapabilityCachePort 集中管理键与有效期
  → 命中：在允许旧值的路径返回有效缓存
  → 未命中或缓存不可用：通过有容量上限的回源器读取数据库
  → 在允许的情况下写入带版本和有效期的缓存

DeviceCapabilityUpdateService
  → 按旧版本条件更新数据库事实，并检查影响行数
  → 同一本地事务登记待失效记录
  → 事务提交后由工作者删除缓存；失败保留记录并重试
```

#### 完整正确示例

```java
public DeviceCapabilityConfig get(DeviceId deviceId) {
    var cached = cachePort.readIfAvailable(deviceId);
    if (cached.isPresent() && cached.get().isUsable(clock.instant())) {
        return cached.get();
    }
    var value = boundedLoader.load(deviceId, Duration.ofSeconds(2), () -> {
        var source = repository.findRequired(deviceId);
        return DeviceCapabilityConfig.from(source, clock.instant());
    });
    cachePort.putIfNewer(deviceId, value, Duration.ofSeconds(30));
    return value;
}

// 控制命令或其他要求最新配置的路径不使用上面的缓存读取方法。
public DeviceCapabilityConfig getCurrent(DeviceId deviceId) {
    return DeviceCapabilityConfig.from(repository.findRequired(deviceId), clock.instant());
}

@Transactional
public void update(UpdateCapabilityCommand command) {
    int changed = repository.updateIfVersion(command.deviceId(), command.expectedVersion(), command);
    if (changed != 1) {
        throw new ConcurrentCapabilityModificationException(command.deviceId());
    }
    invalidationOutbox.record(command.deviceId(), command.expectedVersion() + 1);
}

public void invalidateAfterCommit(CacheInvalidation event) {
    cachePort.evict(event.deviceId());
    invalidationOutbox.markDelivered(event.id());
}
```

`updateIfVersion` 必须在数据库中以设备标识和旧版本为条件更新并递增版本；失效记录与数据修改一起提交，提交失败时两者均不生效。工作者只处理已提交记录，缓存删除失败时保留待执行记录并重试；重复删除应当无害。缓存键、版本、有效期和不可用时的回源逻辑集中在 `cachePort`，`boundedLoader` 限制并发回源和等待，容量耗尽时明确失败而不是无限排队；超时的在途回源不得继续向缓存写入。即使按版本比较写缓存，提交前开始的回源仍可能在失效后写入旧值，因此此方案只保证受有效期与在途回源时长约束的旧值窗口，不保证提交后立即读到新值。不能接受该窗口的路径必须绕过缓存并读数据库，不能只把 TTL 调短就宣称强一致。

#### 错误示例

```java
public Config get(String id) {
    return cache.get("config:" + id).orElseThrow();
}

public void update(Config value) {
    synchronized (value) {
        remoteClient.notifyChanged(value);
        repository.save(value);
        cache.put("config:" + value.id(), value);
    }
}
```

问题：缓存成为唯一来源，缓存丢失即业务失败；缓存键散落且没有版本和失效策略；本地对象锁不可跨实例协调，锁内执行外部调用，数据库更新失败时缓存可能仍是新值。

#### 验证步骤与预期结果

1. 缓存命中且未过期，允许旧值的读取路径返回缓存值；要求最新配置的路径直接读数据库，并能识别版本。
2. 缓存缺失或不可用时，预期在回源容量和超时约束内读取数据库；数据库也不可用时返回明确失败，不把故障当作配置不存在。
3. 多实例同时读取热点键，预期回源并发和等待有上限；容量耗尽时明确失败，不无限创建线程或排队。
4. 并发更新同一设备，预期只有一个旧版本条件写入成功；数据库回滚时不生成已提交的失效记录。
5. 模拟缓存删除失败、工作者重启和旧值回填与删除交错，预期失效记录可重试、旧值不超过约定可见窗口，不能把缓存命中当作立即一致的证据。
6. 更新后由要求最新配置的路径读取，预期取得数据库新版本；若业务还需外部通知，按异步副作用规则另行处理，不混入本地事务或缓存失效成功判定。

#### 人工确认点

- 哪些读取允许短时旧值，哪些必须绕过缓存；可接受的最大旧值窗口及回源超时；
- 缓存键、版本、有效期、负缓存、失效重试和容量策略；
- 数据库版本冲突、失效记录清理和缓存故障时的降级结果；
- 若另有业务确需使用锁，锁对象、顺序、持有时间和释放责任必须单独满足 `BE-041`；
- 缓存和回源依赖故障时允许的业务降级范围。
