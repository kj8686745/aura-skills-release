## 一、规则

### AURA-BASE-BE-028：异常必须保留可定位信息

**必要性**：必须

后端异常处理应保留定位问题所需的业务场景、请求标识、关键对象标识和失败原因。

不得吞掉异常、只打印无意义文本、只返回空结果，也不得把内部堆栈、内部类名、内部地址或敏感信息直接暴露给用户或外部系统。

**为什么需要**：异常信息既要支持定位，也要避免把内部实现和敏感数据暴露给调用方。

**正确写法**：记录业务场景、请求标识、关键对象标识和原始原因，向外转换为稳定的公开错误。

**错误写法**：`catch (Exception e) { log.error("失败"); return null; }`，或把完整堆栈直接返回前端。

**判断要点 / 验证方式**：异常是否保留原因链和定位上下文；公开响应是否隐藏内部实现和敏感信息；触发业务失败、外部失败和系统异常，检查日志与公开响应是否分别符合要求。

**例外**：开发环境可以增加调试信息，但不得把调试堆栈作为公开契约。

### AURA-BASE-BE-029：日志应当区分业务结果和系统故障

**必要性**：应当

后端日志应区分正常业务失败、参数问题、权限拒绝、外部依赖失败、系统异常和数据异常。

不得把所有失败都记录为系统错误，也不得在关键失败路径没有日志。日志字段、敏感信息处理和 TraceId 要求由 `BASE-09` 进一步定义。

**为什么需要**：区分业务失败和系统故障，才能避免错误告警、遗漏故障或重复处理。

**正确写法**：参数不合法记录业务失败，权限拒绝记录安全结果，外部超时记录依赖失败，未预期异常记录系统故障。

**错误写法**：所有异常都用同一错误级别，或者关键失败路径完全没有日志。

**判断要点 / 验证方式**：日志分类是否与结果一致；是否包含必要关联信息；是否泄露密码、令牌和敏感数据；分别触发业务失败、权限失败、外部失败和系统异常，检查日志级别、字段和 TraceId。

**例外**：高频且预期的业务拒绝可以限流或采样，但不能影响必要审计和故障定位。

### AURA-BASE-BE-030：上下文必须按公开契约传递

**必要性**：必须

涉及身份、租户、权限、组织、TraceId、请求来源和调用链路的后端代码，必须按 AURA 公开契约传递上下文。

不得在代码中写死用户、租户、权限、TraceId 或环境地址，也不得伪造、丢弃或覆盖必要上下文。完整安全要求归入 `BASE-07`。

**为什么需要**：上下文决定请求的身份、数据范围和调用链路，丢失或伪造会造成越权、错误归属和无法追踪。

**正确写法**：从公开上下文对象读取身份、租户、权限和 TraceId，并在异步或外部调用边界按契约传递。

**错误写法**：使用固定用户 ID、默认租户、硬编码 TraceId，或在异步线程中直接丢弃原请求上下文。

**判断要点 / 验证方式**：上下文来源是否可信；跨线程、消息和外部调用是否正确传递；是否存在覆盖和伪造；使用不同用户、租户和异步链路测试上下文隔离；人工确认公开契约和敏感字段处理。

**例外**：系统级后台任务可以没有用户上下文，但必须使用明确的系统身份和任务标识。

### AURA-BASE-BE-042：配置和代码职责必须分离

**必要性**：必须

环境差异、可调整参数和外部地址应通过公开配置机制提供；业务规则和安全边界不得被任意配置覆盖。不得在代码中写死环境地址、密钥、租户标识或运行开关。

**为什么需要**：配置和代码职责清晰，才能安全适配环境变化，避免敏感信息和业务边界被随意修改。

**正确写法**：通过类型化配置读取地址和可调参数，代码保留业务规则、默认安全值和校验。

**错误写法**：在代码中写死生产地址、密钥、租户 ID，或用配置开关关闭权限校验。

**判断要点 / 验证方式**：配置是否可追溯、可校验；安全边界和核心业务规则是否不会被任意配置覆盖；检查配置来源、敏感信息处理和不同环境启动结果；人工确认配置变更影响。

**例外**：测试夹具可以使用固定值，但不得进入正式配置和生产代码。

### AURA-BASE-BE-043：依赖版本和使用范围应当可追溯

**必要性**：应当

后端直接使用的框架、库、Starter 和 AURA 能力依赖必须能够追溯其版本和用途。不得引入未使用依赖、在多个模块重复声明冲突版本，或直接使用未公开的传递依赖。

**为什么需要**：可追溯依赖可以控制升级、漏洞修复和兼容风险。

**正确写法**：在统一依赖管理中声明版本，记录直接用途，并通过公开能力入口使用依赖。

**错误写法**：复制传递依赖版本、引入未使用库，或直接调用未公开传递依赖中的内部类。

**判断要点 / 验证方式**：版本来源、用途、兼容范围和升级责任是否明确；执行依赖树、漏洞和重复版本检查；人工确认直接依赖和公开性。

**例外**：临时调试依赖只能在试验分支使用，不得进入正式交付。

### AURA-BASE-BE-044：公共工具应当有稳定语义

**必要性**：应当

抽取公共工具、基类或扩展方法前，应确认其输入、输出、异常和适用范围稳定。不得把单一业务逻辑过早抽成名称含义不清的 `Util`、`Helper` 或万能基类。

**为什么需要**：过早公共化会把局部业务耦合扩散到多个模块，形成难以修改的万能工具。

**正确写法**：确认多个调用方拥有相同语义后，再抽取命名明确、输入输出稳定的公共能力。

**错误写法**：把单一业务校验放入 `CommonUtil`，或使用一个基类承载无关业务扩展。

**判断要点 / 验证方式**：调用方是否共享同一语义；工具的异常、边界和适用范围是否稳定；人工检查调用方和语义一致性；通过公共工具测试验证边界行为。

**例外**：纯技术性、无业务语义的通用工具可以直接复用，但仍需有清晰命名和文档。

### AURA-BASE-BE-045：注释应解释约束而非重复代码

**必要性**：应当

注释应说明业务原因、边界条件、兼容限制和不能改变的约束。不得用过时注释代替清晰命名，也不得保留与实现不一致的示例和说明。

**为什么需要**：有价值的注释解释“为什么不能改”，而不是重复代码已经表达的“做了什么”。

**正确写法**：说明状态转换限制、兼容原因、时区约束、性能边界或外部协议限制。

**错误写法**：`// 设置名称` 这类重复代码的注释，或保留已经失效的旧流程说明。

**判断要点 / 验证方式**：注释是否解释约束和原因；是否与当前实现、规范和示例一致；代码审查时核对关键注释；修改行为时同步更新受影响说明。

**例外**：生成代码或外部协议要求的固定注释可以保留，但不得用注释掩盖不清晰的代码。

### AURA-BASE-BE-046：重复逻辑应在稳定后归并

**必要性**：应当

相同业务语义的重复校验、转换、状态判断和异常处理应在确认稳定后归并。归并不得为了减少文件数量而隐藏职责，也不得把不相同的业务规则强行抽象成同一方法。

**为什么需要**：稳定后归并可以减少维护点，但错误抽象会把差异隐藏并扩大修改影响。

**正确写法**：确认多个规则的语义、异常和生命周期一致后，再抽取共享方法或组件。

**错误写法**：仅因为代码相似就合并不同业务的校验，或把所有转换逻辑塞进一个万能方法。

**判断要点 / 验证方式**：重复是否是真正的语义重复；归并后调用方是否仍能理解职责和差异；对归并前后行为做对照测试；人工确认抽象边界和调用方影响。

**例外**：短期重复但语义尚未稳定时可以暂时保留，并记录后续归并条件。

### AURA-BASE-BE-047：代码结构应控制文件和方法规模

**必要性**：应当

文件、类和方法应保持能够被开发者完整理解的规模。过大的实现应按稳定职责拆分；过小且只服务于一个调用点的文件不应机械拆分，避免产生大量无意义跳转。

**为什么需要**：控制规模是为了降低理解和修改成本，不是为了追求文件数量最少。

**正确写法**：按稳定职责拆分过大的类和方法，保留紧密相关的小逻辑，避免无意义的单方法文件。

**错误写法**：一个 Service 包含多个无关业务，或每两三行逻辑就拆成一个只调用一次的类。

**判断要点 / 验证方式**：文件和方法是否能被完整理解；拆分是否形成清晰职责而不是增加跳转；代码审查关注职责、依赖和可测试性；必要时结合构建和测试验证拆分影响。

**例外**：框架约定的入口、配置和适配类可以保持固定结构，但不得借此堆积业务逻辑。

### AURA-BASE-BE-048：测试边界应覆盖业务行为

**必要性**：应当

新增或修改后端功能时，应至少覆盖正常路径、主要失败路径、边界输入和关键状态转换。测试应验证业务行为，不得只验证方法被调用或简单提高覆盖率数字。

**为什么需要**：业务行为测试才能证明规则、状态和失败处理正确，单纯验证方法被调用不能证明结果正确。

**正确写法**：围绕创建、提交、审核、失败、边界输入和状态转换验证输入、输出和持久化结果。

**错误写法**：只断言 Service 被调用一次，或只为提高覆盖率执行没有业务断言的测试。

**判断要点 / 验证方式**：测试是否验证业务结果；是否覆盖主要失败路径、边界条件和关键状态转换；执行单元测试和必要的应用层测试，记录通过、失败和未覆盖项。

**例外**：纯配置或无业务逻辑的变更可以采用静态检查和构建验证，但需说明原因。

### AURA-BASE-BE-049：外部依赖测试不得替代业务测试

**必要性**：禁止

数据库、HTTP、消息和第三方服务的集成测试可以验证适配边界，但不能替代应用用例和业务规则测试。外部依赖不可用时，应能区分代码失败与测试环境失败。

**为什么需要**：外部依赖测试证明适配边界，不代表业务用例和业务规则已经正确。

**正确写法**：用模拟或夹具验证业务流程，用集成测试验证数据库、HTTP、消息和第三方适配；分别记录环境失败和代码失败。

**错误写法**：只启动测试环境并调用一次接口，就认定业务规则和失败路径已经通过。

**判断要点 / 验证方式**：业务测试与集成测试是否分工；外部环境不可用时是否能标识为环境阻断而不是代码通过；分别运行业务测试、适配测试和必要的集成测试，保留测试范围和环境证据。

**例外**：没有可用外部环境时可以先完成隔离测试，但不得把集成验证标记为已通过。

### AURA-BASE-BE-050：交付前必须完成可重复验证

**必要性**：必须

后端变更交付前，应能说明构建、静态检查、单元测试、必要的集成验证和未覆盖项。不得把“本地能启动”或“接口返回一次成功”作为完整验证结论。

**为什么需要**：可重复验证能够让其他人复现交付结论，避免把偶然启动或单次成功误认为完成。

**正确写法**：记录依赖版本、构建命令、静态检查、测试范围、集成条件、结果和未覆盖项。

**错误写法**：只说明“本地已验证”，不提供命令、范围、环境和失败信息。

**判断要点 / 验证方式**：验证是否可重跑；是否区分通过、失败、环境阻断和未验证；未覆盖项是否明确；在干净环境或固定夹具中重复构建和测试，并保留交付证据。

**例外**：无法运行某项验证时必须记录阻断原因和后续责任，不得默认为通过。

## 二、典型开发场景

以下示例用于说明多条规则如何组合，不构成新的接口契约，也不绑定具体框架、目录名或业务模型。

### 异常和失败路径

**适用任务**：后端接口、后端业务用例、外部调用、异常与日志  
**关联规则**：BE-007、BE-011、BE-023、BE-028、BE-029、BE-030、BE-032  
**示例级别**：完整示例

#### 场景目标

处理设备同步用例中的业务校验失败、权限失败、外部依赖失败、系统异常和空值语义，确保错误不会被伪造成成功。

#### 输入条件

- 请求必须携带可识别的身份、租户和 TraceId 上下文；
- 设备不存在、无权限、外部超时和系统异常需要不同结果；
- “未提供”“明确为空”“不存在”和“查询无结果”不能混用；
- 公开响应不能泄露内部堆栈、地址和敏感信息。

#### 推荐调用结构

```text
SyncDeviceController
  → SyncDeviceApplicationService
    → 校验请求和上下文
    → 查询设备
    → 调用公开能力 Client
    → 转换业务结果或明确失败
  → 统一异常处理
  → 按 BASE-05 接口边界返回错误响应 + 关联日志
```

#### 完整正确示例

```java
public SyncResult sync(SyncDeviceCommand command, RequestContext context) {
    context.requireTenant();
    var device = repository.findVisible(command.deviceId(), context.scope())
        .orElseThrow(() -> new DeviceNotFoundException(command.deviceId()));

    try {
        var remote = deviceClient.sync(device.externalId(), context.traceId());
        return SyncResult.success(resultMapper.from(remote));
    } catch (RemoteTimeoutException e) {
        log.warn("device sync timeout", context.traceId(), device.id());
        return SyncResult.pending("REMOTE_TIMEOUT");
    }
}

```

`DeviceNotFoundException` 交由项目统一异常处理；本例按 `BASE-05` 返回 HTTP `404` 和统一 `R<T>` 错误结构，在 `data` 中给出稳定业务错误码与请求标识。业务失败、权限失败、外部超时和系统异常分别表达；日志保留 TraceId 和设备标识，响应不暴露内部异常。对外 OpenAPI 仍须使用 DTO、公开认证和公开数据范围，但不得另造响应外壳。

#### 错误示例

```java
try {
    return deviceClient.rawSync(id);
} catch (Exception e) {
    return ApiResponse.success(null);
}
```

问题：没有上下文和权限边界，直接返回外部原始结果，吞掉所有异常并伪造成功，调用方无法判断是否需要重试。

#### 验证步骤与预期结果

1. 设备不存在，预期返回稳定的业务错误码，不暴露堆栈。
2. 无权限访问其他租户设备，预期返回权限失败且不调用外部服务。
3. 外部调用超时，预期返回明确待处理或失败状态，并记录 TraceId。
4. 外部返回空字段，预期按已定义的空值语义处理，不用空字符串掩盖缺失。
5. 未预期异常，预期由统一异常处理记录并返回通用系统错误。

#### 人工确认点

- 业务失败、权限失败、外部失败和系统异常的公开错误契约；
- 超时后的重试、补偿或待处理策略；
- 空值和缺失字段在请求、存储和响应中的语义；
- 日志中允许记录的标识和敏感字段范围。

### 配置与依赖

**适用任务**：工程结构、后端业务用例  
**关联规则**：BE-042、BE-043、BE-044、BE-045、BE-046、BE-047  
**示例级别**：完整示例

#### 场景目标

为设备同步服务配置外部地址和超时参数，管理依赖版本，抽取稳定公共工具，并控制代码文件规模和注释质量。

#### 输入条件

- 环境地址和超时可以按环境配置；
- 密钥和敏感信息不能写入源码；
- 依赖版本由统一依赖管理维护；
- 公共工具只能抽取稳定且语义一致的逻辑；
- 文件拆分以职责和可理解性为依据。

#### 推荐目录结构

```text
device-sync/
├─ application/DeviceSyncApplicationService.java
├─ infrastructure/client/DeviceClient.java
├─ infrastructure/config/DeviceClientProperties.java
├─ shared/time/BusinessClock.java
└─ pom.xml
```

#### 完整正确示例

```yaml
device:
  client:
    base-url: ${DEVICE_API_URL}
    connect-timeout: 1s
    read-timeout: 3s
```

```java
@ConfigurationProperties("device.client")
public record DeviceClientProperties(
    URI baseUrl,
    Duration connectTimeout,
    Duration readTimeout) {}

public final class BusinessClock {
    public static Instant now(Clock clock) {
        return Instant.now(clock);
    }
}
```

配置负责环境差异，代码负责业务规则和安全校验；公共工具只提供稳定的时间语义；依赖版本在统一管理文件中声明并可追溯。

#### 错误示例

```java
var client = new DeviceClient("http://10.0.0.12:8080", "prod-secret");
```

### 业务行为测试与外部依赖替身

**适用任务**：后端测试交付、后端业务用例、外部调用  
**关联规则**：BE-048、BE-049、BE-050  
**示例级别**：完整示例

#### 场景目标

为“提交设备审核”用例建立可重复的业务行为测试。测试需要验证正常提交、状态不允许、无权限、重复提交和外部消息失败等真实业务结果；数据库、HTTP 或消息替身只隔离外部边界，不能替代应用用例测试。

#### 输入条件

- 用例包含当前状态校验、权限/数据范围校验、状态转换和消息通知；
- 测试需要区分纯业务行为、适配器契约和真实环境联调；
- 外部消息服务可能不可用，测试必须能判断是代码行为失败还是测试环境失败；
- 测试数据应通过明确的夹具或构造方法建立，不能依赖执行顺序和共享脏状态。

#### 推荐测试结构

```text
业务行为测试（默认必需）
  → 使用内存仓储或受控测试仓储
  → 使用可控消息替身
  → 验证输入、状态、权限、结果和副作用

适配器契约测试
  → 验证 HTTP、数据库、消息序列化和错误转换

真实联调/集成测试
  → 在明确环境条件下验证真实服务连接、认证和兼容性
  → 记录环境状态，不把环境失败写成业务代码通过或失败
```

#### 完整正确示例

```java
@Test
void submit_should_transition_state_and_publish_event() {
    var order = fixture.reviewableOrder();
    orderRepository.save(order);

    var result = service.submit(new SubmitReviewCommand(order.id()), userWithPermission());

    assertThat(result.status()).isEqualTo(ReviewStatus.SUBMITTED);
    assertThat(orderRepository.get(order.id()).status()).isEqualTo(ReviewStatus.SUBMITTED);
    verify(eventPublisher).publish(argThat(event ->
        event.type().equals("REVIEW_SUBMITTED") && event.aggregateId().equals(order.id())));
}
```

```java
@Test
void submit_should_reject_when_state_is_not_reviewable() {
    var order = fixture.alreadySubmittedOrder();
    orderRepository.save(order);

    assertThatThrownBy(() -> service.submit(
        new SubmitReviewCommand(order.id()), userWithPermission()))
        .isInstanceOf(BusinessValidationException.class)
        .hasMessage("ORDER_STATE_NOT_REVIEWABLE");
    verifyNoInteractions(eventPublisher);
}
```

```java
@Test
void message_failure_should_be_distinguishable_from_business_failure() {
    var order = fixture.reviewableOrder();
    orderRepository.save(order);
    doThrow(new MessageTransportUnavailable()).when(eventPublisher).publish(any());

    var result = service.submit(new SubmitReviewCommand(order.id()), userWithPermission());

    assertThat(result.status()).isEqualTo(ReviewStatus.SUBMITTED_PENDING_NOTIFICATION);
    assertThat(orderRepository.get(order.id()).status()).isEqualTo(ReviewStatus.SUBMITTED_PENDING_NOTIFICATION);
}
```

业务行为测试断言“状态、结果、权限和副作用”是否符合业务，不只断言某个方法被调用；消息替身只模拟外部不可控边界，不能替代真实消息契约测试。真实联调应另行记录连接、认证、序列化和环境可用性证据。

#### 错误示例

```java
@Test
void should_call_repository_and_publisher() {
    service.submit(command, user);
    verify(repository).save(any());
    verify(publisher).publish(any());
}
```

问题：只验证调用次数，没有验证状态是否允许、用户是否有权限、结果状态、失败路径和消息失败后的业务语义；即使业务结果错误，测试也可能通过。

#### 验证步骤与预期结果

1. 正常提交，预期状态转换、公开结果和事件副作用均正确。
2. 状态不允许、数据不存在和无权限，预期分别得到稳定业务结果，且不产生错误副作用。
3. 重复提交或并发提交，预期按幂等或并发策略返回明确结果。
4. 外部消息不可用，预期能区分业务提交是否成功与通知是否待处理，不把替身异常吞掉为成功。
5. 适配器契约测试覆盖真实请求/响应、错误码和序列化；业务行为测试不依赖外部服务在线。
6. 真实联调失败时，预期报告环境、网络、认证或服务状态，不直接归因于业务代码。

#### 人工确认点

- 该用例必须覆盖的正常、失败、边界和状态转换路径；
- 外部依赖替身允许模拟的范围，以及哪些契约必须通过真实或契约测试验证；
- 业务提交成功但通知失败时的事务、待处理、补偿和用户可见状态；
- 测试数据隔离、并发执行、重试和环境失败证据的归属。
