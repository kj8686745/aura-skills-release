**规范对象**：使用 AURA 开展业务应用、服务、工具和平台工程开发的团队和开发人员

**跨规范边界**：本规范负责异步任务、消息和外部调用的运行行为；本地事务与数据一致性遵循 `BASE-08`，后端代码落点遵循 `BASE-03`，公开请求、响应和错误契约遵循 `BASE-05`，异常日志与链路信息遵循 `BASE-09`。

**本文件内容**：外部调用适配、协议边界、超时、失败转换、重试、资源释放、降级、数据最小化与补偿。

## 二、外部系统集成与调用

### 1. 调用边界与客户端封装

### AURA-BASE-INTEG-001：外部调用必须经过明确的适配边界

**必要性**：必须

业务用例不得在页面、Controller 或多个业务方法中直接拼接外部请求；外部服务、文件接口和第三方 SDK 应通过命名明确的客户端或适配边界访问。调用 AURA 已封装的能力时，按对应能力包使用公开入口，不另造一层无职责的网关。

**为什么需要**：集中封装可以统一认证、超时、错误转换和版本兼容，避免外部协议渗透到业务代码。

**正确写法**：业务用例调用 `DeviceAnalysisClient.analyze(command)`，由客户端负责协议组装和错误转换。

**错误写法**：多个 Service 自行拼接 URL、请求头和 JSON，并各自解释外部状态码。


**判断要点 / 验证方式**：检查业务层是否直接依赖 HTTP、SDK 或文件协议，确认调用经过单一适配边界。

### AURA-BASE-INTEG-002：外部调用必须声明输入、输出和副作用

**必要性**：必须

客户端或适配器必须说明请求输入、返回结果、错误分类、是否产生外部副作用及其幂等方式，不得以通用 `Object` 或无语义布尔值隐藏调用结果。

**为什么需要**：调用方需要知道失败是否可以重试，以及调用是否已经产生外部变化。

**正确写法**：`createTask` 返回任务标识并说明重复请求行为，`queryTask` 只读且可安全重试。

**错误写法**：所有调用都返回 `true/false`，不区分受理、完成、失败和远端已产生副作用。

**判断要点 / 验证方式**：逐项阅读客户端方法和调用说明，确认结果、错误和副作用可被业务层正确处理。

### AURA-BASE-INTEG-003：外部协议不得直接成为内部业务模型

**必要性**：禁止

外部请求、响应和错误模型应在适配边界转换为业务用例可理解的命令、结果和状态；不得让第三方 DTO、SDK 异常或协议字段直接穿透公开接口和不依赖该协议的业务模块。边界内部可以使用 SDK 自身类型，不必为每个字段重复创建同义模型。

**为什么需要**：外部协议变化不应无边界扩散到业务代码和公开接口。

**正确写法**：将远端 `status=processing` 转换为内部 `TaskState.RUNNING`，并保留必要的原始追踪信息。

**错误写法**：Controller 直接返回第三方 SDK 的响应对象和异常消息。

**判断要点 / 验证方式**：检查跨边界类型引用和异常传播，确认协议转换发生在适配层。

### 2. 时间、资源与失败控制

### AURA-BASE-INTEG-004：外部调用必须设置超时和资源上限

**必要性**：必须

网络连接、读取、文件和 SDK 调用必须设置适用的连接/响应超时、响应大小、批量大小或执行时长上限；调用路径还应有总耗时预算，不能只让每次重试各自等待到上限。不得依赖无限等待；本地数据库访问与任务资源边界分别遵循 `BASE-08/11`。

**为什么需要**：外部依赖无响应时，无界等待会占满线程、连接和内存。

**正确写法**：分别配置连接和读取超时，同时限定整个业务调用的总耗时；文件传输限制大小与处理时长，超时后关闭响应流和连接。

**错误写法**：使用默认无限超时，或把远端大文件一次性读入内存。

**判断要点 / 验证方式**：阻断、延迟或增大外部响应，确认调用能够超时退出且资源得到释放。

### AURA-BASE-INTEG-005：调用失败必须转换为稳定的内部结果

**必要性**：必须

外部超时、限流、不可用、认证失败、参数错误和业务拒绝必须转换为稳定的内部异常或结果分类，不得把 URL、堆栈或第三方原始文本直接返回给使用者。

**为什么需要**：稳定的内部错误语义便于调用方处理，也避免泄露内部实现和敏感信息。

**正确写法**：将远端 429 转换为内部“依赖限流”分类并记录是否可重试；远端参数错误先区分调用方输入不合法与本地适配协议错误，分别返回业务校验失败或依赖集成故障。

**错误写法**：把第三方返回的完整 HTML、堆栈或连接地址直接放进接口响应。

**判断要点 / 验证方式**：注入各类外部失败，核对接口结果、日志字段和敏感信息边界。

### AURA-BASE-INTEG-006：重试必须满足安全条件

**必要性**：必须

只有只读、已确认未产生副作用，或远端承诺按同一幂等键去重的调用，才可在错误类别允许时自动重试。发生超时且远端结果不确定时，应先查询结果或复用受远端保证的幂等键；重试必须设置次数、退避和总耗时，不能掩盖确定性错误。

**为什么需要**：对写操作盲目重试可能产生重复订单、重复任务或重复文件。

**正确写法**：查询可在调用预算内有限重试；创建请求在确认远端支持幂等键且始终复用同一键时才按契约重试，业务校验失败直接终止。

**错误写法**：所有 POST 和文件上传失败后无限重试，不判断远端是否已经成功。

**判断要点 / 验证方式**：模拟响应丢失、远端已成功和确定性失败，检查总耗时与重试次数，确认不会重复产生副作用。

### AURA-BASE-INTEG-007：资源必须在成功和失败路径都释放

**必要性**：必须

连接、响应体、文件句柄、临时文件、锁和线程任务必须在正常、异常、超时和取消路径释放或进入明确的生命周期管理，不得依靠进程退出清理。

**为什么需要**：资源泄漏通常在高负载和连续失败时才暴露，会逐步耗尽系统能力。

**正确写法**：使用结构化资源管理关闭响应体，临时文件在任务终态或期限到达后清理。

**错误写法**：异常路径直接 return，未关闭流、连接和临时文件。

**判断要点 / 验证方式**：连续执行成功、失败、超时和取消场景，观察句柄、连接、线程和临时文件是否持续增长。

### 3. 兼容、降级与数据边界


### AURA-BASE-INTEG-008：外部依赖版本必须显式管理

**必要性**：必须

调用方必须明确所依赖的协议、SDK、能力或文件格式版本，并在版本变化时验证字段、错误和行为兼容性。远端有版本选择机制时按其契约显式指定；没有选择机制时记录实际兼容范围，不假设远端默认行为永远不变。

**为什么需要**：远端默认版本变化会在调用方未修改代码时改变行为。

**正确写法**：远端支持版本请求头时显式传入已验证版本；SDK 升级后验证响应解析、错误转换和关键链路，记录所依赖的服务版本范围。

**错误写法**：始终调用 `/latest` 或使用未锁定的 SDK 版本，只验证项目能够构建；远端无版本入口时却在文档中声称已锁定服务版本。

**判断要点 / 验证方式**：切换旧版、当前版和不兼容响应，确认调用方能识别或安全拒绝。

### AURA-BASE-INTEG-009：降级必须保持业务语义正确

**必要性**：必须

外部依赖不可用时，应根据业务选择缓存、排队、只读、默认结果、人工处理或明确失败；不得返回看似成功但无法代表真实业务状态的假数据。

**为什么需要**：错误降级比明确失败更容易造成数据和决策错误。

**正确写法**：设备分析不可用时进入待处理状态并允许查询，不把“未分析”返回为“分析通过”。

**错误写法**：远端超时就返回空列表或成功状态，让前端误以为没有数据或操作已完成。

**判断要点 / 验证方式**：阻断依赖并检查响应、任务状态、日志和后续恢复，确认降级结果不会伪造事实。

### AURA-BASE-INTEG-010：跨边界传递的数据必须最小化

**必要性**：必须

调用外部系统时只传递完成业务目的所需的字段、身份上下文和文件内容；敏感信息、内部标识和无关字段不得因方便调试而全部透传。

**为什么需要**：减少数据泄露、权限扩大和协议耦合风险。

**正确写法**：仅发送设备标识、必要时间范围和经过授权的业务参数，不发送完整用户对象和内部 Token。

**错误写法**：把请求上下文、数据库实体和完整认证信息序列化后直接转发给第三方。

**判断要点 / 验证方式**：检查请求载荷、日志和重试数据，确认字段最小化、敏感信息脱敏且权限边界未扩大。

### AURA-BASE-INTEG-011：外部副作用必须具备结果确认或补偿方式

**必要性**：必须

创建、发送、删除、控制和写入等外部副作用操作，必须定义成功确认、超时不确定、失败和补偿的处理方式；不能把网络超时直接当作失败并盲目重复执行。

**为什么需要**：调用超时可能发生在远端已成功之后，结果不确定是集成系统的常态。

**正确写法**：超时后通过幂等键查询远端结果，无法确认时进入待确认状态或人工处理。

**错误写法**：写操作超时后立即再次创建，不查询原请求是否已生效。

**判断要点 / 验证方式**：在远端成功但响应丢失、远端拒绝和重复请求场景中检查最终结果。

### AURA-BASE-INTEG-012：外部调用必须可追踪到业务操作

**必要性**：必须

外部调用日志应在适用时记录业务关联标识、客户端/操作名、目标版本、耗时、结果分类和链路标识；目标未提供版本信息时记录实际可知的兼容版本，不编造。指标按客户端、操作和结果等低基数字段聚合，业务标识与追踪标识只用于日志或追踪，不作为指标标签；敏感请求内容不得直接记录。

**为什么需要**：只有能够关联业务操作，才能定位是本地逻辑、网络、远端服务还是数据问题。

**正确写法**：日志记录 `taskId`、`traceId`、客户端操作名、耗时、结果分类和重试次数；指标只按客户端操作和结果聚合，必要的响应定位信息仅保存受控摘要。

**错误写法**：只记录“调用失败”，或把完整 Token、文件内容和响应正文写入普通日志。

**判断要点 / 验证方式**：从一次业务请求追踪到外部调用和最终结果，检查字段完整性与敏感信息边界。

### 4. 模块级正例与反例

### 正例：带幂等和结果确认的外部写调用

```text
业务用例
  → IntegrationClient（固定版本、超时、幂等键）
  → 远端返回成功 / 失败 / 超时不确定
  → 超时先查询幂等键结果
  → 无法确认则进入待确认状态，不盲目重复创建
```

该结构隔离了外部协议，控制了资源和重试，并能正确处理“远端已成功但响应丢失”的场景。

### 反例：业务代码直接透传远端协议

```text
Controller 直接调用第三方 SDK
→ 把完整用户对象和 Token 发送出去

→ 默认无限等待
→ 超时后重复创建
→ 原始异常直接返回前端
```

该实现没有调用边界、数据最小化、超时、幂等和结果确认，容易造成泄露与重复副作用。

#### 典型使用场景：设备分析服务的外部写调用

**场景目标**：业务用例通过统一客户端调用外部分析服务，固定已验证的协议版本并控制超时、请求大小和重试；远端已成功但响应丢失时，系统通过幂等键查询结果，不重复创建任务。

**输入条件**：分析请求只包含设备标识、授权范围和必要参数；客户端已配置连接/读取超时、总耗时预算和响应大小上限；远端支持 `idempotencyKey` 与结果查询；返回状态可能为成功、业务拒绝、限流、超时不确定。

**正确调用链**：

```text
业务用例
  → DeviceAnalysisClient（固定版本、最小字段、超时和幂等键）
  → 适配器转换外部请求/响应
  → 成功返回远端 taskId
  → 业务拒绝直接失败，限流/暂态故障按预算退避
  → 超时不确定时查询同一幂等键
  → 无法确认则进入待确认状态并保留补偿入口
  → 关闭响应、文件和临时资源，记录受控摘要
```

客户端返回内部可理解的结果分类，不把第三方 DTO、URL、堆栈或原始异常文本穿透到 Controller。日志记录 `taskId`、操作名、版本、耗时、结果分类和重试次数，指标使用低基数标签；请求和重试数据不包含完整 Token、用户对象或无关字段。

**错误调用链**：Controller 直接调用 SDK；使用默认无限超时；把全部请求上下文和 Token 转发；POST 超时后更换幂等键再次创建；把远端 HTML 和堆栈直接返回前端；异常路径未关闭响应流和临时文件。

**验证步骤与预期结果**：

1. 注入成功、参数拒绝、权限失败、限流、超时和远端已成功但响应丢失，预期均转换为稳定内部结果。
2. 检查重试次数、退避和总耗时，预期确定性错误不重试，超时不确定时只复用同一幂等键并查询结果。
3. 使用超大响应、取消和连续失败，预期响应大小、连接、文件句柄、临时文件和线程任务均受控释放。
4. 审查请求载荷、日志和指标，预期只包含完成业务目的所需字段，不泄露敏感信息，也不使用业务对象作为高基数标签。

### 5. 开发者自检

- 外部调用是否经过明确的客户端或适配器边界；
- 输入、输出、错误和副作用是否有稳定语义；
- 是否设置超时、响应大小、批次和资源上限；
- 失败转换、重试和降级是否符合业务语义；
- 依赖版本是否显式且经过兼容验证；
- 敏感信息和无关字段是否未跨边界传递；
- 外部副作用在超时不确定时是否有查询、补偿或人工处理；
- 调用是否可以关联到业务操作且日志不泄露敏感内容。
