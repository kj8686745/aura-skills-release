# AURA（天玑）基础编码规范：模块服务边界与规模适配

<!-- 规范编号：BASE-02 -->
<!-- 规范版本：0.1.0-draft -->
<!-- 模板版本：基础编码规范模板 v3 -->

**规范对象**：使用 AURA 开展业务应用开发的团队和开发人员

**规范定位**：定义模块、公共模块、服务的公开边界，以及项目规模变化时的架构适配方式；具体前后端实现遵循相应基础编码规范。



## 一、模块与服务边界

### AURA-BASE-ARCH-013：模块必须代表稳定边界

**必要性**：必须

**为什么需要**：以文件数量或习惯拆出的模块没有稳定责任，后续修改仍会跨模块扩散。

模块应基于稳定的业务责任、数据范围、权限范围、独立依赖、生命周期、部署单元或发布范围划分。

不得仅按文件数量、个人习惯、技术名词或预设目录名称机械创建模块。


**正确写法**：按设备领域、数据责任和发布范围划分 `device` 模块，模块拥有稳定的公开入口。

**错误写法**：因为目录文件数量达到十个就机械新增一个模块。

**判断要点 / 验证方式**：检查模块责任、数据范围、依赖和发布边界是否稳定。
### AURA-BASE-ARCH-014：模块只能通过公开入口交互

**必要性**：必须

**为什么需要**：跨模块依赖内部实现会把对方的重构变成自己的兼容问题。

模块之间只能通过明确的公开接口、公开类型、公开事件或公开服务入口交互。

不得直接引用其他模块的内部文件、内部类、内部状态、内部数据库结构、内部缓存键或未公开的运行机制。公开入口至少应说明输入、输出、前置条件和失败语义。


**正确写法**：模块通过公开的 `DeviceQueryApi` 和事件契约交互。

**错误写法**：跨模块直接引用对方内部 Entity、Mapper、缓存键或数据库表。

**判断要点 / 验证方式**：检查跨模块 import、依赖和调用入口，确认只使用公开契约。
### AURA-BASE-ARCH-015：模块不得形成循环依赖

**必要性**：禁止

**为什么需要**：循环依赖使模块无法独立构建、替换或判断变更影响。

业务模块、公共模块、技术模块和服务之间不得形成循环依赖。

发现互相调用时，应重新判断是否应该合并边界、抽取稳定契约、采用事件解耦或修正依赖方向。不得通过中转类、全局变量或聚合入口掩盖循环依赖。


**正确写法**：将相互依赖的两个模块合并边界，或抽取稳定接口后由实现单向依赖。

**错误写法**：通过静态变量和中转类隐藏 A 模块调用 B、B 模块再调用 A。

**判断要点 / 验证方式**：生成依赖图并确认不存在循环路径。
### AURA-BASE-ARCH-016：公共模块必须具有真实公共语义

**必要性**：必须

**为什么需要**：把单一业务或尚不稳定的代码提前抽到公共模块，会让其他调用方被迫接受其业务假设。

公共模块只有在多个模块确实共享同一语义，且责任、输入、输出和变更影响明确时才可以建立。

只被一个业务使用的逻辑、单一业务规则、尚未稳定的重复代码和依赖大量业务上下文的代码，不得提前放入公共模块。


**正确写法**：多个模块共同使用稳定的 `PageRequest` 语义后，抽取为公共分页类型。

**错误写法**：只被一个业务使用的审批规则被提前放入 `common` 工具包。

**判断要点 / 验证方式**：检查调用数量、语义一致性、输入输出和维护责任。
### AURA-BASE-ARCH-017：公共模块不得反向依赖业务模块

**必要性**：禁止

**为什么需要**：公共模块依赖具体业务后，原本无关的业务也会承受该模块的依赖和发布影响。

公共模块、基础模块和通用组件不得依赖具体业务模块、业务流程、业务数据或业务页面。

业务模块可以依赖公共模块，但公共模块不能为了服务某个业务而吸收该业务实现。


**正确写法**：公共模块只依赖 JDK、框架公开接口和稳定通用类型，不引用订单或设备业务包。

**错误写法**：`common` 模块直接依赖 `order-service` 并调用其业务方法。

**判断要点 / 验证方式**：检查公共模块依赖树，确认没有具体业务模块和业务数据引用。
### AURA-BASE-ARCH-018：多模块项目必须区分模块职责

**必要性**：必须

**为什么需要**：职责和数据责任不清时，不同模块容易重复实现规则或争用同一份状态。

多模块工程中的每个模块都应能说明自己的业务或技术职责。适合建立独立模块的依据包括：

- 可以独立构建或发布；
- 有独立依赖；
- 有独立权限或数据范围；
- 有独立生命周期；
- 存在稳定的跨模块消费者。

没有稳定边界的短小模块应优先归并。


**正确写法**：多模块项目分别明确设备、告警和用户模块的职责、数据所有权和交付边界。

**错误写法**：所有模块都直接读写同一张业务表并自行解释状态。

**判断要点 / 验证方式**：检查模块清单、依赖关系、数据所有权和交付方式。
### AURA-BASE-ARCH-019：跨服务调用必须经过公开契约

**必要性**：必须

**为什么需要**：跨服务读取内部表或缓存会绕过服务自身的行为和兼容约定。

服务之间只能通过公开 API、公开事件或已约定的服务契约交互。

不得直接访问其他服务的数据库、内部表结构、缓存键或内部代码，也不得透传对方内部异常和未承诺的内部状态。请求、响应、错误、超时和失败语义由对应公开契约说明。


**正确写法**：服务间使用版本化 DTO、Feign 接口或事件契约进行调用。

**错误写法**：服务 A 直接读取服务 B 的数据库表或内部缓存。

**判断要点 / 验证方式**：检查客户端、事件和数据访问路径，确认调用基于公开契约。
### AURA-BASE-ARCH-020：服务边界不得按技术名词机械划分

**必要性**：禁止

**为什么需要**：按技术层拆服务会让一个业务动作跨越多个服务，增加调用和故障处理成本。

不得仅因为存在“用户”“订单”“数据”“公共”“服务”等名称就创建独立服务。

服务边界应结合业务责任、数据边界、部署需求、独立扩展、故障影响和实际消费者判断。

**正确写法**：按业务责任、数据所有权和变更影响划分服务，而不是按 Controller、Mapper 等技术名词拆分。

**错误写法**：把所有 Controller 集中成一个服务、所有 Mapper 再拆成另一个服务。

**判断要点 / 验证方式**：检查服务边界是否能说明业务责任、数据范围和变更影响。

## 二、项目规模适配

### AURA-BASE-ARCH-027：小型项目可以合并层级但不得混淆职责

**必要性**：可以  
**适用条件**：采用合并层级时，仍必须保持规则正文列出的职责边界。

**为什么需要**：小项目不必承担完整分层的文件成本，但仍需保留可识别的职责和公开边界。

小型项目可以将职责相近的层级合并在较少文件或模块中，但必须满足：

- 每个入口和代码单元仍有清晰职责；
- 业务规则、协议处理和技术实现不会互相混杂；
- 后续拆分时不需要重写公开契约；
- 公共能力和内部实现仍保持边界。


**正确写法**：小型服务可将用例和领域规则放在同一模块，但仍保持入口、业务和数据访问职责分开。

**错误写法**：为了减少目录，把 Controller、Repository 和数据库配置混成一个类。

**判断要点 / 验证方式**：检查合并后的依赖和职责，确认公开边界未被打破。
### AURA-BASE-ARCH-028：复杂项目应按影响范围细化边界

**必要性**：应当

**为什么需要**：复杂项目若继续共享巨型模块，一处变更会牵动无关领域的测试和发布。

当项目出现多个业务领域、多个部署单元、独立权限、独立数据、复杂状态或独立发布周期时，应细化模块和服务边界。

细化必须以真实变更影响为依据，不得复制没有实际职责的空壳层级。

**正确写法**：复杂项目按权限、数据、外部依赖、测试和发布影响拆分模块，并为每个模块维护公开入口。

**错误写法**：大型项目所有业务共享一个巨型模块，修改任意功能都需要全量回归。

**判断要点 / 验证方式**：检查模块影响范围、独立测试和发布能力是否真实存在。

## 三、项目架构 Profile

项目应根据真实复杂度选择组织方式，而不是机械采用完整分层：

| Profile | 适用项目 | 必须保持的共同边界 | 允许的适配 |
| --- | --- | --- | --- |
| 简单应用 | 单体、少量功能、简单 CRUD 或短生命周期项目 | 业务职责与技术实现分开；公开内容与内部实现分开 | 可以合并相近层级和小范围文件 |
| 标准应用 | 多功能、持续迭代、多个消费者的业务系统 | 入口、业务用例、业务规则、技术适配和公开契约可识别 | 可以将简单职责合并，但不能跨边界混写 |
| 复杂应用 | 多业务模块、多服务、复杂状态或独立发布项目 | 模块、服务、公开契约、数据边界和依赖方向清晰 | 只能在不改变边界语义的前提下合并 |

项目规模、复用范围或发布边界发生变化时，应重新评估 Profile。

## 四、模块与服务依赖允许矩阵

下表只表达模块与服务之间共同适用的边界关系，具体对象名称由对应前后端规范定义：


| 代码边界 | 可以依赖 | 禁止直接依赖 |
| 公共模块边界 | 稳定公共契约和基础能力 | 具体业务模块、单一业务流程、业务数据库结构 |
| 服务边界 | 公开 API、公开事件和服务契约 | 对方数据库、缓存键、内部代码和内部异常 |

## 五、跨模块关系示例

### 2. 正确的跨模块关系

```text
模块甲
  → 模块乙公开契约
    → 模块乙内部实现
```

模块甲不能跳过公开契约直接进入模块乙的内部实现。

### 3. 错误的共同结构

```text
业务入口
  → 直接访问数据库
  → 直接调用外部客户端
  → 读取其他模块内部状态
  → 透传内部模型和异常
```

这种结构同时破坏职责边界、依赖方向、公开契约和模块独立性。

## 六、开发者自检

新增或调整模块、服务和公开边界时，至少确认：

- 模块之间是否通过公开入口交互；
- 是否存在循环依赖或公共模块反向依赖业务模块；
- 公共抽取是否具有真实稳定语义；
- 跨服务是否绕过公开契约访问数据库、缓存键或内部代码；
- 项目规模变化后，当前 Profile 是否仍能控制变更影响；
