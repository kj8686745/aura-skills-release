**规范对象**：使用 AURA 开展业务应用、服务、工具和平台工程开发的团队和开发人员

**规范目标**：要求研发人员在提交联调、提测或交付前，对自己负责的代码和变更完成与风险匹配的自测，并清楚说明已验证和未验证的范围。

**边界说明**：本文件负责研发自测范围、测试层级、核心行为、外部依赖、公开契约和关键链路；不替代测试部门的系统测试、专项测试、验收测试或测试管理流程。静态、性能、兼容与数据要求见同目录其他文件，自测证据和交付结论见同目录其他文件。

## 一、研发自测范围与层级

### AURA-BASE-SELF-001：自测范围必须由业务风险和变更范围决定

**必要性**：必须

研发人员必须依据本次变更实际影响的业务行为、接口、数据、权限、异步链路和外部依赖确定自测范围与层级；未覆盖的相关风险须说明原因。范围可记录在已有任务、变更或自测结果中，不要求为每次改动另建计划文件。不得只因为代码能够编译就认定变更已验证。

**为什么需要**：测试范围必须覆盖真正可能受影响的行为，而不是只覆盖修改过的文件。

**正确写法**：接口新增租户过滤时，同时验证单条查询、批量导出、权限失败和跨租户访问。

**错误写法**：只运行修改类的单元测试，不验证接口、数据范围和调用方行为。

**判断要点 / 验证方式**：从变更内容反查受影响的行为，核对已执行的验证与未验证原因；不以是否另建计划文件判断自测充分性。

### AURA-BASE-SELF-002：核心业务规则必须具备可重复的行为自测

**必要性**：必须

状态转换、资格判断、金额计算、幂等、并发冲突和失败恢复等核心规则必须通过可重复测试表达输入、行为和结果。

**为什么需要**：核心规则发生回归时，只有行为测试才能确认业务结果仍然正确。

**正确写法**：测试名称明确前置状态、执行动作和预期结果，例如 `approveDevice_whenVersionConflict_returnsConflictResult`，断言实际接口契约中的冲突结果和数据未被覆盖。

**错误写法**：只测试方法被调用，或测试名称为 `test1`、`shouldWork`，没有业务断言。

**判断要点 / 验证方式**：执行正常、边界、重复和失败场景，检查断言是否验证业务结果而非内部调用次数。

### AURA-BASE-SELF-003：外部依赖必须与业务行为分层自测

**必要性**：必须

对本次变更触达的外部服务、数据库、消息、文件和能力包边界，必须按风险选择业务规则替身测试、适配器或组件测试，以及需要真实依赖才能确认的集成验证；不要求每项改动机械跑齐所有层级。需要真实验证而尚未执行时，必须标为未验证，Mock 通过不能替代真实契约或链路结果。

**为什么需要**：模拟对象只能证明本地代码按预设响应运行，不能证明真实协议、权限、超时和数据格式可用。

**正确写法**：修改远端客户端时，用受控响应验证错误转换，再在可用的测试环境核对真实请求与响应；环境尚不可用时记录真实链路未验证，不把替身结果写成联调通过。

**错误写法**：所有外部调用都 Mock，发布前没有一次真实接口或消息链路验证。

**判断要点 / 验证方式**：核对本次实际触达的边界、替身与真实依赖各自证明了什么，以及未完成的真实验证是否如实标注。

### AURA-BASE-SELF-004：公开契约变更必须进行契约自测

**必要性**：必须

HTTP API、WebSocket、事件、文件格式、公开组件和跨模块 DTO 变更必须验证本次受影响的提供方与调用方对请求、响应、错误和版本行为的理解一致；存在旧调用方或已发布格式时，还须验证约定的兼容路径。全新且没有旧消费者的契约不要求虚构旧版场景。

**为什么需要**：契约测试能够提前发现字段、状态、空值和错误语义不一致。

**正确写法**：修改已使用的接口字段时，按识别到的旧版与当前调用方分别验证解析和服务端响应；新增接口则验证首批实际调用方与服务端契约。

**错误写法**：只验证服务端 Controller 返回 200，不验证调用方解析、错误码和空数据行为。

**判断要点 / 验证方式**：执行本次命中的契约样例，核对字段、错误和消费者解析；仅在存在已发布消费者时检查兼容结果。

### AURA-BASE-SELF-005：关键业务链路必须自测完整生命周期

**必要性**：必须

涉及异步任务、消息、文件、外部服务或人工处理的关键流程，必须覆盖受理、处理中、成功、失败、重试、取消、超时和恢复等适用状态。

**为什么需要**：单个接口成功不能证明完整业务链路在失败和恢复时仍然可控。

**正确写法**：异步设备审核验证受理响应、任务状态查询、重复提交、依赖超时和最终失败结果。

**错误写法**：只验证消息成功发送，不验证消费失败、重试和任务最终状态。

**判断要点 / 验证方式**：按状态机执行主路径和失败路径，确认每个终态都有可解释结果。

### AURA-BASE-SELF-006：自测层级必须与被验证对象匹配

**必要性**：必须

必须根据被验证对象选择单元、组件或适配器、契约、集成及端到端等适用层级；不要求一次局部改动执行全部层级。不得用低层级替身测试替代必须经过真实边界才能发现的问题，也不得把可在低层稳定验证的规则全部堆到端到端测试中。

**为什么需要**：测试层级与被验证对象不匹配，会造成测试运行缓慢、定位困难，或把真实环境问题隐藏在替身之后。

**正确写法**：金额计算在单元测试中验证，数据库映射在集成测试中验证，跨服务消息和状态流转在测试环境中验证。

**错误写法**：只用 Service 单元测试验证数据库事务、消息投递和远程服务超时，或所有规则都依赖一条难以定位的端到端脚本。

**判断要点 / 验证方式**：逐项核对被测对象、测试层级、替身边界和执行环境，确认每类风险由能够观察该风险的测试承担。

## 二、典型使用示例：设备审核接口变更的自测范围

**场景目标**：设备审核接口新增租户过滤和版本条件更新时，研发人员依据变更影响选择测试层级，验证核心行为、公开契约、权限边界和异常结果，并如实区分真实联调未完成的部分。

**输入条件**：接口已被前端和异步任务调用；变更触达 Controller、应用用例、数据访问和权限上下文；测试数据库可用，真实消息环境暂不可用。

**正确自测链**：

```text
单元层：验证版本冲突、租户条件和错误分类
  → 数据访问/组件层：验证条件更新、事务和零行结果
  → 契约层：验证请求、响应、空值和冲突错误
  → 测试数据库：验证跨租户、重复请求和最终数据状态
  → 真实消息链路未执行：标记阻断并说明原因
```

自测记录关联源码版本、配置、测试数据、命令和报告位置。Mock 只证明本地分支行为；数据库组件测试证明持久化边界；消息链路未验证不能写成联调通过。验证范围包括合法审核、无权限、跨租户、过期版本、重复提交和对象不存在，并明确未覆盖的消费者或环境。

**错误自测链**：只运行 Service Mock 并断言方法被调用；不验证数据库最终状态和调用方解析；因构建成功就标记全部通过；把消息 Mock 结果写成真实消息联调通过。

**验证步骤与预期结果**：

1. 运行正常、权限拒绝、跨租户、版本冲突、重复提交和对象不存在用例，预期行为和接口契约一致。
2. 核对提交号、环境、数据范围、命令和报告，预期可反向定位本次代码版本。
3. 检查受影响前端和异步调用方，预期已验证的消费者范围清楚，未覆盖范围写明原因。
4. 对真实消息环境不可用的部分标记“阻断”，不把替身测试写成真实链路通过。

## 三、开发者自检

- 是否从本次变更反查业务行为、接口、数据、权限、异步和外部依赖的实际影响范围；
- 核心业务规则是否有可重复的正常、边界、重复和失败行为断言；
- 单元、组件、契约及真实边界验证是否分别承担能观察到的风险；
- 替身测试与真实依赖验证的结论是否分开，未执行的必需验证是否明确标为未验证或阻断；
- 受影响的提供方、调用方和适用状态生命周期是否均已覆盖。
