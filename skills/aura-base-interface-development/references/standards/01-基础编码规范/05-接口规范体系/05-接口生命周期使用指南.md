# AURA（天玑）接口生命周期使用指南

> 本指南面向业务应用开发者，说明一个接口从提出到退出的使用顺序。接口设计规则以《01-接口规范》为准，接口契约填写以《03-接口文档模板》为准。

## 一、接口生命周期总览

```text
需求确认
  → 接口边界识别
  → 契约设计
  → 需要时关联详细设计
  → 契约冻结
  → 后端实现与测试
  → 前端/调用方接入
  → 联调
  → 发布
  → 运行维护
  → 兼容变更
  → 废弃迁移
  → 删除退出
```

同一业务模块的相关接口沿用一份模块接口文档，逐接口维护明细；不得由前端、后端分别维护互相独立的定义。

## 二、阶段一：需求确认

在决定新增接口前，先明确：

- 谁提供能力；
- 谁调用能力；
- 调用属于内部业务、服务间还是对外 OpenAPI；
- 是否已有可复用接口；
- 是否需要同步、异步、分页、批量或文件能力；
- 是否涉及权限、租户、组织和数据范围。

如果已有接口能够满足需求，应优先复用，不得为同一能力重复创建语义相同的接口。

## 三、阶段二：契约设计

使用接口文档模板完成：

1. 接口编号、名称、版本、提供方和调用方；
2. 方法、路径、请求头和参数；
3. 成功响应、错误响应、空值和分页；
4. 认证、租户、权限和请求标识；
5. 幂等、并发、超时和重试；
6. 适用的兼容、变更和恢复方式；
7. 正常和异常联调场景。

接口文档必须先确定业务语义，再开始提供方与调用方实现。字段和错误语义不得留到联调阶段临时决定。

## 四、阶段三：详细设计关联与契约冻结

任务需要技术详细设计时，接口文档应关联对应设计；局部且不需要独立技术详细设计的接口变更，直接在接口文档中记录契约与影响。详细设计说明内部技术实现，接口文档说明调用方可见契约。

契约冻结前，提供方和调用方共同确认：

- 路径和 HTTP 方法；
- 请求和响应字段；
- 错误码和状态码；
- 权限、租户和数据范围；
- 幂等、超时和重试；
- 版本和兼容方式。

冻结后发生变化时，必须记录变更内容和影响方，不能只修改代码或只修改文档。

## 五、阶段四：开发实现

后端按接口文档实现公开 Controller、请求模型、响应模型、参数校验、权限校验、业务处理和异常映射；不得将数据库实体、内部异常或第三方原始响应直接作为公开契约。

前端或调用方按接口文档建立领域 API、请求类型、响应类型、错误处理和页面状态；页面和组件不得直接拼接接口地址或依赖内部响应字段。

开发过程中发现契约需要变化时，应先更新接口文档及受影响的技术详细设计，再同步修改提供方与调用方实现。

## 六、阶段五：联调

联调按以下顺序进行：

1. 提供方完成认证、权限、参数、业务和异常场景自测；
2. 调用方完成领域 API、类型和页面状态接入；
3. 双方确认服务入口、网关路径、前端调用路径和请求上下文；
4. 联合验证正常、参数错误、无权限、跨租户、空数据、冲突、超时、重复请求和兼容调用；
5. 将实际差异和处理结果回填接口文档。

Mock 可以辅助页面开发，但不能替代真实接口的权限、租户、错误和数据范围验证。

## 七、阶段六：发布

接口发布前，提供方和调用方同步确认：

- 服务端实现版本；
- 可定位的前端、服务或 SDK 调用版本；未知外部调用方标明范围；
- 实际经过网关时的路径和版本配置；
- 认证、租户和权限配置；
- 接口文档版本；
- 实际存在的旧调用方的兼容方式。

对外 OpenAPI 还必须确认公开认证协议、公开模型、错误码和 SDK 解析方式。

## 八、阶段七：运行维护

接口投入使用后，提供方应维护与契约对应的：

- 请求标识和调用链关联；
- 成功率、错误率和响应耗时；
- 限流、超时、依赖失败和重试状态；
- 业务错误码和主要失败原因；
- 版本使用情况和调用方分布。

运行中发现接口语义、错误码或兼容行为变化时，应回到“兼容变更”阶段处理。

## 九、阶段八：兼容变更

新增可选字段通常可以保持兼容；删除字段、修改字段类型、改变枚举含义、修改路径、改变必填性或改变错误语义时，必须：

1. 从代码引用、公开契约和已知接入方识别可定位的调用方；无法确认的外部调用方标明未知范围；
2. 说明变更前后差异；
3. 选择兼容新增、版本升级或迁移窗口；
4. 更新服务端、调用方、测试和接口文档；
5. 明确可执行的恢复方式；不能安全撤销既有状态或外部副作用时说明前向修复或补偿路径。

## 十、阶段九：废弃与删除

接口不再使用时，应通知可定位的调用方；若业务能力仍需保留，应先提供替代入口。完全终止该能力时，应明确停止使用的条件，并说明：

- 废弃原因；
- 适用的替代接口，或无替代接口的终止原因；
- 迁移方式；
- 停止接受新调用的时间；
- 删除时间；
- 仍未迁移调用方的处理方式。

确认可定位调用方已停止使用，并对无法确认的外部调用方完成适用的废弃窗口与兼容处理后，才能删除接口实现、网关路由、SDK 方法和接口文档中的正式入口。

## 十一、开发者完成判断

一个接口完成交付时，按实际接口类型和变更范围核对以下内容：

- 接口文档已对应当前实现；需要技术详细设计的任务已关联设计文档；
- 契约已明确，适用的提供方和调用方实现已完成；
- 正常及主要异常场景已按实际接入方式联调；
- 涉及版本并存时，提供方和调用方版本已对应；
- 长期运行的接口已纳入项目维护方式；
- 涉及兼容变更或废弃时，切换与恢复路径已明确。
