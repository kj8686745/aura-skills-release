## 一、规范定位

本规范约束接口本身如何设计、实现和使用；[02-接口文档规范](./02-接口文档规范.md)约束这些接口契约如何被记录、维护和验证。

```text
接口规范：接口应该怎样设计和运行
接口文档规范：接口约定应该怎样记录和协作
```

本规范适用于同步 HTTP API，也适用于前后端约定的文件接口、异步事件和跨模块公开调用；具体场景不适用时必须说明原因。

## 二、AURA 框架接口基线

以下认证、租户和请求上下文由 AURA 公共框架统一提供，业务应用不需要重新设计，也不得自行实现另一套同类机制。接口规范只要求业务接口正确接入并按框架约定传递。

| 场景 | 框架统一约定 | 业务应用要求 |
| --- | --- | --- |
| 浏览器业务请求 | 请求层统一注入 `Authorization: Bearer <token>`、`TENANT-ID`，并按框架配置注入 `VERSION`、`Enc-Flag` | 页面和业务组件不得自行拼接认证头；通过公共请求层调用 |
| 用户令牌获取 | 统一认证入口为 `/admin/oauth2/token`，前端使用框架提供的登录/令牌能力 | 不得在业务模块复制令牌获取、刷新和存储逻辑 |
| 服务间调用 | 使用框架/SDK 的 `client_credentials` 能力获取并使用服务令牌 | 不得把客户端密钥下发前端，不得自行实现另一套 Token 客户端 |
| 对外 OpenAPI | 使用框架登记的 HMAC 版本和签名头；响应仍使用本规范统一的 `R<T>` 契约 | 只通过公开 SDK/客户端和登记的签名契约接入 |
| 租户上下文 | 框架优先从 `TENANT-ID` 请求头解析租户选择；现有过滤器仍兼容同名查询参数和默认租户 | 业务接口必须使用框架上下文并校验该选择是否属于当前身份的有效范围；解析到租户值不等于已获授权，不得用请求体或业务字段重新覆盖 |
| 请求追踪 | 请求标识由公共请求/服务链路机制传递并写入日志 | 接口文档必须记录请求标识如何传递，业务日志不得丢失关联关系 |

**请求上下文约定**：业务接口通过 AURA 公共请求层传递认证、租户、版本和加密上下文；新接口必须明确认证来源和租户来源。历史兼容入口不得作为新接口的传递方式。

### 二.一、统一响应与分页契约

AURA 所有 HTTP 业务接口（浏览器、服务间和对外 OpenAPI）使用同一套响应与分页语义，不因调用边界再定义第二套返回结构。

| 契约对象 | 统一约定 | 调用方可见字段 | 规范要求 |
| --- | --- | --- | --- |
| 响应外壳 | `R<T>` | `code`、`msg`、`data`、框架只读兼容字段 `ok`（如实际序列化） | 所有 HTTP 业务接口使用同一解析方式；HTTP 状态码仍表达传输层结果 |
| 分页数据 | 统一的公共 `PageResult<T>` 响应对象 | `records`、`total`、`size`、`current`、`pages` | 内部与对外接口使用同一个分页响应类型；不得分别定义 `OpenPage<T>` 或直接暴露 ORM 的 `Page/IPage` |
| 错误数据 | `R<T>` 的 `data` 承载稳定 `errorCode`、安全消息补充信息、`retryable` 等约定字段 | 业务错误码、处理语义、请求标识 | 失败仍使用统一外壳；请求标识按公共链路机制传递并在接口文档中登记 |

本节规定新接口和存量接口迁移后的目标契约，不表示当前所有模块已完成改造。公共 `PageResult<T>` 类型应由框架统一提供；在该类型落地前，不得把仅同字段的项目私有 DTO 宣称为已实现“同一个对象”。Controller 或适配层负责把 ORM 分页对象转换为公共响应对象，ORM 类型不得进入 HTTP 契约。公开接口可以使用独立的记录 DTO 隐藏敏感字段，但不得改变分页对象和字段。存量 `OpenPage<T>`、`Page/IPage` 等接口须按版本兼容规则迁移，不能在新接口中继续扩展两套契约。

## 三、规范如何指导开发

本规范不是接口结果的描述清单，而是接口实现的共同依据。每条接口规则必须同时回答四个问题：

| 层次 | 要回答的问题 | 产物 |
| --- | --- | --- |
| 规范目标 | 为什么要统一这件事 | 稳定性、安全性、可维护性或协作目标 |
| 规定做法 | 所有新接口具体必须怎么做 | 路径、模型、响应、认证、错误和联调方法 |
| 禁止做法 | 哪些实现不能被采用 | 越界依赖、隐式约定、无边界重试和错误透传 |
| 使用结果 | 开发完成后应达到的状态 | 前后端能够依据同一接口契约实现和联调 |

后续新增或修改规则时，必须明确规定做法和适用边界。模块接口文档负责记录实际采用的接口契约，不得自行创造平台级规则。

## 四、核心规则

### AURA-BASE-API-001：接口必须有稳定身份和版本

**必要性**：必须

**为什么需要**：稳定身份和版本让提供方、调用方及运行环境能够识别同一接口，避免依赖临时配置或口头约定。

每个接口必须能够识别提供方、调用方、所属模块、版本和生命周期；版本不得只存在于口头约定或网关临时配置中。

**正确写法**：接口文档和路由同时登记模块、提供方、调用方与版本，例如 `device-service v1`。

**错误写法**：同一接口在不同环境使用不同路径，调用方只能通过网关配置或聊天记录判断版本。

**判断要点 / 验证方式**：检查接口文档、路由、客户端和发布配置，确认身份与版本可以从仓库和运行配置中还原。

### AURA-BASE-API-002：请求契约必须完整

**必要性**：必须

**为什么需要**：完整请求契约可以让调用方明确字段、类型、必填性和边界，减少参数猜测和无效请求。

请求字段必须说明类型、是否必填、业务含义、默认值、格式、范围和校验失败结果；不得让调用方通过源码猜测约束。

**正确写法**：分页请求的页大小明确为整数，默认 20，最大 100，超限返回稳定参数错误码；响应统一使用 `size` 字段。

**错误写法**：文档只写“传分页参数”，代码中却隐藏最大值和特殊格式要求。

**判断要点 / 验证方式**：使用缺失、空值、非法类型、边界值和超限值调用接口，核对响应与文档是否一致。

### AURA-BASE-API-003：响应契约必须完整

**必要性**：必须

**为什么需要**：明确成功、空结果、分页、受理和失败响应，才能让调用方稳定处理所有业务结果而不是只依赖成功样例。

响应必须定义成功、空结果、分页、异步受理和失败场景的外壳、字段类型、必返性与空值语义。

**正确写法**：内部列表接口的分页 `data` 包含 `records`、`total`、`size`、`current`、`pages`，无数据时 `records` 为 `[]`，其余分页字段仍按契约返回。

**错误写法**：同一接口有时返回 `null`、有时返回 `{}`，调用方只能根据实际响应临时兼容。

**判断要点 / 验证方式**：覆盖成功、空数据、异常和分页场景，确认实际 JSON 与接口文档逐字段一致。

### AURA-BASE-API-004：错误必须可区分并可处理

**必要性**：必须

**为什么需要**：参数、认证、权限、冲突、限流和系统故障需要不同处理方式，稳定错误分类才能支持正确提示和恢复。

错误结果必须区分参数、认证、权限、资源不存在、冲突、限流和系统故障，并提供调用方可执行的处理语义。

**正确写法**：版本冲突返回 `409` 和稳定业务错误码，调用方提示刷新后重试。

**错误写法**：所有失败都返回 `200` 或同一个“操作失败”字符串。

**判断要点 / 验证方式**：逐类触发错误，确认 HTTP 状态、业务错误码、消息和重试建议稳定。

### AURA-BASE-API-005：权限和调用上下文必须进入契约

**必要性**：必须

**为什么需要**：调用方必须知道认证、租户、版本和链路上下文如何传递，才能保证接口调用不会丢失安全和追踪信息。

接口必须明确适用的认证来源、租户选择来源、请求标识和权限边界，并使用 AURA 公共框架上下文。客户端传入的身份字段不得成为认证依据；`TENANT-ID` 等租户选择值须与已验证身份的有效范围核对后才能用于数据隔离。

**正确写法**：服务端从认证上下文获取用户或服务身份，再校验 `TENANT-ID` 所选租户是否在其有效范围内；文档说明缺失、失效或无权选择时的结果。

**错误写法**：直接使用请求体中的 `userId`、`tenantId` 或 `role` 进行授权。

**判断要点 / 验证方式**：篡改请求身份字段、租户字段和权限状态，确认服务端仍按可信上下文判断。

**边界说明**：本规则约束接口契约必须声明哪些身份、租户、权限和链路上下文；服务端如何在代码入口执行这些校验，由 `AURA-BASE-API-016` 和 `BASE-07` 负责。

### AURA-BASE-API-006：分页排序过滤和批量边界必须明确

**必要性**：必须

**为什么需要**：明确数据规模和查询边界可以避免全量返回、结果不稳定、资源耗尽和不同调用方采用不同默认行为。

列表、导出和批量接口必须声明页大小、总量、排序白名单、过滤范围、单次批量上限和超限结果。

**正确写法**：页大小最大 100，排序字段映射白名单，批量导入单次最多 1000 条。

**错误写法**：直接拼接请求中的排序字段，或允许一次请求读取全表和提交无限条数据。

**判断要点 / 验证方式**：使用超大分页、非法排序、超量批量和空过滤条件验证边界。

**边界说明**：本规则约束契约必须公开数据规模、排序、过滤和批量上限；参数校验、查询构造和资源保护的实现由 `AURA-BASE-API-017`、`BASE-08` 和 `BASE-11` 负责。

### AURA-BASE-API-007：写操作必须说明幂等和并发语义

**必要性**：必须

**为什么需要**：网络重试和重复提交不可避免，调用方必须知道重复请求、并发冲突和最终结果如何处理。

创建、修改、删除、异步触发和批量写入必须说明幂等键、重复提交结果、版本冲突和并发处理方式。

**正确写法**：创建请求使用业务幂等键，重复提交返回同一受理结果；更新使用版本条件。

**错误写法**：依赖前端按钮禁用防重复，服务端无幂等和冲突控制。

**判断要点 / 验证方式**：并发和重复提交同一请求，确认不会产生重复资源或静默覆盖。

**边界说明**：本规则约束接口契约必须说明重复请求和并发结果；幂等键、唯一约束、版本校验及冲突处理的实现由 `AURA-BASE-API-018`、`BASE-08` 和 `BASE-10` 负责。

### AURA-BASE-API-008：接口变更必须有兼容策略

**必要性**：必须

**为什么需要**：接口通常由多个版本的调用方共同使用，明确兼容、升级或废弃策略可以避免一次变更同时破坏多个系统。

删除已使用字段、修改已发布路径、改变枚举含义、调整既有响应或升级版本前，必须识别可定位调用方并标出未知外部调用范围，说明适用的兼容窗口、迁移方式和切换条件；全新且无旧调用方的契约不虚构兼容窗口或最终切换时间。

**正确写法**：先新增字段并兼容旧调用方，完成迁移后再删除旧字段。

**错误写法**：直接删除仍被调用的字段，要求调用方自行修复。

**判断要点 / 验证方式**：检查旧版本调用、兼容期日志、迁移完成标志和删除条件。

### AURA-BASE-API-009：提供方和调用方责任必须分开

**必要性**：必须

**为什么需要**：明确责任边界可以避免提供方和调用方互相假设，便于定位参数错误、权限失败和依赖异常的归属。

提供方负责契约、校验、业务结果和错误语义；调用方负责按契约组装请求、处理结果和重试，不得互相承担对方内部职责。

**正确写法**：前端按公开响应处理错误，后端负责权限、数据范围和业务校验。

**错误写法**：前端自行判断权限并绕过后端校验，或后端返回内部实体要求前端解释内部状态。

**判断要点 / 验证方式**：分别检查提供方和调用方代码，确认没有跨边界复制内部逻辑。

### AURA-BASE-API-010：接口必须有可重复的联调验证

**必要性**：必须

**为什么需要**：可重复的请求、响应和失败场景验证，才能证明提供方与实际调用方对契约的理解一致，而不是只证明某次手工调用成功。

接口交付前必须具备可重复的请求方式、适用的测试数据与认证上下文、成功及主要失败断言，并保留实际提供方与调用方的联调结果；服务间和公开接口不要求虚构前端参与方。可复用项目已有测试与联调材料，不强制另建脚本或登记表。

**正确写法**：在实际接入环境使用受控测试租户和脱敏数据，由接口测试或可重放请求验证正常、边界、权限和异常场景，并记录实际调用方结果。

**错误写法**：只在开发者本机手工点击验证，无法说明请求头、数据范围和预期结果。

**判断要点 / 验证方式**：在可复现的接入环境重放适用场景，核对请求、响应、日志和数据结果；只验证提供方时不得声称调用方已联调。

### AURA-BASE-API-023：接口发布必须能对应可定位的版本组合

**必要性**：必须

**为什么需要**：版本对应关系可以还原接口在特定环境中的实际组合，为兼容判断、问题定位和恢复提供事实依据。

在项目已有发布材料中，必须能对应提供方交付版本、公开契约版本和可定位的实际调用方版本；经过网关时还应记录受影响的路由或配置版本。无法确认的外部调用方应标明未知范围，不得据此断言全部调用方已经迁移；不要求为单次接口发布另建版本表。

**正确写法**：项目发布记录关联 `device-service 1.2`、已接入前端 `2.4` 和契约版本；若实际经过网关，再记录相应路由配置版本。

**错误写法**：服务端已升级但调用方和网关仍使用旧契约，发布记录没有对应关系。

**判断要点 / 验证方式**：检查已有发布材料、可定位调用方的依赖版本，以及实际使用的网关配置，确认适用的版本组合可还原。

### AURA-BASE-API-024：接口运行维护必须保留可观测信息

**必要性**：必须

**为什么需要**：接口的耗时、错误、调用方和请求关联信息是定位运行问题和判断影响范围的必要依据。

接口运行期间必须能够观察调用量、成功率、错误率、耗时、请求标识和调用方分布，且不得记录敏感信息。

**正确写法**：按服务、操作和结果记录低基数指标，并通过 `traceId` 关联日志。

**错误写法**：只有一条“请求失败”日志，没有耗时、调用方和请求标识。

**判断要点 / 验证方式**：模拟慢请求、依赖失败和限流，确认指标、日志和链路信息可定位问题。

### AURA-BASE-API-025：接口废弃必须明确替代或终止路径

**必要性**：必须

**为什么需要**：没有替代或终止条件，调用方可能继续依赖旧接口，最终形成无法清理的兼容负担。

接口进入废弃状态时，必须说明废弃原因、可定位调用方和未知外部调用范围、停止新增调用与最终删除的条件。业务能力继续提供时应公布替代接口及迁移方式；能力完全终止时应明确无替代入口的影响及通知方式。涉及旧调用方时保留适用的兼容窗口，不能在未确认影响时直接删除。

**正确写法**：业务能力继续提供时先给出替代接口与迁移提示，旧调用方完成迁移后删除；能力终止时说明影响、通知可定位调用方，并在适用的废弃窗口结束后删除。

**错误写法**：直接下线仍被使用的接口，只在运行时返回 404，未说明替代入口或能力终止的影响。

**判断要点 / 验证方式**：检查废弃说明、可定位调用方与未知范围、适用的迁移或终止结果，以及删除前的实际调用情况。

### AURA-BASE-API-011：接口必须使用稳定、可发现的公开路径

**必要性**：必须

**为什么需要**：稳定路径是调用方、网关、权限和文档共同依赖的入口，避免把内部类名或临时实现暴露为长期契约。

接口路径必须表达资源或明确业务动作，使用统一版本和模块前缀；不得把内部类名、数据库表名、机器地址或临时调试路径暴露给调用方。

**规定做法**：先确定接口边界，再按边界选择已登记的路径前缀、版本位置和资源命名；同时在模块文档登记 Controller 源路径、网关最终路径、前端调用路径和改写责任方。
**正确写法**：使用 `POST /api/devices/{deviceId}/review` 表达设备审核动作，并在模块文档登记网关映射。

**错误写法**：使用 `/invokeReviewDeviceService` 或 `/device_review_record/save` 暴露 Java 类名或数据库表名。

**判断要点 / 验证方式**：检查路由、网关配置和文档，确认路径、版本和资源语义一致。

### AURA-BASE-API-026：对外 OpenAPI 必须使用统一公开路径并登记平台 API

**必要性**：必须

**为什么需要**：API 网关通过统一路径和平台 API 注解识别对外接口并自动收录。缺少任一项都会导致接口无法进入公开 API 目录、SDK 生成范围不完整或网关路由与代码声明不一致。

对外 OpenAPI 的实际访问路径必须以 `/openapi` 开头，并在 Controller 方法上使用框架提供的 `@PlatfomApi` 注解登记 `code`、`version`、`name` 和完整 `requestPath`。`requestPath` 必须与实际 Controller 路径和网关最终路径一致；路径变量约束必须同时写入路由和注解，Java 正则反斜杠按源码转义。内部浏览器接口、服务间接口不得为了“自动收录”添加该注解。

**正确写法**：

```java
import net.fxft.aura.common.core.platformapi.PlatfomApi;

@PlatfomApi(
        code = StreamServerPermissionConstant.DETAIL,
        version = "1.0.0",
        name = "查询服务器详情",
        requestPath = "/openapi/video/stream-server/{id:\\d+}"
)
@GetMapping("/{id:\\d+}")
public R<StreamServerVO> detail(@PathVariable Long id) {
    return R.ok(streamServerService.detail(id));
}
```

Controller 类级别应通过 `@RequestMapping("/openapi/video/stream-server")` 形成完整路径；接口文档同时登记 Controller 源路径、网关最终路径和 `requestPath`。若框架通过配置自动上报，业务服务还必须按网关能力说明引入依赖、开启 `aura.platform-api` 配置并确认启动日志或平台目录中的收录结果。

**错误写法**：

```java
@PlatfomApi(code = "stream-server-detail", version = "1.0.0", name = "查询服务器详情")
@GetMapping("/video/stream-server/{id}")
```

上述写法缺少完整 `requestPath`，实际路径也没有 `/openapi` 前缀，网关不能按公开 API 可靠收录。仅在网关配置中补写路径、只添加注解但不改变实际路由，或把内部接口全部标记为 `@PlatfomApi`，同样不符合本规则。

**判断要点 / 验证方式**：检查 Controller 注解、实际映射、网关路由、平台 API 配置、启动收录结果和接口文档；确认对外路径全部以 `/openapi` 开头，注解与路径逐字对应，内部接口没有误标记，平台目录或自动上报日志能够定位到同一接口。
### AURA-BASE-API-012：HTTP 方法必须表达操作语义

**必要性**：必须

**为什么需要**：方法语义明确可以让缓存、重试、权限和审计行为与实际操作一致，减少接口使用方式的歧义。

`GET` 只读，`POST` 创建或触发动作，`PUT/PATCH` 修改，`DELETE` 删除或撤销；不得用统一 `POST` 隐藏不同操作语义，也不得让 `GET` 改变业务数据。


**正确写法**：查询使用 `GET`，创建使用 `POST`，状态修改使用 `PATCH`，删除使用 `DELETE`。

**错误写法**：使用 `GET /device/delete?id=1` 修改或删除数据。

**判断要点 / 验证方式**：逐个检查 HTTP 方法与实际副作用，确认只读方法不会改变业务数据。
### AURA-BASE-API-013：公开模型必须独立于内部模型

**必要性**：必须

**为什么需要**：隔离公开模型可以防止数据库字段、内部状态和实现细节穿透接口，降低内部改造对调用方的影响。

请求、响应、查询、命令、事件和持久化模型必须按边界定义；数据库实体、内部异常、第三方原始响应和内部枚举不得直接穿透到前端或其他模块。


**正确写法**：定义 `DeviceResponse`，只映射公开字段 `id`、`name` 和 `status`。

**判断要点 / 验证方式**：检查 Controller 返回类型和映射代码，确认内部模型没有穿透公开边界。
### AURA-BASE-API-014：响应结构和空值语义必须统一

**必要性**：必须

**为什么需要**：统一响应外壳和空值含义可以让前端、服务间调用和错误处理使用同一套解析逻辑。

同类接口必须使用统一的成功结果、列表分页、空数据和字段空值语义；不能让调用方通过猜测 `null`、空数组、缺字段或字符串状态判断结果。

**规定做法**：所有 HTTP 接口统一使用 `R<T>` 响应外壳，再定义 `data` 内的公开模型、字段类型、必返性、空值和分页结构；成功、失败、空数据和异步受理分别提供示例。调用边界只影响认证方式、数据范围和允许公开的字段，不改变响应契约。


**正确写法**：列表无数据统一返回 `records: []`，缺省可选字段按文档约定返回 `null` 或省略。

**错误写法**：同一接口在不同分支随机返回 `null`、空对象和空数组。

**判断要点 / 验证方式**：覆盖成功、空数据、分页和异常场景，逐字段比对响应契约。
### AURA-BASE-API-015：错误结果必须使用稳定的错误码

**必要性**：必须

**为什么需要**：调用方应依据稳定错误码决定提示、重试或跳转，不能依赖容易变化的错误文案或异常堆栈。

错误必须同时表达 HTTP 状态、稳定业务错误码和可安全展示的信息；错误码不能使用异常类名、数据库错误或临时日志文本替代。

#### HTTP 状态码统一基线

以下是 AURA 接口的统一状态码基线。业务接口必须优先按此基线设计；历史接口存在差异时，必须在模块接口文档中登记实际映射、兼容原因和迁移计划，不得新增未登记的状态码语义。

| 状态码 | 统一使用场景 | 接口要求 |
| --- | --- | --- |
| `200` | 查询、修改或同步动作成功 | 返回所属边界规定的成功响应外壳 |
| `201` | 创建资源成功 | 返回资源标识或资源表示 |
| `202` | 异步任务已受理 | 必须返回任务/请求标识和查询方式，不表示业务完成 |
| `204` | 成功且无响应体 | 不得再附带 JSON 响应体 |
| `400` | 参数、格式、语义校验或业务输入不合法 | 新接口统一使用 `400`，返回稳定业务错误码和可安全展示信息 |
| `401` | 未认证或令牌无效 | 不泄露认证细节，调用方进入认证处理 |
| `403` | 已认证但无权限或数据范围不足 | 返回稳定权限错误码 |
| `404` | 路径或资源不存在 | 按安全要求处理资源存在性信息 |
| `409` | 版本冲突、重复提交或业务状态冲突 | 返回稳定冲突错误码和可恢复建议 |
| `413` | 请求体或上传内容超过限制 | 文档必须声明大小上限 |
| `415` | 请求媒体类型不支持 | 返回支持的媒体类型范围 |
| `416` | 文件 Range 请求无效 | 文件接口说明有效范围和重试方式 |
| `429` | 超出限流或配额 | 返回限流错误码和 `Retry-After`（如适用） |
| `5xx` | 服务或依赖故障 | 不泄露堆栈，返回请求标识并说明是否可重试 |

`410` 等非默认状态码只能用于有明确生命周期语义的接口，例如文件已过期；必须在接口模块中登记触发条件和调用方处理方式。新接口不得使用 `422` 作为普通参数或语义校验失败状态码；历史接口如已使用 `422`，必须在模块接口文档中登记兼容原因、调用方处理方式和迁移计划，不能在同一模块新增接口中继续扩散。

#### 响应返回统一契约

HTTP 状态码只表示传输层结果，不能替代响应体。AURA 接口必须同时定义 HTTP 状态、响应外壳、业务错误码和 `data` 内的数据模型。

**规定做法**：先选择 HTTP 状态，再为每种失败场景定义稳定业务错误码、可展示消息、请求标识、是否可重试和调用方处理方式；同一错误语义在同一模块内只能有一个映射。


所有 HTTP 业务接口统一使用 `R<T>`，不能按内部或对外边界选择第二套响应外壳：

| 字段 | 类型 | 必返 | 空值规则 | 业务含义 | 调用方处理 |
| --- | --- | --- | --- | --- | --- |
| `code` | integer | 是 | 不为空 | AURA 公共 `R<T>` 的成功码为 `CommonConstants.SUCCESS=200`，默认失败码为 `CommonConstants.FAIL=500`；具体失败码按接口契约登记 | 先判断 `code`，再读取 `data` |
| `msg` | string | 是 | 成功时为安全成功提示；失败时为可安全展示的说明 | 不能包含堆栈、SQL、Token、密钥或内部地址 | 只用于展示或日志摘要，不作为分支判断依据 |
| `data` | object/array/null | 是 | 无业务数据时按接口契约使用 `null`、空对象或空数组 | 承载接口 DTO、`PageResult<T>` 或统一错误详情 | 按接口文档中的字段表解析 |
| `ok` | boolean | 否（框架兼容字段） | 未序列化时不可假定存在 | 表示 `code` 是否为成功码 | 不能替代 `code`、业务错误码或 HTTP 状态 |

成功响应示例：

```json
{
  "code": 200,
  "msg": "success",
  "data": {},
  "ok": true
}
```

#### 分页字段

`data` 为分页结果时统一使用公共 `PageResult<T>` 类型。实现应在 Controller 或适配层把 ORM `Page/IPage` 转换为该对象，不能仅用字段相同的私有类型替代公共类型；ORM 类型不得进入 HTTP 契约。下表为该对象的目标 JSON 字段，不代表现有框架已经提供该 Java 类型。

| 字段 | 类型 | 必返 | 空值规则 | 业务含义 | 调用方处理 |
| --- | --- | --- | --- | --- | --- |
| `records` | array | 是 | 无数据时为 `[]`，不能返回 `null` | 当前页的公开 DTO 列表 | 按数组处理，不从 `null` 推断失败 |
| `total` | integer | 是 | 无数据时为 `0` | 当前过滤条件下的总记录数 | 用于计算分页，不代表本次返回条数 |
| `size` | integer | 是 | 保留本次生效的页大小 | 每页数量 | 以服务端实际生效值为准 |
| `current` | integer | 是 | 保留本次生效的页码 | 当前页码 | 以服务端实际生效值为准 |
| `pages` | integer | 是 | 无记录时为 `0` | 总页数 | 不用 `records.length` 替代 |

#### 错误字段

失败响应仍使用 `R<T>`；`data` 按项目契约承载错误详情。以下字段用于统一表达错误处理语义：

| 字段 | 类型 | 必返 | 空值规则 | 业务含义 | 调用方处理 |
| --- | --- | --- | --- | --- | --- |
| `data.errorCode` | string | 是 | 不为空 | 稳定业务错误码 | 按错误码分支，不依赖 `msg` 文案 |
| `data.requestId` | string | 按项目链路契约 | 无法生成时必须在响应头或日志链路中可定位 | 关联请求、日志和联调记录 | 展示或反馈给排查人员，不向用户暴露敏感信息 |
| `data.retryable` | boolean | 是 | 不为空 | 是否允许按契约重试 | 还必须结合 HTTP 状态、幂等条件和重试预算 |

错误响应示例：

```json
{
  "code": 409,
  "msg": "设备状态已发生变化，请刷新后重试",
  "data": {
    "errorCode": "REVIEW_VERSION_CONFLICT",
    "requestId": "req-20260918-001",
    "retryable": false
  },
  "ok": false
}
```

公开 OpenAPI 仍须使用 DTO、公开认证和数据范围控制可见字段，但不得再定义 `OpenApiResponse`、`OpenPage` 或其他第二套响应外壳。请求标识的传递位置必须在模块接口文档中明确。

**外部响应适配**：接入外部服务时，适配层依据已确认的被调用方契约判断结果，再转换为 AURA HTTP 接口的统一 `R<T>`。审查分别核对原始响应、适配转换和 Controller 实际返回，不将外部协议值定义为 AURA 响应码。内部与对外接口均按本节公共成功码及分页契约实现。

对外 OpenAPI 使用登记的 HMAC 认证协议，至少包括客户端标识、签名版本、时间戳、nonce、签名和防重放约束；不得让调用方猜测认证方式，也不得在同一公开边界内并行自定义第二套签名协议。

**正确写法**：版本冲突返回 HTTP `409`、业务码 `DEVICE_VERSION_CONFLICT` 和 `requestId`。

**错误写法**：把 SQL 异常原文或 Java 异常类名直接放进 `msg`，所有失败都返回 `200`。

**判断要点 / 验证方式**：触发参数、权限、冲突和系统故障，确认状态码、业务码和消息可区分。
### AURA-BASE-API-016：权限和上下文必须在服务端执行

**必要性**：必须

**为什么需要**：只有服务端掌握真实数据和操作边界，才能阻止绕过页面、伪造前端状态或直接调用接口造成越权。

受保护接口必须在后端按实际契约完成身份、租户、组织、数据范围和操作权限中适用的校验；前端按钮、路由或请求参数只能提供交互控制，不能作为授权依据。

**规定做法**：在接口文档中写明适用的认证来源、租户选择来源、权限标识、数据范围和请求标识；由服务端在进入业务处理前完成校验，并按业务风险保留必要的审计和日志关联信息。


**正确写法**：服务端从认证上下文读取用户或服务身份，校验所选租户，并在受保护业务入口执行适用的权限和数据范围判断。

**边界说明**：本规则约束服务端必须执行 `API-005` 已声明的上下文和授权判断；认证平台、权限模型和敏感信息处理的完整要求遵循 `BASE-07`。
### AURA-BASE-API-017：列表和批量接口必须限制范围

**必要性**：必须

**为什么需要**：限制页大小、批次和过滤范围可以保护数据库、网络和前端资源，避免一次请求放大为不可控负载。

列表、分页、排序、过滤、导出和批量接口必须设置默认值、最大值和数据范围；禁止无边界查询、无上限批量提交和由调用方任意拼接内部查询条件。

**规定做法**：在接口文档先登记默认值、最大值、排序白名单、过滤字段和批量上限，再在参数校验、查询构造和服务层重复执行边界控制。


**正确写法**：分页最大 100，排序字段使用白名单，批量接口限制单次 1000 条。

**错误写法**：直接拼接 `sort` 参数，或允许接口一次读取全表。

**判断要点 / 验证方式**：使用超大页、非法排序和超量批量请求验证是否被拒绝或截断。

**边界说明**：本规则约束接口实现必须落实 `API-006` 的规模和查询边界；数据库查询、事务、数据生命周期和运行时资源上限分别遵循 `BASE-08` 和 `BASE-11`。
### AURA-BASE-API-018：写操作必须具备明确的幂等或冲突策略

**必要性**：必须

**为什么需要**：明确写操作的重复和并发语义，可以避免重复创建、状态覆盖和调用方无法判断最终结果。

创建、提交、审核、删除、批量和异步触发接口必须说明幂等键、重复请求结果、版本校验或冲突处理；不能依赖前端禁用按钮保证唯一执行。

**规定做法**：按业务选择幂等键、业务唯一约束或版本控制，并明确重复请求、并发冲突和超时重试的最终结果；前端禁用按钮只能作为交互优化。


**正确写法**：创建接口使用 `Idempotency-Key`，更新使用 `version` 条件，冲突返回 `409`。

**错误写法**：仅依赖前端按钮禁用，服务端重复请求生成多个资源。

**边界说明**：本规则约束接口实现必须落实 `API-007` 声明的重复和并发语义；异步任务与消息重试的完整处理遵循 `BASE-10`，本地数据一致性遵循 `BASE-08`。

**判断要点 / 验证方式**：并发提交相同请求，确认不会重复创建或静默覆盖。
### AURA-BASE-API-019：接口调用必须定义超时、重试和失败归属

**必要性**：必须

**为什么需要**：同步调用必须在有限资源内结束，并让调用方知道哪些失败可以重试、哪些失败应由提供方处理。

提供方和调用方必须分别明确超时、可重试错误、重试次数、退避方式、降级结果和最终失败归属；不得对所有错误无条件重试。

**规定做法**：按接口是否幂等、依赖是否可恢复和业务是否允许补偿，分别登记连接/读取/整体超时、可重试错误、次数、退避、熔断和最终失败状态。


**正确写法**：远程调用设置连接和读取超时，仅对明确的瞬态错误有限重试并记录最终失败。

**错误写法**：没有超时和重试边界，或对所有异常无限重试。

**判断要点 / 验证方式**：模拟超时、拒绝和持续不可用，核对重试次数、退避和最终错误归属。
### AURA-BASE-API-020：接口变更必须保持兼容或明确升级

**必要性**：必须

**为什么需要**：明确变更策略可以让不同版本的提供方和调用方平稳迁移，避免字段删除或语义变化造成隐式故障。

新增字段应优先向后兼容；删除字段、改变枚举含义、修改路径、改变必填性或改变错误语义时，必须通过版本、迁移、灰度或明确的升级窗口处理。

**规定做法**：变更前登记消费者和影响面，选择兼容新增、版本升级、灰度迁移或废弃窗口，并同步更新服务端、前端类型、测试和接口文档。


**正确写法**：新增字段先兼容旧调用方，完成迁移后再删除旧字段并发布新版本。

**错误写法**：直接删除仍被使用的字段或改变枚举含义而不提供迁移窗口。

**判断要点 / 验证方式**：使用旧版调用方执行回归，检查兼容期、迁移记录和删除条件。
### AURA-BASE-API-021：前端调用必须经过领域接口封装

**必要性**：必须

**为什么需要**：集中封装可以隔离路径、请求转换、错误处理和响应适配，避免页面散落接口细节并形成重复实现。

页面和组件不得散落接口地址、请求客户端配置和原始响应字段；应由领域 API 统一封装请求、类型、转换、错误和状态处理。

**规定做法**：领域 API 统一管理路径、请求类型、响应类型、模型转换、错误映射和加载/空/失败状态；页面只使用领域 API 输出的业务模型。


**正确写法**：页面通过 `deviceApi.review()` 调用接口，由领域层把响应转换为页面模型。

**错误写法**：在多个页面直接调用 `axios` 并各自解释响应字段。

**判断要点 / 验证方式**：扫描页面网络调用，确认请求集中在领域 API 模块且转换逻辑可复用。
### AURA-BASE-API-022：跨模块调用必须通过公开契约

**必要性**：必须

**为什么需要**：公开契约可以保护模块内部实现和数据所有权，避免跨模块直接读表、引用内部类型或依赖私有路径。

模块之间只能通过公开 API、事件、文件契约或登记的能力入口交互；不得直接访问其他模块数据库、内部类、内部缓存或内部消息主题。

**规定做法**：先登记提供方和调用方的公开契约、版本、认证、超时和失败语义，再通过公开客户端、事件或文件入口接入；内部实现只能留在提供模块内部。


**正确写法**：跨模块只依赖版本化的公开 DTO、Feign 接口或事件契约。

**错误写法**：直接引用其他模块的 Entity、Mapper、内部缓存键或数据库表。

**判断要点 / 验证方式**：检查依赖树和跨模块引用，确认调用经过公开入口且版本和所有权明确。

## 五、统一禁止做法

以下做法属于接口规范明确禁止的实现方式；如确有历史兼容原因，必须在模块接口文档中登记兼容边界和替代方案。

| 禁止项 | 不允许的做法 | 应采用的方式 |
| --- | --- | --- |
| 路径 | 将数据库表名、Controller 类名、内部服务地址或临时调试地址作为公开路径 | 使用已登记的资源/动作路径，并记录三层路径关系 |
| 响应 | 直接返回 Entity、Map、Page、第三方原始响应或未登记的裸对象 | 使用边界对应的统一响应外壳和公开模型 |
| 错误 | 所有失败都返回 HTTP 200、只返回字符串、直接透传异常堆栈或供应商错误码 | 使用统一 HTTP 状态、业务错误码、消息和请求标识 |
| 认证 | 仅依赖前端按钮、路由或请求体中的租户字段完成授权 | 服务端校验身份、租户、组织和数据权限 |
| 查询/批量 | 无分页上限、无限制导出、无批量上限或把任意查询条件直接拼接到数据库 | 登记边界并在请求模型、服务和查询层执行限制 |
| 写入 | 依赖前端禁用按钮防止重复提交，或对所有写请求无条件重试 | 使用幂等键、唯一约束、版本控制和明确重试边界 |
| 跨模块 | 直接访问其他模块数据库、缓存、内部类或未公开消息主题 | 通过公开 API、事件、文件契约或登记的能力入口 |
| 前端调用 | 页面和组件直接拼接 URL、读取内部字段或自行解析公共响应 | 通过领域 API 统一类型、转换、错误和状态处理 |
| 异步 | 返回“成功”但不区分已受理和已完成，或没有任务/事件标识 | 明确受理状态、查询入口、事件版本、幂等和补偿 |
| 文件 | 通过对象存储地址绕过业务权限，或不限制大小、有效期和清理 | 先完成业务授权，再按生命周期和传输规则提供文件 |

禁止项不得以“当前能够运行”作为采用理由；历史兼容场景应在模块接口文档中说明边界和替代方案。

## 六、接口类型约定

| 类型 | 约定重点 |
| --- | --- |
| 查询接口 | 只读、分页边界、过滤和空数据语义 |
| 写入接口 | 校验、事务、幂等、并发和错误结果 |
| 文件接口 | 文件大小、类型、命名、权限、超时和失败清理 |
| 异步事件 | 事件版本、唯一编号、投递语义、消费幂等和失败补偿 |
| 跨模块能力 | 公开入口、版本、上下文、超时、重试和兼容 |

## 七、前后端协作要求

1. 后端先确定公开契约、权限、错误和状态语义，前端再进行调用封装和页面实现；
2. 前后端共同使用[接口文档规范](./02-接口文档规范.md)和[接口文档模板](./03-接口文档模板.md)，不得各自维护一份互相冲突的接口定义；
3. Mock 只能用于页面开发和早期联调，真实接口具备条件后必须验证真实权限、错误和数据范围；
4. 接口变更必须同时检查后端实现、前端领域 API、类型、页面状态、测试和接口文档；
5. 任何无法由代码或契约直接确定的业务语义，必须在联调前完成人工确认。

## 八、开发者自检

- [ ] 路径、版本和 HTTP 方法表达稳定语义；
- [ ] 请求、响应、错误和公开模型边界明确；
- [ ] 权限、租户、数据范围和上下文由服务端执行；
- [ ] 分页、批量、幂等、并发、超时和重试有明确策略；
- [ ] 前端通过领域 API 封装，不直接依赖内部响应结构；
- [ ] 跨模块调用只使用公开契约；
- [ ] 变更具备兼容、迁移或升级方案；
- [ ] 已按接口文档模板完成联调验证记录。
