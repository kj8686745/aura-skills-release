> 本示例展示前后端共同维护一份接口契约。数据库表、内部类和内部服务地址不属于公开接口。

## 二、职责与调用边界

- 后端负责：身份、租户、权限、设备状态、版本冲突、审核记录和错误语义。
- 前端负责：组装请求、展示加载/成功/失败状态、阻止重复点击和刷新列表。
- 前端不得依赖：数据库表、内部类或内部服务地址。

## 接口逐项契约：API-DEVICE-REVIEW-001 提交设备审核结果

## 三、请求契约

```http
POST /api/devices/{deviceId}/review
Content-Type: application/json
Authorization: Bearer <token>
TENANT-ID: tenant-demo
```

请求标识通过项目已登记的公共请求链路传递；本示例不假定统一的请求头名称。用于真实项目时，须在模块接口文档中填明实际传递方式，并与日志中的关联标识核对。

| 位置 | 参数名 | 类型 | 必填 | 枚举/格式 | 业务含义 | 校验失败 |
| --- | --- | --- | --- | --- | --- | --- |
| path | `deviceId` | string | 是 | `D-` 开头 | 设备编号 | 格式错误：`INVALID_DEVICE_ID`；格式正确但无资源：`DEVICE_NOT_FOUND` |
| body | `reviewResult` | string | 是 | `APPROVED`/`REJECTED` | 审核结果 | `INVALID_REVIEW_RESULT` |
| body | `reviewRemark` | string | 否 | 最大 500 字符 | 审核备注 | `REMARK_TOO_LONG` |
| body | `version` | integer | 是 | 正整数，当前设备版本 | 并发控制 | 格式错误：`INVALID_VERSION`；版本过期：`REVIEW_VERSION_CONFLICT` |

`Authorization` 由公共请求层注入；`TENANT-ID` 是租户选择值，服务端必须结合已验证身份校验其可选范围，不能直接作为授权依据。本接口没有查询参数或默认请求体字段。

请求示例：

```json
{
  "reviewResult": "APPROVED",
  "reviewRemark": "设备资料完整",
  "version": 3
}
```

## 四、响应契约

成功响应 `200`，使用统一 `R<T>`：

```json
{
  "code": 200,
  "msg": "审核成功",
  "data": {
    "deviceId": "D-1001",
    "reviewStatus": "APPROVED",
    "reviewId": "R-20260918-0001",
    "notificationStatus": "PENDING"
  },
  "ok": true
}
```

`notificationStatus` 表示通知处理状态，不代表审核是否成功；审核状态以 `reviewStatus` 为准。

| `data` 字段 | 类型 | 必返 | 空值规则 | 业务含义 |
| --- | --- | --- | --- | --- |
| `deviceId` | string | 是 | 不为空 | 已审核设备编号 |
| `reviewStatus` | string | 是 | 不为空 | 本次审核后的设备状态 |
| `reviewId` | string | 是 | 不为空 | 本次审核记录标识 |
| `notificationStatus` | string | 是 | 不为空 | 示例值 `PENDING` 表示通知待处理，不表示已送达；真实项目须在模块契约中列明实际支持的状态、含义和查询入口，不照搬示例值 |

审核成功响应不代表通知已送达。页面以 `reviewStatus` 判断审核结果；通知的最终处理由通知模块独立记录和处理，本 HTTP 接口不提供通知完成的承诺。

## 五、错误契约

统一 `R<T>` 的 `code` 保持平台数值状态，业务错误码放在 `data.errorCode`：

```json
{
  "code": 409,
  "msg": "设备状态已发生变化，请刷新后重试",
  "data": {
    "errorCode": "REVIEW_VERSION_CONFLICT",
    "requestId": "req-20260918-001",
    "retryable": false
  },
  "ok": false
}
```

| HTTP | 业务错误码 | 触发条件 | 可重试 | 前端处理 |
| --- | --- | --- | --- | --- |
| 401 | `UNAUTHENTICATED` | 凭据缺失或失效 | 否 | 进入统一认证处理 |
| 400 | `INVALID_DEVICE_ID` | 设备编号格式错误 | 否 | 标记设备编号错误 |
| 400 | `INVALID_REVIEW_RESULT` | 枚举值非法 | 否 | 标记表单字段错误 |
| 400 | `REMARK_TOO_LONG` | 审核备注超过 500 字符 | 否 | 标记表单字段错误 |
| 400 | `INVALID_VERSION` | 版本字段缺失或格式错误 | 否 | 标记版本字段错误；修正或重新加载当前设备版本后，由用户重新提交 |
| 403 | `REVIEW_FORBIDDEN` | 无审核权限 | 否 | 提示无权限 |
| 404 | `DEVICE_NOT_FOUND` | 设备不存在或不在可见范围 | 否 | 刷新列表，不展示内部资源信息 |
| 409 | `REVIEW_VERSION_CONFLICT` | 设备已被其他人处理 | 否 | 提示刷新后重试 |
| 500 | `REVIEW_PERSIST_FAILED` | 审核事务写入失败 | 结果确认后 | 保留输入，先刷新确认审核结果再决定是否重试 |

## 六、权限、租户与上下文

- 权限：后端校验 `device:review`。
- 租户：从 `TENANT-ID` 和登录上下文取得，不接受请求体租户字段覆盖。
- 数据范围：只能审核当前用户所属组织可见的设备。
- 请求标识：使用项目登记的请求标识贯穿调用链；事件使用独立 `eventId`。

## 七、幂等、并发、超时与重试

- 并发控制：请求携带设备 `version`，版本不一致返回 `409`。
- 重复提交：相同设备和相同版本只允许一个审核结果成功写入；后续相同版本请求返回 `409/REVIEW_VERSION_CONFLICT`，不创建第二条审核记录。客户端未收到第一次响应时，先查询最新状态，不盲目重发。
- 前端重试：不自动重试 `400`、`403`、`404`、`409`；网络超时先查询最新设备状态。若仍无法排除原请求在途，不得把查询结果当作“未执行”的证明；只有服务端确认原请求未写入，或模块已登记的幂等契约允许安全重试，才由用户决定是否重新提交。
- 通知：通知属于异步过程，接口成功只代表审核完成，不代表通知已发送。

## 十、联调约定

联调前准备：具备审核权限与无审核权限的测试账号、可见与跨租户设备、待审核和已审核状态、可制造版本冲突的两份请求；记录实际服务/前端版本、网关最终路径、测试数据编号及请求标识。以下“待验证”表示场景定义，不表示已经执行。

1. 后端先验证 `200/400/401/403/404/409/500` 场景；
2. 前端完成领域 API 封装，页面不直接拼接 URL 或读取内部字段；
3. 双方核对服务入口、网关最终路径和前端调用路径；
4. 联合验证正常审核、重复提交、版本冲突、越权、跨租户、通知失败和网络超时；
5. 双方确认接口版本、前端版本和问题处理结果。

| 场景 | 提供方预期 | 调用方预期 | 处理结果 |
| --- | --- | --- | --- |
| 正常审核 | 返回成功并生成审核记录 | 展示审核成功并刷新列表 | 待验证 |
| 未认证 | 返回 `401/UNAUTHENTICATED`，不写入 | 进入统一认证处理 | 待验证 |
| 参数错误 | 返回 `400` 和对应字段错误，不写入 | 标记表单字段 | 待验证 |
| 无权限 | 返回 `403/REVIEW_FORBIDDEN` | 展示无权限，不重试 | 待验证 |
| 版本冲突 | 返回 `409/REVIEW_VERSION_CONFLICT` | 提示刷新，不覆盖本地状态 | 待验证 |
| 跨租户资源 | 返回 `404/DEVICE_NOT_FOUND` 且不泄露资源 | 展示统一错误 | 待验证 |
| 重复提交 | 只有首次写入，后续同版本请求返回 `409` | 刷新状态，不盲目重发 | 待验证 |
| 通知失败 | 审核成功，通知进入重试/失败状态 | 不把通知失败误报为审核失败 | 待验证 |
| 网络超时 | 查询最新状态；无法排除原请求在途时保持结果待确认，不创建第二条审核记录；仅在确认原请求未写入或符合已登记的幂等契约时允许重新提交 | 先刷新查询；结果仍不确定时停止提交并继续核实，不仅凭超时或一次查询发起新审核 | 待验证 |
